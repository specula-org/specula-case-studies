### 2.2 Shared state

* `safety_rules: Arc<Mutex<MetricsSafetyRules>>` (`round_manager.rs:354`, set up at `epoch_manager.rs:883`). Locked synchronously by both the main loop (`vote_block` :1556, `sign_timeout_with_qc` :1053) AND by the spawned proposal task (`Self::generate_proposal` :717). The proposal task locks `safety_rules` while the main loop may be trying to vote. Because the lock is held for the duration of the persistent-storage write inside SafetyRules, this serialises but does not order proposal-signing vs. voting; a slow proposal sign does not race the vote round, but it does block timeout signing during the same instant.
* `block_store: Arc<BlockStore>` (`round_manager.rs:350`) — internally uses `RwLock`s. The leader's proposal task at :529 captures `self.block_store.sync_info()` BEFORE the spawn, so the spawned task uses a snapshot taken at proposal-event time, but the data feeding `proposal_generator.generate_proposal` is fetched fresh by the proposal generator from the same `Arc<BlockStore>`. Read window is therefore "between event and task spawn".
* `round_state: RoundState` is owned by `RoundManager` (no external sharing). Because `start`'s `select!` is single-task, mutating `round_state` from within handlers is safe — but the spawned proposal task at :533 does NOT touch `round_state`; it only consumes the snapshotted `NewRoundEvent`. Hence a stale proposal can be broadcast even after the local round has advanced.
* `pending_opt_proposals: BTreeMap<Round, OptBlockData>` :371 — owned by the main loop, only mutated in handlers, no race window.
* `pending_order_votes: PendingOrderVotes` :366 — same single-loop ownership, but garbage-collect at :504 happens at every new round event.
* `proposal_generator.last_round_generated: Mutex<Round>` (`proposal_generator.rs:405`) — guards "at most one proposal per round" across the spawned proposal task and any future call.
* `proposer_election` is `Arc<UnequivocalProposerElection>` :410 with its own `Mutex<(Round, HashValue)>` to detect leader equivocation.

**Observation: there is one key state-staleness window.** The `tokio::spawn`ed proposal task at :533 captures `sync_info` and `epoch_state` at spawn time. If a `process_certificates` triggers a *second* `NewRoundEvent` (e.g., a TC arrives moments later for a higher round) before the spawned proposal-signing finishes, the leader will still broadcast its r-proposal (signed for r) even though it has just learned of round r+1. `safety_rules.sign_proposal` would refuse only if r ≤ `last_voted_round`, and `last_voted_round` is only bumped by *voting*, not by becoming aware of a TC.

### 2.3 Recovery manager loop

`RecoveryManager::start` (`recovery_manager.rs:120`) runs an *alternative* event loop. On any successful recovery message it calls `process::exit(0)` :156. There is **no return path** to RoundManager — recovery completes by terminating the process and relying on the operator/launcher to restart. Anything in flight on other channels is dropped, including votes pending in `round_manager_tx` (KLAST queue, so the latest message of each (author, discriminant) pair is the only one kept).

## 3. Per-handler line-cited findings

### 3.1 `process_proposal_msg` (`round_manager.rs:764`)

* Calls `ensure_round_and_sync_up` :781. That function (line 954) returns early `Ok(false)` if `message_round < current_round` :960 *without* calling `sync_up`, so a peer can poll us with a higher SyncInfo by attaching a stale proposal and still get us to advance. (This is intentional — only newer messages should cause syncing — but it means a Byzantine leader can never push us *backwards*; conversely a malicious peer sending only a high SyncInfo and an out-of-date `proposal_msg` cannot push us forward through this handler — they have to use `process_sync_info_msg`.)
* Inside `process_proposal` :1149 the `is_valid_proposal` call :1239 catches both wrong-author and double-proposal, but the call happens *after* `block_store.insert_block` via the path `process_proposal → process_verified_proposal → vote_block → block_store.insert_block` :1539 — actually the order in `process_proposal` is reversed: `is_valid_proposal` :1239 is checked before any block_store mutation, but `insert_block` at :1300 happens BEFORE the back-pressure / payload check. A duplicate proposal that fails `is_valid_proposal` is rejected before insertion; OK.
* `failed_authors` validation :1267 is gated by `!proposal.is_opt_block()`. **Opt-proposals therefore skip `failed_authors` validation entirely** — the regular-proposal path validates the list, but opt blocks (which become regular proposals via `Block::new_from_opt` :902) inherit an empty / synthesised list. Attacker scenario: a Byzantine leader can omit failed-authors metadata via the opt-proposal path that the regular path would have caught, slightly skewing the failed-author counters and any reward/penalty downstream.

### 3.2 `process_opt_proposal_msg` (`round_manager.rs:820`)

* Sync uses `sync_up` :851 *not* `ensure_round_and_sync_up`. Reading the body: it calls `sync_up` and then either loops the proposal back if the round matches OR queues it in `pending_opt_proposals` :870.
* The pre-queue check `is_valid_proposer` :864 is only run in the queue branch (`else`). If the round already matches at :854, the opt block is loopbacked into `process_opt_proposal` without verifying the *author* matches the round's expected leader. Inside `process_opt_proposal` :881 there is no `is_valid_proposer` either — the only validation is "HQC certifies the parent" (:891, :897). The downstream `process_proposal` :912 does call `is_valid_proposal` :1239, so the author check is eventually applied. **However**, between insertion into `pending_opt_proposals` :870 and the `process_opt_proposal` call later, the opt block is held in memory — it cannot be exploited yet, but represents a path-asymmetry to keep in mind for replay/retention attacks.
* The verify_well_formed (`opt_proposal_msg.rs:54`) ensures `block_data.epoch == sync_info.epoch` :64 and `grandparent_qc.certified_block().id() == sync_info.highest_quorum_cert().certified_block().id()` :69. The grandparent QC is verified at line 124 of `opt_proposal_msg.rs`. But there is **no signature on the OptBlockData** itself — the leader is not required to BLS-sign the opt block (`block_data().payload().verify` only checks payload proofs, not block-level signature). The author binding comes only from `proposer() == sender` at `opt_proposal_msg.rs:107`, i.e., it relies on the network identity match. If the network channel can be impersonated by another validator (e.g., shared keys, mTLS misconfig), an opt-proposal can be forged.
* In `process_opt_proposal` :881, the receiver demands `hqc.certified_block().id() == opt_block_data.parent_id()` :897 — but it never checks that this HQC corresponds to a block actually in `block_store` for the opt-block's *parent round* (it only matches IDs). The opt block is then converted to a regular proposal at :902 with the local HQC (NOT the proposer's grandparent QC). This means:
  1. The proposer's `grandparent_qc` sent in the OptBlockData is never re-checked against the block_store at vote-time.
  2. The receiver's local HQC is used as the QC for voting purposes.
  
  This is correct for liveness, but it means an opt-proposal essentially commits the receiver to the receiver's *own* view of QC — there's no value-binding between what the proposer claimed and what the receiver votes on, beyond the parent-id match.

### 3.3 `process_vote_msg` (`round_manager.rs:1733`)

* `ensure_round_and_sync_up(vote.round, vote.sync_info, vote.author)` :1739 — round is `vote_data().proposed().round()`. This means a vote for round R requires the local round to be R, *not* R+1. Combined with the leader's "votes go to next round leader" rule :1782, the recipient (next leader) gets the vote — its current round is R because round transitions happen on QC formation :1131. OK.
* Inside `process_vote` :1758, `if !self.local_config.broadcast_vote && !vote.is_timeout()` :1782 ensures the recipient is the next-round leader. **Timeout votes are NOT filtered** — any node can collect a timeout vote even if it is not the next leader. This is the intentional 2-chain behaviour, but it means a malicious validator can flood every honest node with timeout votes that all need pending-vote bookkeeping.
* The "block already had a QC" short-circuit :1796 is observed *before* inserting the vote, so duplicate votes are dropped. But the duplicate test runs `block_store.get_quorum_cert_for_block(block_id)` — if the QC is in flight (computed in `pending_votes` but not yet inserted), this check is racy in the sense that the same vote may be counted twice if it arrives concurrently in two channels (extremely unlikely given single-task `select!`).

### 3.4 `process_order_vote_msg` (`round_manager.rs:1582`)

* Gate at line 1583: only runs if `order_vote_enabled()`. If the on-chain config flag flips off mid-epoch, in-flight order votes are silently dropped.
* Range check :1607 — `order_vote_round > highest_ordered_round && order_vote_round < highest_ordered_round + 100`. That's the only round filter. **The handler does NOT call `ensure_round_and_sync_up`** — there is no synchronisation effect from order votes, and no SyncInfo is carried in `OrderVoteMsg`. So a peer can send order votes well above its own state to trigger insertion of a foreign QC into the local pending pool without ever revealing its own SyncInfo.
* QC verify is done only on the FIRST order vote per ledger-info digest :1613; subsequent votes for the same digest skip QC verification :1627. The protocol comment :1610 acknowledges this. The implication: if QC was correctly verified once, all later votes contributing to its aggregate signature are safe — but the per-vote signature is only verified inside `pending_order_votes::insert_order_vote → sig_aggregator.add_signature` and ultimately by `aggregate_and_verify` :123 of `pending_order_votes.rs`. That's correct.
* **The critical asymmetry:** `OrderVoteMsg::verify_order_vote` (`order_vote_msg.rs:48`) only checks:
  - `order_vote.author() == sender` (:54)
  - `quorum_cert.certified_block() == order_vote.ledger_info().commit_info()` (:60)
  - `order_vote.verify(validator)` — signature only (:63)
  
  **It does NOT check that `order_vote.epoch() == quorum_cert.epoch()`.** Both objects carry their own epoch; an attacker could (in principle) craft an OrderVote signing a ledger-info whose `commit_info.epoch` differs from the QC's epoch. Although `EpochManager::check_epoch` filters at the OrderVoteMsg level by `order_vote.epoch()`, the QC inside the message is not bound to that epoch by the verifier. The downstream `quorum_cert.verify` :1617 uses the *current epoch's* `ValidatorVerifier`, so a QC whose internal `certified_block().epoch()` differs from the local epoch will fail signature verification in the common case — but there is a subtle window during epoch transitions where the local `epoch_state.verifier` was rotated and an order-vote in the OLD epoch is replayed: the OrderVote signature verifies (against the new verifier? or old?), and the QC inside might or might not. The note at safety_rules.rs:412-413 ("TODO: add guarding rules in unhappy path") and the brief's reference to PR #13711 ("missing epoch check in `verify_order_vote_proposal`") both point at exactly this layer of defense. **The fix landed in `safety_rules::verify_order_vote_proposal` :87** — it now calls `self.verify_epoch(proposed_block.epoch(), &safety_data)` :94. But this only guards order-vote *signing* by us, NOT the receive-and-aggregate path here.
* Even after PR #13711's fix on the signing side, the receive path :1582 still relies on the EpochMgr filter only checking the OrderVoteMsg-level epoch — there is no programmatic enforcement that the included QC's `certified_block().epoch()` matches the OrderVote's epoch. (See Finding 1 below.)

### 3.5 `process_round_timeout_msg` (`round_manager.rs:1889`)

* Mirrors `process_vote_msg` and uses `ensure_round_and_sync_up` :1900. Then `insert_round_timeout` :1925 only inserts if `timeout.round() == self.current_round` (`round_state.rs:311`) — so timeouts for past rounds are dropped, but only *after* SyncInfo verification could bump our round.
* The timeout-aggregation echo logic at :1877 calls `process_local_timeout` if not yet sent. This is the path the brief refers to ("commit f58e184471 added timeout-signing checks earlier paths skipped"). Looking at `safety_rules_2chain.rs:19` (`guarded_sign_timeout_with_qc`): epoch verify :26, signature verify :28, `verify_tc` :32, `safe_to_timeout` :36, `verify_and_update_last_vote_round` :44 (only if round > last_voted_round) — these are all the checks. But notice `if timeout.round() < safety_data.last_voted_round { return Err(...) }` :37 — *equality* with last_voted_round is allowed, only strictly less is rejected. The earlier path `process_local_timeout → process_vote_reception_result(EchoTimeout) → process_local_timeout` (recursion) at :1856 means the handler can be called with the *same* round that we already voted on, which would re-sign the timeout for the same round. The check at `safety_rules.rs:218` (`verify_and_update_last_vote_round`) rejects `round <= last_voted_round` — strictly less-or-equal. That's consistent with the timeout's "round > last_voted_round" guard at line 43-45 of safety_rules_2chain.rs (only updates if strictly greater). Net effect: if we already voted in round R, signing a timeout for R bypasses `verify_and_update_last_vote_round` (only called for `>`), but the `last_voted_round < R` check at line 37-42 only fires for `R < last_voted_round`. **For `R == last_voted_round`, no last-voted check runs at all.** This is by design (you can timeout the round you voted in), but it means a round-state divergence between in-memory `RoundState.current_round` and persisted `safety_data.last_voted_round` can lead to repeated timeout signing for the same round on restart.

### 3.6 `process_sync_info_msg` (`round_manager.rs:976`)

* Calls `ensure_round_and_sync_up(sync_info.highest_round() + 1, &sync_info, peer)` :988. So sync_info pushes us forward to one beyond what the peer has. **Sender is `peer` from the channel** — this is the peer-id derived from the network connection at the EpochMgr level, not a signature. The handler does NOT call `validator.is_validator(peer)`. EpochMgr did filter unknown-epoch messages, but it did not assert the sender is in the *current* validator set. The verification at `sync_info.verify` :138 only validates that the carried QC/HOC/HCC/TC have valid 2f+1 aggregate signatures from the current epoch's validators — but the *sender* of the SyncInfo never has to be one of those validators. Implication: a non-validator (or a former validator from a previous epoch whose stake was slashed but who still holds a valid network identity) can keep pushing us SyncInfos. The QC/TC inside still need 2f+1 valid signatures from the current set, so this is largely benign — but it broadens the attack surface for resource exhaustion.
* `process_sync_info_msg` always returns `Ok(())` :991 regardless of whether sync actually advanced. Errors from `ensure_round_and_sync_up` are wrapped with context but not surfaced as different security events.

### 3.7 `process_local_timeout` (`round_manager.rs:1031`)

* Two divergent code paths: `enable_round_timeout_msg` true → broadcasts a `RoundTimeoutMsg` :1074; false → broadcasts a `VoteMsg` with timeout flag :1119. The signing for both goes through `safety_rules.sign_timeout_with_qc`. **The two paths use slightly different state.** The msg path :1043 unconditionally builds a `TwoChainTimeout` from `self.epoch_state.epoch` and `self.block_store.highest_quorum_cert()`. The vote path at :1083 falls back to the previously-recorded vote if the round matches. If the previously-recorded vote was for a *different* round (e.g., due to a race during round transition), the `match` :1083 falls to the second arm and generates a NIL vote — but the NIL block uses the same HQC. Both paths therefore tie the timeout to the current local HQC; if a Byzantine peer fed us a malformed SyncInfo that bumped HQC to something we shouldn't trust, the resulting timeout would carry that HQC. The HQC is verified via `sync_info.verify` before insertion, so this is contained, but worth noting.
* The early-return :1032 `if !self.round_state.process_local_timeout(round)` — `process_local_timeout` (`round_state.rs:233`) returns false if `round != self.current_round`. So a stale timeout fires before the round advances are dropped — but the timeout from a prior round can still be in-flight when we already have the QC for it.
* **There is a subtle ordering issue.** `process_local_timeout` :1031 reads `self.block_store.highest_quorum_cert()` :1050 for the HQC to embed in the timeout. If `process_certificates` has just inserted a new QC but `process_new_round_event` hasn't fired yet (they run synchronously in the main loop, but the new-round handler can be re-entered through `process_local_timeout`), the HQC reflects the *new* QC while `current_round` reflects the *old* round. The signing check `safety_rules.sign_timeout_with_qc → safe_to_timeout` requires `round == qc_round + 1 || round == tc_round + 1` (`safety_rules_2chain.rs:133`), so the new HQC for round r-1 paired with current_round r-1 fails this check (r-1 ≠ r-1 + 1). The signing fails — but we still call `bail!` at :1081 / :1126, which surfaces as a logged warning. Not security-critical, but a transient liveness hit.

### 3.8 `process_new_round_event` (`round_manager.rs:458`)

* `pending_order_votes.garbage_collect(self.block_store.sync_info().highest_ordered_round())` :504 — uses `sync_info()` which can lag behind in-flight order vote insertions if `process_certificates` for an order-cert happens between this call and a subsequent insertion. Benign (order votes for older rounds get GC'd).
* The leader spawns the proposal task at :533, capturing `sync_info`, `safety_rules`, `proposal_generator`, etc., as Arcs. `safety_rules` is then locked from the spawned task at :717 — running on a Tokio worker, not the round-manager's main task. Two implications:
  1. The leader's `sign_proposal` runs *concurrently* with the next message handlers. If a new `NewRoundEvent` fires for round r+1 *before* the round-r proposal signs, the signing for round r still completes and the proposal is broadcast for round r. This was discussed in §2.2.
  2. `proposal_generator.generate_proposal` :715 freshly inspects `self.block_store.path_from_commit_root(parent_id)` :572. If the block_store has just been mutated (e.g., a fresh QC inserted via vote handling), the proposal would extend whatever the latest HQC is — generally desirable.

### 3.9 Recovery handlers (`recovery_manager.rs`)

* `RecoveryManager::sync_up` :84 verifies `sync_info` :85, then asserts `sync_info.highest_round() > self.last_committed_round` :87 and `sync_info.epoch() == self.epoch_state.epoch` :91. The epoch check is here (good).
* Calls `BlockStore::fast_forward_sync` :104 which fetches blocks, *saves the tree* (`storage.save_tree` at sync_manager.rs:619), and calls `execution_client.sync_to_target` :629. **There is no atomicity** between save_tree, sync_to_target, and the in-memory state assembly. A crash between these steps leaves persistent storage with a partially-updated tree but stale execution state. On restart, `storage.start` reads the tree and produces FullRecoveryData — but the execution-side ledger hasn't reached the same round, so `RoundManager::init` may mismatch.
* On any successful recovery branch, `process::exit(0)` :156 fires and the operator must restart the node. Anything queued in the channel after the success message is dropped. If the `event_rx` next event is also a SyncInfo from a peer who is *further* ahead, that information is lost across the restart.

## 4. Recovery flow trace

### 4.1 Entry conditions

Recovery is entered when `LivenessStorageData::PartialRecoveryData(ledger_data)` is returned from `storage.start` (`epoch_manager.rs:1503`). This happens when the persistent block tree cannot be reconstructed into a `FullRecoveryData` — i.e., the locally-persisted block tree's blocks/QCs don't form a coherent root anchored to the persisted commit ledger info. Typical cause: the node fell behind and the local block_store's window root no longer covers what the latest commit cert references.

Once in recovery (`recovery_mode = true` :1529), `start_recovery_manager` :705 spawns `RecoveryManager` and reuses `round_manager_tx` so the same network-listener forwarding logic ships proposal/vote/sync_info events to the RecoveryManager's `event_rx`.

### 4.2 What state it accepts from peers

The recovery loop (`recovery_manager.rs:130-170`) accepts:
- `VerifiedEvent::ProposalMsg` → extracts sync_info, calls `sync_up` :75.
- `VerifiedEvent::VoteMsg` → extracts sync_info, calls `sync_up` :81.
- `VerifiedEvent::UnverifiedSyncInfo` → calls `sync_up` directly :147.

All three converge on `RecoveryManager::sync_up` :84.

### 4.3 What `sync_up` persists

1. `sync_info.verify` :85 — full verification of HQC/HOC/HCC/TC against the current epoch's validator set.
2. `BlockStore::fast_forward_sync` :104:
   - `retriever.retrieve_blocks_in_range` (sync_manager.rs:510) fetches blocks from `peer`.
   - `LedgerRecoveryData::find_root` (sync_manager.rs:593) sanity-checks the recovery is going to work BEFORE writing storage (good — defensive).
   - `storage.save_tree(blocks.clone(), quorum_certs.clone())` (sync_manager.rs:619) — persists.
   - `block_store.abort_pipeline_for_state_sync()` (sync_manager.rs:625) if a block_store was passed (it's `None` in the recovery path :113) — so for recovery this is a no-op.
   - `execution_client.sync_to_target(highest_commit_cert.ledger_info().clone())` :629 — drives execution to catch up.
   - `storage.start` :635 — re-loads RecoveryData.
3. Returns `RecoveryData` (no in-memory RoundManager state created — the recovery manager just produces `RecoveryData`).

### 4.4 Control return

Looking at `recovery_manager.rs:153-157`:

```rust
match result {
    Ok(_) => {
        info!("Recovery finishes for epoch {}, RecoveryManager stopped. Please restart the node", self.epoch_state.epoch);
        process::exit(0);
    },
```

**Control does NOT return to RoundManager in the same process.** The node calls `process::exit(0)` and restarts. On restart, `EpochManager::start_round_manager` is invoked because `storage.start` should now return `FullRecoveryData`, and `RoundManager::init` (`round_manager.rs:2052`) jump-starts from the certificates in storage.

### 4.5 Crash windows

| Window                                      | What's persisted                              | What's not                                                      | Risk                                                                                                     |
|---------------------------------------------|-----------------------------------------------|-----------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| Before `storage.save_tree` :619             | None of the recovery state                    | All fetched blocks/QCs in memory                                | None — restart re-enters recovery cleanly                                                                |
| Between `storage.save_tree` and `execution_client.sync_to_target` | Block tree saved        | Executed-state DB still at old commit                           | On restart, `storage.start` may produce inconsistent FullRecoveryData (block tree ahead of execution); `RoundManager::init` would extend a chain whose commit ledger info doesn't match execution. Aptos relies on `find_root` to catch this; if it does, recovery loops again. |
| Between `execution_client.sync_to_target` and the `Ok(_) => process::exit(0)` :156 | Both block tree and execution are advanced  | Operator hasn't restarted                                       | Stale entry — if the node receives further messages, they will be processed against the now-up-to-date storage but the in-memory `RecoveryManager` does not track them; a second `sync_up` call could fire and is ABLE to re-issue the same syncs. The next call's `ensure!(sync_info.highest_round() > self.last_committed_round)` :87 may correctly reject older info. |
| In safety-rules persistence during signing  | Signed but `set_safety_data` not yet flushed  | `last_voted_round` could revert on restart                      | If a vote was signed and broadcast but `set_safety_data` failed to flush before crash, on restart we could vote again on the same round (CRITICAL — but this is a safety_rules concern, not recovery). The current code at `safety_rules_2chain.rs:91-92` updates `safety_data.last_vote = Some(vote.clone())` then `set_safety_data` — synchronous in the same call. If `set_safety_data` fails the vote was never broadcast (caller bails). If the process crashes between `set_safety_data` and `network.broadcast_vote`, on restart `last_vote` is set but the network never saw it — that's safe (we just don't re-broadcast). The dangerous direction would be the reverse: broadcast first, then persist. The code does it in the safe order. |

## 5. Top suspicious findings

### Finding 1 — `OrderVoteMsg::verify_order_vote` does not bind the OrderVote's epoch to the inner QC's epoch
- File:line: `consensus/consensus-types/src/order_vote_msg.rs:48-67`
- Mechanism: `verify_order_vote` checks `order_vote.author() == sender`, that the QC's certified-block matches the LedgerInfo's commit-info, and that the OrderVote BLS signature verifies. There is no `ensure!(self.order_vote.epoch() == self.quorum_cert.certified_block().epoch())`. EpochManager filters incoming `OrderVoteMsg` by `order_vote.epoch()` only (epoch_manager.rs:1777, via `UnverifiedEvent::epoch()` returning `order_vote.epoch()` at round_manager.rs:283). The QC inside is verified later in `process_order_vote_msg` :1617 against the *current epoch's* `ValidatorVerifier`, but the QC's internal `certified_block().epoch()` is never asserted equal to the message-level epoch.
- Attacker scenario: a Byzantine validator constructs an `OrderVoteMsg` whose `OrderVote` is correctly signed for the current epoch but whose embedded `quorum_cert` is from a *prior* epoch (whose 2f+1 signatures are still valid against the historical validator set). At an epoch boundary where the local node has just rotated `epoch_state.verifier`, the QC verify at :1617 fails for normal cases — but if the validator set is identical across the boundary (a no-op reconfig), the historical QC's signatures may still pass. The order vote then commits the local node to processing an order cert that pre-dates the current epoch, creating cross-epoch confusion in `pending_order_votes`. PR #13711 added the same epoch check in `safety_rules::verify_order_vote_proposal` :94 but did not propagate it to the RX path here.
- Bug Family: **cross-epoch replay**

### Finding 2 — Optimistic-proposal path skips `failed_authors` validation that the regular path enforces
- File:line: `consensus/src/round_manager.rs:1259-1274` — the `if !proposal.is_opt_block()` guard
- Mechanism: When an opt-proposal is converted to a regular proposal via `Block::new_from_opt` :902 and processed by `process_proposal` :1149, the `failed_authors` check at :1267 is skipped because `is_opt_block()` is true. The regular proposal generator at `proposal_generator.rs:522` always populates `failed_authors`; the opt-proposal generator at `proposal_generator.rs:683` does not (OptBlockData has no failed_authors field). After `new_from_opt`, the resulting block's `failed_authors()` is whatever default `OptBlockBody` carries — likely empty.
- Attacker scenario: Byzantine leader uses the opt-proposal path to omit the failed-authors list whenever there were missed leaders in the prior rounds, suppressing penalty/accountability bookkeeping. Honest leaders following the regular path are correctly accounted for. Net effect: a Byzantine leader can avoid being recorded as a failed author when proposing optimistically.
- Bug Family: **optimistic-proposal bypass**

### Finding 3 — Spawned proposal-signing task can broadcast a stale-round proposal after the local round advanced
- File:line: `consensus/src/round_manager.rs:533-549` (spawn) and the safety-rules check at `consensus/safety-rules/src/safety_rules.rs:356-362`
- Mechanism: `process_new_round_event` for round r captures `new_round_event`, `sync_info`, and `safety_rules` and spawns a Tokio task to sign and broadcast. While that task is running, the main loop can process a vote that completes a TC for round r and triggers another `NewRoundEvent` for r+1. The spawned task is unaware of the round transition. `safety_rules.guarded_sign_proposal` rejects only if `block_data.round() <= safety_data.last_voted_round` :356. `last_voted_round` is updated only on *voting*, not on round-advancement. So the round-r proposal is signed and broadcast even though the leader's own state has progressed to r+1 — which is wasteful but not unsafe. **However**, the spawned task at :533 also captures `sync_info`. By the time it broadcasts, peers may have moved on and the stale sync_info field will fail their `ensure_round_and_sync_up`. Worse: if the leader is then elected for r+2, it may double-propose for r+2 because the proposal_generator's `last_round_generated` :447 is checked atomically per round — so r+2 would succeed once. But if the spawned task is delayed, the leader will broadcast its r-proposal *after* its r+2 proposal — peers see proposals in non-monotonic order from the same leader.
- Attacker scenario: Byzantine validators artificially delay the leader's signing by saturating the safety-rules lock from concurrent vote-handling, then exploit the out-of-order proposal arrival to confuse honest validators' `is_valid_proposal` race detection (which compares against `already_proposed.0`).
- Bug Family: **pipeline race**

### Finding 4 — `safety_rules::sign_commit_vote` has acknowledged TODOs for unhappy-path guards and extension checks
- File:line: `consensus/safety-rules/src/safety_rules.rs:412-413`
- Mechanism: `guarded_sign_commit_vote` :372 verifies the ordered-LI matches the new-LI commit info, verifies 2f+1 signatures on the ordered LI, and signs. It does **not** verify that the `new_ledger_info`'s `commit_info` corresponds to a block our SafetyRules is willing to commit (no preferred-round / one-chain check), and it does not verify that the new LI is an extension of an LI we've previously seen. These TODOs are explicit at lines 412-413.
- Attacker scenario: a Byzantine BufferManager (or anyone with access to the local execution-client RPC) supplies a `LedgerInfoWithSignatures` whose ordered-only commit info matches a real ordered cert, but with a `new_ledger_info.commit_info` that injects an arbitrary executed-state-id (since `match_ordered_only` :397 only matches the ordered subset). The local validator then signs a commit vote for arbitrary executed state. In the current pipeline this requires compromise of the local execution path, so it's a defense-in-depth issue rather than a remote attack. But future refactors that route `sign_commit_vote` from a less-trusted source would expose it.
- Bug Family: **certificate value-binding**

### Finding 5 — `process_sync_info_msg` accepts SyncInfo from any peer, no `is_validator(sender)` check
- File:line: `consensus/src/round_manager.rs:976-992`
- Mechanism: The handler logs the SyncInfo, then calls `ensure_round_and_sync_up` :988 with `peer` as the author. `sync_up` :916 calls `sync_info.verify` (which checks aggregate signatures of the contained QC/TC) but never asserts that `peer` is in the current `epoch_state.verifier`. `EpochManager::check_epoch` filters by message epoch, not by validator membership.
- Attacker scenario: a non-validator peer (e.g., an aptos full-node with a stolen network identity, or a former validator who was slashed but kept the network identity) keeps sending crafted SyncInfo objects with valid aggregate signatures (which they snapshot from honest gossip) plus extra timeout certificates aimed at maximising the per-message work the receiver must do (especially once the SyncInfo causes a `block_store.add_certs` :938, which can fan-out into block fetches). The asymmetric work amplifies their bandwidth cost.
- Bug Family: **certificate value-binding** / DoS-adjacent (no direct safety violation, the carried QCs are correctly signed)

### Finding 6 — Order-vote handler skips `ensure_round_and_sync_up`
- File:line: `consensus/src/round_manager.rs:1582-1660` (no call to `ensure_round_and_sync_up`)
- Mechanism: `process_order_vote_msg` operates on `pending_order_votes` and on the per-block QC, but never harmonises the local round with the order vote's round. An order vote can therefore add to local pending state for a round well above the current round (up to `highest_ordered_round + 100` :1608) without first synchronising. If 2f+1 such order votes assemble, `OrderVoteReceptionResult::NewLedgerInfoWithSignatures` fires and `new_ordered_cert` :2020 is called. That calls `new_qc_from_order_vote_msg` :1973, which checks `need_fetch_for_quorum_cert` :1980 — for a high-round QC the result is `NeedFetch` :1996, and the function returns an error without fetching ("we just log a warning here to avoid a long sequence of block fetches" :2000). So the order-cert never gets recorded locally, but the `pending_order_votes` map has been mutated.
- Attacker scenario: 2f+1 colluding validators flood honest nodes with order votes for non-existent (or far-future) blocks. Honest nodes verify QCs and signatures (CPU cost) but cannot use the resulting order cert. A subsequent sync-info or proposal might then bring in those blocks, at which point the order cert is suddenly inserted retroactively (the LedgerInfoWithSignatures is in `OrderVoteStatus::EnoughVotes` and the next call to `insert_order_vote` returns it :84-89). The pre-staged commit then fires without ever having been ratified by the local view of the chain.
- Bug Family: **order-vote vs regular-vote asymmetry**

### Finding 7 — Opt-proposal path: the proposer's claimed `grandparent_qc` is never re-checked against block_store at vote time
- File:line: `consensus/src/round_manager.rs:881-913` (`process_opt_proposal`) and `consensus/consensus-types/src/opt_proposal_msg.rs:69-74` (verify_well_formed)
- Mechanism: The OptProposalMsg verifier ensures `grandparent_qc.certified_block().id() == sync_info.highest_quorum_cert().certified_block().id()` (opt_proposal_msg.rs:69). But by the time `process_opt_proposal` is invoked (via the loopback), the OptBlockData has been stripped of its sync_info link — the function `process_opt_proposal` :881 reads the local `block_store.highest_quorum_cert()` :889 and compares its certified-block id to `opt_block_data.parent_id()` :897. The proposer's `grandparent_qc` (which is part of `OptBlockBody` :50) is *never* re-read at this point. The block is then converted via `Block::new_from_opt` :902 which substitutes the local HQC. Consequently, an opt-proposal whose original `grandparent_qc` referred to a fork is silently rebound to the local QC.
- Attacker scenario: Byzantine leader sends an opt-proposal with `grandparent_qc` pointing at a fork (say, a competing QC for the same round). Honest receivers with the *winning* parent QC accept it. Honest receivers with the *fork* parent QC also accept it but vote on different parent ledger info. Since `Block::new_from_opt` substitutes the local HQC, both groups vote on the same opt-block-id but with different effective parents — leading to an inconsistent QC formation downstream.
- Bug Family: **optimistic-proposal bypass** / **certificate value-binding**

### Finding 8 — Recovery exits via `process::exit(0)`, dropping in-flight messages and any unflushed safety state
- File:line: `consensus/src/recovery_manager.rs:154-157`
- Mechanism: On successful recovery, the process terminates rather than handing control back. Anything in `event_rx` past the success message is dropped. The `safety_rules` instance held by the (now-dead) RecoveryManager has only had its `epoch_state` initialised; if the operator's restart script is misconfigured, the node may be down longer than necessary and miss timeout votes, weakening liveness. More subtly, the recovery does not capture or persist the *round* the node was at before recovery — so on restart, `RoundManager::init` :2052 jump-starts from `block_store.sync_info()`, which means the persisted `last_voted_round` may be lower than what we briefly observed during recovery (since we only fetched blocks/QCs, not vote-tracking state).
- Attacker scenario: a Byzantine peer sends crafted SyncInfo to push us into recovery during a routine epoch transition; when we restart, our `last_voted_round` is the *old* persisted value, so we may legally vote for blocks at rounds we'd already conceptually progressed past. The safety_rules check at safety_rules.rs:356-362 still gates this (we cannot vote for round ≤ persisted last_voted_round), so this is constrained — but it widens the window for vote-divergence.
- Bug Family: **recovery divergence**

### Finding 9 — `process_local_timeout` re-entry through `EchoTimeout` can re-sign the same round's timeout
- File:line: `consensus/src/round_manager.rs:1855-1857` (the `EchoTimeout` arm in `process_vote_reception_result`) and `consensus/safety-rules/src/safety_rules_2chain.rs:37-45`
- Mechanism: `process_vote_reception_result` :1810 has `VoteReceptionResult::EchoTimeout(_) if !self.round_state.is_timeout_sent()` → `process_local_timeout(round)` :1856. If `is_timeout_sent()` is checked atomically with `process_local_timeout`, only one timeout per round fires. But `is_timeout_sent` (round_state.rs:217) checks `self.timeout_sent.is_some() || self.vote_sent.as_ref().is_some_and(|v| v.is_timeout())`. There's a brief window between starting `process_local_timeout` (which calls `safety_rules.sign_timeout_with_qc` synchronously) and recording `self.timeout_sent` — but since the entire `process_*` chain is synchronous on a single Tokio task, there is no actual concurrent re-entry. **However**, if the node crashed mid-signing and restarted, the safety_rules persisted state has `last_voted_round = R` and `highest_timeout_round = R` (assuming the timeout was signed and persisted), and `RoundState` reconstitutes with `current_round = R+1` (from `process_certificates` based on the QC inserted from sync_info). A timeout vote message for round R that arrives now goes through `ensure_round_and_sync_up(R, ...)` which fails because `R < current_round = R+1` :960 (returns `Ok(false)`). So this is contained — but the same logic does NOT shield the case where R == current_round and a vote with `is_timeout` echoes us back into `process_local_timeout`. The safety-rules guard at `safety_rules_2chain.rs:37` (`timeout.round() < safety_data.last_voted_round`) only rejects strictly-less rounds, so a re-entry for `round == last_voted_round` proceeds to `safe_to_timeout` :36 → success → sign again. The `record_round_timeout` :1071 then bumps `timeout_sent`, so subsequent `is_timeout_sent` is true and the next echo is a no-op. Net effect: at most two timeouts may be signed for the same round on a node that crashes between `sign_timeout_with_qc` and `record_round_timeout`.
- Attacker scenario: Byzantine peer floods a node with timeout votes near a crash window to maximise the chance the node signs two timeouts for the same round. Two timeouts for the same round don't violate the 2-chain safety rule but they could be combined with another fault to create equivocation evidence — and they consume validator-key signatures that should be unique per round.
- Bug Family: **crash-window double vote**

### Finding 10 — `sync_info` passed to leader's spawned proposal task is captured at spawn time, not at sign time
- File:line: `consensus/src/round_manager.rs:529-549` (the `let sync_info = self.block_store.sync_info();` at :529 is captured into the closure spawned at :533)
- Mechanism: The leader proposal flow snapshots `sync_info` from the block_store before spawning. The proposal generator at `proposal_generator.rs:494` then re-reads `block_store.highest_quorum_cert()` :501 to choose the branch — but the SyncInfo used to build the broadcast `ProposalMsg` is the *snapshot*. If between snapshot and broadcast the local block_store has advanced (e.g., absorbed a higher QC), the leader's broadcast proposal will carry an OLDER SyncInfo than the local view — peers receiving it will not benefit from any newer info the leader has, and the leader's own `ensure_round_and_sync_up` (when receiving votes for the proposal) may end up syncing back to a state strictly ahead of what the proposal carried.
- Attacker scenario: Byzantine collusion times message delivery so that the leader's snapshot is taken just before a fast-arriving QC, ensuring the broadcast proposal under-reports the leader's state. Honest validators receiving the proposal must sync further than expected (extra round-trip for QC fetch). At scale this slows commit latency without any safety violation.
- Bug Family: **pipeline race**

## Summary

The Aptos round_manager event loop is well-factored: a single `select!` task owns mutable `RoundState`, `pending_opt_proposals`, and `pending_order_votes`; safety-critical signing is funnelled through a single `Mutex<MetricsSafetyRules>`; and pipeline phases are decoupled into separate Tokio tasks behind channels.

The main asymmetries are:
1. **Order votes** are the only consensus message that lacks an `ensure_round_and_sync_up` call (Finding 6) and that doesn't bind the inner QC's epoch to the message-level epoch (Finding 1).
2. **Optimistic proposals** skip `failed_authors` validation (Finding 2), are not BLS-signed at the block level (relying on network identity for proposer binding), and have their `grandparent_qc` claim silently rebound to the local HQC at vote time (Finding 7).
3. **Recovery** is process-exit-and-restart (Finding 8), with no graceful handoff of round state or in-flight messages.
4. **Acknowledged TODOs** in `safety_rules::sign_commit_vote` :412-413 (Finding 4) — guard rules for the unhappy path and extension checks are still missing.
5. **Spawned proposal task** captures sync_info / safety_rules at spawn time and may broadcast stale-round proposals or under-state SyncInfo (Findings 3 and 10).
6. **No `is_validator(sender)` check** on `process_sync_info_msg` (Finding 5), and a **crash window** in the timeout path can yield two signed timeouts for the same round (Finding 9).

The code is consistently defensive in obvious places (epoch verification at EpochManager, signature verification on entry, `UnequivocalProposerElection` at vote-time), but the order-vote and optimistic-proposal extensions inherit weaker validation than the regular vote/proposal pipeline. Cross-epoch replay (Finding 1) and order-vote pre-staging (Finding 6) are the two cleanest attack vectors warranting deeper trace-based analysis.
