## Trigger

`DecodeWithBackupKey` in `base.tla:318` increments `rsp_rx_gen` by 1, but the real
implementation's combined `activate(REQUESTER,false) + create_update(REQUESTER)` sequence
is **idempotent** on key generation: the net result is the same active key as before the
backup decode fired (gen-1 both before and after). The model over-counts key generations.

## Evidence

**CE step that cannot be reproduced:**
- TLA counterexample State 4 (`MCDecodeWithBackupKey`): `rsp_rx_gen` advances from 1 → 2.
- In the implementation, after `activate(REQUESTER,false)` + `create_update(REQUESTER)`:
  - `activate(false)`: restores `application_secret.request_data_secret = old_key` AND
    CLEARS the backup slot (`requester_backup_valid = false`).
    (`libspdm_secmes_session.c:499–558`)
  - `create_update`: copies `old_key` back to backup, derives `KDF(old_key) = new_key`.
  - Net: `active = KDF(old_key) = new_key` — **identical** to the state after the initial
    `create_update` in `RspRecvUpdateKey`.

**Predicted state (from CE):** after `DecodeWithBackupKey`, `rsp_rx_gen = 2` = expected key
is `KDF(KDF(old_key))`.

**Realized state (from repro run):** after `activate(false)+create_update`, active key =
`KDF(old_key) = a466ca66d620853c...` — same as after `RspRecvUpdateKey` alone.
Requester's TX key after `ReqRecvKeyUpdateAck` = `KDF(old_key) = a466ca66d620853c...` — match.

**Code citation:**
- `libspdm_secmes_session.c:499–558` — `libspdm_activate_update_session_data_key` with
  `use_new_key=false`: restores active from backup, then zeroes the backup slot and sets
  `requester_backup_valid = false` unconditionally.
- Because `activate(false)` CLEARS the backup before `create_update` is called, the second
  `create_update` derives from `old_key` (restored active), producing `KDF(old_key)` — not
  `KDF(KDF(old_key))`.
- The `g_tla.rsp_rx_gen++` instrumentation at `libspdm_rsp_receive_send.c:266` is incorrect:
  it counts `create_update` invocations, not actual key-generation advances.

**Reproduction test:** `spec/repro/test_bug1_key_desync.c`
- Level 0: heartbeat after `libspdm_key_update` succeeds — PASS
- Level 2a: `activate(false)+create_update` idempotency check — PASS (both assertions)
  - `rsp_rx_gen` after backup-decode == `rsp_rx_gen` after initial `create_update`:
    secret `a466ca66...` = `a466ca66...` (MATCH)
  - RSP active RX key == REQ active TX key: `a466ca66...` = `a466ca66...` (MATCH)
- Level 2b: exact TLA counterexample Steps 2–6 — PASS
  - Step 2→3: RSP key unchanged by backup-decode (MATCH)
  - Final: RSP committed RX == REQ committed TX (invariant holds)

## Proposed change

In `base.tla`, `DecodeWithBackupKey` action (lines 312–324):

**Current:**
```tla
/\ rsp_rx_gen'          = rsp_rx_gen + 1
```

**Proposed:**
```tla
/\ rsp_rx_gen'          = rsp_rx_gen   (* activate(false) rolls back before create_update *)
```

Rationale: The combined `activate(REQUESTER,false) + create_update(REQUESTER)` sequence is
idempotent. `activate(false)` first restores the active key to `old_key` (gen-0), then
`create_update` re-derives `KDF(old_key) = new_key` (gen-1) — the same generation-1 key
material as after the initial `RspRecvUpdateKey` call. No net generation advance occurs.

After the repair, `KeySynchronization` should hold for all `MC_hunt_family1.cfg` states:
both `rsp_rx_gen` and `req_tx_gen` correctly reach 1 after a key update cycle that includes
a backup-decode event.
