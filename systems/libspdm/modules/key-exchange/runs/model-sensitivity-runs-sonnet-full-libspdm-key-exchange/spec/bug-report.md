# Bug Report: libspdm KEY_EXCHANGE / FINISH Session Establishment

Generated by TLA+ model checking (Phase 3B). Spec: `base.tla` / `MC.tla`.
Date: 2026-06-08.

---

## Spec Convergence Summary

Base model checking (`MC.cfg`, structural invariants only) required three spec fixes before converging:

| Fix | Classification | Description |
|-----|---------------|-------------|
| Remove `SYMMETRY`/`VIEW` directives from all CFGs | Config error | `Sessions = 1..N` produces integers; TLC symmetry requires model values |
| `ReqSendFinish` consumes `KEY_EX_RSP` | Case B (spec) | KEY_EX_RSP was never removed from `msgs`, creating unreachable garbage and false deadlocks |
| `RspCommitEstablished` requires `finish_rsp.session_id = s_derive` | Case B (spec) | Any FINISH_RSP could satisfy any session's `CommitEstablished`, enabling cross-session consumption |
| `FinishRspConsistency` widened to `{KEYS_DERIVED, ESTABLISHED}` | Case A (invariant) | F1 bug causes a session to be committed via another session's FINISH_RSP path, leaving its own FINISH_RSP in `msgs` while ESTABLISHED; structural invariant is preserved |
| `auth_session = s` in `ReqSendFinish` | Case B (spec) | Requester always computes FINISH MAC for the session it negotiated; `auth_session ≠ s` is a responder-side F1 bug (routing via `latest_session_id`), not a requester-side bug |

After these fixes, base MC explored **792,637 states / 499,614 distinct states** with no invariant violations.

## Findings

### BUG-001 — Session Identity Confusion Under HANDSHAKE_IN_THE_CLEAR (F1)

**Severity**: Critical  
**Category**: Authentication bypass / session confusion  
**Status**: Confirmed — Case C (real implementation bug)  
**Invariant violated**: `MCSessionEstablishedOnlyAfterOwnFinish`  
**Config**: `MC_hunt_family1.cfg`  
**States explored**: 18,513 / 10,731 distinct  

#### Root Cause

`libspdm_com_context_data_session.c:221` unconditionally overwrites `spdm_context->latest_session_id` on every successful session allocation. When two KEY_EXCHANGE handshakes are in flight:

1. Session 1 allocated (HITC=TRUE) → `latest_session_id = 1`
2. Session 2 allocated → **`latest_session_id = 2`** (overwrites)
3. Session 1's FINISH arrives cleartext (HITC path, no session_id in header)
4. `libspdm_rsp_finish_rsp.c:484`: `session_id = spdm_context->latest_session_id` → **resolves to session 2!**
5. Session 1's FINISH MAC (computed for session 1) is verified against session 2's context
6. `libspdm_rsp_receive_send.c:828-831`: HITC commit path also uses `context->latest_session_id` → session 2 marked ESTABLISHED with wrong authentication

Session 2 is ESTABLISHED but was never actually authenticated by session 2's own requester.

#### Counterexample (10 states)

| State | Action | Key Variables |
|-------|--------|---------------|
| 1 | Initial | sessions: [not_started, not_started], latest_session_id=0 |
| 2 | MCReqSendKeyExchange(TRUE,1,"none") | msgs: {KEX(hitc=TRUE)} |
| 3 | MCReqSendKeyExchange(FALSE,1,"none") | msgs: {KEX(hitc=TRUE), KEX(hitc=FALSE)} |
| 5 | RspHandleKeyExchange(KEX(hitc=TRUE), s=1) | session_state=[HANDSHAKING,NOT_STARTED], hitc_negotiated[1]=TRUE, **latest_session_id=1** |
| 6 | RspHandleKeyExchange(KEX(hitc=FALSE), s=2) | session_state=[HANDSHAKING,HANDSHAKING], hitc_negotiated[2]=FALSE, **latest_session_id=2** |
| 7 | ReqSendFinish(KEY_EX_RSP_s1, auth=1) | FINISH: {session_id=1, **session_id_valid=FALSE** (HITC!), auth_session=1} |
| 8 | RspDeriveDataKeys | **target=latest_session_id=2** (F1 bug), finish_authenticated_for[2]=1, session_state[2]=KEYS_DERIVED |
| 9 | RspCommitEstablished(s=2) | session_state[2]=**ESTABLISHED** |
| 10 | VIOLATION | session_state[2]=ESTABLISHED, **finish_authenticated_for[2]=1 ≠ 2** |

#### Affected Code

- `libspdm/library/spdm_common_lib/libspdm_com_context_data_session.c:221` — unconditional `latest_session_id` overwrite
- `libspdm/library/spdm_responder_lib/libspdm_rsp_finish_rsp.c:481-485` — HITC path uses global `latest_session_id`
- `libspdm/library/spdm_responder_lib/libspdm_rsp_receive_send.c:828-831` — HITC commit also uses `latest_session_id`

#### Impact

A second simultaneous KEY_EXCHANGE (from any client or replayed) can cause the responder to establish session 2 with session 1's FINISH MAC. Session 2's requester is never authenticated. An attacker that initiates a second KEY_EXCHANGE at the right moment can hijack session establishment for another connection.

#### Confirmation

**Code audit**: `libspdm_com_context_data_session.c:221` — `spdm_context->latest_session_id = session_id;` — no guard, no previous-value restore. `libspdm_rsp_finish_rsp.c:481-485` — HITC path: `session_id = spdm_context->latest_session_id;` — uses the global, not any per-session identifier. `libspdm_rsp_receive_send.c:828-831` — HITC commit path also reads `context->latest_session_id` to transition to ESTABLISHED.

**Developer intent**: `latest_session_id` exists to carry the current session ID into the HITC FINISH path because the HITC FINISH header has no session_id field. The design assumes at most one session is in HANDSHAKING at a time. The comment in `libspdm_free_session_id` that resets the field (line 243) confirms the field is intended as "current active session", not "most recently allocated session".

**Reproduction test**: `repro/test_bug1_hitc_session_confusion.c` — Level 0. Single requester does KEY_EXCHANGE twice (both HITC), then sends FINISH for the first session. Responder routes FINISH using `latest_session_id`, which was overwritten by the second KEY_EXCHANGE.

**Reproduction result**:
```
Requester initiates TWO KEY_EXCHANGE sessions before either FINISH.
[Step 1] req KEY_EXCHANGE session S1 (HITC=TRUE)
[Step 2] req KEY_EXCHANGE session S2 (HITC=TRUE) — overwrites latest_session_id
[BUG CONDITION] latest_session_id=0xfffefffe (S2), NOT session1_id=0xffffffff
[Step 3] FINISH for session S1 (HITC cleartext path)
!!! verify_finish_req_hmac - FAIL !!!
[BUG CONFIRMED] FINISH for S1 failed: 0x8001000f
  Responder processed FINISH using S2's context (latest_session_id=0xfffefffe)
```

**Classification**: REPRODUCED. Confidence: HIGH. The `verify_finish_req_hmac - FAIL` message is emitted by `libspdm_rsp_finish_rsp.c` itself, confirming the bug pathway is exercised and the MAC is verified against the wrong session context.

### BUG-002 — Mutual Auth Cert Slot Not Stored on Non-Encap Path (F2)

**Severity**: High  
**Category**: Authentication bypass (wrong certificate used for FINISH verification)  
**Status**: Confirmed — Case C (real implementation bug)  
**Invariant violated**: `MCMutAuthUsesNegotiatedSlot`  
**Config**: `MC_hunt_family2.cfg`  
**States explored**: 3,653 / 2,540 distinct  

#### Root Cause

In `libspdm_rsp_key_exchange.c:570-578`, the `peer_used_cert_chain_slot_id` field is only written on the **encap** mutual-auth path (line 576), not on the **non-encap** path:

```c
if (!need_encap) {
    spdm_response->mut_auth_requested = mut_auth_requested;
    spdm_response->req_slot_id_param = req_slot_id;   // only in response buffer
    // peer_used_cert_chain_slot_id NOT set here  ← BUG
} else if (need_encap && req_encap_cap) {
    spdm_response->mut_auth_requested = mut_auth_requested;
    session_info->peer_used_cert_chain_slot_id = req_slot_id;  // set here on encap
    ...
}
```

When the FINISH signature verification runs (reading `peer_used_cert_chain_slot_id` at `libspdm_rsp_finish_rsp.c:49,153,200,340`), it gets `NO_SLOT` (0) for non-encap sessions, verifying the signature against the wrong (default) certificate.

#### Counterexample (7 states)

| State | Action | Key Variables |
|-------|--------|---------------|
| 1 | Initial | cert_advertised=[0,0], peer_cert_slot=[0,0] |
| 2 | MCReqSendKeyExchange(FALSE,1,"non_encap") | mode=non_encap, req_slot_id=1 |
| 4 | RspHandleKeyExchange(non_encap, s=1) | mut_auth_mode[1]=non_encap, **cert_advertised[1]=1**, **peer_cert_slot[1]=0** (NO_SLOT — missing write) |
| 5 | ReqSendFinish | FINISH sent |
| 6 | RspDeriveDataKeys | **cert_slot_verified[1]=peer_cert_slot[1]=0** (should be 1) |
| 7 | RspCommitEstablished | session_state[1]=ESTABLISHED |
| 8 | VIOLATION | mut_auth_mode[1]=non_encap, cert_advertised[1]=**1**, cert_slot_verified[1]=**0** → cert mismatch |

#### Affected Code

- `libspdm/library/spdm_responder_lib/libspdm_rsp_key_exchange.c:571-573` — non-encap branch writes `req_slot_id` to response buffer only, not to session state

#### Impact

For non-encap mutual authentication, the responder verifies the FINISH signature against the default slot 0 instead of the negotiated slot. A requester can present a certificate from slot 1 during negotiation but sign FINISH with slot 0's key, and the responder will accept it. Mutual authentication is silently bypassed for non-encap flows.

#### Confirmation

**Code audit**: `libspdm_rsp_key_exchange.c:570-578` — the `if (!need_encap)` branch (line 572) writes `req_slot_id` only to `spdm_response->req_slot_id_param` (the outgoing buffer). The `else if (need_encap && req_encap_cap)` branch (line 575) additionally writes `session_info->peer_used_cert_chain_slot_id = req_slot_id`. The non-encap branch has no corresponding write to `session_info`. `libspdm_rsp_finish_rsp.c:49,153,200,340` reads `peer_used_cert_chain_slot_id` to select the certificate for FINISH signature verification.

**Developer intent**: The field `peer_used_cert_chain_slot_id` is initialized to `0` (default slot) when a session is allocated. The encap branch updates it explicitly because encap auth was added later. The non-encap branch predates this field and was never updated to write it. The `req_slot_id_param` copy to the response buffer is correct (it tells the requester which slot to use), but the session-state copy is missing.

**Reproduction test**: `repro/test_bug2_nonencap_cert_slot.c` — Level 3. Provides a custom `libspdm_key_exchange_start_mut_auth` callback returning `*req_slot_id = 1` (non-default slot). Sets `g_key_exchange_start_mut_auth = SPDM_KEY_EXCHANGE_RESPONSE_MUT_AUTH_REQUESTED` to activate non-encap mutual auth. Reads `session_info->peer_used_cert_chain_slot_id` from the responder after KEY_EXCHANGE.

**Reproduction result**:
```
[State Inspection] session_info->peer_used_cert_chain_slot_id = 0
[BUG CONFIRMED] peer_used_cert_chain_slot_id=0 but requested slot was 1.
IMPACT: FINISH signature will be verified against slot 0 cert, not slot 1.
        A requester using slot 1 key will have its FINISH accepted incorrectly.
```

**Classification**: REPRODUCED. Confidence: HIGH. Direct read of `session_info->peer_used_cert_chain_slot_id = 0` (instead of 1) after a non-encap KEY_EXCHANGE with `req_slot_id = 1` is definitive.

### BUG-003 — Session Slot Leak on Key-Derivation / Encode Failure (F3)

**Severity**: Medium  
**Category**: Resource leak / denial of service  
**Status**: Suspected — confirmed by code analysis; not directly detectable with safety invariants alone (temporal property needed)  
**Invariant violated**: `MCSessionEstablishedOnlyAfterOwnFinish` (F1 found first by BFS); zombie scenario detected via code analysis  
**Config**: `MC_hunt_family3.cfg`  
**States explored**: 3,866 / 2,717 distinct  

#### Root Cause

In `libspdm_rsp_finish_rsp.c:739-765`, if TH2 hash computation or `libspdm_generate_session_data_key` fails, the function returns an error **without calling `libspdm_free_session_id`**:

```c
result = libspdm_calculate_th2_hash(...);
if (!result) {
    return libspdm_generate_error_response(...);  // NO free_session_id ← BUG
}
result = libspdm_generate_session_data_key(...);
if (!result) {
    return libspdm_generate_error_response(...);  // NO free_session_id ← BUG
}
```

Compare: the KEY_EXCHANGE handler (`libspdm_rsp_key_exchange.c`) DOES call `libspdm_free_session_id` on all failure paths (a known historical fix, commit `56384085e8`). The FINISH handler has not received the same treatment.

The session remains in `KEYS_DERIVED` state with `data_keys_live=TRUE` indefinitely. The session slot is permanently occupied.

#### TLC Finding

The BFS trace for Family 3 found `MCSessionEstablishedOnlyAfterOwnFinish` (the F1 violation) at 8 states, which is shorter than the F3 zombie path. The zombie requires `MCEncodeFailures=1` to fire, but F1 takes precedence in BFS shortest-path search.

The `MCNoDataKeysBeforeEstablished` invariant correctly allows `data_keys_live=TRUE` with `KEYS_DERIVED` (transient state) — detecting the zombie as a permanent stuck-state requires a liveness/temporal property (`<>(~∃s: session_state[s] = KEYS_DERIVED)`) which is present in the config but commented out.

#### Affected Code

- `libspdm/library/spdm_responder_lib/libspdm_rsp_finish_rsp.c:741-764` — missing `libspdm_free_session_id` on crypto failure paths
- Contrast with `libspdm_rsp_key_exchange.c:559-568` — correctly calls `libspdm_free_session_id` on equivalent failure paths

#### Impact

A requester that can trigger a TH2 hash failure (e.g., by corrupting the transcript or using an implementation with unstable hardware crypto) can permanently exhaust session slots. If all `MaxSessions` slots are leaked, no new sessions can be established — denial of service.

#### Confirmation

**Code audit**: `libspdm_rsp_finish_rsp.c:739-752` — after `libspdm_calculate_th2_hash` returns false (line 740), the next executed statement is `return libspdm_generate_error_response(...)` (line 742). There is no call to `libspdm_free_session_id` on this path. The pattern repeats at line 754-758 for `libspdm_generate_session_data_key`. Compare: `libspdm_rsp_key_exchange.c:559, 564, 603, 615, 630, 650, 663, 685, 710, 734, 745, 754, 762, 770, 779, 787, 801, 809, 824` — every failure path calls `libspdm_free_session_id`.

**Developer intent**: The KEY_EXCHANGE handler received a cleanup audit (referenced in commit `56384085e8`) that added `libspdm_free_session_id` to all failure paths. The FINISH handler did not receive the same treatment. The session slot management assumes the caller of `libspdm_rsp_finish_rsp` will free the session on error, but `libspdm_process_request` / `libspdm_build_response` do not.

**Reproduction test**: `repro/test_bug3_session_slot_leak.c` — Level 3. Uses `--wrap=libspdm_calculate_th2_hash` to intercept the TH2 hash call and return false. To prevent LTO from inlining the symbol, `libspdm_rsp_finish_rsp.c` is recompiled without `-flto` (machine-code `.o` linked before the pre-built `.a`) so the call site is a real CALL instruction that `--wrap` can intercept.

**Reproduction result**:
```
[Step 1] KEY_EXCHANGE succeeded, session_id=0xffffffff
         Responder slots: 1/4, state=1 (1=HANDSHAKING)
  [WRAP] libspdm_calculate_th2_hash: FORCED FAILURE
[Step 2] FINISH result: 0x8001000a (ERROR)
         --wrap fired:   YES
         Slots after:    1/4
         Session state:  1 (HANDSHAKING (leaked))
[BUG CONFIRMED] Session slot NOT freed after TH2 hash failure!
  session_id=0xffffffff remains in HANDSHAKING state (slot not released).
[Step 3] Filling remaining 3 session slots...
         Filled slot 1: session_id=0xfffeffff
         Filled slot 2: session_id=0xfffdffff
         Filled slot 3: session_id=0xfffcffff
         Total occupied: 4/4 (all slots full)
[Step 4] Extra KEY_EXCHANGE: 0x8001000a (FAILED (expected))
[DoS CONFIRMED] Zombie session from failed FINISH blocks new connections.
```

**Classification**: REPRODUCED. Confidence: HIGH. Session slot remains in HANDSHAKING state (not freed) after forced TH2 failure; with 4/4 slots occupied, new KEY_EXCHANGE is rejected — matching the TLA+ liveness/DoS scenario.

### BUG-004 — Sequence Counter Advanced Before AEAD Verification (F4)

**Severity**: High  
**Category**: Protocol state desynchronization / replay-attack amplification  
**Status**: Confirmed — Case C (real implementation bug)  
**Invariant violated**: `MCSeqCounterStableOnDecryptFailure`  
**Config**: `MC_hunt_family4.cfg`  
**States explored**: 289 / 223 distinct  

#### Root Cause

In `libspdm_secmes_encode_decode.c:420-432`, the sequence counter is incremented **before** calling `libspdm_aead_decryption` at line 483:

```c
// Lines 420-432: counter incremented here ← BUG (before AEAD)
if (session_state == LIBSPDM_SESSION_STATE_HANDSHAKING) {
    ...request_handshake_sequence_number++;
} else {
    ...request_data_sequence_number++;    // advanced here
}

// ... (header parsing, buffer setup) ...

// Line 483: AEAD decryption happens here — AFTER counter already advanced
result = libspdm_aead_decryption(...);
// If result == false: AEAD failed, but counter is permanently incremented
```

If AEAD decryption fails (wrong key, corrupted ciphertext, or injected packet), the counter has already moved forward. The legitimate next message will arrive with the old counter value, which the responder now expects as `counter+1` — the sequence check fails and the session is permanently desynchronized.

#### Counterexample (11 states)

| State | Action | Key Variables |
|-------|--------|---------------|
| 1-6 | Handshake | Session 1 ESTABLISHED, expected_seq[1]=0 |
| 7 | MCReqSendAppData(1, authentic=FALSE) | msgs: {APP_DATA(seq=0, authentic=FALSE)} |
| 9 | RspDecodeSecuredMessage | seq_before_advance[1]=0, **expected_seq[1]=1** (incremented), AEAD fails → **last_decode_rejected[1]=TRUE** |
| 10 | VIOLATION | last_decode_rejected[1]=TRUE, expected_seq[1]=**1** ≠ seq_before_advance[1]=**0** |

#### Affected Code

- `libspdm/library/spdm_secured_message_lib/libspdm_secmes_encode_decode.c:420-432` — counter increment before AEAD call at 483

#### Impact

A network attacker who can observe the cleartext sequence number in the message header (the sequence number is not encrypted per SPDM spec) can:
1. Capture the current `expected_seq` value from any packet
2. Send one malformed packet with correct `session_id` and `seq_num` but invalid ciphertext
3. The responder increments the counter and rejects the AEAD — but the requester's counter stays at the old value
4. All subsequent legitimate traffic fails the sequence check → **permanent session desynchronization with a single injected packet**

The mitigation path (`SESSION_TRY_DISCARD_KEY_UPDATE`, `libspdm_secmes_encode_decode.c:523-527`) only applies after a `KEY_UPDATE` handshake, not normal application data.

#### Confirmation

**Code audit**: `libspdm_secmes_encode_decode.c:420-432` — `request_data_sequence_number++` (or the handshake equivalent) happens unconditionally. `libspdm_aead_decryption` is called at line 483. If it returns false (line 529), `libspdm_release_receiver_buffer` is called and the function returns an error — but the counter is never decremented or restored. The SPDM spec (DSP0274 §10.3.1) requires the receiver to discard packets with duplicate or unexpected sequence numbers, which creates the window: once the counter is one ahead of the sender, every subsequent packet is "unexpected" and discarded.

**Developer intent**: The increment-before-AEAD pattern is likely inherited from a reference implementation or a misreading of the spec. The natural position is: parse header (including extracting seq_num), validate seq_num against expected counter, then AEAD decrypt the body. Moving the increment after a successful AEAD would make the counter advance only on authenticated messages. The pre-AEAD increment was probably done to avoid a "double-check" of the sequence number.

**Reproduction test**: `repro/test_bug4_seq_counter_before_aead.c` — Level 0. The `req_send_fn` callback flips the last 16 bytes (AES-256-GCM tag) of the message. The counter is read from within `req_recv_fn` immediately after `libspdm_process_request` returns an error, before the requester's `send_receive_data` can clean up the session.

**Reproduction result**:
```
[Setup] Session established, session_id=0xffffffff
[Step 1] Sending legitimate app data (req_seq=0, rsp_expects=0)
         req_seq: 0->1, rsp_seq: 0->1
[Step 2] Sending app data with corrupted AEAD tag
         Before: req_seq=1, rsp_expects=1
  [INJECT] Corrupted AEAD tag at bytes [61..76]
         rsp counter inside callback: 2
         req_seq after call: 18446744073709551615 (session freed by requester)
[BUG CONFIRMED] Responder counter advanced despite AEAD failure!
  Before inject: rsp expects seq 1
  After  inject: rsp expects seq 2 (advanced by 1 despite failure)
[Step 3] Sending next legitimate message after desync
         Requester session was freed (session cannot recover).
[IMPACT CONFIRMED] Session permanently broken with a single injected packet.
```

**Classification**: REPRODUCED. Confidence: HIGH. Counter captured inside the callback (before session cleanup) shows `rsp_seq = 2` after rejecting the corrupted packet at `seq = 1`; the requester's session is freed, confirming no recovery path.

## Spec Modifications Made

All changes are in `base.tla` to improve spec fidelity (Case B fixes) and one `MC.cfg` fix:

1. **`ReqSendFinish`** — consumes `KEY_EX_RSP` from `msgs` (was: `Send` only, leaving RSP stranded)
2. **`RspCommitEstablished`** — added precondition `finish_rsp.session_id = s_derive` (session RSP must match the session being committed)
3. **`FinishRspConsistency`** — widened range to `{KEYS_DERIVED, ESTABLISHED}` (F1 bug causes ESTABLISHED session to have stranded FINISH_RSP; primary detection is extension invariant)
4. **`ReqSendFinish`** — constrained `auth_session = s` (requester always uses its own session's keys; over-approximation was causing false F1 counterexamples on non-HITC paths)
5. **All CFGs** — removed `SYMMETRY Symmetry` and `VIEW MCView` (Sessions is integer-ranged, not model-valued)
