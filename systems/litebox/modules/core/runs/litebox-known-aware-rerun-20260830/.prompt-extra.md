# LiteBox rerun guidance

LiteBox is a Rust concurrent systems/runtime target. This rerun should prioritize findings that provide new actionable evidence for maintainers, not merely rediscover already acknowledged technical debt.

## Known or maintainer-aware areas to deprioritize

Before treating a finding as new, check whether the same mechanism at the same site is already documented in an issue, PR discussion, source comment, TODO, or FIXME.

Do not spend confirmation budget reproducing a known/maintainer-aware behavior unless the run adds a new harmful consequence, a new live consumer, or a materially stronger trigger scenario.

Known examples from the previous run:

- `do_dup_inner` fd-table rollback / recycled fd race is already covered by upstream issue #1170.
- LinuxKernel cross-core TLB shootdown is already covered by upstream issue #671.
- Overlay/resolver coarse lock behavior is explicitly documented by source comments around `litebox/src/fs/overlay.rs` and `litebox/src/fs/resolver.rs`.

## What to prioritize

Look for concurrency bugs where a suspected or documented race has been assumed benign, but a real caller observes a harmful result.

For each candidate, separate:

- filed duplicate status: is there an existing issue/PR/CVE for the same mechanism at the same site?
- maintainer awareness: is the behavior mentioned in comments, TODOs, FIXMEs, or PR review?
- newly demonstrated consequence: does this run show a new harmful consumer, permission bypass, data corruption, resource leak, deadlock, or starvation scenario?

## Phase 4 confirmation guidance

A reproduced inconsistency is not enough. Confirm the live consumer and the observable consequence.

If a finding is already developer-known and the run adds no new harmful consequence, classify it as known/maintainer-aware technical debt rather than presenting it as a new bug.
