# Nanvix Process Management Scope

Focus on the complete process-management subsystem under `src/kernel/src/pm`, prioritizing:

- `process/manager/` and `process/state/` for process creation, state transitions, signals,
  termination, zombie retention, waiting, and resource cleanup
- `thread/` for ready/running/sleeping/interrupted/zombie transitions and join/detach lifecycle
- `kcall/` as the externally reachable entry points for duplicate, exec, create/join/detach thread,
  kill, terminate, sleep, signal, mutex, condition-variable, mmap, and munmap operations
- `sync/` for mutex/condition-variable ownership, waiting, wakeup, and cancellation behavior

Use code outside `src/kernel/src/pm` only to establish real callers, scheduler boundaries, memory
ownership, and IPC/event preconditions. Treat the Rust implementation and its actual call graph as
ground truth.

Investigate these questions:

- Can any process or thread occupy zero or multiple lifecycle states/queues, or be scheduled after
  termination?
- Can create, duplicate/fork, exec, terminate, wait, join, or detach partially update accounting or
  ownership, leak slots/resources, double-clean them, or leave an unreapable zombie?
- Can thread/process limits be bypassed or permanently exhausted because a failed or zombie object
  retains a slot longer than intended?
- Can signal delivery, masking, pending queues, interruption, sigsuspend, or sigreturn lose,
  duplicate, reorder, starve, or deliver a signal to the wrong lifecycle state?
- Can kill/terminate race logically with sleep, blocked kernel calls, mutex/condition waits, join,
  detach, or exception delivery and cause missed wakeups or stale waiters?
- Can mutex/condition-variable ownership and wakeup paths permit double unlock, lost notification,
  use-after-destroy, or a waiter that can never resume?
- Do rollback paths for process/thread creation, exec image replacement, address-space changes, and
  capability updates restore every affected resource and state?

Out of scope unless needed to prove a PM precondition:

- physical-memory allocator internals
- filesystem/network protocol correctness
- performance-only scheduling behavior without a safety or liveness consequence
