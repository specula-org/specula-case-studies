## Main handoff

1. **Model trainer publication, transport ACK, response bookkeeping and consumer acceptance separately.** A successful Cell submission ACK is not evidence that FedAvg accepted the contribution. `SubmitUpdateCommand` returns an empty string regardless of the runner's semantic result; the command agent maps that non-None return to Cell `OK`, and the client maps Cell `OK` to successful sending (`server_commands.py:232-246`; `server_command_agent.py:96-110`; `client_run_manager.py:145-151`). Full paths below establish the distinction.
2. **Failed task to normal round handoff remains a substantive cross-component question.** Outbound filter exceptions cancel the whole workflow task through `handle_exception`, but do not trigger runner abort. The server runner regards normal return from `control_flow` as normal workflow progression and has no separate task-completion-status guard (`server_runner.py:344-356,130-183`; `wf_comm_server.py:372-390`). The parent analysis owns whether FedAvg observes zero standing tasks and commits/advances an incomplete round. No counterexample or confirmed current bug is claimed here.
3. **Shared body alias is intentional for the built-in quantizer.** It explicitly says that first-client quantization changes common server data and that distinct per-client filters must deep-copy themselves. Its data-ID locks and quantized metadata compensate for concurrent identical transforms (`quantizer.py:235-316`). Shared body alias alone must not become a defect or a re-creation of an old fix.
4. **The split `_processing_tasks` check/claim is a code-review question only.** Both accesses are individually locked, but they are separated by `_try_to_get_task`; no whole-operation reservation is made (`server_runner.py:306-327`). `CallbackAdmission` counts simultaneous handlers rather than serializing them (`callback_admission.py:26-31`), and WFComm explicitly supports resend while a result remains outstanding (`wf_comm_server.py:230-241`). This establishes a scheduling window, not an externally meaningful current bug: quantizer locks/flags and serial cooperative client execution compensate in important paths. Do not promote it to a model target without a legal retry schedule and distinct impact; no reproduction was attempted.

## Actual Recipe client path

`FedAvgRecipe` defaults `launch_external_process=False`, `params_transfer_type=FULL`, and tensor offload disabled (`nvflare/recipe/fedavg.py:230-250`). It creates `ScriptRunner` per site, passing framework/format, launch and memory options (`:414-430,445-447`). `ScriptRunner` defaults/selects `in_process` unless explicitly switched to external and registers `ClientAPIExecutor` for wildcard tasks (`nvflare/job_config/script_runner.py:78-125,188-223`). Attach requires direct `ClientAPIExecutor`; it is not selected by Recipe/ScriptRunner (`:115-125`). Filters are optional configured components; this audit does not assume filters are present in default Recipe.

The default path is:

1. `ClientRunner._try_run` fetches/runs/submits one task at a time; a daemon heartbeat thread independently reports activity (`client_runner.py:520-546`). Auxiliary END_RUN may arrive concurrently and trigger the run signal (`:876-881`). DO_TASK also exists, but its independent task invocation is not the default Recipe polling flow (`:883-889`).
2. `ClientRunManager.get_task_assignment` constructs assignment identity from the received header (`client_run_manager.py:133-140`). The client runner validates peer job ID, finds executor, applies configured input filters, executes it with a child signal, validates the Shareable result, and applies output filters (`client_runner.py:259-518`).
3. ClientAPIExecutor initializes the selected backend at START_RUN, maps generic backend errors/non-Shareable results to `EXECUTION_EXCEPTION`, passes abort/finalize events, and preserves the special UnsafeJobError path (`client_api_executor.py:327-397`). Default result wait is unbounded unless `result_wait_timeout` is explicitly supplied (`:69-82,139-144`); Recipe's ScriptRunner does not add a result-wait bound (`script_runner.py:193-220`).
4. InProcessBackend starts one daemon trainer thread, installs its API in the process-local DataBus and subscribes to global/local result and stop/abort topics (`in_process_backend.py:104-151`). `flare.init()` selects that API through APIContext and public receive/send delegate to it (`client/api_context.py:96-105`; `client/api.py:53-111`).
5. Backend `execute` resets its result slot, publishes the Shareable, waits for local result or abort/death/timeout, and copies the assignment's current-round header into the returned result (`in_process_backend.py:153-249`). Its documented correlation assumption is one task at a time, with latched abort preventing reuse after timeout (`:176-180`). The trainer API converts the Shareable to FLModel and representation errors are latched so `receive()` raises rather than silently waiting (`client/in_process/api.py:140-175,298-320`).
6. `flare.send()` converts a shallow wire model to a Shareable and publishes LOCAL_RESULT. Default clear-cache releases model references and clears receive_called (`client/in_process/api.py:177-220`). This is a local publication acknowledgement: no server callback runs on this stack. DataBus executes callbacks on a new thread pool and waits for their completion, while callback exceptions are not read from Futures (`fuel/data_event/data_bus.py:113-142`). Backend stores the local result (`in_process_backend.py:341-347`), then the client runner submits it separately.
7. At normal completion or abort, the client ends through ABORT_TASK when needed, ABOUT_TO_END_RUN, readiness, END_RUN, messaging/streaming shutdown (`client_runner.py:689-704,812-835`). In-process finalization sends STOP, joins trainer for at most 30 seconds, closes its API and removes owned subscriptions; a stuck trainer is an explicitly abandoned daemon (`in_process_backend.py:251-311`). No promise of forced Python-thread cancellation should be modeled.

## Identity and retry contract

| Field/stage | Concrete rule | Source |
|---|---|---|
| Job | Peer job ID must match the runner at task processing/submission. | `client_runner.py:293-302`; `server_runner.py:495-499` |
| Workflow | Server adds workflow cookie; results with an explicitly different cookie are dropped. | `server_runner.py:411-413,520-528` |
| Client task | Server command attaches task ID both as header and cookie; submission reads the cookie. | `server_commands.py:177-185,239-242` |
| Reply identity | After success/error processing, client overwrites reply task-name/task-ID headers from TaskAssignment and echoes its cookie jar. | `client_runner.py:225-234` |
| Round | FLModel conversion carries current round in Shareable header; default in-process backend overwrites result round with received assignment's round when present. | `fl_model_utils.py:79-80,126-147`; `in_process_backend.py:217-220` |
| Task check | Server returns whether the ClientTask ID remains in `_client_task_map`; this check does not reserve acceptance or prove future task validity. | `wf_comm_server.py:392-395`; `server_runner.py:594-605` |
| Result retry | Client checks task, sends result, retries communication/not-ready results; TASK_UNKNOWN or run abort ends retry. Every send attempt has a fresh message-root ID while assignment identity is retained. | `client_runner.py:590-687` |
| Pull retry | Failed pull returns no task; client loops after interval. Communicator remembers last successfully received task ID and transmits it on later requests. | `communicator.py:355-466`; `client_runner.py:548-571` |
| Repeat request | WFComm can resend the same ClientTask if no result timestamp exists. | `wf_comm_server.py:230-241` |
| Duplicate result | WFComm checks active task owner/name/completion/timestamp and a bounded completed-task cache before invoking consumer callback. This is semantic deduplication, not transport exactly-once. | `wf_comm_server.py:448-521` |
| Transport ACK | SubmitUpdateCommand returns `""`; agent maps non-None to Cell OK; client maps Cell OK to True even when runner/communicator dropped the submission. | `server_commands.py:232-246`; `server_command_agent.py:96-110`; `client_run_manager.py:145-151` |

`fetch_and_run_one_task` fires AFTER_SEND_TASK_RESULT even if `_send_task_result` returns false (`client_runner.py:584-588`). Thus that event alone is not evidence of delivery or consumer acceptance. After a lost reply the result may already have been accepted; after task-check OK the task may complete before submission; both are legal states for the transport abstraction, with semantic duplicate/completion checks above.

## Error/cancellation interactions to carry into the model

- **Outbound server task filter error:** `apply_filters` materializes active-filter lazy payloads then invokes each filter with no catch (`task_utils.py:55-68`). Server catches an exception, calls communicator.handle_exception, clears its processing tracker and returns TRY_AGAIN (`server_runner.py:333-356`). WFComm looks up the client-task, cancels its parent task and logs cancellation (`wf_comm_server.py:372-390`). No panic or run-abort signal is set on this path. A configured built-in ModelQuantizer calls ordinary GPU/quantization operations that can raise and re-raises caught failures (`quantizer.py:145-169,277-302`); DXOFilter propagates process_dxo failures (`dxo_filter.py:70-73,91-102`). This is an ordinary operational exception boundary, not a malformed-input or security scenario.
- **Incoming server result filter error:** result becomes `TASK_RESULT_FILTER_ERROR` and is still passed to communicator (`server_runner.py:534-561`). Any whole-callback exception not already handled is logged by the outer catch (`:566-570`). Actual consumer mutation/error propagation must be checked in FedAvg; parent analysis owns that code.
- **Client executor/input/output errors:** client runner produces distinct result codes, restoring task identity in `_process_task`. An abort observed during executor execution takes precedence and yields TASK_ABORTED; the run signal then prevents result retry (`client_runner.py:343-356,385-445,476-489,225-234,595-597`). A local result code must not be equated with server runner abort: only RUN_MISMATCH, TASK_UNKNOWN, UNSAFE_JOB form its runner-level fatal list (`server_runner.py:82-86,501-508`).
- **Normal workflow return versus failure:** only exceptions escaping `control_flow` call system_panic; normal return leads current_wf closure, controller/communicator finalization and workflow index progression when abort is clear (`server_runner.py:130-183`). Finalization exceptions are logged (`:169-175`). Normal run teardown emits END_RUN and invokes `persist_components(completed=True)` (`:206-237`). This is a call-site observation, not a persistence durability claim.
- **Completion admission compensation:** submission admission/status/current-workflow and downstream processing now share an RLock, and normal runner completion sets done inside the same gate (`server_runner.py:101-104,207-209,460-471`). Current workflow is cleared under the lock before finalization (`:159-166`). Do not model a late submission entering finalized workflow state by simply removing this fix.

## Payload/streaming boundary only

Shareable values must be serializable; its bytes API is FOBS (`apis/shareable.py:41-46,124-144`). FLModel-to-Shareable preserves ordinary params/metrics and round headers without an extra task identity layer (`fl_model_utils.py:46-86`). Cell supports per-message/channel/topic pass-through and otherwise decodes before invoking the handler (`fuel/f3/cellnet/cell.py:91-131`); receive waits and decoding carry the abort signal (`:568-614`). Sender timeout/error is an ambiguous delivery outcome, not rollback of a consumer that may already have run.

External mode's current documented contract distinguishes RESULT_ACCEPTED envelope admission from downstream tensor settlement; source identity remains the trainer, and early source loss after acceptance is run-fatal (`docs/design/client_api_execution_modes.md:229-268`). Attach materializes at the CJ before acceptance and does not make the trainer the server-facing source (`:270-279`). Those are mode-specific interface references, not a full audit of external/Attach/streaming internals. The current executor/filter code adds an important qualification to older design prose: when a local result consumer/filter requires concrete data, ClientAPIExecutor routes result reception to the CJ and materializes there (`client_api_executor.py:372-382,400-453`), and `apply_filters` materializes lazy values before active filtering (`task_utils.py:59-67`). Source takes precedence over the broader older statements at design-doc lines 237-239/284-287.

At the server Cell adapter boundary a decode exception on streamed SUBMIT_UPDATE in a job cell explicitly terminates that job process (`fuel/f3/cellnet/cell.py:112-123`); it does not produce a valid decoded Shareable or a semantic FedAvg result. Treat this as an explicit transport/terminal failure outcome, not as the same action as consumer rejection. Full transfer internals, chunking, transaction expiry, file cleanup, authentication, job admission/resources, HA and other workflow policies are excluded.

## Shared-data question and exclusions

WFComm creates a deep protected broadcast snapshot once, then returns `make_copy` per client (`wf_comm_server.py:305-324,360-370`). `make_copy` deliberately shallow-copies body and deep-copies headers (`shareable.py:157-173`), so outbound filters run after runner/communicator assignment locks on a body that can still be shared (`server_runner.py:317-343`). This is not an undocumented guarantee of per-client deep isolation. ModelQuantizer explicitly relies on 1-N shared mutation, serializes by underlying data identity and publishes quantized metadata before reuse (`quantizer.py:235-316`); different per-client transforms are instructed to copy (`:243-244`). PercentilePrivacy, for comparison, creates a new delta dictionary and replaces dxo.data (`filters/percentile_privacy.py:70-94`). No default-Recipe aliasing defect was established.

The `_processing_tasks` reservation gap is retained as **CR-unconfirmed**, not dropped silently and not promoted to MC. No per-client lock is visible in ServerCommandAgent; its admission gate tracks active callbacks for shutdown (`server_command_agent.py:54-63`; `callback_admission.py:26-39`). However a meaningful defect still requires a specific supported filter/callback effect escaping the existing quantizer synchronization and the serial cooperative client loop. A structural window alone is insufficient.
