# WFCommServer functional lifecycle audit

Pinned source: `/home/ubuntu/nvflare-runs-20260913/source-fedavg`, `53ba7ee567468ea7971dad4faccef13c6cb35dc2`. Read-only source/history analysis on 2026-09-13. Category A: distributed polling/task-result protocol, with explicit local Python lock and callback interleavings. Cooperative participants; no Byzantine model, security reproduction, implementation edit, test execution, trace validation, or model checking.

The strongest in-scope handoff is **abnormal task termination versus successful round completion**. WFCommServer exposes queue emptiness independently of the task's terminal status. Ordinary outbound filter errors cancel the active task; the communicator removes it; Recipe FedAvg polls only queue length before aggregating and updating the model. Whether a partially accepted round may advance must be decided against the actual FedAvg error/quorum policy, not assumed from WFComm task removal. This is an unresolved cross-layer functional scenario, not a reproduced defect (`server_runner.py:344-356`; `wf_comm_server.py:372-390,786-827,1064-1109`; `fedavg.py:214-238`).

All source citations below are relative to the pinned repository. Historical commits are evidence of mechanisms, not targets for recreating fixed bugs.

## Reconnaissance: state and atomicity map

| Operation/state | Actual boundary | Implication |
|---|---|---|
| Task request | `_controller_lock` around whole `_do_process_task_request`; `_task_lock` for selection and later publication; `task.cb_lock` around before/after callbacks and snapshot | Requests cannot interleave with another request, result submission, or monitor `check_tasks`; callback code can schedule another task because `_task_lock` is released. (`wf_comm_server.py:209-210,219-277,349-370`) |
| Result processing | Same outer controller lock; active/history lookup under `_task_lock`; result callback under task callback lock | Setting result, manager check, callback, and final `result_received_time` all precede another normal request/submission/monitor check. (`:434-451,475-521`) |
| Monitor completion | Same outer controller lock; decide status and remove under `_task_lock`; later root cleanup and done callback under task callback lock | Controller control-flow reads can observe zero standing tasks before root cleanup/done callback finishes. Normal result callbacks cannot interleave into this gap. (`:1060-1109,1116-1155`; `controller_spec.py:265-275`) |
| Scheduling | Initialize fresh Task fields before `_task_lock` append | Scheduling can happen while an outer controller lock is held by a callback; publication is append to `_tasks`. A Task may not be reused. (`:523-575`) |
| Cancellation | `cancel_task` writes status only; `cancel_all_tasks` writes statuses under `_task_lock` | Cancellation is mark-only and asynchronous with respect to queue removal. Neither method acquires `_controller_lock` or sends a run-abort signal. (`:794-827`) |
| Finalization | `_controller_lock`; snapshot/clear maps under `_task_lock`; synchronous reference release | Current finalization does not rely on a future monitor pass. It intentionally does not run task-done callbacks for residual tasks. (`:829-895`) |
| Dead client state | Separate `_dead_clients_lock`; report time and later disconnect time; active notification removes watch entry | Death observation and task/quorum checks are distinct local steps. Event callbacks execute while the dead-client lock is held, but no arbitrary extension callbacks are added to the default FedAvg scope. (`:181-188,1024-1058,1250-1273`) |
| Wait/control flow | `get_num_standing_tasks` is a plain `len`; `wait_for_task` is unsynchronized polling | Empty queue, terminal status, and done callback completion must remain different states. (`:786-792,1189-1212`) |

All these locks are ordinary non-reentrant `Lock`s (`wf_comm_server.py:105,110,112`; `controller_spec.py:114`). Comments saying callbacks execute "outside the lock" refer to the task-list lock, not the outer controller lock; treating callbacks as unconstrained concurrent accept/aggregate handlers would erase a current compensating mechanism (`wf_comm_server.py:266-268,434-435,497-507,1060-1062`).

## Protocol behavior and compensations

**Publication and ownership.** A scheduled Task records fixed current targets when `targets=None`; explicit list targets are deduplicated for broadcast. Task object reuse is rejected. Before first publication, the first client's `before_task_sent_cb` runs, then one deep payload snapshot is cached as `_broadcast_data`. Each response copies its top-level Shareable and deep-copies headers; payload objects are shared from the snapshot. Per-client task ID/root/TTL are set on the per-client header copy. This protects later clients' broadcast input from mutations of the original task/model data, but does not turn each outbound filter into an isolated payload owner (`wf_comm_server.py:277-370,531-575`; `shareable.py:157-173`). Snapshot capture is at first request, **not at `broadcast()` return** (`wf_comm_server.py:305-324,625-628`). Default FedAvg does not change the model between scheduling and first request in the read run path (`fedavg.py:214-238`).

**Receipt versus acceptance.** Active task submissions check assigned client/name, task completion, and prior result receipt before invoking processing. `result_received_time` is set after the callback, including when the callback throws and the Task is marked ERROR. Thus it is a processing-attempt-completed indicator, not proof that aggregation accepted a contribution (`wf_comm_server.py:475-521`). The inherited `TaskManager.check_task_result` is a no-op for BcastTaskManager, so semantic contribution acceptance belongs to the controller (`task_manager.py:85-96`; `bcast_manager.py:28-89`).

**Current duplicate defense.** Results for a live ClientTask with a receipt marker are dropped. Removed ClientTasks with a receipt marker enter a bounded 10,000-entry LRU map containing client and task names; exact matches are dropped after cleanup. Tasks without a result are not remembered; unknown/mismatching retired submissions follow the existing controller unknown-task handler. Finalization clears history (`wf_comm_server.py:397-412,448-473,493-495,870-874,1106-1109`). These are current defenses from #4597/#4772; recreating their pre-fix state or cache-eviction-only probes is not a default three-client/two-round modeling target.

**Completion/quorum.** Bcast manager counts ClientTask receipt markers, not accepted model contributions. It does not finish before any assignment. All fixed targets responding permits immediate OK regardless of configured grace; `min_responses=0` requires all targets. Otherwise the grace timer is first recorded when a monitor pass observes enough responses, rather than at network arrival time. Task-specific exit is checked before task timeout and dead-client exit (`bcast_manager.py:42-89`; `wf_comm_server.py:1072-1098`). There is no independent promise of a response-arrival-based hard grace deadline. Recipe timeout zero disables ordinary task timeout (`controller_spec.py:90`; `wf_comm_server.py:1086-1089`).

**Dead clients.** Repeated dead reports preserve the first report. A monitor pass turns a sufficiently old report into a disconnect timestamp; explicit active notifications can revive the client. After a lead time, a task is declared CLIENT_DEAD only when every target without a result is disconnected. Job policy separately considers all-dead, minimum sites, and required sites and can panic before normal task checks (`wf_comm_server.py:181-188,1024-1058,1157-1187,1214-1273`). Do not simplify a transient report directly into task failure, or assume all task termination is OK.

**Error handling.** Before/after-send callback failures and snapshot-copy failure set ERROR and suppress assignment; result callback failures set ERROR; upper outbound filter exceptions call `handle_exception`, which marks CANCELLED. These status writes alone do not call `system_panic`. The monitor removes completed tasks regardless of status, and then may invoke a done callback (`wf_comm_server.py:280-345,372-390,504-521,1067-1070,1100-1151`; `server_runner.py:333-356`). Separately, dead-client job-policy violations do panic (`wf_comm_server.py:1051-1057`).

## Current questions for synthesis

### WFC-S1: abnormal task termination must not silently become a successful round

Mechanism: a queue-empty completion observation loses the reason a task ended. Ordinary task-data filter failure is an in-scope functional trigger; no malformed/security traffic is needed. The communicator's own callback ERROR cases are additional status-producing paths, but the concrete default-controller path must be established before adding one to the model (`server_runner.py:333-356`; `wf_comm_server.py:372-390,504-521`).

The audited chain is filter failure -> `handle_exception` -> CANCELLED -> monitor removal -> standing count zero. FedAvg then reaches aggregation and update without receiving task status through that count. Whether this violates its intended resilience/minimum-success policy, and which accepted subset remains, is the parent FedAvg audit's decision (`wf_comm_server.py:786-827,1064-1109`; `fedavg.py:214-238`).

Suggested model distinctions: `responded`, `accepted`, `completionStatus`, `standing`, `abort`, `round`, and `modelVersion`. Keep current locking and fixed snapshot behavior. This scenario concerns **current cross-layer status propagation**, not replaying any historical fix. Verification method: model-checkable cross-layer question, followed only later by local functional regression confirmation if warranted. No current result is claimed here.

### WFC-CR1: controller monitor-period configuration is not forwarded to the field the communicator reads

Current code evidence: `Controller.set_communicator` assigns `communicator.task_check_period`, while WFCommServer initializes/uses `_task_check_period`. The server config constructs `WFCommServer()` with its own default 0.2, then calls `set_communicator`; BaseModelController's default is 0.5 (`controller.py:26-35,47-53`; `wf_comm_server.py:92,107,1058,1212`; `server_json_config.py:151-153`; `base_model_controller.py:39-67`). No property/setter for the public name exists in either fully read communicator class/contract. Consequently controller poll period and communicator monitor period can differ. This is a narrow **code-review-only configuration mismatch**, with low functional impact (timing behavior), not a TLA safety defect or executed reproduction.

### WFC-CR2: public API prose differs from current implementation

`ControllerSpec`/`WFCommSpec` say `targets=None` allows clients joining later; current scheduler snapshots current clients. The internal string `"*"` branch cannot be reached through public broadcast's list-only input validator. `broadcast_forever` contract says its callback can change task data, whereas current implementation documents a frozen first-client snapshot. Cancellation contract says immediate queue removal and no effect for non-standing tasks, but implementation is mark-only and unconditionally writes status (`controller_spec.py:342-351,391-401,520-523`; `wf_comm_spec.py:53-62,107-117,234-239`; `wf_comm_server.py:54-69,539-566,674-691,794-812`). Treat as code/doc contract drift, not proof of a default Recipe bug. Current modeling should use fixed scheduled targets and mark-only cancellation.

### WFC-CR3: multi-standing-task retry bookkeeping, outside this Recipe scope

In `_do_process_task_request`, selecting an existing unresponded ClientTask does not break the task scan. A later active task resets `resend_task=False`; if that later task returns NO_BLOCK, the earlier selected ClientTask remains. Publication then appends it as if new, potentially duplicating the same ID/object in `task.client_tasks`; cleanup pops each listed ID without a default (`wf_comm_server.py:222-264,349-358,1105-1109`; `task_manager.py:61-70`). This is a code-reading candidate, not executed. The default Recipe has one standing train task, so this mechanism is explicitly **excluded from current-scope model checking**. Do not invent custom events/concurrent tasks to promote it. Existing tests separately cover multiple scheduled tasks and single-task retries, but the read groups do not assert this cross-product (`controller_test.py:267-360,1066-1093`).

### WFC-CR4: waiting does not mean task-done callback has finished

`wait_for_task` exits on non-None completion status before checking the callback-set done marker. Monitor sets terminal status and removes the task before invoking the done callback (`wf_comm_server.py:1079-1109,1140-1155,1189-1212`). This is a real observable boundary, but the public wording only promises task completion and Recipe's run loop does not use a task-done result. Keep it as a semantic/code-review note; no separate current Recipe bug is established. Existing callback tests explicitly call `check_tasks()` before asserting callback effects, so they do not establish a stronger wait-return contract (`controller_test.py:779-824`).

## Explicit false positives and historical containment

1. **Normal simultaneous `accept`/`aggregate` from receipt-before-callback** is not a current finding: #1124 moves the marker after the callback and #1537 serializes submissions/checks (`wf_comm_server.py:434-435,504-521,1060-1062`).
2. **First client's headers overwrite later clients' task IDs** is compensated by per-client deep-copied headers set after copying (`wf_comm_server.py:360-370`; `shareable.py:157-173`).
3. **Per-client broadcast callback payload differences must be preserved** contradict current documented first-client snapshot design (`wf_comm_server.py:590-600`; full #4129 discussion). The old #356 advice is not a present default-FedAvg contract.
4. **Finalization leaks because the monitor stops before draining** is fixed by current synchronous clear and resource release; in-flight downloads have their own current cleanup hook (`wf_comm_server.py:135-146,829-895`). #4493's first fix covered task-held references; #4501 covers in-flight state. Do not replay either pre-fix condition.
5. **Finalization must invoke residual done callbacks** is explicitly rejected as an unconditional invariant: finalization intentionally clears those callbacks after control flow exits (`wf_comm_server.py:856-860`; full #4493 discussion).
6. **Cancelled tasks should disappear synchronously or prohibit every overlapping result effect** overstates current mark-only cancellation. A callback already running can finish; normal monitor drain follows (`wf_comm_server.py:794-827,504-521,1064-1109`). Whether upper layers misuse cancellation outcomes belongs to WFC-S1.
7. **Duplicate after cleanup bypasses all deduplication** is fixed for exact remembered duplicates; mismatches/never-received retired results intentionally remain unknown-task behavior (`wf_comm_server.py:397-412,448-473`; full #4772 discussion). No memory-cache eviction hunt is proposed for the bounded Recipe.
8. **`min_responses=0` means complete after the already-assigned subset** is fixed by #2733: current code compares receipt count with fixed target count (`bcast_manager.py:64-75`).
9. **Task timeout, grace timeout, deployment minimum, and contribution acceptance are the same condition** is false. Current code checks separate state/timers, and Recipe's timeout zero has its own meaning (`controller_spec.py:90`; `bcast_manager.py:42-89`; `wf_comm_server.py:1086-1098,1214-1248`).

## Handoff boundaries

Use small client/task/round identities and abstract model versions; preserve receipt versus acceptance, abnormal terminal status, scheduled membership, callback completion, and real controller-lock exclusion. Model only current supported default-Recipe operations and ordinary local faults. Do not add model extensions whose effect is reverting known fixes, arbitrary multi-task custom callbacks, BFT behavior, full tensor streaming internals, admin lifecycle, HA recovery, or ML numerics. This audit establishes source/history evidence and questions; later formal/runtime phases must supply their own execution and validity evidence.
