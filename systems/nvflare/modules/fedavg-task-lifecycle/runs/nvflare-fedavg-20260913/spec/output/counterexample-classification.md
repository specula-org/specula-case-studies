## S3 metric preparation — Case C, MC-1

81-state counterexample. c2 succeeds (states 43–55); c1 then applies both parameter keys and appends parameter history (63–67). Metric preparation fails at 68. c1 is published rejected at 69 and receives a receipt by 71. Monitor retires OK at 75. At 81 GLOBAL_MODEL is updated with both c1 and c2 parameter provenance, but callback count is 1 and only c2 is accepted. The counterexample stops at update, before save; the Phase 2.5 `metric_preparation_failure` trace independently includes actual file persistence under a different client-result order.

`base_model_controller.py:263-291` defines definitive consumer acceptance and catches the exception, leaving accepted false. `fedavg.py:299-330` changes parameter state before metric preparation/count; `weighted_aggregation_helper.py:162-224` updates without transaction/rollback. `fedavg.py:223-259,346-365` later exposes those totals. Guards and communicator/runner locks serialize processing but do not reverse an exception's prior mutations. The ordinary allocation-failure interface is explicit; the harness uses benign scalar data and a one-shot MemoryError. This is a functional contribution/accounting defect, not a claim about natural failure frequency.

## S3 parameter failure — Case C, same MC-1

77-state counterexample. c1 succeeds (43–55). c2 increments first-key contribution statistics at 63, fails before that key's value update at 64, and is rejected at 65. At 77, parameters contain only c1, while first-key statistics contain both clients. **This shortest counterexample does not contain a rejected parameter value.** The public statistics can misreport a partially matched key: `weighted_aggregation_helper.py:243-254` compares key count 2 with history length 1, even though the sole accepted contributor supplied both keys. This is the same nontransactional accounting mechanism. A separate value-only oracle will explore the later parameter failure window without disabling the original full consistency check or changing any state-space bounds. The config's lazy-offload interface has not been executed by the local harness; the existing `partial_param_allocation` trace exercises a corresponding ordinary allocation failure after key 1.

## S4 direct cancellation — Case A (unpromised whole-round condition)

54 states. c1's consumer has returned true and acceptance is already published (40–42); direct cancel occurs at 43 before receipt stamping. Removal at 47 retains CANCELLED and outstanding c2. Saving c1 at 54 violates only the asserted no-partial-round condition. `wf_comm_server.py:794-827` cancels the task without triggering the job abort signal or revoking accepted work; `controller_spec.py:512-527` describes task cancellation, not cancellation of the enclosing workflow. `fedavg.py:223-259` consumes available aggregate after standing tasks drain. The model's `outcome=normal` denotes a normal controller return, not a guarantee that all clients contributed. No such unified no-save contract or product `AllowPartialCompletion` setting is established. Remove this oracle from this cfg; retain callback/round/receipt/accepted-provenance checks. This does not assert that every application desires this policy.

## S4 filter failure — Case A as an unconditional outcome oracle; contract gap retained

62 states. c1 returns true at 47. c2's outbound filter fails at 48 while c1 still holds the runner lock; c1's acceptance/receipt completes, then exception handling cancels the task after acquiring that lock. Removal at 55 retains CANCELLED; saving at 62 includes only accepted c1. `server_runner.py:333-356` deliberately returns TRY_AGAIN and calls task exception handling; `wf_comm_server.py:372-390,794-812` marks the task without run abort. These are real behaviors, also present in `filter_cancellation.ndjson`. However, default all-response broadcast completion (`bcast_manager.py:52-75`) does not establish that exceptional task termination must abort the surrounding workflow or forbid saving accepted work. No per-round no-partial policy is supplied. The old invariant conflates these contracts; remove its wiring, keep the behavior and the usability/failure-policy question explicit. No claim of a confirmed implementation bug or of universally desirable behavior is made.

## S4 before-send error — Case A as an unconditional outcome oracle; contract gap retained

60 states. c1 succeeds; c2's preparation raises at 47, setting task ERROR. Removal at 53 preserves that status and missing c2. At 60 accepted c1 is saved. `wf_comm_server.py:281-345` records task failure and returns TRY_AGAIN; it does not promise a job abort. `fedavg.py:223-259` has the same post-drain aggregate path. The unconditional no-save oracle again requires a product guarantee not established by the task API. Preserve this result separately from the direct-cancel and filter paths, remove this oracle from the cfg, and continue checking actual contribution and lifecycle constraints.

## S5 permitted client death — Case A (configured policy exception)

61 states. c1 completes; c2 is reported dead at 37, grace expires, and the monitor retires CLIENT_DEAD at 54; c1 is saved at 61. The actual cfg has three clients, selected c1/c2, min_sites=1 and no required sites. This permits the job to continue with live c1/c3. `wf_comm_server.py:1046-1057,1092-1097,1157-1187,1214-1248` explicitly separates job-policy panic from retiring a task whose outstanding targets are dead. Prohibiting every such save adds a stronger round policy not configured here. Remove the unconditional no-partial oracle and retain source-backed receipt, contribution and round-isolation checks.

## Revision scope and falsifiability

The four affected cfgs drop only `AbnormalTerminationVisible`; its original definition and all original counterexamples remain available. No transition, failure budget, client/round/key bound, guard, or `AllowPartialCompletion` value is changed. The unsupported property is marked **not applicable**, not converted to TRUE or counted as passing coverage. Existing `AtMostOneConsumer`, `ReceiptAfterDecision`, `CallbackRoundIsolation`, `CallerLockDiscipline`, `SavedWasCommitted` and `CommittedAcceptanceConsistency` are enabled in those cfgs. They still reject duplicate consumer calls, receipt before a decision, wrong-round callback mutation, lost caller serialization, unsourced saves, or used/reported contributions inconsistent with the actual decision; success/failure/standing/committed antecedents are reachable in the preserved counterexamples. These cover the remaining valid lifecycle constraints, not the removed policy claim.
