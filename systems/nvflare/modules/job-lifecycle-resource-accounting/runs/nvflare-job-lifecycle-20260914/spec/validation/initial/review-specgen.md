## Issues Found

- **[P1] Failure outcomes bypass the real pending-client acceptance guard.** `base.tla:1057-1064` processes every `OutcomeFailed` message and, when the job is registered/running, clears pending outcomes, marks failure, and sends stop commands. The actual entrypoint first returns without lifecycle changes when `is_client_outcome_pending(job_id, client_name)` is false (`nvflare/private/fed/server/fed_server.py:938-940`), before calling `fail_run` at lines 942–955. This matters for ordinary delayed outcomes from a site excluded after a non-strict start timeout: the model's own pending-set intersection removes that site (`base.tla:597-605`), but its later failure report can still affect the job. `Trace.tla:1239-1250` and instrumentation row `ServerEngineReceiveFailureOutcome` inherit the mismatch. Split ignored and accepted outcomes, preserve the pending-client gate, and map the actual receiver as well as its downstream helpers. This is a functional lifecycle guard even with cooperative participants.

- **[P1] Heartbeat recovery of missing terminal outcomes is absent.** `FederatedServerHeartbeatCleanup` (`base.tla:1031-1042`) represents only asking a client to stop a job absent from the protected server set. The same production heartbeat handler also detects a client that no longer lists a job with a pending outcome (`nvflare/private/fed/server/fed_server.py:1045-1074`). `_resolve_missing_client_outcome` can record an infrastructure failure and resolves that site's outcome (`fed_server.py:1086-1094`). This remains in scope with connected cooperative sites after an ordinary reporting failure and client process removal. In the model, no heartbeat action can perform that transition; pending outcomes instead need a report or the outcome deadline, potentially producing a different final status. Add the request's observed job set and the missing-outcome branch, including its actual guards and corresponding trace hooks. The coverage claims at `brief-coverage.md:14,45-46` should remain qualified until this path is represented.

- **[P1] The expiry tick demands a stored TTL value that production never writes.** `AutoCleanResourceManagerTick` writes every positive TTL as `ttl-1`, including zero, and `FinishExpiry` then requires zero (`base.tla:415-433`). In `_check_expired`, a stored TTL of 1 is decremented only in local variable `t`; the zero branch appends the token to `tokens_to_remove` and skips the assignment back to `reserved_resources` (`nvflare/app_common/resource_managers/auto_clean_resource_manager.py:107-116`). Immediately before removal, its stored tuple still contains 1. Instrumentation explicitly requires the actual stored cleanup counter and a snapshot before popping (`instrumentation-spec.md:30,72-73`), while `Trace.tla:446-470` compares the complete RM state. An honest expiry snapshot therefore disagrees with the model. Represent the scan's local expired-token set separately, or define and document an independent projection from the captured local scan state; do not label a synthesized zero as a direct RM snapshot. Preserve the existing lock boundary.

- **[P1] Server abort cleanup incorrectly requires a full ten-second wait and an existing map entry.** `TraceServerEngineTerminateAfterGrace` requires `elapsedSeconds >= 10` (`Trace.tla:1292-1302`). Production sets the grace to zero after a command exception (`nvflare/private/fed/server/server_engine.py:361-378`) and also leaves the wait early when the normal exit waiter has already removed the entry (`server_engine.py:390-404`). The captured handle is still terminated in that ordinary graceful-exit branch. Its subsequent `pop(job_id, None)` is unconditional and may be a no-op (`server_engine.py:408-409`), whereas `ServerEngineRemoveAfterTerminate` requires `serverRegistered` (`base.tla:1110-1116`). Consequently, both an early termination hook and its idempotent removal hook can fail replay. Split deadline, already-removed, and zero-grace continuations; capture the actual grace/branch and support the no-op removal event required by the mapping.

- **[P2] MC counter-bounds normal heartbeat cleanup.** `MCFederatedServerHeartbeatCleanup` consumes `faults.heartbeat` (`MC.tla:97-100`) and appears only in `FaultNext`, with no corresponding normal fairness obligation. `MC.cfg` permits one such action globally; the Scenario 4 hunt permits two, and several other hunts, including Scenario 5, disable it. These are normal periodic protocol responses (`nvflare/private/fed/server/fed_server.py:988-1002`; `nvflare/private/fed/client/communicator.py:620-646`), so fault exhaustion can remove supported cleanup for other jobs/sites or after a lost response. Move normal heartbeat processing into unbounded reactive actions with appropriate progress assumptions; bound injected loss/error instead. This directly violates checklist item 5's fault-only bounding requirement.

- **[P2] The binary outcome abstraction loses observable ABORTED behavior.** Client report codes are reduced to `OutcomeOK`/`OutcomeFailed`, and accepted failures set a single `serverFailed` flag (`base.tla:933-939,1057-1064`). Completion then selects ABORTED only from `runAborted`, otherwise FAILED from `serverFailed` (`base.tla:1212-1218`). Production also reports `JobReturnCode.ABORTED` (`nvflare/private/fed/client/client_executor.py:41-46`), routes it through `fail_run` (`fed_server.py:942-951`), and classifies that stored code as `FINISHED_ABORTED` independently of `job.run_aborted` (`job_runner.py:548-553`). That distinction also controls the ABORTED lifecycle event (`job_runner.py:536-538`). Preserve an aborted outcome/status class and its precedence; a single failure boolean is insufficient for the status and event observations required by `instrumentation-spec.md:29`.

- **[P2] Structural type checking is omitted from every hunt.** All eight `MC_hunt_*.cfg` files start their invariant lists with `ResourceConservation`; none enables `MCTypeOK` or `TypeOK` (for example, `MC_hunt_s4_exit_cleanup.cfg:61-68` and `MC_hunt_s5_scheduling_progress.cfg:61-67`). The main `MC.cfg` does enable `MCTypeOK`, but that does not protect executions using different hunt configurations. Enable `MCTypeOK` in each hunt so state-domain/fault-counter errors are distinguished from scenario violations.

- **Coverage limitation, already disclosed:** TV-2 failure-branch service death and TV-3 competing completion deletion are deferred, as the brief permits. `JobRunnerRemoveCompleted` blocks when startup-failure cleanup has removed the entry (`base.tla:1276-1282`); the actual unconditional deletion can raise, and the model has no completion-service exit state. `PendingCompletionRemoval` is defined but not enabled (`base.tla:1598-1599`). Accordingly, the Scenario 5 configuration checks progress assuming live services, not containment of these service failures. This is not an undisclosed omission or a demand for production confirmation during spec review; retain the boundary and detect/report entry into unsupported paths before interpreting future progress or conformance results.

## Verdict: NEEDS_IMPROVEMENT

Correct the outcome acceptance/recovery paths and the concrete trace mismatches before treating this suite as ready for implementation trace convergence. The existing generation checks establish useful structural consistency, but do not cover these behavioral branches. Keep the clearly documented test-first and timing-feasibility limits separate from the required model repairs.
