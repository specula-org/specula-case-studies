## Mechanisms that affect current novelty decisions

- Reservation allocation without an extant token was fixed by `1058e40c96` (#485, 2022). The shared manager introduced by #905 preserves token-pop allocation, cancellation/expiry only over reservations, and one mutex around check/reserve. These guards are historical reference, not new MC findings.
- `55e74fe2af` (#766) moved resource consumption before engine.start_app and added exception-only rollback. Returned error strings and exceptions after a live handle exists cross a different ownership boundary and remain worth current-source review; they are not repaired merely by the old rollback.
- `a6dcce63ed` (#624) originally serialized launch/register/RUNNING publication. `6f75707f34` (#1387) explicitly removed broad runner locks and retained only map-operation locking. Thus the current registration-versus-final-status publication gap has old architectural roots, distinct from event-ID repair #5216.
- `e120606196` (#5216) is already pinned and explicitly repairs sticky-ID lifecycle event accounting; #4471 only used a fresh context and did not solve shared sticky values. Model explicit event job ID and idempotent scheduler membership; do not treat the old wrong-event-job bug as new.
- #4910/#4904 preserve early abort through pending handles and STARTING state. #5097 keeps STOPPED-but-live owned children reclaimable. These are current defense boundaries, not proof that every later launch/cleanup exception has an owner.
- #5072 introduces an acknowledged per-client terminal-outcome barrier with timeout fallback; #5221 bypasses it on authoritative failure. #5194 retains a documented best-effort STOPPED notification ambiguity. Admission, start acknowledgement, process ownership, outcomes and cleanup remain different stages.
- #5191 is not a merged core-history commit at the fetched branch snapshot; its status/discussion must be supplied by live PR audit. Absence from this history does not classify it as open/closed/new.
