## Atomicity and control-flow map

- `server_deployer.py:136-145` starts `JobRunner.run` in a thread, without a supervisor or retry wrapper. `job_runner.py:638-639` starts an independent completion thread. The admission loop sleeps one second (`641-650`); completion loops independently (`441-541`). Ordinary admin commands arrive through a registered Cell HCI callback (`fuel/hci/server/hci.py:76-80`), not the admission thread.
- The scheduler's `self.lock` protects only scheduled-job list checks/modifications (`job_scheduler.py:263-285`); it does not enclose admission, deployment, status storage, or child start. `JobRunner.lock` protects individual local map/set operations, not an atomic lifecycle transition. Server process tracking uses `engine.lock`, a different lock.
- Lifecycle event delivery is **synchronous** through `JobRunner._fire_job_lifecycle_event` (`366-372`) → `FLComponent.fire_event_with_data` (`fl_component.py:86-94`) → `ServerEngine.fire_event` (`server_engine.py:578-579`) → `RunManager.fire_event` (`run_manager.py:103-104`) → `private/event.py:18-29` → `fire_event_to_components` (`apis/utils/event.py:27-84`). Every handler receives the original event data reset before dispatch; handler `Exception`s are logged/recorded and swallowed (`74-82`). A simple raising event-handler mock does **not** demonstrate a production admission exception escaping `_try_job`.
- Explicit event job ID (`job_runner.py:371`) wins over sticky `CURRENT_JOB_ID` (`job_utils.py:111-123`). Scheduler list insertion/removal checks membership under a lock (`275-285`), so same-type repeated events are idempotent at this layer. There is no asynchronous lifecycle-event queue in this production chain; do not invent delayed JOB_STARTED after JOB_COMPLETED without a supported publisher path.
- `JobDefManager.set_status` unconditionally updates the requested status and associated timestamps (`apis/impl/job_def_manager.py:459-481`); it has no expected-state/monotonicity compare-and-swap. Built-in FilesystemStorage metadata update is get/update/write (`app_common/storages/filesystem_storage.py:251-275`), not a lifecycle transaction. Source-level status-read and status-write gaps therefore remain real despite the local map locks.

## New source-supported modeling candidates

### R1. Accepted abort before startup can be overwritten by admission

**Strength:** High static confidence; supported API path; no local reproduction yet. **Mechanism:** status validation, external stop decision, and process creation are separate operations.

`run` rechecks SUBMITTED at `job_runner.py:661` and DISPATCHED at `697`, but `_deploy_job`/`_start_run` and later status writes are outside those checks. `JobCommandModule.abort_job` reads stored status at `job_cmds.py:1059-1060`; for SUBMITTED or DISPATCHED it stores FINISHED_ABORTED and returns a successful "before running" acknowledgement (`1061-1066`) without calling `stop_run` or marking the in-memory `Job.run_aborted` flag. Meanwhile the admission path unconditionally writes DISPATCHED (`job_runner.py:670`) and RUNNING (`711`).

Two supported interleavings deserve one scenario:

1. Admission passes SUBMITTED check, then deployment takes time; an admin abort reads SUBMITTED and completes; deployment returns and its DISPATCHED write overwrites the terminal abort, allowing the later DISPATCHED check and start.
2. Admission passes the DISPATCHED check; abort reads DISPATCHED and completes while server/client startup is in progress; startup then writes RUNNING. The abort path never stopped those processes.

The status rechecks compensate only when abort becomes visible **before** the corresponding read. Reservation TTL does not compensate an abort that is overwritten and proceeds to allocation. Completion may eventually terminate the job normally, but it does not make the acknowledged pre-run abort effective. Model explicit status-read results, stored status, launch progress, and abort acknowledgement; keep actual process liveness separate. No security or malicious metadata needed.

### R2. Completion can be terminalized and then overwritten by the delayed RUNNING publication

**Strength:** High static confidence; very short server/job or delayed startup/status publication needed; no local reproduction. **Mechanism:** completion-map visibility precedes RUNNING publication.

`_start_run` launches the server (`304`) before waiting on client-start replies (`310`); the server process waiter runs independently (`server_engine.py:203-234,328`). Once `_start_run` returns, `run` inserts `running_jobs[job_id]` under its lock (`job_runner.py:709-710`), releases the lock, then writes RUNNING (`711`). The completion thread can observe that entry with no live server process (`444-450`), resolve/skip the pending outcome barrier, select a terminal state (`484-491`), store it (`524`), and remove the runner entry and scheduler slot (`531-538`) before the admission thread's RUNNING write.

The necessary terminal outcome can be a quick authoritative server failure (which bypasses pending client wait), or normal completion after pending client reports resolve. `wait_for_complete` waits for actual process exit plus at most two seconds for status reporting (`server_engine.py:203-217`); this delays but does not order it behind the parent's RUNNING write. No guard in `set_status` rejects a terminal-to-RUNNING write. After the stale write, the completion map entry is already gone; the regular completion loop has no second trigger to repair the persistent RUNNING status. HA/startup reconciliation is outside scope and must not be used as a live compensator.

Model `RegisterRunning` and `PublishRunning` as separate actions, competing with `ObserveProcessExit`, `SelectTerminal`, `PublishTerminal`, and `RemoveRunning`. Observable consequence: stored RUNNING with no tracked/live job and released scheduling slot. This is distinct from fixed #5220's failure-versus-client-outcome barrier.

### R3. Startup status failure can collide with completion removal

**Strength:** Medium static confidence; contingent on transient metadata error plus interleaving; prioritize R1/R2 first. After insertion at `710`, a RUNNING write may raise (`711`). The catch removes `running_jobs[job_id]` (`715-717`) before driving stop and publishing FAILED_TO_RUN. Concurrent completion may already hold `job = self.running_jobs.get(job_id)` (`446-447`) and later execute unconditional `del self.running_jobs[job_id]` (`532`), which raises KeyError if startup failure removed it. The completion loop has no outer exception handler (`441-541`), so this can stop completion of unrelated jobs. The `self.lock` serializes the two deletes but does not make the second delete conditional.

The built-in metadata store documents/propagates ordinary write I/O errors (`filesystem_storage.py:259-275`). Existing per-job archival/status retries do not wrap the delete. This is a concrete adjacent mechanism, but local controlled-fault confirmation is still needed before claiming a production incident. It can be a small code-review/local-test candidate rather than a separate broad TLA+ hunt.

## Code-review / local-test candidates and known issues

- **R4: ordinary store error can terminate the admission service.** The outer admission loop has no exception guard around `get_jobs_to_schedule` (`job_runner.py:650`) or the pre-deploy reload (`661`). More pointedly, an exception in deployment/start enters the catch, but `_stop_run` (`719`), FAILED_TO_RUN status update (`720`) and deploy-detail update (`724-725`) are themselves unguarded. If the initial error is transient storage unavailability, a second status write can fail and escape `run`, ending its unsupervised thread (`server_deployer.py:144-145`). Later resource/store recovery cannot restart that thread in the shown live path. If JOB_STARTED had fired, missing JOB_ABORTED at `728` can retain its scheduler slot. Prefer a local controlled ordinary-I/O-error test; not a needlessly broad distributed model. This is adjacent to #5191 but outside the scheduler's proposed exception guard.
- **Known #5191 overlap:** `_try_job` has no reservation cleanup `finally` after checking resources (`job_scheduler.py:199-261`); `_do_schedule_job` updates history only after `_try_job` returns (`365-375`). Its outer catch logs once for the entire candidate pass (`292-296`). These are acknowledged upstream; do not relabel them new. Missing cancellation acknowledgements alone remain bounded reservation uncertainty under TTL.
- **Admission abort/deploy-exclusion leaves reservation cleanup to TTL:** when rechecks reject ready jobs (`job_runner.py:661-663,697-701`), and when optional deploy failures are filtered out (`692-695`), this runner does not explicitly cancel the affected tokens. They have not been allocated by this start path, so the built-in expiry is a valid owner/backstop; do not claim a permanent allocation leak from these paths.
- **Startup failure is not quiescence:** `_stop_run` sends client abort only while the server run_process record exists (`374-394`). Its abort reply is deliberately not checked (`409-411`), server abort returns after spawning asynchronous cleanup (`server_engine.py:354-383`), and `run` can publish FAILED_TO_RUN/JOB_ABORTED before children stop (`719-728`). Actual client allocation cleanup must be traced through JobExecutor by the client audit. Scheduler list release alone cannot establish capacity reuse.
- **Startup fail-report race:** `fail_run` may pop pending outcomes during `_start_run` (`job_runner.py:841-842` versus `309-310,359-360`), producing KeyError at intersection. The outer startup catch can still stop and mark FAILED_TO_RUN, so the exception alone is not a new leak. Any claim requires downstream cleanup failure or incorrect status consequence, not merely noting the KeyError.

## Startup participant policy (preserve actual semantics)

Admission requires connected required sites and enough resource-positive replies (`job_scheduler.py:139-175,207-254`). Deployment treats None replies as failures and applies min_sites/required_sites (`job_runner.py:250-282`); production `send_requests_and_get_reply_dict` initializes every requested token to None (`admin.py:286-305`), so absent replies cannot disappear from the deployment decision map. Optional failed deployment sites are excluded from start; not every target is required to start.

Start-reply checking defaults **non-strict** (`job_runner.py:313-317`). `check_client_replies` always rejects an empty reply list or count mismatch (`admin.py:101-105`). Strict mode maps None replies to timeout sites, rejects missing site identities and non-OK headers, and raises ERROR-prefixed string bodies (`111-132`); JobRunner then enforces required/min participant thresholds on the timeout exclusion (`324-343`). Non-strict mode ignores None and checks only ERROR-prefixed string bodies (`133-137`), then JobRunner derives `JOB_CLIENTS` and pending outcomes from nonempty replies (`345-360`). The helper docstring's claim that non-OK headers always raise is stronger than this implementation. Do not assume strict defaults or interpret permitted timeout continuation as a proven policy bug. For a non-OK header/structured body case, establish the real Client StartJobProcessor response shape in the client audit.

## Completion guarantees and exclusions

- Already-fixed identity: lifecycle explicit IDs plus dispatch resetting preserve correct job identity despite sticky CURRENT_JOB_ID changes. `fl_context.py:102-175` confirms sticky props remain shared; that does not undo the explicit lifecycle ID fix. Known JobMetricsCollector cross-attribution is outside the requested accounting boundary.
- Already-fixed server failure barrier: completed server process with execution/abnormal failure removes pending client outcomes (`job_runner.py:448-465`). Normal server completion waits only until configured outcome deadline (`466-480`, default900 at `109-111`); an administrative `run_aborted` flag bypasses that wait. These behaviors must remain in the model; the old #5115/#5220 bugs are reference context.
- Workspace failure: selected terminal status is latched (`484-492`), archive cleanup failures retry per job and stop blocking terminal publication after 60 s (`494-522`); status-store failure retries (`523-530`). Later jobs remain eligible for completion because these branches `continue` the per-job loop. Model only delay/error/success and status publication; omit workspace contents. A persistently failing metadata store may reasonably prevent publication until it recovers, unlike termination of the service thread.
- Client terminal notifications: `fed_server.py:925-956` takes explicit job ID plus registered client identity, ignores untracked pairs, and resolves the pending set. It does not use shared CURRENT_JOB_ID to select a job. `fail_run` preserves authoritative failure codes under engine lock (`job_runner.py:813-843`), and finished-state latching prevents reclassification during retries. Investigate race ordering only if an observable consequence is established; don't inject arbitrary other-job notifications from cooperative publishers.
- Locks follow consistent order in the examined nested path: fail_run takes runner then engine (`815-816`); completion releases engine lock before taking runner (`448-455`), avoiding that candidate lock inversion.
