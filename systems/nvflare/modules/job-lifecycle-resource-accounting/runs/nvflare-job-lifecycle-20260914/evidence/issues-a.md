## #5191 exact current status and interpretation

Live API and browser agree: OPEN, not merged, not draft; head `27ecde2ab85b38734072b90128dc5dc2e8390882`; base `9a4e30a9d3a26a9514d00d43322661d21b7c09b8`; last update `2026-08-26T23:20:32Z`. Its proposed changes are **not** the pinned implementation. PR body, all 3 timeline comments, all 7 submitted reviews, all 9 inline comments, and all 5 file patches are archived.

The acknowledged core mechanism is an exception leaving normal admission before reservation cancellation and before retry-history bookkeeping, causing the candidate scan to end early. Current pin still checks resources and dispatches AFTER_CHECK_CLIENT_RESOURCES without a cancellation `finally` (`job_scheduler.py:199-205`), unlike the proposal. Returned normal admission failures and raised exceptions must be distinguished.

Reviews added completeness checks for partial/missing resource replies, cancellation acknowledgement validation, and cleanup ownership through post-admission history updates. Review replies describe branch fixes at `585c3db7d`; do not import those into the pin or count them as novel discoveries.

[Comment 5432240101](https://github.com/NVIDIA/NVFlare/pull/5191#issuecomment-5432240101) accepts centralized cleanup but explicitly disputes turning missing cancellation acknowledgement into a hard failure of the whole pass. Built-in managers have reservation expiry; a lost acknowledgement after successful cancellation is not a permanent capacity leak. The comment requests verify-and-log cancellation errors, continued scanning, retaining cleanup fixes, and guarding bookkeeping errors. These are **requested changes**, not a merged behavior guarantee.

The pin confirms the backstop precisely: `AutoCleanResourceManager` defaults to `expiration_period=30` and `check_period=1.0` (`auto_clean_resource_manager.py:27-37`), starts the expiry thread on SYSTEM_START (`93-99`), and decrements reservation TTL under the same lock as cancellation/allocation (`102-116`, `123-131`, `140-164`). A timer step removes only a still-reserved token; successful allocation pops it out of the reservation map. Consequently, expiry repairs an orphan reservation under a live cleanup thread but cannot repair orphan **allocations**. The implementation counts cleanup ticks rather than wall-clock elapsed time, so the discussion's ~30 s statement is the default normal-scheduling expectation, not a hard real-time bound.

`JobRunner.run` retries its outer pass periodically (full deep audit follows). A cancellation acknowledgement proves a command response, not application quiescence. The model must retain expiry, preserve participant policy, and separately represent reservation ownership, transferred allocation ownership, start execution, and process termination. The known admission-exception bookkeeping issue belongs in reference/known-issue context; only independently verified residual mechanisms should become novel modeling targets.
