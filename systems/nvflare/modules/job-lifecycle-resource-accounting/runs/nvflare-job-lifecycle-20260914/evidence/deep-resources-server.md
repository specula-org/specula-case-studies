# Deep audit: resources, server engine and launch composition

Pin: `53ba7ee567468ea7971dad4faccef13c6cb35dc2`. Category A: server/site lifecycle messages compose with concurrent local callbacks and independent cleanup loops. This subtask read the shared deep-analysis and distributed-analysis references fully; it read all 1,115 lines of `server_engine.py`, all of `auto_clean_resource_manager.py`, `list_resource_manager.py`, `scheduler_cmds.py`, `list_resource_consumer.py` and `process_launcher.py`. Adjacent production transport, event dispatch, client engine/executor, metadata validation and existing tests were followed for compensating behavior. No source modifications, experiments, GPU computation, security reproduction or tests were performed. Findings below are source analysis, not confirmed model counterexamples or production reproductions.

## Main conclusions

1. **Reservation expiry/cancel versus allocation is serialized correctly for valid integer requirements.** Missing-token allocation rejection is an old implemented defense, not a new finding. Expiry cannot reclaim a token already popped into allocation.
2. **There is a source-backed launch-identity race across competing jobs:** `ListResourceConsumer` stores resource identity in process-global environment before the per-job process launcher copies it. Server request timeout permits another job to reach the same client while the earlier callback remains in progress. This is a strong candidate for a current two-job scenario; it needs model checking and local trace/controlled execution confirmation.
3. **Startup rollback crosses multiple ownership stages but only distinguishes exception versus return.** Normal child-exit cleanup waits for actual process exit; returned pre-launch errors and exceptions after launch need separate treatment. Existing event-handler exceptions are normally swallowed by production dispatch and must not be modeled as direct propagation from a simplified mock.
4. **Server abort removes process bookkeeping after a terminate request, without observing exit.** This is a code-review/controlled-fault boundary, not sufficient evidence that the default cooperative local path causes a persistent live-server process leak or violates `max_jobs`. Do not equate logical scheduler slots with all OS processes during every launch/teardown interval.

## Atomicity and ownership map

| Operation | Actual atomic boundary | Ownership implication |
|---|---|---|
| Check + reserve | One `AutoCleanResourceManager._lock` block, lines 123-137; subclass capacity check and dequeue occur inside it | Competing valid reservations cannot both take the same initially unique unit |
| Reservation expiry | Same lock; pop token then `_deallocate`, lines 102-117 | Only `reserved_resources` is inspected; allocations have left this map |
| Cancel reservation | Same lock; guarded pop, lines 140-151 | Cancel-after-allocate, cancel-after-expiry and repeated cancel are no-ops |
| Allocate | Same lock; require live token and pop, lines 153-164 | Transfer from TTL-owned reservation into caller-owned payload; no allocation ledger remains in manager |
| Free | Same lock; blindly deallocate supplied payload, lines 166-172 | Exactly-once and no-live-use safety are caller responsibilities; token argument is unused |
| Consume | Global `os.environ` write, consumer lines 31-37; outside manager lock | Reservation uniqueness alone does not establish process resource identity |
| Process launch | Environment snapshot at launcher line 68, spawn line 81 | Separate from consume and from executor registration/waiter setup |
| Client startup | Pending handle registered under executor lock, executor 299-307; launcher called outside lock 308-316; attach 318; event 326; waiter start 334 | Pending handle owns abort intent but resource cleanup handoff is not explicitly committed |
| Client ordinary cleanup | Wait at executor 628, outcome handling 630-674, resource free 676-679, map pop 680-681 | A stop request or STOPPED status alone does not run normal free |
| Server ordinary cleanup | Wait at server engine 204; bounded child status wait; map removal under lock 218-233 | Observes server process exit before ordinary removal |
| Server abort cleanup | Captured handle, grace wait, terminate request 402-407, unconditional map pop 408-409 | Abort path is weaker than ordinary exit observation |

## Candidate R1: resource selection is carried through a shared environment

**Evidence.** `list_resource_consumer.py:27-37` implements GPU resource selection by assigning `os.environ["CUDA_VISIBLE_DEVICES"]`. `scheduler_cmds.py:115-128` allocates, then consumes, then calls `ClientEngine.start_app`. The engine enters per-job startup at `client_engine.py:349-382`; executor metadata reads/writes, launcher selection and process-argument setup occur at `client_executor.py:221-298` before actual launch at 309. `process_launcher.py:66-83` copies the current global environment at 68 and supplies that copy to spawn at 81. No common mutex spans the global assignment and snapshot.

**Production reachability.** `ConnManager` uses a 100-worker frame executor (`sfm/conn_manager.py:43,90-91`), submits each frame independently at 390-396, and DATA frames call the registered receiver at 365-374. `CoreCell._process_request` invokes the callback at `core_cell.py:1806-1834`; `FedAdminAgent` dispatches to the processor at `client/admin.py:100-177` without a job-start serialization lock. Server start requests wait 20 seconds (`server_engine.py:1068-1083`), then the sender proceeds. Timeout removes the request waiter, not the already executing client callback (`core_cell.py:1563-1574`, late reply handling 1986-2028).

**Scenario shape.** Use distinct jobs with distinct successful reservations at one participating site, default process launcher, `ListResourceManager` + `ListResourceConsumer`, and concurrency limit at least two. An earlier start callback consumes its assigned resource then is delayed before the launcher's environment snapshot (ordinary file/metadata/launcher preparation or scheduling delay). Its start reply times out. Under the selected default non-strict reply policy, the server can complete that startup pass and later admit another eligible job while the first callback is still active. The second callback consumes its own distinct resource and launches. When the first resumes, its process can inherit the second job's selected devices. Both allocation payloads remain distinct even though actual launch identities overlap. If the second job exits, its ordinary free may expose a resource still selected by the first.

**Policy boundary.** Non-strict mode defaults false for `STRICT_START_JOB_REPLY_CHECK` (`job_runner.py:313-323`). It derives active metadata from actual replies (`345-360`) but missing replies do not cancel the delayed callback. This scenario does not assume all targeted sites must start or that a missing reply proves failure. With strict mode, use a non-required timed-out site and enough other sites satisfying min_sites if allowed by the parent-selected policy; do not assume strict behavior identical to default. The root task should pin the exact policy in the brief.

**Compensating mechanisms checked.** Manager locking prevents duplicate allocation payloads but does not protect environment handoff. Client executor lock protects job-ID registration, not global resource selection. Pending handle protects early abort only after registration. Transport reply correlation prevents cross-request reply confusion but does not revoke execution on timeout. Reservation TTL is irrelevant after successful token-pop allocation. No GPU computation is needed to observe the launch-environment mismatch; evidence should focus on allocation identity and each launched child environment.

**Classification.** Model-checkable scenario candidate, high priority. Proposed state additions: per-job allocation, shared pending resource environment, per-process snapshotted resource selection, separate consume/snapshot/launch/exit/free transitions. Proposed property: each running job's selected managed units belong to its own current allocation; managed units simultaneously selected by different jobs must not overlap when resources are exclusive. Preserve unique valid configured units. No public consequence or upstream novelty is claimed until issue audit and local confirmation are complete.

## Candidate R2: allocation cleanup ownership across startup outcomes

**Returned-error branch.** `StartJobProcessor` only frees at `scheduler_cmds.py:129-133` when an exception propagates. `ClientEngine.start_app` can return early for already-STARTED or absent app (`client_engine.py:357-367`) after allocation has already transferred out of TTL tracking. No waiter is created by those returns. The server may classify an error reply, but its cancel path can only reclaim still-reserved tokens. This is a verified branch asymmetry. A new real finding still requires an ordinary supported end-to-end reason to reach that early return with a fresh nonempty allocation: replay of the identical token is rejected before the engine; same-job duplicate fresh reservation must not be invented if production scheduling cannot issue it; arbitrary workspace mutation is outside the chosen scope. Keep this as a code-review/controlled-fault candidate until trigger reachability is established.

**Raised post-launch branch.** Executor's protected launch block ends at 316. A real process exists before the waiter is started at 334. An ordinary thread-creation failure there propagates through engine.start_app into processor exception rollback. The processor immediately frees the allocation without first terminating or waiting for the live job. The pending process registration remains; no waiter was started to own its cleanup. Later heartbeat/abort may eventually stop it, but that does not remove the interval in which resource capacity has been returned while a live process exists. This is a source-backed handoff failure candidate; a controlled local failure is needed before reporting runtime impact. Do not claim double free from Thread.start failure alone: that particular path creates no waiter. Double free requires a separately established path where both rollback and waiter own the same allocation.

**Production event dispatch.** `JobExecutor` fires AFTER_JOB_LAUNCH at 326. The actual `fire_event_to_components` catches ordinary handler exceptions at `apis/utils/event.py:54-82`, records them in context and continues. A mock whose `engine.fire_event` directly raises does not demonstrate production callback failure propagation. Context/dispatcher setup errors outside that per-handler catch are different and require explicit source-valid preconditions. Existing valid components and the real dispatcher must remain in any confirmation harness.

**Ordinary cleanup protection.** Client abort marks intent and terminates/sends stop (`client_executor.py:486-547`) but does not free or pop. `_wait_child_process_finish` waits before free (`622-681`). STOPPED is explicitly recognized as possibly still-live and reclaimable (`client_engine.py:392-402`, executor 513-521). Therefore normal abort/completion notification overlap alone does not establish double free or premature release. Resource manager free is not idempotent, but caller misuse must be demonstrated.

**History.** #766 (`55e74fe2af`) introduced consume-before-start and exception-only free in 2022. #4910/#4904 fix pending startup abort visibility, not all post-launch ownership-transfer exceptions. #5191 concerns admission cancellation/retry paths, not automatically these allocation-stage cases; discussion verification remains separate.

## Candidate R3: partial reservation mutation before a token exists

`ListResourceManager._check_required_resource_available` compares counts but never validates that all counts are nonnegative integers (`list_resource_manager.py:57-67`). `_reserve_resource` iterates keys and dequeues incrementally (`69-76`); the manager stores a token only after the helper returns (`auto_clean_resource_manager.py:128-131`). A later count that passes the numeric capacity comparison but cannot be used by `range` can raise after earlier resource-key queues have already changed. There is then no reservation token entry for TTL or cancellation to reclaim. `CheckResourceProcessor` converts the exception into rejection (`scheduler_cmds.py:83-88`) without undoing internal manager mutation.

The submission validator checks the resource spec's dictionary shape and portable fields (`job_meta_validator.py:265-284`); `validate_portable_resource_spec` intentionally leaves site-specific custom fields unrestricted (`job_launcher_utils.py:263-300`), and manager normalization preserves those fields (`311-323`). Thus custom resource input validation is not supplied by the general portable validator. This remains input robustness/code-review or test evidence, not a valid-integer model-checking fault. Do not restrict the theorem merely to hide a supported requirement defect; first establish the ListResourceManager input contract and classify incompatible custom counts separately. No runtime reproduction was performed.

## Candidate R4: terminate request versus observed server exit

Server `_remove_run_processes` calls the captured handle's terminate operation and removes bookkeeping even after an exception (`server_engine.py:385-409`). `ProcessHandle.terminate` delegates directly (`process_launcher.py:48-49`); `ProcessAdapter.terminate` only requests process-group SIGKILL (`process_utils.py:226-232,293-316`) and does not wait. Missing-process errors are correctly benign. Generic errors are logged and suppressed.

A default local same-user child created with setsid (`process_utils.py:333-352`) has no established ordinary persistent permission-denial trigger in this audit. SIGKILL delivery and exit observation are separate events, but that fact alone does not prove indefinite use of resources or bad scheduler accounting. The server resource check explicitly assumes unlimited server resources (`server_engine.py:1013-1015`). Scheduler max_jobs is logical job concurrency; there is no justified universal equality with all live OS processes during startup and cleanup.

The existing `server_engine_test.py:323-373` tests intentionally require terminate and map removal even when a mocked K8s cleanup fails. That historical backend policy cannot establish a production local-process failure. Keep the missing exit-confirmation/error-retention concern under code-review/controlled-fault evidence. A future model may retain explicit stop-sent, exit-observed and bookkeeping state to avoid an invalid invariant, but should not spend an MC finding slot recreating an unproved arbitrary failure of local SIGKILL.

## Confirmed defenses and explicit exclusions

- Expiry/cancel versus allocation: same mutex and guarded token pop; whichever wins determines whether allocation succeeds. After allocation, expiry/cancel cannot return the owned units. Full valid manager behavior is preserved in the reference model, not treated as a new defect (#485/#905 history).
- Repeated successful allocation using the same token: rejected by absence of the token. Repeated cancel/expiry does not duplicate units. Repeated free is not protected, but ordinary supported calls must first demonstrate duplicate ownership of cleanup.
- Lost cancel acknowledgment: `server_engine.py:1052-1066` discards replies, but reserved tokens retain TTL cleanup. Do not call this a permanent resource leak; #5191 discussion explains the intended backstop.
- Delayed replies remain correlated by waiter ID and destination (`core_cell.py:1512-1525,1571,1986-2028`); `ClientReply` retains the originating request/name (`message_send.py:22-35,68-110`). A late reply for a removed waiter is dropped, not applied to the next scheduling attempt. Delayed request execution remains possible and is materially different.
- Return-code file read/remove exceptions fall back to handle status (`fed_utils.py:547-564`); do not model a normal RC-file read failure as necessarily terminating the client cleanup waiter.
- The server launch path registers after launch and starts its watcher at `server_engine.py:315-328`, another owner-handoff boundary. Watcher Thread.start failure can leave bookkeeping without a waiter; root JobRunner exception cleanup attempts abort. Evidence must follow that compensating owner rather than assert an immediate permanent leak.
- `ServerEngine.get_engine_info` recomputes global machine status from run_processes (`142-159`); transient `engine_info.status=STOPPED` writes from one completion do not alone prove another job's scheduler count changed.
- `get_job_clients` returns actual connected selected sites (`331-338`); `_start_runner_process` falls back to all current clients when the selected map is empty (`318-319`). This is a participant-snapshot edge worth parent policy review if all intended clients disconnect before server launch, but no downstream wrong-job resource consequence is established here.
- No meaningful TODO/FIXME in these selected resource paths; server-engine line 101 only requests base-server interface cleanup. HA restore, snapshots, external launchers, model transfer and training computation are excluded.
