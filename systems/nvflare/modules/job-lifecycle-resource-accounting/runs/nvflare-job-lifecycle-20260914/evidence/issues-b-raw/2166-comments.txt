After staring at the graph for a while, I noticed a few things:
- The training has been going on for over 13 hours. Since each round took a few hours, some aggregation should have happened, but we don't see any memory usage surge in the first 13 hours. This seems to indicate that the training was going fine.
- Then the surge happened. A surge is usually the effect of multiple things added up. If there is a systematic memory leak, the curve should be steadily going up, but not a surge. Is it possible that somehow multiple clients started submitting their model weights to the server at the same time period?
- Another possibility has to do with network speed/stability. Did you see any timeout errors in the client's log? If the client fails to get a task due to timeout, it will send the getTask request again to the server. So if the timeout parameter is too short, it could cause cascading effect: the server keeps trying to send the same task (with model weights) to the clients again and again. This will cause memory surge. 
- Did you try to re-run the same job with NVFLARE 2.3.5? If the surge was caused by accidental multiple weight submissions, the chance of that happening again should be low.
