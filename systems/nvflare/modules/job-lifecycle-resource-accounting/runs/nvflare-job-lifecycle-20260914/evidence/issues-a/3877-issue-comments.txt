@virginiafdez 

Hello. As a user who has built a similar system architecture, I've experienced similar errors.

Please try the following:

1. Kill all server, client, and API server processes (if using Docker, delete the container and rebuild it).
2. Ensure that all server, client, and API server processes maintain the same nvflare version. For Docker, we recommend sharing an image with nvflare==2.7.0 installed.
3. Completely delete the existing provisioned project (**_project/prod00/*) and re-provision it.
4. Create an admin session using the newly created startup kit and test it using the API or command.

Similarly, when upgrading from version 2.5.2 to version 2.7, most server-admin connection errors were caused by the new version of nvflare and the startup kit (certificates) generated by the old version, as shown above.

When checking the current log, when the _try_command() function is executed while creating a new admin session,

"/app/.venv/lib/python3.12/site-packages/nvflare/fuel/hci/conn.py", line 63, in receive_and_process

The problem occurs when the receive_and_process() function is called.

The reason for the error being due to version differences is that the function exists only in version 2.5.2, not in version 2.7. Please check the git repo.

Your API server appears to be running version 2.5.2, and the target FL server appears to be running version 2.7.

Resolve this issue by synchronizing versions.

I don't remember the previous version, but at least in 2.7, each folder contains a file called signature.json. The file contains signatures for all files in each folder where signature.json exists, and appears to serve the purpose of checking for file tampering.

The startup kit or job configs.json files are not compatible between major nvflare updates. The file structure is different, and the json key:value format is slightly different.

sir, plz no.

As someone with experience, I have two strong recommendations:

1. **delete everything from old, provision a new project and start up kits**
and, fortunately, since you're the administrator, deploy the new startup kits to the API server, FL aggregation server, and clients.
The startup kits you currently have are based on older versions and won't work properly.

Don't be afraid to delete all the startup kits and provision them anew.
These startup kit files don't contain much. They're just the root certificate you created previously and the bash shells that open the admin console.

If you keep all your existing provisioning settings (from the old 2.2.5 days), and provision them the same way, they'll work the same on the new system.
Use the archived project_templet.yaml, or if you don't have one, create a new one, paying close attention to the server address and port, and then provision it.

2. Whether you use the CLI admin console or the API with the new_secure_session() function in Python, they both reference the same file.
Since the API function is identical to running the fl_admin.sh file, if you're running the latest version of nvflare while maintaining an older version of the startup kit, problems will occur in both the console and the API.

In your code:

```
session = new_secure_NHSFlame_session(
    username="admin",
    startup_kit_location=admin_dir,
    )
```

This is why you specify startup_kit_location as above.

Please use the new provisioning and start-up kit.

I hope this resolves the issue.
