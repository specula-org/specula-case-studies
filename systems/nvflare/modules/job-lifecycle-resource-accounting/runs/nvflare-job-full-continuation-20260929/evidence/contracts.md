### 1.3 Relevant resource-spec resolution (portable CPU / memory feature)

- `PORTABLE_RESOURCE_DEFAULT_KEY = "@default"`, `PORTABLE_RESOURCE_KEYS = ("num_of_gpus", "num_of_cpus", "memory")`
  (`nvflare/utils/job_launcher_utils.py:225-226`).
- What the FLARE resource manager sees: `get_resource_manager_spec` "Return resources enforced by the site's NVIDIA FLARE resource manager"
  and **drops** `num_of_cpus` and `memory`: `result = {key: value for key, value in resolved.items() if key not in ("num_of_cpus", "memory")}`;
  and drops `num_of_gpus: 0` (and `mem_per_gpu_in_GiB`) (`job_launcher_utils.py:311-323`). The scheduler uses exactly this for every applicable
  site (`job_scheduler.py:179-182`).
- `get_portable_resource_spec` "Return the portable fields that launchers must enforce for a site." (`job_launcher_utils.py:326-339`).
  The process launcher (`process_launcher.py:66-83`) does not read any resource spec, i.e., on the default local-process path
  CPU/memory portable fields are validated but neither reserved by the resource manager nor enforced by the launcher (see 2(g)).
- Design doc: `resource_spec` "is scheduler-facing: the scheduler reads it at job admission time to decide if the site has the
  required hardware." (`docs/design/job_launcher_and_job_handle.md:169-170`).
- Launcher-config design doc: "resource_spec: abstract resource requirements, used by the server scheduler for placement and by launchers for
  hardware-related configuration. This section stays launcher-agnostic." / "launcher_spec: ... The scheduler ignores this section entirely."
  (`docs/design/job_meta_launcher_config.md:102-103`); "GPU counts should remain in flat resource_spec so the scheduler and launchers read the
  same resource requirement." (`job_meta_launcher_config.md:216`); for the process mode the GPU value is "passed as an environment variable or
  argument" (`job_meta_launcher_config.md:121`), which in the default config is the `GPUResourceConsumer` `CUDA_VISIBLE_DEVICES` mutation.

## 2. Documented contracts

### (a) Resource manager API

Spec (`nvflare/apis/resource_manager_spec.py`), mirrored verbatim in `docs/programming_guide/resource_manager_and_consumer.rst:111-170`.

- **A1 check = reserve.** `check_resources` "Checks whether the specified resource requirement can be satisfied." Returns
  `(is_resource_enough, token)`; "token is for resource reservation / cancellation for this check request."
  (`resource_manager_spec.py:28-40`). Implementation reserves only when enough: `# reserve resource only when enough resource`
  (`auto_clean_resource_manager.py:127-131`), with the check-and-reserve done atomically under `self._lock` (`:123-137`).
  Token is `""` when not enough (`:125`).
- **A2 cancel.** `cancel_resources` "Cancels reserved resources if any." / "Note: If check_resource didn't return a token, then don't
  need to call this method" (`resource_manager_spec.py:44-55`). Implementation: unknown/expired token is a no-op with a debug log
  (`auto_clean_resource_manager.py:140-151`).
- **A3 allocate consumes the reservation.** `allocate_resources(resource_requirement, token, fl_ctx) -> dict` "Allocates resources." /
  "Note: resource requirements and resources may be different things." / token = "a resource reservation token returned by check_resources"
  (`resource_manager_spec.py:58-72`). Implementation pops the reservation and **raises if the token is not (or no longer) reserved**:
  `raise RuntimeError(f"allocate_resources: No reserved resources for token {token}.")` (`auto_clean_resource_manager.py:153-164`).
- **A4 free.** `free_resources(resources, token, fl_ctx)` "Frees resources." (`resource_manager_spec.py:75-83`). Implementation ignores the
  token and unconditionally `_deallocate(resources=resources)` (`auto_clean_resource_manager.py:166-172`); there is no idempotence /
  double-free guard at this layer (GPU: `self.resources[k].memory += v`, `gpu_resource_manager.py:148-150`; list: `appendleft`,
  `list_resource_manager.py:52-55`).
- **A5 report.** `report_resources(fl_ctx) -> dict` "Reports resources." (`resource_manager_spec.py:86-88`); exposed through admin
  `report_resources` (`nvflare/private/fed/client/scheduler_cmds.py:160-169`).
- **A6 reservation lifetime / expiry.** `AutoCleanResourceManager` "will automatically clean up reserved resources." /
  `expiration_period (int): Number of seconds to hold the resources reserved. default to 30. If check_resources is called but after
  "expiration_period" no allocate resource is called, then the reserved resources will be released.` /
  `check_period (float): Number of seconds to check for expired resources. default to 1.0.` (`auto_clean_resource_manager.py:27-38`).
  Same wording in `GPUResourceManager` (`gpu_resource_manager.py:90-92`) and `ListResourceManager` (`list_resource_manager.py:38-40`).
  Mechanism: each reservation stores a countdown initialised to `expiration_period` (`auto_clean_resource_manager.py:131`); the cleanup
  thread decrements it once per `check_period` sleep and deallocates at 0 (`:102-117`). The thread starts on `SYSTEM_START` and stops on
  `SYSTEM_END` (`:93-100`). Default provisioned value: `expiration_period: 300` (`master_template.yml:78`).
- **A7 GPU manager semantics.** A requirement without GPUs is always satisfiable: `if not resource_requirement: return True` and
  `if num_gpu == 0: return True` (`gpu_resource_manager.py:152-163`); missing `num_of_gpus` key in a non-empty requirement raises
  `ValueError` (`:156-157`). Reserve decrements per-GPU memory on the first `num_gpu` GPUs whose remaining memory >= requested
  (`:175-197`). Docs: "the current implementation of GPUResourceManager will NOT keep updating the GPU count and memory usage ... just
  checks using nvidia-smi at init time and then virtually assumes it has this much resources on site." and "If another process outside
  of NVFlare is occupying the GPU resource ... GPUResourceManager is not responsible for that." (`resource_manager_and_consumer.rst:99-101`).
- **A8 consumer.** `ResourceConsumerSpec.consume(resources: dict)` (`resource_manager_spec.py:20-23`). Docs: "Once the job is started on the
  client, it will call the Resource Consumer to consume the resources." (`docs/user_guide/core_concepts/job.rst:290-292`) and the consumer
  "simply sets the CUDA_VISIBLE_DEVICES system variable ... This ensures that each concurrent job will be using different GPU devices."
  (`job.rst:313-316`). Code: consumer is called only when the allocation is non-empty (`scheduler_cmds.py:119-121`);
  `GPUResourceConsumer.consume` mutates the parent process `os.environ["CUDA_VISIBLE_DEVICES"]` (`gpu_resource_consumer.py:25-33`),
  which `ProcessJobLauncher` later copies with `os.environ.copy()` (`process_launcher.py:68`).
- **A9 client-side wiring of the API (the intended ownership chain).**
  - Check: `CheckResourceProcessor` calls `check_resources` unless a `BEFORE_CHECK_RESOURCE_MANAGER` handler set `JOB_BLOCK_REASON`,
    in which case it replies `(False, block_reason)` (`scheduler_cmds.py:77-85`); any exception -> `(False, "resource manager raised an
    exception; see site log")` (`:86-88`).
  - Start: `StartJobProcessor` allocates with the server-supplied token, consumes if non-empty, calls `engine.start_app(...)`, and frees
    the allocation **only if an exception is raised** (`scheduler_cmds.py:114-133`); a non-exception return value is sent back as the reply
    (`:135-137`).
  - Cancel: `CancelResourceProcessor` calls `cancel_resources`; exception -> `EXECUTION_EXCEPTION` return code (`scheduler_cmds.py:140-157`).
  - Free after run: `_wait_child_process_finish` waits for the job handle, reports the terminal outcome to the server, then
    `resource_manager.free_resources(resources=allocated_resource, token=token, ...)` if the allocation is non-empty, then removes the
    job from `run_processes` and fires `JOB_COMPLETED` (`nvflare/private/fed/client/client_executor.py:622-688`).
  - Docs: "Once a job is dispatched to a client, the Resource Manager is called to allocate the required resources (using the
    allocate_resources method)." and "Once the job is finished (completed normally or aborted), the Resource Manager is called again to
    free the resources (using the free_resources method)." (`job.rst:290-295`).
- **A10 server-side wiring.** `check_client_resources` skips the server (`# assume server resource is unlimited`), sends CHECK_RESOURCE to each
  resolvable client with a 15 s timeout, and maps a missing reply to `(False, "")` and a non-OK return code to `(False, message)`
  (`nvflare/private/fed/server/server_engine.py:1010-1041`). `cancel_client_resources` sends CANCEL_RESOURCE only for results with
  `is_resource_enough and token`, ignoring replies (`server_engine.py:1052-1066`). `start_client_job` sends the `DispatchInfo` token in the
  START_JOB header with a 20 s timeout (`server_engine.py:1068-1083`).
- **A11 passthrough manager (non-default).** "optimistically approves all resource requests ... If the requested resources are not available
  when the job executes, the job will fail at that point rather than at scheduling time." (`passthrough_resource_manager.py:23-31`);
  check always `(True, uuid)`, cancel/free no-op, allocate `{}` (`:38-94`).
- **A12 same classes on all clients.** "Make sure each client has the same resource manager and resource consumer class, even though the
  arguments can be different." (`resource_manager_and_consumer.rst:89-91`).

### (b) Scheduler admission

- **B1 who schedules.** "There is a Job Scheduler on the Server, which decides whether a job is runnable. It asks these clients whether they can
  run the job, given the resource requirements" (`job.rst:272-274`). Runner loop: every 1.0 s, only in `HotState`, only if some client is
  registered, fetch `get_jobs_to_schedule` and call `schedule_job` (`nvflare/private/fed/server/job_runner.py:641-658`). One job is
  returned per call (`job_scheduler.py:364-371`).
- **B2 runnable condition.** "If runnable clients meet the job's client requirements (minimum number of clients and mandatory clients), then the
  job is runnable for the system, and the job is dispatched to these clients." (`job.rst:279-280`). Code: required sites must be connected
  (`job_scheduler.py:160-164`), connected applicable sites >= `min_sites` (`:166-176`), sites whose check returned OK >= `min_sites`
  (`:229-237`), and every required site's check OK (`:239-254`). The dispatch set is exactly the sites whose check returned
  `is_resource_enough` (`:212-222`) plus the server (`:256-259`).
- **B3 cancel on non-admission.** "After checking all the clients and if the Job Scheduler decides the job is not runnable. The client's Resource
  Manager will be called to cancel the resources it might have reserved for the job (using the cancel_resources method in Resource
  Manager)." (`job.rst:284-286`). Code: `_cancel_resources` on the two post-check rejection paths (`job_scheduler.py:229-254`).
- **B4 no resource re-check for server.** `# we are assuming server resource is sufficient` (`job_scheduler.py:178`), server `DispatchInfo(...,
  resource_requirements={}, token=None)` (`:256-259`).
- **B5 resource-less jobs.** "for simple FL jobs or in POC mode, resources are not a concern. ... The FL client always answers "Yes" when asked
  whether it can run a job without required resources." (`job.rst:263-265`).
- **B6 max concurrent jobs.** `max_jobs: max number of concurrent jobs allowed` (`job_scheduler.py:49`); docs: "The ``max_jobs`` parameter
  controls how many jobs at the maximum are allowed at the same time." (`job.rst:397-398`); "NVFLARE is a multi-job system that allows
  multiple jobs to be running concurrently, as long as system resources are available." (`job.rst:395`). Code counts `scheduled_jobs`, which
  gains a job on `JOB_STARTED` and loses it on `JOB_COMPLETED`/`JOB_ABORTED` (`job_scheduler.py:275-285`), and refuses to schedule when
  `len(self.scheduled_jobs) >= self.max_jobs` (`:263-273`, `:339-341`). `JOB_STARTED` is fired at the end of `_start_run`
  (`job_runner.py:364`); `JOB_COMPLETED` is fired by `_job_complete_process` only after the terminal status is published
  (`job_runner.py:523-538`); `JOB_ABORTED` is also fired on the FAILED_TO_RUN path (`job_runner.py:728`).
- **B7 retry / give-up.** "a job may fail to be scheduled if required resources are unavailable. The scheduler will have to try it again at a
  later time." (`job.rst:365-366`). `max_schedule_count: max number of times to try to schedule a job` (`job_scheduler.py:50`); docs: "if you
  set this number to be too small, then the job may be given up prematurely (in this case the status code of the job is set to
  FINISHED:CANT_SCHEDULE)" (`job.rst:400-403`). Code: when `schedule_count >= max_schedule_count` the job is put in `blocked_jobs`
  (`job_scheduler.py:347-354`) and set to `RunStatus.FINISHED_CANT_SCHEDULE` (`:305-308`); fatal job errors (`SCHEDULE_RESULT_BLOCK`: no
  deploy map, site outside study, invalid required sites) also block (`:114-159`, `:374-375`).
- **B8 back-off.** Docs: "The job will be retried no less than the ``min_schedule_interval``, and no less than the max." / "the scheduler wakes up
  every 1 second" / "It doubles the interval every time it fails, until it reaches the ``max_schedule_interval``." (`job.rst:405-410`).
  Code: `required_interval = min(self.max_schedule_interval, (2**n) * self.min_schedule_interval)` with `n = 0 if schedule_count == 0 else
  schedule_count - 1` (`job_scheduler.py:356-362`).
- **B9 ordering.** "it tries to schedule a waiting job as quickly as possible in the order of job submissions" (`job.rst:368-369`); code sorts by
  `SUBMIT_TIME` (`job_scheduler.py:343-344`) and returns the first admissible job.
- **B10 one-shot.** "Once submitted, a job only has one chance to be executed, whether the execution succeeds or not. Once executed, the job
  status will be updated and won't be scheduled again." (`job.rst:342-345`).
- **B11 scheduler spec return.** `schedule_job(...) -> (Job | None, dict[str, DispatchInfo] | None)`, "job is the Job that satisfies the criteria
  of the scheduler. sites_dispatch_info is dict of {site name: DispatchInfo} for the job." (`nvflare/apis/job_scheduler_spec.py:43-58`).
  `DispatchInfo(app_name, resource_requirements, token)` (`job_scheduler_spec.py:22-28`).
- **B12 what is checked.** Per-site requirement passed to the client = `get_resource_manager_spec(...)`, which excludes `num_of_cpus`, `memory`
  and zero GPUs (`nvflare/utils/job_launcher_utils.py:311-323`; used at `job_scheduler.py:179-182`). Docs: "CPU and memory are enforced by the
  selected job launcher rather than reserved by the site's NVIDIA FLARE resource manager. Positive GPU requests and additional site-specific
  fields continue through resource-manager admission." (`job.rst:111-112`).
- **B13 status gate before dispatch.** After scheduling, the runner deploys only if the job is still `SUBMITTED`
  (`job_runner.py:660-663`) and starts only if it is still `DISPATCHED` (`job_runner.py:697-701`).
  `get_jobs_to_schedule` (`JobDefManagerSpec`) "Get job candidates for scheduling." (`job_def_manager_spec.py:233-242`).


### (c) Deployment / startup success criteria (min_sites, required sites)

- **C1 meaning.** meta keys `min_clients` -> `Job.min_sites`, `mandatory_clients` -> `Job.required_sites`
  (`nvflare/apis/job_def.py:62-63`, `job_from_meta` `:236-243`, default `min_sites=meta.get(JobMetaKey.MIN_CLIENTS, 1)`).
  Docs: "min_clients: minimum clients required for this job" / "mandatory_clients: mandatory clients required for this job"
  (`docs/user_guide/core_concepts/job.rst:83-84`). Submission validation: `min_clients` must be positive and not exceed the explicit
  deploy-map client count (`nvflare/private/fed/server/job_meta_validator.py:237-249`); mandatory clients must appear in the deploy map
  (`job_meta_validator.py:252-262`); the deploy map must include the server (`:147`).
- **C2 lifecycle narrative.** "3. **Deploy the applications**: If enough clients are available and all mandatory clients can participate,
  ``JobRunner`` deploys the server application and the applications for the selected clients. The job is then marked ``DISPATCHED``."
  / "4. **Start the job processes**: ``JobRunner`` starts the SJ and then asks each selected CP to allocate the required resources and
  start a CJ. Once startup succeeds, the job is marked ``RUNNING``." (`docs/system_architecture/system_architecture.rst:203-207`).
- **C3 deployment phase.** Server app deploy failure or signature failure raises (whole job fails) (`job_runner.py:183-214`).
  Client deploy: a non-OK reply **or no reply** counts as a failed client: "No reply means the client timed out during deployment. Count this
  as a failure so the min_sites / required_sites check can decide whether to abort" (`job_runner.py:250-267`). Abort iff
  `num_ok_sites < job.min_sites` or a failed client is required (`job_runner.py:269-282`); otherwise the failed clients are returned and
  excluded from start: `deployable_clients = {k: v for k, v in client_sites.items() if k not in failed_clients}` (`job_runner.py:692-695`).
  Release note: "FLARE 2.7.2 correctly classifies deployment timeouts as failures, applying the existing ``min_sites`` / ``required_sites``
  tolerance check at the deployment phase. Timed-out clients are excluded from the job before ``start_client_job`` is called"
  (`docs/release_notes/flare_272.rst:285-288`).
- **C4 start phase, explicit errors.** Any client START_JOB reply whose body starts with `ERROR_MSG_PREFIX` (and, in strict mode, any non-OK
  return code) raises regardless of `min_sites`/required: "Explicit errors (non-OK return code or error body) always raise regardless of this
  flag." (`nvflare/private/fed/server/admin.py:80-140`, quote at `:89-91`). No replies at all, or a reply-count mismatch, also raise
  (`admin.py:102-105`).
- **C5 start phase, timeouts (`strict_start_job_reply_check`).** Config var comment: "# server: require all start-job replies to be
  non-timeout and OK before considering the run started" (`nvflare/apis/fl_constant.py:574-575`); read with default `False`
  (`job_runner.py:313-317`). Strict: timed-out required site -> fatal ("A required site timing out is fatal regardless of min_sites, same as
  deploy phase." `job_runner.py:327-331`); remaining < `min_sites` -> fatal (`:333-337`); otherwise timed-out clients are excluded with a
  warning (`:338-343`). Non-strict: "In non-strict mode, check_client_replies() does not return timed-out clients. Build active clients
  directly from actual replies so JOB_CLIENTS stays accurate." (`job_runner.py:345-353`). Docs: "In non-strict mode, timed-out clients are
  silently excluded from the active set and the job continues — but ``min_sites`` / ``required_sites`` constraints are **not enforced** for
  those timeouts, so startup problems can go undetected. In strict mode, timeouts are detected and surfaced: ``required_sites`` and
  ``min_sites`` are then checked, and the job only continues (with a warning) if constraints are still satisfied."
  (`docs/programming_guide/timeouts.rst:2460-2467`; same at `docs/user_guide/timeout_troubleshooting.rst:300-302`); release note
  (`docs/release_notes/flare_272.rst:308-312`).
- **C6 recorded participants.** After exclusions, `job.meta[JOB_CLIENTS]` = active clients only ("Set metadata once, after any timeout
  exclusion, so it always reflects active participants." `job_runner.py:355-360`), and the pending-outcome set is intersected with the
  active set (`:359-360`). The SJ's `PARTICIPANTS` record, however, is the dispatch/deployable set passed to `start_app_on_server`
  before the start round (`job_runner.py:296-304`, `server_engine.py:318-326`).
- **C7 ordering / status.** `DISPATCHED` is written after `_deploy_job` returns (`job_runner.py:669-670`); `RUNNING` after `_start_run`
  returns and the job is inserted in `running_jobs` (`job_runner.py:703-712`). Any exception in deploy/start ->
  `FAILED_TO_RUN`, `_stop_run` if a job id was assigned, `JOB_ABORTED` event (`job_runner.py:713-731`).
- **C8 SJ start = process spawn.** `start_app_on_server` refuses if the job is already in `run_processes` or the server app dir is
  missing, otherwise launches and records `{JOB_HANDLE, JOB_ID, PARTICIPANTS}` and starts a `wait_for_complete` thread
  (`server_engine.py:179-196`, `:315-329`). Design doc: process launcher "Start verification | None" (`docs/design/job_launcher_and_job_handle.md:514`)
  and "The Process launcher has no start timeout." (`job_launcher_and_job_handle.md:653`).
- **C9 CJ start.** Client refuses to start a job already registered ("client app for job '{job_id}' is still registered",
  `client_executor.py:299-307`), requires the deployed app (`client_engine.py:365-367`, returns an `ERROR_MSG_PREFIX` string, not an
  exception), and requires START_JOB metadata to match the deployed metadata for job id / resource_spec / launcher_spec / scope / study
  (`client_executor.py:231-240`). If `launch_job` raises, the pending registration is removed and the exception propagates
  (`client_executor.py:308-316`) so `StartJobProcessor` frees the allocation (`scheduler_cmds.py:129-133`).

### (d) Job status semantics and transitions

- **D1 enumeration** (`nvflare/apis/job_def.py:26-38`): `SUBMITTED`, `APPROVED`, `DISPATCHED`, `RUNNING`,
  `FINISHED_COMPLETED="FINISHED:COMPLETED"`, `FINISHED_ABORTED="FINISHED:ABORTED"`, `FINISHED_EXECUTION_EXCEPTION="FINISHED:EXECUTION_EXCEPTION"`,
  `FINISHED_ABNORMAL="FINISHED:ABNORMAL"`, `FINISHED_CANT_SCHEDULE="FINISHED:CAN_NOT_SCHEDULE"`, `FAILED_TO_RUN="FINISHED:FAILED_TO_RUN"`,
  `ABANDONED="FINISHED:ABANDONED"`. Every terminal value starts with `FINISHED:`.
- **D2 documented meanings** (`docs/system_architecture/system_architecture.rst:324-346`): `SUBMITTED` "Job submitted, awaiting scheduling";
  `DISPATCHED` "Job assigned to clients, processes starting"; `RUNNING` "Job actively executing"; `FINISHED_COMPLETED` "Job completed
  successfully"; `FINISHED_ABORTED` "Job aborted by admin request or by a failure classified as an abort"; `FINISHED_EXECUTION_EXCEPTION`
  "Job failed due to an execution exception, such as a launcher startup failure or a Kubernetes job pod stuck in ``Pending``/``Unknown``
  beyond ``pending_timeout``". `FINISHED:CANT_SCHEDULE` = job given up after `max_schedule_count` (`job.rst:400-403`).
  No in-tree doc defines `APPROVED`, `FINISHED_ABNORMAL`, `FAILED_TO_RUN`, `ABANDONED` beyond code usage (see section 3).
- **D3 terminality (client tools).** A status is terminal iff it starts with `FINISHED:` (or a legacy alias):
  `return isinstance(status, str) and (status.startswith("FINISHED:") or status in _TERMINAL_JOB_STATES)` (`nvflare/tool/job/job_cli.py:1926-1936`;
  `nvflare/fuel/flare_api/flare_api.py:81-107`). Only `FINISHED:COMPLETED` is success; every other `FINISHED:*` is reported as a failure
  (`job_cli.py:2769-2795`). Docs: exit code 1 for "a terminal failure state, such as ``FAILED``, ``FINISHED_EXCEPTION``, ``ABORTED``, or
  ``ABANDONED``" (`docs/user_guide/nvflare_cli/job_cli.rst:233-239`).
- **D4 one-shot / no re-scheduling.** "Once executed, the job status will be updated and won't be scheduled again." (`job.rst:342-345`).
  Only `SUBMITTED` jobs are scheduling candidates; any other status tags the job so it is never scanned again ("skip this job in all future
  calls") (`nvflare/apis/impl/job_def_manager.py:104-120`).
- **D5 writers (code-derived transition map; the spec `set_status` "Set status of an existing Job." states no transition rule,
  `job_def_manager_spec.py:221-230`, and `SimpleJobDefManager.set_status` is an unconditional merge `store.update_meta(..., replace=False)`,
  `job_def_manager.py:459-481`):**

  | From | To | Writer (file:line) |
  |---|---|---|
  | (new) | SUBMITTED | `job_def_manager.py:324,345` (create / clone) |
  | SUBMITTED | FINISHED:CAN_NOT_SCHEDULE | scheduler blocked/exceeded count, `job_scheduler.py:305-308` |
  | SUBMITTED | DISPATCHED | runner after deploy, `job_runner.py:669-670` (gated on SUBMITTED re-read at `:661`) |
  | DISPATCHED | RUNNING | runner after `_start_run`, `job_runner.py:711` (gated on DISPATCHED re-read at `:697`, before `_start_run`) |
  | SUBMITTED/DISPATCHED (deploy/start exception) | FINISHED:FAILED_TO_RUN | `job_runner.py:713-720` |
  | SUBMITTED, DISPATCHED | FINISHED:ABORTED | admin `abort_job`, `job_cmds.py:1061-1062` (status write only) |
  | RUNNING | FINISHED:COMPLETED / ABORTED / EXECUTION_EXCEPTION / ABNORMAL | `_job_complete_process`, `job_runner.py:484-492,524` |
  | RUNNING, DISPATCHED (server restart) | FINISHED:ABANDONED / FINISHED:ABNORMAL | `job_runner.py:762-796` (HA/restart, out of scope) |

- **D6 terminal classification of a finished RUNNING job** (`job_runner.py:484-492`, `:543-585`): if `job.run_aborted` -> `FINISHED_ABORTED`
  (takes precedence); else by the SJ's recorded return code: `INFRASTRUCTURE_ERROR(104)` -> `FINISHED_ABNORMAL`; `ABORTED(9)` ->
  `FINISHED_ABORTED`; `CONFIG_ERROR(103)`, `EXCEPTION(101)`, `UNSAFE_COMPONENT(102)`, `EXECUTION_ERROR(1)` -> `FINISHED_EXECUTION_EXCEPTION`
  ("An external failure (e.g. launcher resource timeout) marked the run as exception. Preserve that even if the SJ later reported a clean
  shutdown"); else if the SJ reported finish: exe-error -> `FINISHED_EXECUTION_EXCEPTION`, otherwise `FINISHED_COMPLETED`; never reported:
  `-9` -> `FINISHED_ABNORMAL`, otherwise `FINISHED_EXECUTION_EXCEPTION`. No exception record -> `FINISHED_COMPLETED` (`:545-546`).
- **D7 return codes.** `JobReturnCode(ProcessExitCode)`: `SUCCESS = 0`, `EXECUTION_ERROR = 1`, `ABORTED = 9`, `UNKNOWN = 127`
  (`nvflare/apis/job_launcher_spec.py:66-70`); `ProcessExitCode`: `EXCEPTION = 101`, `UNSAFE_COMPONENT = 102`, `CONFIG_ERROR = 103`,
  `INFRASTRUCTURE_ERROR = 104` (`nvflare/fuel/common/exit_codes.py:16-21`). Design doc meanings: `ABORTED` "Job was terminated/aborted.",
  `UNKNOWN` "Status cannot be determined (still running, or lost)." (`docs/design/job_launcher_and_job_handle.md:88-100`).
  Return-code resolution: RC file `_process_rc.txt` in the run dir first, else `job_handle.poll()`; a launcher `INFRASTRUCTURE_ERROR`
  wins (`nvflare/private/fed/utils/fed_utils.py:547-564`; design doc `job_launcher_and_job_handle.md:217-225`).
- **D8 authoritative failure / precedence.** `fail_run` "establishes an authoritative terminal failure. Remaining client reports cannot change
  that status and must not hold terminal publication behind the normal outcome grace period (900 seconds by default)" (`job_runner.py:837-840`);
  it never overwrites a recorded `INFRASTRUCTURE_ERROR` and an `ABORTED` never overwrites an existing code (`job_runner.py:828-833`); the SJ's
  own exit code does not overwrite an externally recorded one (`server_engine.py:223-232`). Release note: "An explicit job abort that wins the
  terminal-state race remains ``ABORTED``." (`docs/release_notes/flare_290.rst:571-572`).
- **D9 client outcome wait (`client_outcome_wait_timeout`).** "# server: max time to wait for client terminal outcomes after the server
  process exits" (`fl_constant.py:580-581`), default `900.0` read once in `JobRunner.__init__` (`job_runner.py:109-111`). After the SJ exits,
  terminal status is deferred while client outcomes are pending (unless the server failed or the run was aborted) until the deadline
  (`job_runner.py:455-481`). Client outcomes: CJ exit reported via `REPORT_JOB_FAILURE` (`client_executor.py:647-674`);
  codes `CONFIG_ERROR/EXCEPTION/INFRASTRUCTURE_ERROR/ABORTED` -> `fail_run`, `UNSAFE_COMPONENT` -> `stop_run`, all resolve the outcome
  (`nvflare/private/fed/server/fed_server.py:942-957`); a missing outcome from a dead/missing client after the SJ ended ->
  `fail_run(INFRASTRUCTURE_ERROR)` (`fed_server.py:1086-1094`, `:1105-1106`).
- **D10 publish-after-archive.** "# Publish terminal status only after artifacts are ready for download." (`job_runner.py:493`); workspace
  archival is retried for `WORKSPACE_SAVE_RETRY_GRACE_TIME = 60` s before publishing anyway (`job_runner.py:51`, `:494-522`). The job
  leaves `running_jobs` and `JOB_COMPLETED` (plus `JOB_ABORTED` for aborted) is fired only after `set_status` succeeds (`job_runner.py:523-538`).

### (e) Abort / cancel / delete semantics

- **E1 abort_job (admin).** Spec: `description="abort a job if it is running or dispatched"` (`nvflare/private/fed/server/job_cmds.py:218-225`);
  docs: "Aborts the job of the specified job_id if it is running or dispatched" (`docs/user_guide/admin_guide/deployment/operation.rst:42`).
  Code (`job_cmds.py:1051-1084`): status `SUBMITTED` or `DISPATCHED` -> `set_status(FINISHED_ABORTED)` only, message "Aborted the job {job_id}
  before running it."; status `FINISHED:*` -> "already completed"; otherwise `job_runner.stop_run` -> `_stop_run` (abort to connected
  participants + abort SJ) and `mark_run_aborted` (sets `job.run_aborted = True` if in `running_jobs`, else error "Job {job_id} is not
  running.") (`job_runner.py:798-811`). The runner re-reads status before deploy (SUBMITTED) and before start (DISPATCHED) and skips the job
  if it changed (`job_runner.py:661-663`, `:697-701`).
- **E2 server-side abort mechanics.** `abort_client_run` sends TrainingTopic.ABORT with a 2.0 s optional timeout and ignores replies ("There isn't
  much we can do here if a client didn't get the message or send a reply", `job_runner.py:395-413`). `abort_app_on_server` sends ABORT to the
  SJ (1.0 s) and starts a non-daemon cleanup thread (`server_engine.py:354-383`) that waits up to 10 s (0 s if the command failed) for the
  run process to end and then "always call terminate() for the captured job handle. For launcher-managed jobs this is the resource cleanup
  path, not only a force-kill path." (`server_engine.py:385-409`).
- **E3 client-side abort.** `ClientEngine.abort_app`: "A CJ reports STOPPED after its runner returns, before process-local archival and
  communication teardown finish. Keep treating it as a live job while the executor still owns its handle so a server-side failure can reclaim
  a CJ that hangs in that final teardown window." (`client_engine.py:390-404`). `JobExecutor.abort_app` marks abort requested; STARTING ->
  terminate immediately (a `_PendingJobHandle` "Hold[s] an abort request until a launcher returns the real job handle",
  `client_executor.py:52-77`, `:299-320`); STARTED -> send ABORT to the CJ then terminate after <= 10 s if still registered; STOPPED ->
  terminate after <= 10 s (`client_executor.py:486-601`).
- **E4 heartbeat reconciliation.** "Each FL client periodically sends heartbeat messages to the FL server. The message contains the job IDs of the
  jobs that the client is running. ... If there is a discrepancy with the client running a job that should not be running, the server will ask
  the client to abort it." (`job.rst:355-358`). Code: `# jobs that are running on client but not on server need to be aborted!`
  (`fed_server.py:1004-1017`), with the keep-alive rule "Keep normally completed jobs alive until clients report their outcomes, but do not
  protect client jobs after the server job has already failed." (`fed_server.py:1012-1016`); client aborts them with
  `heartbeat_cleanup=True` (`communicator.py:640-649`). `sync_client_jobs_require_previous_report` (default true) "Requires a prior positive
  heartbeat report before treating "missing job on client" as a dead-job signal." (`timeouts.rst:2454-2456`; code `fed_server.py:1019-1069`).
- **E5 resource cancel.** See A2/B3. Only the two scheduler post-check rejection paths call cancel (`job_scheduler.py:229-254`); cancel is sent
  only for `(True, token)` results (`server_engine.py:1056-1064`).
- **E6 delete_job.** Spec: `description="delete a job and persisted workspace"` (`job_cmds.py:210-217`); docs: "Delete the job from the job store"
  (`operation.rst:47`). Code: refuses `DISPATCHED`/`RUNNING` ("job: {job_id} is running, could not be deleted at this time.",
  `job_cmds.py:516-521`), otherwise `job_def_manager.delete(job_id)` (`job_cmds.py:523-535`), i.e., SUBMITTED and FINISHED:* jobs are deletable.
  `SimpleJobDefManager.delete` removes the store object; `get_job` of a missing job returns `None` (`job_def_manager.py:354-356`, `:379-385`).
- **E7 list_jobs.** Spec: `description="list submitted jobs"` (`job_cmds.py:179-188`); docs: "Lists the jobs on the server." (`operation.rst:39`);
  scoped to the active study (`operation.rst:19-21`). Code reads `get_all_jobs` and reports the stored status (`job_cmds.py:435-505`); the
  displayed status is whatever the last `set_status` wrote (no derived state).
- **E8 run-deletion on clients.** `_delete_run` sends DELETE_RUN to clients and removes the server run folder (`job_runner.py:415-439`); client
  `delete_run` removes the run dir (`client_engine.py:482-487`). `delete_workspace` admin command is disabled (`job_cmds.py:163-171`).


### (f) Process exit / cleanup semantics

- **F1 handle contract.** `JobHandleSpec.terminate` "To terminate the job run."; `poll` "To get the return code of the job run.";
  `wait` "To wait until the job run complete." (`nvflare/apis/job_launcher_spec.py:79-105`). Design doc: `terminate()` "Stop the job
  immediately."; `poll()` "Non-blocking query for current return code. Returns `UNKNOWN` while running."; `wait()` "Block until the job
  finishes." (`docs/design/job_launcher_and_job_handle.md:49-53`). `launch_job` "Start a job and return its handle." (`:59-61`).
- **F2 process implementation.** Spawn in a new session: `os.posix_spawn(path, cmd_args, env, setsid=True)`, else
  `subprocess.Popen(..., preexec_fn=os.setsid)` (`nvflare/utils/process_utils.py:319-352`). `ProcessAdapter.terminate` "Terminate the process
  group. Sends SIGKILL to the entire process group." (`process_utils.py:226-232`); a vanished process/group is treated as success
  (`:300-316`). `poll` "None if process is still running, otherwise the exit code." (`:234-243`); for posix_spawn pids an already-reaped
  pid is "treat[ed] as terminated" with code `-1` (`:268-274`). `ProcessHandle.poll` maps `None -> UNKNOWN` and only `{0: SUCCESS, 1:
  EXECUTION_ERROR, 9: ABORTED}`, everything else -> `EXECUTION_ERROR` (`nvflare/app_common/job_launcher/process_launcher.py:29`, `:51-55`).
  Design doc: `poll()` "Maps exit code: 0 → `SUCCESS`, 1 → `EXECUTION_ERROR`, 9 → `ABORTED`, `None` → `UNKNOWN`." (`job_launcher_and_job_handle.md:248`);
  comparison table: process "Start verification | None", "Terminate | Process signals" (`:514-515`).
- **F3 child-recorded RC.** The job process writes `_process_rc.txt` exclusively-create ("Never replace that result with main_func's later
  implicit success value.") when it has to hard-exit with lingering threads (`nvflare/fuel/f3/mpm.py:180-199`); the parent prefers that file
  and deletes it (`fed_utils.py:547-564`).
- **F4 SJ exit (server parent).** `wait_for_complete`: `process.wait()`, wait <= 2 s for the SJ's `UPDATE_RUN_STATUS`, compute the return code,
  record non-zero codes in `exception_run_processes` unless an external code is already recorded, then `self.run_processes.pop(job_id, None)`
  (`nvflare/private/fed/server/server_engine.py:203-234`). `UPDATE_RUN_STATUS` sets `PROCESS_FINISHED` (and `PROCESS_EXE_ERROR` on
  execution error) (`fed_server.py:594-604`). `_job_complete_process` treats "job in `running_jobs` but not in `run_processes`" as finished
  and runs the completion protocol of D6/D9/D10 (`job_runner.py:441-541`).
- **F5 CJ exit (client parent) = resource release point.** `_wait_child_process_finish`: `job_handle.wait()`; RC resolution; a generic RC 1
  without abort request is reclassified ("A generic RC 1 is actionable only while a checked-in worker is still active. STARTING remains an
  infrastructure failure", `client_executor.py:636-643`); report outcome to server (best effort, `job_query_timeout` default 5.0 s,
  `client_executor.py:194-196`, `:648-674`); then `free_resources(allocated_resource, token)` if non-empty, pop `run_processes`, fire
  `JOB_COMPLETED` (`client_executor.py:676-688`). Docs: "5. **End and clean up**: When the server signals the end of the run,
  ``ClientRunner`` completes the end-run sequence and the CJ terminates. The CP then frees the resources allocated to the job."
  (`docs/system_architecture/system_architecture.rst:226-227`).
- **F6 abort cleanup.** Server: abort always ends with `job_handle.terminate()` after <= 10 s (E2, `server_engine.py:385-409`). Client:
  terminate after <= 10 s if the job is still registered (`client_executor.py:581-601`); the CJ process exit then triggers F5.
- **F7 parent death.** SJ/CJ poll their parent pid and stop the runner when it disappears (`nvflare/private/fed/app/utils.py:45-50`,
  used at `nvflare/private/fed/app/client/worker_process.py:50,123` and `nvflare/private/fed/app/server/runner_process.py:65,126`).
- **F8 server-side artifacts.** Terminal status is published only after the run/result/log/audit dirs are archived via
  `job_manager.save_workspace` and removed ("Only remove sources after the complete set has been archived successfully.",
  `job_runner.py:587-631`), with the 60 s retry grace of D10. `JobRunner._delete_run` (client DELETE_RUN + server run-folder removal,
  `job_runner.py:415-439`) has no caller in the tree.
- **F9 SYSTEM_END.** The reservation-expiry thread is stopped on `SYSTEM_END` (`auto_clean_resource_manager.py:96-100`); the runner
  stops scheduling on `SYSTEM_END` (`job_runner.py:134-135`, `:741-742`).

### (g) Documented limitations / caveats

- **G1** Resource checks are advisory to NVFlare only: "Note that this check is solely done by the ResourceManager, so if the resource manager
  tells the FL server that the resource is enough, NVFlare will assume that it is OK to start the job on that site." / "If outside of NVFlare
  another process occupied the resources and the resources became unavailable that might lead to the failure of job execution at runtime."
  (`docs/programming_guide/resource_manager_and_consumer.rst:17-20`); GPU manager does not re-probe (`:99-101`).
- **G2** Server resources are never checked: "The default scheduler assumes that server resources are sufficient."
  (`docs/system_architecture/system_architecture.rst:200-201`; code `job_scheduler.py:178`, `server_engine.py:1013-1015`).
- **G3** Non-strict start mode does not enforce `min_sites`/`required_sites` for start timeouts ("so startup problems can go undetected",
  `docs/programming_guide/timeouts.rst:2460-2463`).
- **G4** Sync is eventual: "in a distributed system, it is impossible to keep all parts of the system in sync at all times. For example, when
  deploying or starting the job, some clients may succeed while others may fail. NVIDIA FLARE implements a heartbeat-based mechanism for the
  system to keep in sync most of the time. In case they become out of sync, the mechanism can also gradually bring the parties back in sync."
  (`docs/user_guide/core_concepts/job.rst:349-353`).
- **G5** Portable CPU/memory are launcher-enforced only: "CPU and memory are enforced by the selected job launcher rather than reserved by the
  site's NVIDIA FLARE resource manager." (`job.rst:111-112`); enforcement exists only in Docker/K8s/Slurm launchers
  (`nvflare/app_opt/job_launcher/docker_launcher.py:582-690`, `k8s_launcher.py:1056-1210`, `slurm/launcher.py:113-129`); the default
  `ProcessJobLauncher` ignores them (`process_launcher.py:66-83`). The design doc lists the process backend's resource manager as
  `GPUResourceManager` and GPU config as "`GPUResourceManager` / `CUDA_VISIBLE_DEVICES`" (`job_launcher_and_job_handle.md:512-513`).
- **G6** Process launcher has no start timeout / start verification (`job_launcher_and_job_handle.md:514`, `:653`).
- **G7** Orphan recovery is future work for container/scheduler backends: "Docker, Kubernetes, and Slurm do not terminate workloads that survive
  an SP/CP restart." (`job_launcher_and_job_handle.md:661-662`); "Unified cleanup" is future work (`:651`).
- **G8** Scheduler parameters trade-off: `max_schedule_count` too small => "the job may be given up prematurely ... if the resources could be
  freed up by running jobs" (`job.rst:400-403`); guidance `min_schedule_interval * max_schedule_count` slightly larger than the longest job
  (`job.rst:422-423`).
- **G9** Isolation claim: "This design allows multiple jobs to be running in their isolated space at the same time. The success or failure of a
  job won't interfere with the execution of other jobs." (`docs/user_guide/admin_guide/configurations/job_configuration.rst:12-14`).
- **G10** Deleting a job with a submit token leaves a `job_deleted` record (`docs/user_guide/nvflare_cli/job_cli.rst:156-159`).


## 3. Doc/code disagreements and ambiguities

### 3.1 Documentation disagrees with code / templates

- **X1 POC default resource manager.** Docs: "For example, the default in POC looks like: ... `"args": { "num_of_gpus": 1, "mem_per_gpu_in_GiB": 4 }`"
  then "This means they specify this site has 1 GPU and memory per GPU is 1 GiB." (`docs/programming_guide/resource_manager_and_consumer.rst:60-84`;
  also internally inconsistent 4 vs 1). Actual POC/provisioned default: `num_of_gpus: 0`, `mem_per_gpu_in_GiB: 0`, `expiration_period: 300`
  (`master_template.yml:72-80` + `static_file.py:436-441` + `dummy_project.yml` has no `capacity`).
- **X2 "stay in the queue" vs give-up.** "Otherwise, the job will stay in the queue." (`resource_manager_and_consumer.rst:15`) vs
  `FINISHED:CAN_NOT_SCHEDULE` after `max_schedule_count` attempts (`job_scheduler.py:347-354`, `:305-308`; documented at `job.rst:400-403`).
- **X3 status literal.** Docs "FINISHED:CANT_SCHEDULE" (`job.rst:403`) vs value `"FINISHED:CAN_NOT_SCHEDULE"` (`nvflare/apis/job_def.py:36`).
- **X4 back-off wording.** "The job will be retried no less than the ``min_schedule_interval``, and no less than the max." (`job.rst:405-406`)
  vs `required_interval = min(self.max_schedule_interval, (2**n) * self.min_schedule_interval)` (`job_scheduler.py:359`), i.e., the wait is
  capped at the max (not "no less than the max").
- **X5 "all relevant sites".** "For a job to be runnable, all relevant sites must be able to support its resource requirements." (`job.rst:105`)
  vs dispatch to the subset of sites whose check succeeded when `min_sites` and required sites are satisfied (`job_scheduler.py:212-261`;
  consistent with `job.rst:279-280`).
- **X6 portable resources on the default path.** "``resource_spec["@default"]`` applies to every targeted site, including the server." and
  "CPU and memory are enforced by the selected job launcher" (`job.rst:111-114`) vs: the scheduler never checks the server
  (`job_scheduler.py:178`, `server_engine.py:1013-1015`), `get_resource_manager_spec` drops CPU/memory (`job_launcher_utils.py:318-319`),
  and the default `ProcessJobLauncher` does not read `resource_spec` (`process_launcher.py:66-83`). On the local-process path these fields
  are validated at submission only (`job_meta_validator.py:57,284`).
- **X7 config location.** "This configuration is included in the fed_client.json of the FL Client's Startup Kit." for resource manager/consumer and
  "fed_server.json" for the scheduler (`docs/programming_guide/system_architecture.rst:70-72,97-99,112`), and "NVIDIA FLARE provides a simple
  resource manager that manages resources as a list of items: ListResourceManager" (`:103-105`) vs the template placing them in
  `local/resources.json.default` with `GPUResourceManager` (`master_template.yml:61-99,182-240`; `site_policy_management.rst:70` says they
  "are now moved to local resources.json.default").
- **X8 site-policy example is not constructible / mismatched.** Server example `"max_jobs": 1` (`site_policy_management.rst:101-108`) vs template
  `4` (`master_template.yml:214`). Client example pairs `ListResourceManager` with `GPUResourceConsumer` and passes `"gpu_resource_key": "gpu"`
  (`site_policy_management.rst:137-158`), but `GPUResourceConsumer.__init__(self)` takes no arguments and expects `{gpu_id: mem}`
  (`gpu_resource_consumer.py:22-33`), while `ListResourceManager` allocates `{"gpu": [ids]}` (`list_resource_manager.py:69-76`); the matching
  consumer is `ListResourceConsumer` ("This class can be used with ListResourceManager.", `list_resource_consumer.py:40-45`).
- **X9 strict start semantics.** Constant comment: "require all start-job replies to be non-timeout and OK before considering the run started"
  (`fl_constant.py:574-575`) vs strict mode tolerating timeouts of non-required clients when `min_sites` still holds (`job_runner.py:324-343`;
  docs `timeouts.rst:2464-2466`, `flare_272.rst:308-312`).
- **X10 where SP-side flags are read.** `strict_start_job_reply_check`, `client_outcome_wait_timeout` and
  `sync_client_jobs_require_previous_report` are documented under "**application.conf** (job-level)" (`docs/user_guide/timeout_troubleshooting.rst:287-296`)
  and `ConfigVarName` says "These variables can be set in job config files (config_fed_server or config_fed_client)" (`fl_constant.py:539`), but they
  are read by the server parent (`job_runner.py:109-111,313-317`, `fed_server.py:1019-1023`) via
  `ConfigService.get_*_var(..., conf=SystemConfigs.APPLICATION_CONF)`. The `APPLICATION_CONF` section is only added from the job config inside the
  job process (`nvflare/private/fed/server/server_json_config.py:187-197`); the SP's `ConfigService` only loads startup/resources sections
  (`nvflare/private/fed/app/fl_conf.py:195-203`). Effective SP sources are therefore SP `--set` vars / `NVFLARE_*` env
  (`config_service.py:305-321`). `client_outcome_wait_timeout` is also read once at `JobRunner` construction and cached (`config_service.py:258-264`).
- **X11 abort_job scope.** "abort a job if it is running or dispatched" (`job_cmds.py:220`; `operation.rst:42`) vs code also aborting SUBMITTED
  jobs and, for SUBMITTED/DISPATCHED, only writing `FINISHED_ABORTED` without sending any stop signal (`job_cmds.py:1061-1066`).
- **X12 lifecycle table incomplete.** `system_architecture.rst:324-346` lists 6 states; code defines 11 (`job_def.py:26-38`). `APPROVED` is defined
  but never written anywhere in `nvflare/` (only `job_def.py:29`), although docs mention "submitted, approved, running, completed"
  (`job.rst:99`) and "new submitted / approved jobs" (`job.rst:330`); `get_jobs_to_schedule` returns only SUBMITTED (`job_def_manager.py:113-120`).
  `FINISHED_EXECUTION_EXCEPTION` "such as a launcher startup failure" (`system_architecture.rst:343-346`) vs a process-launch exception inside
  `_start_run` producing `FAILED_TO_RUN` (`server_engine.py:315`, `job_runner.py:713-720`).
- **X13 scheduler spec docstring.** "Returns: A tuple of (job, sites_dispatch_info, failed_jobs, blocked_jobs)" (`job_scheduler_spec.py:53-56`) vs the
  annotated and implemented 2-tuple (`job_scheduler_spec.py:45`, `job_scheduler.py:287-311`).
- **X14 expiration units / types.** "expiration_period (int): Number of seconds to hold the resources reserved" (`auto_clean_resource_manager.py:34-36`)
  vs a per-`check_period` tick counter (`:102-116`): lifetime is ~`expiration_period * check_period`, equal to seconds only for the default
  `check_period=1.0`. `GPUResourceManager` accepts `expiration_period: Union[int, float]` with `>= 0` (`gpu_resource_manager.py:80,107-110`) but the
  base class rejects non-int or `<= 0` (`auto_clean_resource_manager.py:42-45`).
- **X15 "always answers Yes".** "The FL client always answers "Yes" when asked whether it can run a job without required resources." (`job.rst:264-265`)
  vs `No` when a `BEFORE_CHECK_RESOURCE_MANAGER` handler sets a block reason or the manager raises (`scheduler_cmds.py:77-88`). Also, even an empty
  requirement creates a token and a (empty) reservation entry that lives until allocate/cancel/expiry (`auto_clean_resource_manager.py:127-131`).
- **X16 consumer timing.** "Once the job is started on the client, it will call the Resource Consumer" (`job.rst:290-292`) vs consume happening before
  `start_app` in the CP by mutating process-global `os.environ` (`scheduler_cmds.py:119-122`, `gpu_resource_consumer.py:33`), copied at spawn
  (`process_launcher.py:68`). The "each concurrent job will be using different GPU devices" guarantee (`job.rst:315-316`) therefore also depends on
  START_JOB handling for different jobs not interleaving between `consume` and `os.environ.copy()` in one CP (not verified).

### 3.2 Ambiguous or unspecified behavior (no in-tree contract found)

- **U1 reservations of dispatched-but-unused sites.** Docs promise cancel only when "the Job Scheduler decides the job is not runnable"
  (`job.rst:284-286`). No doc covers reservations for: sites that fail/time out at deploy (`job_runner.py:692-695`), a job skipped because its status
  changed after scheduling (`job_runner.py:661-663,697-701`), deploy/start exceptions (`job_runner.py:713-731`), or late CHECK replies that the server
  recorded as `(False, "")` (`server_engine.py:1039-1040`; cancel requires `is_resource_enough and token`, `:1058`). In code these are reclaimed
  only by expiry (A6; 300 ticks by default). Deployed-but-unstarted client apps are also not removed (`_delete_run` has no caller, F8).
- **U2 max_jobs accounting window.** "how many jobs at the maximum are allowed at the same time" (`job.rst:397-398`) does not say whether a job whose
  SJ has exited but whose terminal status is pending (client-outcome wait up to 900 s, archival retry up to 60 s) counts. Code: it keeps its slot until
  `JOB_COMPLETED`/`JOB_ABORTED` (`job_scheduler.py:275-285`, `job_runner.py:455-538`). A scheduled job is not counted until `JOB_STARTED`
  (`job_runner.py:364`), which is safe only because the runner loop is single-threaded (`job_runner.py:641-731`).
- **U3 partial tolerance vs disconnection.** Tolerance (`min_sites`/required) is applied to deploy failures/timeouts (C3) and strict-mode start timeouts
  (C5), but a scheduled client that is no longer registered at deploy makes `_deploy_job` raise "unknown clients" (`job_runner.py:222-226`;
  `client_manager.py:445-459`), and at start a missing client yields fewer replies than sites, which raises "not enough replies" (`admin.py:104-105`;
  requests built only for resolvable clients, `server_engine.py:1077-1079`). Any explicit error reply from a non-required client also fails the whole
  job (C4). Docs do not state which of these is intended.
- **U4 participants views.** After start exclusions `job.meta[JOB_CLIENTS]` shrinks (`job_runner.py:355-358`) but the SJ's `PARTICIPANTS`
  (returned to the SJ via `GET_CLIENTS`, `fed_server.py:584-593`) stays the pre-start set (`server_engine.py:318-326`). No doc says which is
  authoritative.
- **U5 signal exits.** `ProcessHandle.poll` maps negative (signal) codes to `EXECUTION_ERROR` (`process_launcher.py:55`), so a SIGKILLed process is not
  `ABORTED` (value 9 is exit status 9) and the `-9 -> FINISHED_ABNORMAL` branch (`job_runner.py:569-571`) is unreachable for process-launched SJs
  unless `-9` comes from the RC file. Design doc: `ABORTED` "Job was terminated/aborted." (`job_launcher_and_job_handle.md:94`).
- **U6 status write discipline.** Neither `JobDefManagerSpec.set_status` (`job_def_manager_spec.py:221-230`) nor `SimpleJobDefManager.set_status`
  (`job_def_manager.py:459-481`) constrains transitions (blind merge). Docs only imply terminality/one-shot (`job.rst:342-345`).

### 3.3 Code-vs-contract tensions worth modeling (static reading only; NOT verified, no reproduction attempted)

- **T1 abort_job vs runner status writes (Q3).** `abort_job` on DISPATCHED writes `FINISHED_ABORTED` (`job_cmds.py:1061-1062`); the runner re-checks
  DISPATCHED only before `_start_run` (`job_runner.py:697-701`) and writes `RUNNING` unconditionally after it (`job_runner.py:709-711`); likewise
  SUBMITTED is re-checked before `_deploy_job` (`:661`) and `DISPATCHED` is written unconditionally after it (`:670`). An abort landing inside
  deploy/start could be overwritten (terminal -> non-terminal) and the job would run, contradicting E1/B10/D3.
- **T2 deleting a SUBMITTED job during scheduling (Q4).** `delete_job` permits SUBMITTED (`job_cmds.py:516`); the runner then calls
  `_check_job_status`, which dereferences `job_manager.get_job(...)` (returns `None` for a deleted job, `job_def_manager.py:379-385`,
  `filesystem_storage.py:310-327`) outside the loop's `try` (`job_runner.py:660-666`). An exception there (or from `get_jobs_to_schedule`,
  `:650`) would end `JobRunner.run`, which is started once (`nvflare/private/fed/app/deployer/server_deployer.py:136,144-145`), stopping all later
  admissions.
- **T3 non-exception start failures (Q1/Q4).** `StartJobProcessor` frees an allocation only when an exception is raised (`scheduler_cmds.py:122-133`),
  but `ClientEngine.start_app` returns strings for "Client app already started." and the missing-app error (`client_engine.py:357-367`); no CJ is
  launched on those paths, so the allocation would not be freed by F5 either. (No capacity effect with the default 0-GPU manager: allocation `{}`.)
- **T4 check/expiry vs allocate (Q1).** If START_JOB arrives after the reservation expired (A6), `allocate_resources` raises (A3) and the job fails
  (C4 -> `FAILED_TO_RUN`). This is consistent with A6 but means scheduler success does not guarantee allocation when deploy is slow.
- **T5 stale per-job state.** `exception_run_processes` entries are removed only by `_job_complete_process` for jobs in `running_jobs`
  (`job_runner.py:540`); FAILED_TO_RUN jobs and late `fail_run` calls for inactive jobs (`job_runner.py:823-836`, entry written before the
  `job_is_active` check) leave entries behind. Keys are unique job ids, so no cross-job effect was identified.
