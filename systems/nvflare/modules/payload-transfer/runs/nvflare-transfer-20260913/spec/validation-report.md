## Caller and configuration boundaries

The main corpus registers two refs before exposing them, declares exactly two receiver identities, enables confirmation at both endpoints, and uses a supported pipelining Consumer with one ordinary one-byte DATA unit. The producer is a supported test Downloadable whose `release` drops its owned `base_obj` reference. Actual raw epoch timestamps and a controlled integral clock are retained. Receiver budgets are normally 3 fixture seconds, transaction inactivity 10 (5 in the timeout scenario), forced drain 2, receipt retention 4 and finished-ref retention 9. Production operation drain is 60 seconds. Header values are actual fixture settings; they are not claims about universal defaults.

The actual `CellClientAPI._wait_for_result_transfers` helper is exercised with a minimal caller object. At `nvflare/client/cell/api.py:624-648`, it rejects terminal None and all non-COMPLETED outcomes. Its source-progress callback at `api.py:481-487` is a no-op used for tracking. The result publication path declares the downstream receiver count/identities at `api.py:497-550`. ViaDownloader finishes object registration before exposing the serialized refs (`nvflare/fuel/utils/fobs/decomposers/via_downloader.py:774-826`).

Phase 2.5 evidence is reused with verified provenance, not presented as new test execution: 11 separate caller/upstream profile tests passed, and three malformed validator-control copies were rejected. Ordinary two-target broadcast passes count 2 plus both identities; pass-through broadcast passes count 2 without final identities; fire-and-forget omits both in the observed encode call (`harness/logs/caller-profiles.json`). This is argument-propagation evidence with ordinary bytes, not a full externalized-payload success/lifetime reproduction. Legacy and disabled-confirmation tests retain their weaker producer-served contract.

## Remaining coverage limits

- The 94/94 action-name coverage does not imply complete branches, combinations or schedules. Existing pipeline failure traces do not contain the contradictory COMPLETED delivery found by S1; that exact runtime schedule remains unconfirmed.
- The existing enqueue/submit-exception trace observes two settlement chains and one receipt under a controlled `_adjust_thread_count` exception. It establishes behavior after that injected failure, not spontaneous production reachability. No resource-exhaustion experiment was performed.
- Real Cell/Consumer/DownloadService methods run in one process. In-process routing may bypass TCP; byte transports, serialization internals and deployment behavior are outside this evidence. The separately inspected pass-through E2E suite includes a simulated CJ hop and was not run here.
- Conditional `EventualSettlementObservation` is defined under `FairSpec` but is not enabled in the supplied finite safety configurations. This phase must not claim a liveness proof or universal waiter/shutdown time bound.
- The supplied S4 hunt checks the core receipt/confirmation/aggregation/cleanup/caller invariants while exercising budget transitions. It has no independent temporal oracle guaranteeing receiver-budget termination. Budget-scope conclusions therefore also rely on source mapping and the specifically observed functional traces.
- Concurrent timestamp publication remains a coverage question: `_Ref.mark_receiver_active` samples time before separately publishing under the ref and transaction stats locks (`download_service.py:441-450`). The model retains the captured request time and permits overlapping requests to publish those timestamps in a different order. The supplied cfgs do not assert monotonic receiver activity, and the existing corpus does not establish budget behavior for every such reordering. This is an unverified source/model coverage question, not an additional classified MC finding.
- Simulation uses a configured depth limit of 100. Long complete multi-ref transfer schedules can require more steps; a large number of sampled traces does not certify those longer schedules or scheduling fairness.
- No late object addition, transaction/ref reuse, nonce replacement/retry traffic, adversarial participants, hook reentrancy, process BaseException, HA, full trainer lifecycle or numerical/ML behavior is certified.
