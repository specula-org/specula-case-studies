## Issues Found

- **[P1] Budget candidate construction and finalization do not follow the implementation's two-pass control flow.** `base.tla:568-603` initializes `ftodo[Budget]` to all pairs, tests each candidate against the *current* final-status map, and immediately switches an eligible candidate to `recheck`/`commit`. The implementation first snapshots the ref's final receivers and constructs the complete `failures` list (`download_service.py:475-502`), then iterates that saved list to recheck activity and finalize (`504-514`). Consequently, two eligible receivers are selected before either is finalized in the source, while the model requires processing the first before selecting the second. A receiver finalized after the source snapshot can also still reach a rejected `_finalize_receiver` call; the model's fresh status test can remove that call entirely. The lazy abstraction is disclosed in `brief-coverage.md:53`, but it conflicts with the exact event/continuation contract in `instrumentation-spec.md:49,54,70,114-115` and `Trace.tla:585-600`. This is a trace-fidelity defect even where final outcomes coincide. **Repair:** represent the per-ref final snapshot, failure-list construction, and subsequent enforcement loop separately; derive trace bookkeeping from those actual locals.

- **[P2] Request and drain timestamps are sampled too late in the model.** `RefMarkReceiverActive` sets both `pullTime[p]` and `refLast[p]` to the current `st.now` at publication (`base.tla:195-213`). The source captures `now` *before* acquiring `_progress_lock`, then publishes that saved value under two successive locks (`download_service.py:441-450`). Similarly, `TransactionDoneDrainBegin` captures `drainAt` atomically with closing the gate (`base.tla:801-809`), whereas `_drain_ops` computes its deadline before acquiring `_ops_cond` (`download_service.py:841-849`). Time can advance while either lock is awaited. The current actions lose that elapsed time and reject the corresponding actual captured timestamps under `ValidatePostState`; a consistent clock scale does not remove this gap. **Repair:** split timestamp/deadline sampling from lock-protected publication and preserve the sampled local through subsequent steps. Update the mappings at `instrumentation-spec.md:78,133` accordingly.

- **[P2] Monitor timeout retirement retests current completion instead of using the implementation's earlier classification decision.** `MonitorRetireTimeout` requires `~Finished(st.status)` in the same transition that retires the transaction (`base.tla:664-677`). In the source, `is_finished()` returns before the inactivity comparison and deletion (`download_service.py:1875-1890`); already admitted finalizers update receiver status under `_progress_lock`, without reacquiring `_tx_lock` (`313-335,1796-1803`). Thus completion can change after the monitor's negative check but before timeout retirement. A source trace can contain that intervening final-status update followed by TIMEOUT retirement, which the model guard rejects. The monotone-scan explanation in `brief-coverage.md:52` does not provide an exact post-mutation trace point for this combined action: at the earlier check, retirement has not happened and the timeout decision is not yet known. **Repair:** preserve the completion-test result and timeout decision in monitor-local state, then retire using those decisions while representing the table-lock exclusion of new admissions.

- **[P2, coverage follow-up] Two temporal properties are defined but never configured for checking.** `FinalStatusesImmutable` (`base.tla:1304`) appears in no cfg. `EventualSettlementObservation` and its fair specifications (`base.tla:1406-1495`; `MC.tla:98-102`) likewise have no runnable property configuration. The latter formula is appropriate to this monotone, single-transaction model; the issue is wiring, not a temporal typo. The liveness deferral is explicitly disclosed in `brief-coverage.md:27`, so this is not a false execution claim and is not the primary reason for the verdict. Add an applicable immutability check and a separate liveness configuration with justified time/drain coverage and without receiver symmetry before claiming those properties checked. Do not simply enable liveness in the existing zero-time-budget safety hunts.

- **[P3] The subsequent-event schema example lacks a mandatory post-state field.** The `DownloadObjectStart` example in `instrumentation-spec.md:21-25` supplies `consumer` and `pullPC`, but omits `futureStarted`, required by `Trace.tla:65` and the mapping row at `instrumentation-spec.md:74`. Expanding its two functions to all four pairs, as instructed, still leaves an event that cannot match. Add the complete `futureStarted` function or explicitly label this example as an incomplete encoding fragment and provide a schema-valid example.

The principal S1/S3 extensions are otherwise well structured: receiver truth is distinct from served EOF and delivered progress; queued settlement survives submission failure without an assumed entry latch; callbacks, release attempts, and receipt ownership remain separate. These observations do not confirm either candidate as a runtime defect.
