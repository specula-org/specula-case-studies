## Source-established contracts and actual modes

- `ObjectDownloader.get_waiter()` explicitly promises an aggregate terminal outcome, with COMPLETED requiring every expected receiver to succeed; this is the primitive upper layers use for payload-delivery completion (`obj_downloader.py:98-105`). `transaction_done_cb` receives original base objects, not Downloadable wrappers (`obj_downloader.py:45-60`). Its status is a TransactionDoneStatus, whereas `outcome_cb` has the stronger success/failure meaning (`obj_downloader.py:48-50`).
- `ClientAPI` result acknowledgement is layered: CJ `RESULT_ACCEPTED` acknowledges the envelope; a managed trainer retains the real payload through all downstream DownloadService transactions (`client_api_execution_modes.md:229-249`). Actual `CellClientAPI.send` registers a waiter for each created transaction, checks envelope acceptance, waits for every outcome, then clears model resources only if all outcomes are COMPLETED (`client/cell/api.py:481-560,624-648`). A timed waiter return of None is not itself terminal failure; the caller re-reads `waiter.outcome` after `done()` to close a polling race (`api.py:632-640`).
- Failure after envelope acceptance invokes transaction deletion and invalidates re-submission state while preserving submitted model contents for inspection (`api.py:561-571`). Outcome completion, source-settled acknowledgement, and complete trainer shutdown are distinct transitions (`api.py:572-588`; design doc `:290-323`). The selected model should capture the transfer barrier, not full process management.
- Managed external result receiver identity comes from the task Shareable's `FOBSContextKey.RECEIVER_IDS` header (`api.py:869,926-933`); if missing, the actual sender passes `receiver_ids=None`, `num_receivers=1` (`api.py:501,536-537`). The backend's `server.<job>` fallback (`external_process_backend.py:1068-1077`) is used for accepted-source monitoring, not stamped back into the task sent to the trainer (`:978-992`). Therefore ordinary unstamped results are count-only even though the backend knows a monitoring destination.
- Swarm stamps the real aggregation-client job FQCN (`swarm_client_ctl.py:969-970`). A local result consumer/filter intentionally routes the result to CJ by stamping CJ FQCN (`client_api_executor.py:436-444`). Attach explicitly uses CJ as the materializing receiver (`api.py:498-501`; design doc `:270-279`). These paths must not be treated as equivalent ultimate receiver identities.
- Direct Cell `broadcast_request` encodes one shared payload with target count and explicit target identities; pass-through broadcasts keep the count but omit identities because first-hop targets are forwarders (`cell.py:303-317`). The task-ready API path declares the exact trainer FQCN for new CJ-owned payloads and records waiters only for cancellation cleanup (`external_process_backend.py:1273-1339`); accepted task reply is its materialization acknowledgement. Already-lazy forwarded refs do not create a new CJ-owned transaction.
- Per-call `_encode_message` constructs a fresh props dictionary, then a fresh FOBS context copy; it does not write transfer callbacks or receiver declarations into the shared Cell context (`cell.py:421-443`, `core_cell.py:570-579`). A generic `get_fobs_context()` call therefore cannot infer the destination list by itself.

Main model configuration should explicitly set cooperative receiver identities and receiver-confirmation enabled, as required by the target guidance. The production count-only paths above belong to separate mode/exclusion notes and the additional test candidate below. They must not be silently strengthened into explicit receiver contracts.

## Registration, batch, and timeout lifecycle

`_DecomposeCtx` deduplicates objects by identity inside a lock and allocates one item ID per object (`via_downloader.py:372-391`). Each decomposer type has its own collected batch (`:559-568`). Post-processing creates a Downloadable and ref datum for each type; only a final callback creates the transaction and registers all prepared refs (`:712-746,751-826`). This deliberately starts transaction lifetime after potentially slow source preparation. `Cell._send_request` only starts sending after `_encode_message` has returned (`cell.py:480-488`), so the ordinary encode path registers its refs before exposing the envelope. Model fixed refs at transfer start; do not invent forbidden late additions.

A pass-through hop creates `_LazyBatchInfo` and `LazyDownloadRef` without physical acquisition (`via_downloader.py:851-889,924-934`), then forwards the original FQCN/ref (`:510-538,828-849`). Mixing source batches within one decomposer type is now explicitly rejected (`:526-533`); do not revive the historical mixed-batch suspicion. Materialization groups lazy refs by `(dot,fqcn,ref_id)` and downloads a whole original batch once before replacing matching leaves (`:275-324`). Missing or None downloaded items fail explicitly (`:936-961`), retaining the historical incomplete-download fix.

The generic source inactivity timeout floor is `streaming_idle_timeout`, default 600 seconds (`transfer_progress.py:26-30`; `via_downloader.py:584-610`). The per-type min-download setting can override that fallback. An applicable progress-context override or message-root TTL is clamped to that min floor. `_MIN_DOWNLOAD_TIMEOUT=300` remains a compatibility constant; it is not the current unconditional source timeout. Download request timeout defaults to 600 seconds unless call-context/per-type configuration supplies it (`via_downloader.py:981-985`). ViaDownloader does not explicitly pass receiver budgets; ObjectDownloader forwards None and DownloadService resolves optional application config (`obj_downloader.py:65-78`, `download_service.py:263-267,728-731`). Thus receiver acquisition/idle budgets are not enabled merely by having a waiter. Exact identities enable meaningful acquisition budgets; `(None,)` is progress-only unknown-single-receiver metadata (`via_downloader.py:644-675,798-807`).

## Source lifetime and callback ordering

| Boundary | Evidence and implication |
|---|---|
| Terminal producer serve versus final receiver success | ViaDownloader returns only when `download_arrays` has completed Consumer processing (`np_downloader.py:130-142`). ItemConsumer updates its result during consume (`cacheable.py:249-260`); actual confirmation/terminal semantics reside in DownloadService. Do not collapse source serving and receiver materialization. |
| Cache clearing versus source release | `downloaded_to_all` and `transaction_done` clear cached chunks; `base_obj` remains until separate `release()` (`cacheable.py:92-120`). A cleared cache can regenerate chunks from live source (`:122-161`). Cache eviction is not source retirement. |
| In-flight source reads | CacheableObject reads cache/source under its own lock, then performs `produce_item` outside it (`:122-161`). ArrayDownloadable reads `self.base_obj` during production (`np_downloader.py:37-42`). The service activity gate, not the cache lock, normally protects settlement against active production. |
| Bounded drain | `transaction_done` drains operations for `OP_DRAIN_TIMEOUT=60` and explicitly proceeds if the bound expires (`download_service.py:257-260,895-910`). The source handler itself documents timeout/delete potentially releasing concurrently with slow production and returning a process exception (`:1711-1722`). CacheableObject's nearby statement that the race cannot open is too broad for this forced-settlement path (`cacheable.py:133-140`). Model bounded drain rather than assume every reader has finished before forced release. |
| Callback visibility | Settlement snapshots base objects, invokes per-object callbacks, then transaction_done_cb, then outcome_cb (`download_service.py:948-978`). Callbacks can inspect original data before release. Ordinary Exception failures are contained independently (`:645-655`). |
| Release before waiter publication | Each source release is attempted in finally, then outcome is recorded and waiters may wake (`download_service.py:984-1000`). A raising release cannot suppress sibling releases or recording. The contract guarantees release invocation order, not arbitrary user release implementation success. |
| Physical memory reclamation | `CacheableObject.release` drops base_obj; it cannot force collection of application references. Local settlement `base_objs` still exists until the function returns (`download_service.py:953,998-1002`). TensorDownloadable cancels queued prefetch futures and drops source state; already-running futures may retain task arguments until they return (`tensor_downloader.py:79-106`). A waiter is not a guarantee that all tensor memory has already been reclaimed. No defect is asserted solely from remaining caller/future references. |
| File source ownership | FileDownloadable inherits the no-op base release and stores a path; application owns the file (`file_downloader.py:37-83`, `Downloadable.release` at `download_service.py:193-201`). Consumer success closes the destination before returning (`file_downloader.py:181-221`). Do not model unconditional file deletion as a library guarantee. |

Additional exception-path note for code review, without a defect claim: `_process_items_to_datum` records manager errors but final callbacks still run; `_finalize_download_tx` can register previously prepared objects even when another type failed (`via_downloader.py:740-746,774-826`; `datum.py:149-168`). The encode then fails; tracked callers delete observed transactions, and untracked ones retain the source until their finite transaction timeout. This is bounded cleanup context, not evidence of an unresolved waiter.

## Current test-verifiable candidate TV-CALLER-1

**Missing receiver count on ordinary multi-target fire-and-forget.** `Cell._fire_and_forget` encodes a payload once with plain `self.get_fobs_context()` and only afterwards iterates the target list (`cell.py:344-379`). It supplies neither NUM_RECEIVERS nor RECEIVER_IDS. ViaDownloader then defaults to one unknown receiver (`via_downloader.py:774-807`). This differs from direct broadcast_request's explicit count/identity propagation (`cell.py:303-317`).

Full supported path: a local application uses auxiliary request timeout zero with `bulk_send=False` and two targets; AuxRunner resolves both job FQCNs and calls `Cell.fire_and_forget` with the complete list (`private/aux_runner.py:349-422`). Cell dispatch selects its streaming wrapper for ordinary auxiliary channels (`cell.py:49-55,246-263`). Its sender encodes once; `StreamCell.send_blob` only validates and sends the resulting byte payload and cannot repair transfer receiver metadata (`stream_cell.py:108-145`; `cellnet/utils.py:133-165`). A fresh Cell context supplies no implicit target-derived count (`core_cell.py:570-579`).

Ordinary scheduling question: receiver A consumes/confirms the complete payload before receiver B begins physical download. Count-only completion is now satisfied for each ref after A; `_handle_confirm` retires the transaction and removes all refs (`download_service.py:359-369,875-893,1782-1811,1411-1425,1525-1539`). B has no successful tombstone entry and is rejected when it starts (`:1687-1697`). The first receiver's own success is valid, but source lifetime/accounting used for the two-target call is too short.

**Status:** source-grounded functional candidate; no regression test or runtime reproduction in this phase. **Verification:** targeted local two-target supported fire-and-forget test with ordinary arrays and a controlled receiver-start gate; contrast direct broadcast_request and single-target call. This is straightforward argument propagation and belongs in Test-Verifiable/Code-Review-Only, not a costly MC scenario. Historical #4025 review already questioned this alternate path but did not repair or establish it; current source is the primary evidence. Keep it separate from the explicit-expected-receiver main scenario.

## False positives and limits

1. Do not treat CJ RESULT_ACCEPTED as downstream completion: actual send waits on all outcomes.
2. Do not treat cache eviction or `downloaded_to_all` as source reclamation; separate release ordering exists.
3. Do not recreate removed msg-root lifetime coupling or pre-fix incomplete-item decoding: both are historical fixed context.
4. Do not infer strict identity certification for count-only production paths; the supplied main scenario explicitly chooses identities.
5. Do not require final object-registration interleavings after envelope exposure: ordinary FOBS finalization registers refs first.
6. Do not interpret a blocking/hung user callback as supported nonblocking FINISHED callback behavior; callback pool documentation explicitly requires FINISHED callbacks not to block (`download_service.py:1429-1434`). Ordinary exceptions remain required coverage.
7. No complete trainer lifecycle, HA, scheduling, byte-transport implementation, serialization-internal correctness, or numerical behavior was investigated as a candidate.
