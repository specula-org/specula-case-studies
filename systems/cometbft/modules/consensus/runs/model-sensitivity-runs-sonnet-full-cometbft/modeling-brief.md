# Modeling Brief: cometbft/cometbft

## 1. System Overview

- **System**: CometBFT v0.38.19 — production BFT consensus engine used by Cosmos-ecosystem blockchains
- **Language**: Go, ~12,000 LOC consensus core (`consensus/state.go` 2799 lines, `consensus/reactor.go` 2010 lines)
- **Category**: **Category A (Distributed / Message-Passing) + BFT overlay** — network gossip, disk persistence, protocol state machine across validator nodes with f < n/3 Byzantine tolerance
- **Protocol**: Tendermint PBFT with proposer-based timestamps (PBTS), ABCI++ vote extensions (`ExtendVote`/`VerifyVoteExtension` callbacks added in v0.38)
- **Key architectural choices**:
  - Vote extension data is per-precommit, generated by `ExtendVote` ABCI call per vote, verified per-peer via `VerifyVoteExtension` ABCI call at consensus time — but light client and blocksync paths skip both crypto and ABCI verification
  - Evidence pool has a `consensusBuffer` flushed unconditionally on each `Update()` call, discarding unprocessed Byzantine evidence
  - WAL writes peer messages non-fsynced, own messages fsynced — asymmetric durability
  - Remote signer interface (`privval`) predates vote extensions; `extensionsEnabled` never transmitted on wire
- **Concurrency model**: Single `receiveRoutine` goroutine for all state machine writes; reactor gossip on separate goroutines per peer; `pingLoop` goroutine for remote signer keepalive

**Adversary dimensions (BFT)**:
- Corruption type: static; threshold `n ≥ 3f + 1`
- Network model: partial synchrony (post-GST)
- Authentication: authenticated with unforgeable honest signatures
- Byzantine behaviors: equivocation (double vote), invalid content in proposals, light-client forking attacks, censorship of evidence

## 2. Bug Families

### Family 1: Vote Extension Verification Asymmetry

**Mechanism**: The full-node consensus path applies two layers of verification per vote extension (cryptographic `VerifyExtension` + ABCI `VerifyVoteExtension`), but light client, block sync, and `ValidateBlock` apply zero extension verification. A commit containing fraudulent extension data is accepted unconditionally by all non-consensus code paths.

**Evidence**:
- Open Issue #5204: Chain deadlock when proposer's own vote extension fails `VerifyVoteExtension` — proposer's extension bypasses the ABCI call in `addVote` via address-equality shortcut. PR #5890 (proposer self-verify, open) and PR #5864 (predecessor, closed) address this but are not merged.
- Open Issue #2523: "Ensure that all vote extensions in the commit info are verified" — maintainer-acknowledged gap.
- Open Issue #3642: `extensionsEnabled` never transmitted to remote signer; signer decides extension signing from vote content alone.
- Code analysis: `light/verifier.go:57,72-75,125-128` — all three `VerifyAdjacent`/`VerifyNonAdjacent`/`Verify` paths call `VerifyCommitLight*` which never touches `ExtensionSignature` on any `CommitSig`.
- Code analysis: `state/validation.go:92-95` — `VerifyCommit` on `block.LastCommit` verifies precommit signatures only; `ExtensionSignature` fields are not present in `Commit` (stripped by `ExtendedCommit.ToCommit()`).
- Code analysis: `blocksync/reactor.go:531` (TODO comment) and lines 548-554 — extension presence checked via `EnsureExtensions`; individual extension signatures never verified cryptographically.
- Code analysis: `state/execution.go:167-189` — `ProcessProposal` ABCI call builds commit info without extension data; validators running `ProcessProposal` cannot validate extensions from the previous commit.
- Code analysis: `consensus/state.go:2303-2334` — the `!bytes.Equal(vote.ValidatorAddress, myAddr)` guard skips ABCI `VerifyVoteExtension` for votes claiming the local validator's address (regardless of actual origin), bypassing application-level extension validation for any peer-crafted vote matching the local address.

**Affected code paths**:
- `consensus/state.go:addVote()` — extension verification, self-vote skip guard
- `consensus/state.go:signVote()` — extension generation via `ExtendVote`
- `light/verifier.go:VerifyAdjacent/VerifyNonAdjacent/Verify` — no extension verification
- `state/validation.go:verifyCommitLightInternal/verifyCommitLightTrustingInternal` — no extension verification
- `blocksync/reactor.go:handlePeerResponse()` — presence check only, no signature verification
- `state/execution.go:processProposal()` — extension data absent from `ProposedLastCommit`

**Suggested modeling approach**:
- Variables: `extensionSig[validator][height][round]` to track per-vote extension data; `extVerified[validator][height][round]` as a per-node boolean for whether ABCI verification succeeded
- Actions: Split `AddVote` into `AddVoteFromPeer` (must call `VerifyVoteExtension`) and `AddVoteFromSelf` (currently skips ABCI check) to expose the asymmetry; add `LightClientVerify` action that skips extension signature check
- Invariant: `ExtensionInCommitWasVerified` — every extension in a committed `ExtendedCommit` was ABCI-verified by the committing node before inclusion

**Priority**: High
**Rationale**: Three open issues, confirmed code gap, maintainer-acknowledged problem. The asymmetry between consensus-time verification and light-client/blocksync acceptance is a non-trivial protocol question: can a Byzantine proposer produce a commit where extensions pass consensus but would fail verification if a light client were to check? TLA+ is well-suited to exploring this cross-path state space.

### Family 2: Double-Sign Protection Off-by-One

**Mechanism**: `checkDoubleSigningRisk` uses strict less-than `i < doubleSignCheckHeight` instead of `i <= doubleSignCheckHeight`, checking one fewer past commit than configured. At `height = 1` (first block of a chain or after `InitialHeight = 1`), the loop `for i := 1; i < 1` never executes, providing zero lookback regardless of configuration.

**Evidence**:
- Open Issue #5435: "double_sign_check_height = 1 does not perform any double sign checks" — filed and triaged (COMET-317).
- Open PR #5668: "fix(consensus): correct loop condition in checkDoubleSigningRisk for height=1" — approved by maintainer `aljo242`, not yet merged.
- Code analysis: `consensus/state.go:2647` — `for i := int64(1); i < doubleSignCheckHeight; i++` where `doubleSignCheckHeight` is `min(config.DoubleSignCheckHeight, height)`. At `height=1`, this is `for i:=1; i<1`, never executes.
- Code analysis: `consensus/state.go:2640-2644` — guard `height > 0 && cs.config.DoubleSignCheckHeight > 0` is satisfied at height 1, but the loop still runs 0 iterations.

**Affected code paths**:
- `consensus/state.go:checkDoubleSigningRisk()` — called from `receiveRoutine` on start (line 399)
- Recovery path after node restart without WAL at chain start height

**Suggested modeling approach**:
- Variables: `safetyState[validator][height]` tracking whether the node has checked for double-signing risk; `walPresent[validator]` for WAL availability on restart
- Actions: `RestartWithoutWAL` where double-sign check runs but loop executes 0 iterations at height 1; model privval's `LastSignBytes` as a separate persistent safety guard
- Invariant: `NoDoubleSign` — a validator with `DoubleSignCheckHeight > 0` never signs conflicting votes for any height within the lookback window on restart

**Priority**: Medium
**Rationale**: Confirmed off-by-one with approved fix pending merge. The practical question for TLA+ is whether the WAL and privval's `LastSignBytes` independently prevent double signing at height 1, or whether the combination of the loop bug + a specific restart scenario creates a real safety window.

### Family 3: Evidence Hash Collision via Off-by-One

**Mechanism**: `LightClientAttackEvidence.Hash()` copies only `tmhash.Size - 1 = 31` bytes of the conflicting block's 32-byte hash before hashing, zeroing the last byte. Two distinct attack evidences whose conflicting-block hashes differ only in the last byte produce the same evidence hash, making them indistinguishable in the pool's deduplication keying.

**Evidence**:
- Open Issue #5902: "Evidence `Hash` is 1byte off" — filed 2026-05-29, not yet triaged.
- Code analysis: `types/evidence.go:326` — `copy(bz[:tmhash.Size-1], l.ConflictingBlock.Hash().Bytes())` — confirmed, `tmhash.Size - 1 = 31` bytes copied instead of 32. Position `bz[31]` remains zero; extension field at `bz[32:]` is correct.
- Code analysis: `evidence/pool.go:224-228` — pool uses `evidence.Hash()` for deduplication via `keyPending` and `keyCommitted` DB keys.
- Code analysis: `evidence/pool.go:461-538` — `consensusBuffer` processing: if the block height has advanced more than 1 step since the vote was buffered, the buffer entry is discarded with a log error but no retry. Unbuffered Byzantine votes from `ReportConflictingVotes` are permanently lost.

**Affected code paths**:
- `types/evidence.go:LightClientAttackEvidence.Hash()` — key computation
- `evidence/pool.go:AddEvidence()`, `addToCache()`, `checkEvidence()` — deduplication
- `evidence/pool.go:processConsensusBuffer()` — evidence from `ReportConflictingVotes`

**Suggested modeling approach**:
- Variables: `evidencePool[validator]` as a map from evidence key → evidence record; `hashCollision` flag for when two distinct evidences map to the same key
- Actions: `SubmitLightClientEvidence` where the key is the (buggy) truncated hash; `DuplicateEvidenceFiltered` where the second valid evidence is suppressed by collision
- Invariant: `EvidenceDeduplicationCorrect` — distinct `LightClientAttackEvidence` entries with different conflicting blocks are never mapped to the same pool key

**Priority**: High
**Rationale**: Confirmed implementation bug (off-by-one, open issue). The consequence — evidence deduplication bypass or suppression — is a direct accountability correctness concern in a BFT system. TLA+ is suited to ask: can a Byzantine node suppress honest evidence by pre-populating the pool with a hash-colliding entry?

### Family 4: Blocksync Peer State Manipulation

**Mechanism**: `pool.maxPeerHeight` is raised unconditionally by any peer-reported height with no upper-bound check. `IsCaughtUp()` compares local height against `maxPeerHeight`, so a malicious peer inflating this field can indefinitely delay the transition from blocksync to consensus mode.

**Evidence**:
- Open Issue #5801: "Malicious Peer Can Disrupt Blocksync Synchronization" — filed 2026-06-03; security advisory GHSA-22qq-3xwm-r5x4 referenced.
- Open PR #5880: "IsCaughtUp must stay false when all peers are pruned ahead" — not merged.
- Code analysis: `blocksync/pool.go:411-413` — `SetPeerRange` updates `maxPeerHeight` with no sanity bound.
- Code analysis: `blocksync/msgs.go:43-52` — `ValidateMsg` for `StatusResponse` rejects only `height < 0` and `base > height`; arbitrary positive heights pass.
- Code analysis: `blocksync/pool.go:449-451` — `removePeer` calls `updateMaxPeerHeight()` only if `peer.height == pool.maxPeerHeight`. If the malicious peer sent two different heights (inflated, then lower), the `peer.height` stored is the second value but `maxPeerHeight` may have been set to the first inflated value and is not recalculated.
- Code analysis: `blocksync/pool.go:863-864` — timer leak: `defer retryTimer.Stop()` inside `OUTER_LOOP` creates a new deferred call per loop iteration without stopping the previous timer.

**Affected code paths**:
- `blocksync/pool.go:SetPeerRange()`, `removePeer()`, `updateMaxPeerHeight()`, `IsCaughtUp()`
- `blocksync/reactor.go:poolRoutine()` — transitions node from blocksync to consensus when `IsCaughtUp()` returns true

**Suggested modeling approach**:
- Variables: `maxPeerHeight` (global pool state), `peerHeight[peer]` (per-peer latest reported height); `byzantinePeer` flag
- Actions: `PeerReportHeight` (unconditionally updates `maxPeerHeight`), `PeerDisconnect` (updates `maxPeerHeight` via iteration), `CheckCaughtUp` (compares local height to `maxPeerHeight`)
- Invariant: `CatchupLiveness` — a node with all honest peers at height `H` eventually transitions to consensus mode when local height reaches `H - 1`, even if a Byzantine peer previously reported height `H + 10^15`

**Priority**: Medium
**Rationale**: Open security advisory. The liveness question (can a single Byzantine peer permanently prevent a node from joining consensus?) is suitable for TLA+ model checking. The timer leak and exact `removePeer` logic are implementation issues better verified by testing.

### Family 5: ABCI Response Callback Deadlock

**Mechanism**: Both `socketClient` and `grpcClient` invoke response callbacks (`resCb`, `reqres.InvokeCallback`) while holding `cli.mtx`. Any callback that re-enters the client (calls `Error()` or another ABCI method) deadlocks.

**Evidence**:
- Open PR #5850: "fix(abci): fix deadlock when response callback re-enters the client" — describes the fix (snapshot callback under lock, then release before invocation). Open, not merged.
- Code analysis: `abci/client/socket_client.go` and `grpc_client.go` — callback invocation under `cli.mtx` confirmed in PR description.

**Priority**: Low (for TLA+)
**Rationale**: This is a Go mutex semantics bug. TLA+ cannot model goroutine-level mutex re-entrancy faithfully. Better addressed by the existing Go test in PR #5850 (`TestResponseCallbackNoDeadlock`). Excluded from § 6.1.

### Family 6: Remote Signer Extension Protocol Gap

**Mechanism**: The `SignVote` RPC from consensus to remote signer carries no `extensionsEnabled` field. The remote signer independently decides whether to sign extensions based on vote type and block ID, using the same heuristic as old code that predates vote extensions. During the height at which extensions transition from disabled to enabled (or vice versa), the signer may attach or omit the extension signature incorrectly.

**Evidence**:
- Open Issue #3642: "privval: consensus should tell the privval whether to sign vote extensions" — accepted as a valid design gap, fix deferred.
- Open Issue #5437: "Resource Exhaustion of External Private Validator Endpoint" — `SendRequest` holds `instanceMtx` for full round-trip; `pingLoop` competes on the same mutex; no request queue bound.
- Code analysis: `privval/signer_client.go:96-113` — `SignVote` has no `extensionsEnabled` parameter.
- Code analysis: `privval/signer_requestHandler.go:49-68` — signer decides from `vote.Type == PrecommitType && !IsNilBlockID`.
- Code analysis: `privval/signer_listener_endpoint.go:109-132,216-231` — mutex contention between sign requests and ping keepalive.

**Priority**: Low (for TLA+)
**Rationale**: The wire protocol gap is a design issue for the team to resolve (adding `extensionsEnabled` to the protobuf message). The resource exhaustion is implementation-level. Neither is suitable for TLA+ model checking. Both go to § 6.3.

## 3. Modeling Recommendations

### 3.1 Model (with rationale)

| What | Why | How |
|------|-----|-----|
| Vote extension verification split by code path | Family 1: consensus verifies extensions, light client and blocksync do not | Split `AddVote` into `AddVoteConsensus` (calls `VerifyVoteExtension`) and `AddVoteLightClient`/`AddVoteBlockSync` (no extension check); add invariant over committed `ExtendedCommit` |
| Proposer self-vote extension bypass | Family 1, Issue #5204: proposer skips ABCI check for own address | Add a `FaultySelfExtension` adversary action where the proposer's extension passes cryptographic check but would fail ABCI `VerifyVoteExtension` |
| Evidence hash deduplication | Family 3: off-by-one in `Hash()` allows collision between distinct evidences | Model evidence pool as a map keyed by truncated hash; add adversary action `SubmitCollisionEvidence` |
| Double-sign protection lookback loop | Family 2: off-by-one prevents checks at height=1 | Model `checkDoubleSigningRisk` as returning true/false based on whether the loop executes ≥1 iteration; crash-restart scenario at height=1 |
| `maxPeerHeight` inflation | Family 4: blocksync stuck in sync mode | Track `maxPeerHeight` as variable updated unconditionally on peer report; `removePeer` recalculates only on exact-max removal; model `IsCaughtUp` |
| Byzantine receiver-side extension verification | BFT overlay: receiver-side predicate is the bug surface | Route `FaultySelfExtension` through the actual `!bytes.Equal(vote.ValidatorAddress, myAddr)` guard to expose whether the application-level check is bypassed |

### 3.2 Do Not Model (with rationale)

| What | Why |
|------|-----|
| ABCI client mutex deadlock (Family 5) | Go goroutine/mutex semantics; TLA+ cannot faithfully model re-entrant lock acquisition; PR #5850 already has a test |
| WAL non-atomic durability (non-fsync for peer msgs) | Compensated by `EndHeightMessage` fsync and ABCI handshake replay; crash recovery path already documented as correct |
| Remote signer `extensionsEnabled` wire gap (Family 6) | Interface protocol fix (add field to protobuf); not a distributed protocol safety question |
| Remote signer resource exhaustion (Family 6) | Implementation-level; better addressed by bounded request queue and connection management changes |
| Mempool `CheckTx` read-vs-write lock (Issue #2444) | Uncertain status; if real, it's a Go data race handled by the race detector, not TLA+ |
| Proposer timestamp (PBTS) | Open tracking issue #1731 for separate PBTS analysis; out of scope for this analysis round |

## 5. Proposed Invariants

| Invariant | Type | Description | Targets |
|-----------|------|-------------|---------|
| `ConsensusAgreement` | Safety | No two honest nodes commit different blocks at same height | Standard Tendermint |
| `ExtensionInCommitVerified` | Safety | Every extension in a committed `ExtendedCommit` was verified by `VerifyVoteExtension` before the committing node cast its precommit | Family 1 |
| `LightClientExtensionConsistency` | Safety | If a light client accepts a commit at height H, the extension signatures it skips must be valid under the honest validator keys | Family 1 |
| `NoDoubleSignAtHeight1` | Safety | A validator restarting without WAL at height=1 with `DoubleSignCheckHeight > 0` does not sign conflicting votes | Family 2 |
| `EvidenceDeduplicationSound` | Safety | Two distinct `LightClientAttackEvidence` with different conflicting blocks are never assigned the same pool key | Family 3 |
| `BlockSyncLiveness` | Liveness | A node with honest peers eventually transitions from blocksync to consensus mode | Family 4 |
| `MaxPeerHeightBoundedOnDisconnect` | Safety | After a Byzantine peer disconnects, `pool.maxPeerHeight` equals the maximum height among remaining honest peers | Family 4 |
