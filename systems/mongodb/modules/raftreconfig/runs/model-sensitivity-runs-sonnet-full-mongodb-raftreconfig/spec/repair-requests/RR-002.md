## Trigger

The counterexample requires `AdvanceCommitIndex(n1)` to interleave between
`SafeReconfigSwap(n1)` and `SafeReconfigCaptureBarrier(n1)`. In the real code,
these two actions are executed under the same replication mutex (`_mutex`),
making this interleaving impossible.

## Evidence

- **CE step that cannot be reproduced**: Step `AdvanceCommitIndex(n1)` in the
  counterexample occurs after `SafeReconfigSwap` has installed the new config but
  before `SafeReconfigCaptureBarrier` captures `lastCommittedInPrevConfig`. This
  advances the commit index using the new config's (smaller) quorum, inflating
  `lastCommittedInPrevConfig` above what new members have in their logs.

- **Missing guard — mutex atomicity**: In `replication_coordinator_impl.cpp`:
  - Line 4037: `_setCurrentRSConfig(lk, opCtx, newConfig, myIndex)` (= SafeReconfigSwap)
  - Line 4065: `_topCoord->updateLastCommittedInPrevConfig()` (= SafeReconfigCaptureBarrier)
  Both calls are guarded by the same `WithLock lk` (`_mutex`). The developer
  comment at line 4062 explicitly states:
  > "Once we have acquired the replication mutex above, we are ensured that no new
  > writes will be committed in the previous config, since any other system operation
  > must acquire the mutex to advance the commit point."
  `AdvanceCommitIndex` → `_advanceCommitPoint` also acquires `_mutex`; it cannot
  run while the reconfig path holds the lock.

- **Additional safeguard**: After the config swap, `awaitReplication(configOplogCommitmentOpTime)`
  (line 4161) blocks until a quorum of the **new** config has replicated all
  committed entries. This ensures the `CommitPointSafety` property is satisfied
  before the second reconfig can proceed (the second `SafeReconfigStart` cannot
  begin until the first `awaitReplication` completes).

- **Spec model gap**: The TLA+ spec models `SafeReconfigSwap` and
  `SafeReconfigCaptureBarrier` as two separately interleave-able actions with
  no shared mutex variable. This over-approximates the real concurrency: the
  mutex makes them effectively atomic with respect to `AdvanceCommitIndex`.

- **Code citations**:
  - `replication_coordinator_impl.cpp:4037` — `_setCurrentRSConfig(lk, ...)`
  - `replication_coordinator_impl.cpp:4065` — `updateLastCommittedInPrevConfig()`
  - `replication_coordinator_impl.cpp:4161` — `awaitReplication(...)`
  - Developer comment at line 4062: mutex guarantees no interleaving

## Proposed change

Option A (minimal): Merge `SafeReconfigSwap` and `SafeReconfigCaptureBarrier`
into a single atomic action in `base.tla`:
```tla
SafeReconfigSwapAndBarrier(n) ==
    (* models _setCurrentRSConfig + updateLastCommittedInPrevConfig atomically *)
    /\ configState[n] = Reconfiguring
    /\ ...
    /\ config' = ...
    /\ lastCommittedInPrevConfig' = [lastCommittedInPrevConfig EXCEPT
           ![n] = commitIndex[n]]  (* capture BEFORE any new advances *)
    /\ configState' = [configState EXCEPT ![n] = PostSwap]
```

Option B (cleaner): Add a `reconfig_mutex` variable to the spec that prevents
`AdvanceCommitIndex` from interleaving with the swap+barrier section. This more
faithfully models the real mutex semantics.

Option A is simpler and sufficient for model checking.
