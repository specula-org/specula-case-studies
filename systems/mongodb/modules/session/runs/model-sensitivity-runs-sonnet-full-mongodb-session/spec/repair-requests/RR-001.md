## Trigger
`DiskReapTxn(s1)` fires in the counterexample after `RefreshSucceed(s1)`, but in the
implementation the disk reap calls `findRemovedSessions` before every delete; a session
refreshed after memory-reap would be present in `config.system.sessions` and would not
be returned as expired — so the delete would never execute.

## Evidence
- CE step that cannot happen at the code level: states 23–24 (`MCDiskReapImage(s1)`,
  `MCDiskReapTxn(s1)`) fire in the second reap cycle (reapCutoff=4) for session s1
  whose `sessionLastRefreshed[s1]=4 >= reapCutoff=4` (refreshed at state 12).
- Predicted state: disk reap deletes s1's txn record despite s1 being "live".
- Realized state: the real disk reap calls `sessionsCollection.findRemovedSessions()`
  at `session_catalog_mongod.cpp:321` inside `removeSessionsTransactionRecordsIfExpired`.
  After `RefreshSucceed(s1)`, s1 is re-upserted to `config.system.sessions` with a
  fresh TTL. At disk-reap time, `findRemovedSessions` sees s1 as *present* (not removed)
  and excludes it from `transactionSessionIdsToReap`. The delete at line 272-291 never
  fires for s1.
- Missing guard in the spec (SPEC_REPAIR): `DiskReapImage` and `DiskReapTxn` lack the
  precondition that `sessionLastRefreshed[s] < reapCutoff`. In the implementation this
  is enforced by `findRemovedSessions` re-checking `config.system.sessions` at disk-reap
  time, which returns only sessions whose `lastUse` timestamp has actually expired from
  the collection — i.e., sessions not refreshed since the reap cutoff.
  Code citation: `session_catalog_mongod.cpp:321` (the `findRemovedSessions` call in
  `removeSessionsTransactionRecordsIfExpired`).

## Proposed change
Add `sessionLastRefreshed[s] < reapCutoff` as a precondition to both `DiskReapImage`
and `DiskReapTxn` actions. This models the fact that the real disk reap only proceeds
with sessions that remain absent from `config.system.sessions` (i.e., were not refreshed
after the reap cutoff was set). After this repair, `TxnRecordSafeWhileLive` should hold.
