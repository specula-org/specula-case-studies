# Apache Solr Operator ↔ Managed-System Semantic Bug Hunt

## Objective

Audit end-to-end semantic gaps between accepted Solr CR changes, generated Kubernetes state,
operator actions, and the behavior actually observed from Solr. Treat this as a distributed,
message-passing control plane with asynchronous application operations and reconciliation.

This is a blind candidate-generation run. Do not use `.autors/`, `research/`, archived Argus or
Specula outputs, or a prior bug list as candidate sources. Derive candidates from the clean source
and product contracts first; use upstream history afterward only for archaeology and novelty.

## Required breadth for Phase 1

Before selecting primary Scenarios, inspect every surface below and record what was covered:

- SolrCloud scale up/down, managed updates, addressability transitions, and cluster-operation locks.
- SolrBackup target selection, repository preparation, sync/async API lifecycle, recurrence, and cleanup.
- Solr Admin APIs, application preconditions, terminal responses, retries, timeouts, and version gates.
- Generated `solr.xml`, `security.json`, JVM/environment options, shell/exec arguments, and exact-value rendering.
- BasicAuth, TLS/mTLS, ZooKeeper identity/ACLs, referenced Secrets/ConfigMaps, and multi-cloud isolation.
- Status truthfulness and convergence for SolrCloud, SolrBackup, and SolrPrometheusExporter.

Read these entry points first: `controllers/solrcloud_controller.go`,
`controllers/solrbackup_controller.go`, `controllers/solrprometheusexporter_controller.go`,
`controllers/solr_cluster_ops_util.go`, `controllers/solr_pod_lifecycle_util.go`,
`controllers/util/`, `controllers/util/solr_api/`, and `api/v1beta1/`.

## Questions to investigate

1. Can a supported CR transition make previously healthy Solr data unavailable or change application identity silently?
2. Can a managed update or scale operation violate shard availability because replica type, state, placement, or node identity is misread?
3. Do valid boundary states such as zero/one node, reversed scaling intent, failed placement, or restart recover without panic, silent abandonment, or livelock?
4. Can synchronous or asynchronous Solr failures be mistaken for success, retried forever, forgotten, or cleaned up in the wrong order?
5. Can accepted values cross JSON, XML, properties, environment, JVM-option, or shell boundaries with different semantics or cross a real trust boundary?
6. Can Secret, ConfigMap, TLS, authentication, or ZooKeeper changes leave status claiming the desired application state is ready when it is not?
7. Can version-dependent features or process-global state make one supported Solr version or one SolrCloud corrupt or block another operation?

## Candidate and handoff rules

- Keep a candidate only when it has concrete harm, a realistic public trigger, and a required contract grounded in source comments, docs, tests, or application semantics.
- Prefer ordinary operations and single-fault transitions over deliberately self-conflicting administrator input.
- Deduplicate by root cause; do not count the same helper once per field or generated resource.
- Promote the highest-impact independent root causes to numbered Scenarios. Within each Scenario,
  keep distinct code-site hypotheses separate so later phases can test and report them separately.
- Do not spend primary Scenario capacity re-proving known or fixed bugs; use them only as depth checks.

## Later phases

Phase 2/3: preserve every concrete hypothesis or explicitly record why it is not model-checkable;
do not let a broad Scenario collapse distinct outcomes. Validate against real implementation paths.

Phase 4 only: reproduce through normal interfaces first. A mock, generated manifest, or internal
state alone is not a reproduced bug unless a real consumer observes the claimed harmful outcome.

## Out of scope

Exclude style issues, pure documentation gaps, immediately rejected invalid input with truthful
status, and self-inflicted overrides unless they cause silent harm or cross a demonstrated trust boundary.
