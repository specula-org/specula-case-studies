# Target: Solr Operator ⇄ Apache Solr interaction boundary

## What to model

The target of this run is **NOT** an internal distributed algorithm inside a
single system. It is the **operator–application interaction boundary** between:

- **The operator**: Apache Solr Operator (Go, Kubernetes controller-runtime).
  Local checkout: `https://github.com/apache/solr-operator` (commit `ed5c5c7`).
  Key code:
  - `controllers/solrcloud_controller.go` — main reconcile loop, cluster op lock
  - `controllers/solrbackup_controller.go` — backup lifecycle
  - `controllers/util/solr_util.go`, `controllers/util/solr_scale_util.go`,
    `controllers/util/backup_util.go`
  - `controllers/util/solr_api/` (esp. `v2.go`) — the HTTP client for Solr's
    Collections/Cluster admin API, async-request status handling
  - `controllers/util/*rolling_update*`, PVC expansion, pod eviction paths

- **The application**: Apache Solr / SolrCloud (Java).
  Local checkout: `https://github.com/apache/solr` (main branch).
  Key code:
  - `solr/core/src/java/org/apache/solr/handler/admin/api/` — Collections/Cluster
    admin v2 API handlers (BALANCE_REPLICAS, REPLACENODE, MOVEREPLICA,
    DELETENODE, CLUSTERSTATUS, REQUESTSTATUS, backup/restore APIs)
  - `solr/core/src/java/org/apache/solr/cloud/api/collections/` — the
    OverseerCollectionMessageHandler command implementations and their
    preconditions
  - async request tracking (`REQUESTSTATUS`, `DELETESTATUS`) and the ZooKeeper
    `/overseer/collection-map-*` state that backs it
  - Solr version gating: endpoints that exist only in 9.3+, 9.6+, etc.

The system under specification is the **conversation** between these two: the
operator issues admin API calls, observes Solr/Kubernetes state, and drives
cluster operations (scale up/down, rolling restart, PVC expansion, backup).

## Bug classes to hunt (target these explicitly)

These are the empirically dominant patterns of operator–application interaction
failures. Every invariant you write should be traceable to one of these:

| Pattern | Share | Description |
|---|---|---|
| **Semantic violations** | 63.7% (58/91) | The operator violates operation semantics / **preconditions required by the application**. E.g. calling a Solr admin API without establishing its documented precondition, calling it in an illegal order, or on state where Solr's own handler requires something else first (replica placement, node liveness, collection existence, leader election settled, an in-flight async op finished, etc.). |
| **State** | 16.5% (15/91) | The operator fails to observe **internal observability state** of the application. E.g. it decides from Kubernetes pod readiness or a stale cached CLUSTERSTATUS instead of Solr's actual replica/shard/leader state; it treats "pod Ready" as "replicas drained"; it ignores an async request still `running`. |
| **Version incompatibility** | 12.1% (11/91) | The operator fails to handle **behavior that differs across application versions**. E.g. an endpoint only present in Solr 9.3+, changed response shape, changed default, or a v1 vs v2 API divergence — while the CRD permits older `solrImage` tags. |
| **Mishandling app. errors** | 7.7% (7/91) | The operator **mishandles errors returned by the application**. E.g. it conflates a transport 404 with "unsupported API" and then with "success"; it drops a non-nil error; it treats `notfound` async status as terminal-success or hangs on it; it clears a cluster-op lock on a failed operation so level-triggered reconciliation can never self-heal. |

## Modeling guidance

1. **Model Solr's preconditions explicitly.** For every admin API the operator
   calls, read the Solr-side handler and encode its *actual* precondition and
   its *actual* failure/response modes (including async accept-then-fail) as
   guards in the spec. A bug is when the operator's reachable states include a
   call whose Solr-side precondition does not hold, or whose failure response is
   not correctly consumed.
2. **Model Solr's response space faithfully**, not optimistically: success,
   4xx with a body, 5xx, timeout, async `submitted`/`running`/`completed`/
   `failed`/`notfound`, and version-dependent "endpoint absent".
3. **Model operator restarts / reconcile interleavings.** The operator is
   level-triggered and can crash between issuing an async op and observing its
   result. Losing async-request tracking across an operator outage is a real
   observed bug shape here.
4. **Model version skew** as a spec constant: the Solr image version is a CRD
   field; the operator's assumptions about available endpoints must hold for
   every version the CRD accepts.
5. Prefer **conversational / temporal properties** (the operator eventually
   converges, never reports success for an operation Solr did not perform,
   never releases the cluster-op lock on an unfinished op) over shallow
   `No<X>ReadyWhileY` shape invariants.

## Known-good grounding (do not re-report these as new findings)

Prior work on this same boundary already confirmed:
- SolrBackup stays `inProgress` forever after REQUESTSTATUS returns `notfound`
  (async tracker lost across an operator outage).
- Stale CLUSTERSTATUS ⇒ scale-down deletes a non-empty ephemeral pod without
  going through REPLACENODE.
- BALANCE_REPLICAS: a 404 from a Solr version lacking the endpoint is turned
  into `balanceComplete = true`, and the cluster-op lock is cleared as
  "complete" (`solr_scale_util.go` tests `isUnsupportedApi` before testing
  `err`, then sets `err = nil`).

Use these as *calibration* that the modeling depth is right. Hunt for **new**
violations beyond them.

## Anchoring requirement

Every reported finding must anchor to concrete **source lines in Go
(solr-operator) and, where the precondition lives in Solr, in Java (solr)** —
not merely to lines in the TLA+ model.
