## Trigger

The replacement counterexample executes `MCFdbOrchMclagAdvertise(k1,p1)`, represents the resulting ASIC entry as dynamic, permits `MCSaiAgeEvent(k1,ev1)` to remove it, and then consumes the one-shot event after a failed recreate without setting retry intent. The first two transitions admit an implementation-inconsistent premise: production translates a logical MCLAG `type=dynamic` row to a SAI static entry with MAC moves allowed, so ordinary dynamic FDB aging cannot remove that current entry.

## Evidence

- `spec/output/repair_final_MC_hunt_scenario_2_incarnation_bfs.out:175-183` shows `MCFdbOrchMclagAdvertise(k1,p1)` installing `asic[k1].kind = "dynamic"`, while `:245` identifies the cache origin as MCLAG.
- The same trace at `:314-322` lets `MCSaiAgeEvent(k1,ev1)` remove that entry. At `:459-514`, the next state has `fdbFailure = TRUE`, `fdbRetry = FALSE`, and an empty event queue; `:529-595` retains cache/STATE_DB while ASIC/kernel are absent.
- Production `orchagent/fdborch.cpp:2035-2043` maps every MCLAG advertised type except `dynamic_local` to `SAI_FDB_ENTRY_TYPE_STATIC`; `:2052-2058` adds `SAI_FDB_ENTRY_ATTR_ALLOW_MAC_MOVE=true` for the logical dynamic row.
- The installed SAI contract describes `SAI_SWITCH_ATTR_FDB_AGING_TIME` as dynamic-entry aging (`/tmp/fdb-harness-bootstrap-test/root/usr/include/sai/saiswitch.h:1524-1533`) and restricts `SAI_FDB_ENTRY_ATTR_ALLOW_MAC_MOVE` to static entries (`saifdb.h:181-191`).
- Executed test `repro/test_bugMC-5_remote_age_retry.sh` drives the real MCLAG table path and captures `programmed_sai_type=STATIC allow_mac_move=true`; timing-only Level 1 produces no AGE event. Its Level-2 trace-shaped injection demonstrates the conditional dropped-recreate branch but records `admissible=false`, because it first assumes removal of that SAI-static current entry.
- The MCLAG HLD in https://github.com/sonic-net/SONiC/pull/596 documents the intended static-plus-allow-move representation specifically to suppress remote-MAC aging while retaining hardware move behavior.

## Proposed change

Distinguish the advertised row's logical FDB type from its installed SAI type, or track an explicit hardware aging-eligibility field. `MCFdbOrchMclagAdvertise` should represent a logical remote `dynamic` row as SAI static with MAC moves allowed, and ordinary `MCSaiAgeEvent` should require a currently age-eligible hardware-dynamic entry. Preserve failure-ownership checks for any separately modeled stale, flush-derived, or otherwise admissible notification path.

## Repair analysis

- `base.tla` now represents the software MCLAG row as logical `dynamic` and the installed ASIC row as SAI `static`; `SaiAgeEvent` requires `asic.kind = "dynamic"`. This directly removes the request's impossible MCLAG-advertise -> ordinary-AGE premise without changing the event or failure budgets.
- Raw LEARN/MOVE delivery preserves an already installed static type. The model applies the source's static-to-dynamic SAI mutation only at the guarded same-port MCLAG LEARN or changed-port MCLAG MOVE handler step (`fdborch.cpp:470-503,823-880`). A different-port transition of an installed static allow-move row is classified as MOVE.
- Remote/static AGE no longer falls through ordinary destructive cleanup. `FdbOrchNotificationRepairComplete` models successful recreation and the already-satisfied duplicate-create disposition while preserving software state (`fdborch.cpp:634-720`). The failure action remains reachable when the ASIC row is absent or divergent.
- Failure ownership uses implementation-visible destination, bridge-port generation, and translated SAI type. The audit-only FDB generation is deliberately excluded from duplicate-create equivalence because SAI and the C++ FDB key do not carry it. A queued matching LEARN/MOVE is recorded as continuation ownership, matching RR-002's notification-continuation semantics.
- Successive scoped counterexamples were checked rather than suppressed: already-installed current rows are compensation, static type persists until the handler, different-port static transitions use MOVE, and the successful remote AGE return is explicit. The final scoped result is no longer `FailedWorkRetainsRetryIntent` and does not execute the cited impossible aging path.
