## Trigger
The counterexample applies a repair-failure transition to the queued same-port local MOVE `MCSaiMoveEvent(k1,p1,ev2)`, but the implementation can call the cited SAI repair operation only when the cached entry is MCLAG-origin and the incoming bridge port differs from the cached bridge port.

## Evidence
- `output/MC_hunt_scenario_2_incarnation_final_bfs.out:34,859-1096` reports `UniqueEffectiveDestination`, then moves State 7 to State 8 by consuming the pending event while incrementing `repairFailure`, with ASIC/kernel at generation 2 and cache/STATE_DB/observer at generation 1; every one of those records nevertheless has destination `p1`, bridge-port generation 1, and kind `dynamic`.
- `orchagent/fdborch.cpp:870-872` guards the repair loop on both `FDB_ORIGIN_MCLAG_ADVERTIZED` and a changed bridge-port id. The exact LEARN(p1) -> MOVE(p1) trace creates a local LEARN-origin cache entry on the same bridge port, so the loop at `orchagent/fdborch.cpp:894-901` is unreachable.
- `orchagent/fdborch.cpp:155-160` treats that same-port local event as a duplicate; `orchagent/fdborch.cpp:193-196` persists only `port` and `type`, not a generation; and `orchagent/fdborch.cpp:935` still notifies observers after the ignored store return.
- The executed test `worktree/tests/mock_tests/fdborch/fdborch_vxlan_ut.cpp:4294` is captured in `reproduction-output.txt`: the exact trace made zero repair calls and left cache, STATE_DB, and the observer on Ethernet0. A separately reachable MCLAG_FDB_TABLE(p1) -> MOVE(p2) sequence forced all three SAI repair writes to fail and still left all three real consumers on Ethernet4.

## Proposed change
Constrain the modeled repair-failure transition to the implementation's MCLAG-origin and changed-bridge-port guards. Model the same-port local MOVE as the implementation's idempotent duplicate-store path that continues to observer notification, rather than as a failed SAI repair that strands a production-visible incarnation.

## Repair analysis
- The original failure transition was unreachable for its local same-port MOVE: clean source guards the attribute-repair loop on MCLAG origin and a changed bridge port at `orchagent/fdborch.cpp:823-857`, while the local same-port store returns as a duplicate at lines 154-160 and notification processing continues.
- `base.tla` now tracks `cacheOrigin`, provides a ready `FdbOrchMclagAdvertise` input, and splits notification repair failure by the implementation branch. MOVE failure requires MCLAG origin plus a destination/bridge-port change, retains the queued MOVE as the continuation owner, and then follows the normal cache/STATE_DB/observer path. Remote/static AGE recreation failure remains a one-shot return with no retry, matching `orchagent/fdborch.cpp:634-720`.
- `MC.tla` adds the bounded `MCFdbOrchMclagAdvertise` wrapper/counter and every model-checking config declares `MaxMclagInputLimit`; the scenario-2 hunt sets it to one so the real MCLAG branch remains reachable. Same-port local LEARN/MOVE commits only ghost incarnation progress while preserving the real duplicate path's existing `FdbData` and pending boolean.
- The repaired model cannot apply repair failure to the original LEARN(p1) -> MOVE(p1) trace, so the source-impossible State 7 -> State 8 transition and its `UniqueEffectiveDestination` artifact are gone. The final scoped run instead reports a distinct four-state remote AGE recreation failure under `FailedWorkRetainsRetryIntent`; that current violation is cited at `output/repair_final_MC_hunt_scenario_2_incarnation_bfs.out` and indexed as the revised MC-5.
