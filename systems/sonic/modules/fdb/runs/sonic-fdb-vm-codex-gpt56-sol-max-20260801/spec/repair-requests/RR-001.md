## Trigger
The INVARIANT requires every flush callback to match the latest pending request epoch, although the implementation and SAI callback contract expose only scope/type matching plus a per-entry boolean and do not promise request-identity correlation.

## Evidence
- `output/MC_hunt_mc1_stale_flush_final_bfs.out:1456-1468` reaches State 11 with the ASIC entry already absent and pending epoch 2; `:2164-2180` then records the delayed epoch-1 callback clearing software generation 1 while the ASIC, cache-derived count, and STATE_DB all end absent. The reported mismatch is `ackEpoch = 1` versus `markedEpoch = 2`, not removal of a post-flush ASIC incarnation.
- Executed reproduction `repro/test_bugMC-1_overlapping_flush.sh` drove two normal `FLUSHFDBREQUEST` `PORTVLAN` operations through `FdbOrch::doTask`, then legitimate consolidated `SAI_FDB_EVENT_FLUSHED` notifications through the ASIC_DB notification consumer. At Levels 0, 1, and timing-only Level 3, it printed `flush1_had_entry=1 flush2_had_entry=0`; after each callback it printed `cache_present=0 state_db_present=0 asic_present=0 vlan_count=0 port_count=0`. Exact State-11 injection at Level 2 produced the same aligned result. No real consumer observed a wrong outcome.
- Production stores only `bool is_flush_pending` at `orchagent/fdborch.h:84`, sets it after a successful matching flush at `orchagent/fdborch.cpp:1561-1568`, and consumes it using scope, type, and MAC at `orchagent/fdborch.cpp:309-314`; no request identity exists. Commit [`8dae35645962b0ce8b9b4ddc80d64162b51b5f65`](https://github.com/sonic-net/sonic-swss/commit/8dae35645962b0ce8b9b4ddc80d64162b51b5f65) / [PR #2136](https://github.com/sonic-net/sonic-swss/pull/2136) deliberately introduced that boolean to prevent a flush notification from deleting an entry that was added outside the pending flush window; its tests establish pending-versus-not-pending behavior, not epoch ownership. The SAI FDB event payload likewise contains event, FDB entry, and attributes but no flush request identifier ([`sai_fdb_event_notification_data_t`](https://github.com/opencomputeproject/SAI/blob/master/inc/saifdb.h)).

## Proposed change
Revise `FlushAckMatchesRequest` so the prohibited outcome is deletion of an entry incarnation that was not covered by any successful matching flush, rather than inequality between a callback epoch and the latest boolean marker. Preserve scope/type matching and make the oracle fail when a callback removes a generation learned after every applicable flush snapshot; allow the idempotent overlap here, where request 1 already removed the only ASIC incarnation and request 2 flushed an empty set.

## Repair analysis
- The old oracle imposed request-epoch identity (`ackEpoch = markedEpoch`) that neither `FdbData::is_flush_pending` (`orchagent/fdborch.h:84`) nor `handleSyncdFlushNotif` (`orchagent/fdborch.cpp:294-358`) can observe. The original counterexample and reproduction remain valid evidence that this equality is not a system guarantee.
- `base.tla` now records `flushRemoved[e][k]`, the execution-time ASIC incarnation actually removed by `SaiFlushSuccess`. `SuccessfulFlushCovered` accepts cleanup of an incarnation only when a successful, scope/type-matching flush removed that generation or a later one; a later removal proves an older cached incarnation was already superseded, but cannot cover a post-flush relearn. `FlushAckMatchesRequest` uses this predicate and no longer compares request epochs.
- `StaleEventCannotDeleteNewer` now applies only to non-flush deletions and was removed from `MC_hunt_mc1_stale_flush.cfg`: a FLUSHED callback carries no incarnation token, and the repaired flush-specific oracle owns this check. The invariant remains enabled in `MC_hunt_mc2_stale_age.cfg`, where AGE payload ordering makes it applicable.
- The revised oracle is non-vacuous. `output/repair_final_RR001_mc1_bfs.out` reaches a successful generation-1 flush, a same-port generation-2 relearn after that success, and then delayed cleanup of generation 2. No successful matching flush covered generation 2, so `FlushAckMatchesRequest` is false while scope/type matching remains true. This is a different current violation, indexed as MC-1; the original benign epoch mismatch is no longer treated as unsafe.
