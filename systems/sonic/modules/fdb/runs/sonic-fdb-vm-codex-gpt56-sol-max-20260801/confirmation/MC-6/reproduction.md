## Expected versus actual

The latest AppDB value after the `p2` SET is endpoint `10.0.0.102`, so endpoint
`10.0.0.101` must not become externally visible. Actual replay calls
`sai_fdb_api->create_fdb_entry` once with endpoint `10.0.0.101`. Three further
idle executor cycles do not resend or reconcile the newer value; a distinct
external dependency event for endpoint `10.0.0.102` would be required.

The real wrong-outcome consumer is the SAI/ASIC forwarding plane at
`orchagent/fdborch.cpp:2277`. The output is not automatically masked: the
single stale create remains after idle processing, and source audit found no
timer, AppDB re-read, loopback, or resend that makes the `p2` dependency appear.
The FDB and IMET producers are separate tables and event paths
(`fdbsyncd/fdbsync.h:95-96`, `fdbsyncd/fdbsync.cpp:669-696,787-859`), so a new
external `p2` membership event can repair the state but is not automatically
generated by this completed trigger.
