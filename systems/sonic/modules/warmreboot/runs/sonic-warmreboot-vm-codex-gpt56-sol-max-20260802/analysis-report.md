# Code Analysis Report: SONiC warm-reboot orchestration

**Repository**: `/users/Pial/targets/sonic-buildimage-warmreboot`  
**Analysis date**: 2026-08-01 UTC  
**Category**: **A — Distributed / Message-Passing**  
**Primary handoff**: `modeling-brief.md`

## Executive result

The selected implementation does not have one global warm-reboot transaction. It composes shell flags, systemd/container stops, Redis request/reply events, per-ASIC dump files, syncd phase strings, asynchronous daemon timers, and hardware mutations. Individual Redis commands or Lua scripts may be atomic, but the safety-relevant boundaries—admission, producer freeze, checkpoint publication, APPLY, and recovery completion—are not.

The highest-value protocol risks are:

1. no epoch/CAS/owner for concurrent reboot admission or cancellation;
2. orchagent's `READY` reply precedes its last drain, FDB changes, flush, and heartbeat freeze;
3. per-ASIC freeze/shutdown/mode/checkpoint failures can be masked and aggregated into global progress;
4. syncd APPLY mutates hardware before a separately non-atomic ASIC_DB/map rewrite, without a durable dirty marker or recovery journal;
5. object identity reconciliation is partly randomized and its detailed map validator is skipped for equal-sized maps;
6. timeout-based auxiliary reconciliation and finalization can expose terminal state or clear flags before output and late participants are complete.

The audit also confirmed several direct implementation defects best addressed by tests or review, including `fast-reboot -N` returning 23 on success, `swss@N` killing the literal `swss` container, tuple-corrupting route comparison, cross-table fpmsyncd reconciliation, and a normal non-ZMQ `RECONCILED`-before-pipeline-flush window.

No source repository files were modified. All line references are to the pinned revisions below.

## 2. Phase 1 — architecture and reference mapping

### 2.1 End-to-end lifecycle

1. `warm-reboot`, a utilities `fast-reboot` mode, performs prechecks, chooses kexec/reboot behavior, rejects some existing reboot state, and writes warm/fast enable fields.
2. It clears component state, coordinates LAG/CPA handling, and asks each orchagent instance to freeze through `orchagent_restart_check`.
3. Orchagent handles RESTARTCHECK in its main event loop, inspects pending work, replies `READY`, then drains its route ring, disables dynamic FDB behavior, flushes SAI, and freezes heartbeat/progress.
4. A package-manifest graph generated by `service_creator/creator.py` determines a topological shutdown order. Typical edges stop BGP before swss, swss before teamd, and teamd before syncd.
5. After swss stop, the coordinator requests syncd PRE_SHUTDOWN. Syncd drains its ASIC command queue, removes counters, asks SAI for warm restart/pre-shutdown behavior, and publishes phase state on success.
6. Final syncd shutdown requests warm mode, stops containers, prunes STATE_DB, centralizes Redis instances, performs synchronous `SAVE`, and copies dump files under `/host/warmboot$DEV`.
7. The host stops Docker and reboots/kexecs. Database startup uses `SONIC_BOOT_TYPE` and dump existence to decide whether to restore, then moves a loaded dump to `.old`.
8. WarmStart consumers inspect system/component flags and `restore_count`; missing restore state causes cold behavior.
9. Orchagent asks syncd to enter INIT_VIEW, restores and bakes cached state, runs iterative processing, programs mux/mirror/ACL state, verifies no pending tasks, asks APPLY_VIEW, invokes warm-end hooks, and publishes `RECONCILED`.
10. In warm syncd startup, VID/RID mappings and switch objects are reconstructed. INIT_VIEW redirects incoming desired state to TEMP view. APPLY_VIEW compares current/TEMP views, executes hardware changes, rewrites current ASIC_DB and maps, and returns success/failure.
11. Auxiliary daemons either use AppRestartAssist (`STALE`, `SAME`, `NEW`, `DELETE`) or WarmStartHelper (restored vector vs refreshed map, timer/EOIU reconciliation).
12. The finalizer waits in parallel for component terminal states, but after its timeout it logs unresolved components, clears per-ASIC/global warm flags, and saves configuration.

### 2.2 Principal state and communication channels

| State/channel | Writers | Readers | Safety role |
|---|---|---|---|
| `STATE_DB` warm enable/state/restore fields | reboot scripts, daemons, finalizer | scripts and component startup | admission, component phase, completion |
| APPL_DB RESTARTCHECK request/reply | helper and SwitchOrch/orchdaemon | reboot coordinator | orchagent freeze acknowledgement |
| ASIC_DB current/TEMP views | orchagent/sairedis, syncd | syncd comparison/recovery | desired/current view handoff |
| VIDTORID/RIDTOVID maps | syncd | syncd translation/recovery | object identity authority |
| syncd restart-query channel | shell/RedisRemoteSaiInterface | syncd main loop | INIT/APPLY/PRE/final mode control |
| package stop-order file | service creator | fast-reboot | producer shutdown dependencies |
| `/host/warmboot$DEV` dumps | reboot/checkpoint scripts | database container startup | checkpoint authority |
| EOIU/timer/selectable events | routing/aux daemons | warm helpers | input-completeness proxy |
| SAI hardware | syncd/vendor SAI | syncd discovery and traffic | persistent data-plane authority |

### 2.3 Concurrency model

- The shell coordinator launches per-ASIC work in parallel and relies on `wait`, files, flags, and exit statuses.
- Orchagent is primarily a selectable event loop plus a route-ring producer/consumer path. Its ring indices/idle state are ordinary shared variables rather than an explicit atomic fence.
- Syncd serializes normal commands and notification translation with its main mutex, but still has independently ready Redis selectables and a notification worker.
- Auxiliary daemons combine select loops with timers; lack of new input becomes a state transition.
- Systemd/container lifecycle, Redis durability, filesystem copies, and hardware operations have independent failure and crash points.
- Redis Lua pruning is atomic only within one Redis instance. `SAVE`, cross-instance centralization, file copy, producer stop, and hardware state are not one transaction.

### 2.4 Reference obligations used in this audit

No standalone formal spec or paper was found for the exact repository-wide orchestration. The following obligations were derived from SONiC's intended freeze → checkpoint → restart → INIT/APPLY → recovery structure:

- one admitted reboot attempt owns global progress;
- a freeze acknowledgement fences every pre-checkpoint producer and drains earlier work;
- shutdown/checkpoint covers every writer and every selected ASIC namespace;
- a consumed checkpoint is complete and belongs to the chosen attempt;
- INIT precedes APPLY for one coherent desired view;
- APPLY exposes one authoritative agreement among hardware, ASIC_DB, and identity maps;
- any partial irreversible failure leads to an explicit recoverable state or cold fallback;
- reconciliation cannot infer deletion before input completeness;
- terminal state and flag clearing follow durable output publication for every required participant.

These are carried into the modeling brief as standard and implementation-specific invariants.

## 5. Validated findings

Severity here reflects orchestration impact, not exploitability. “Model fit” determines the handoff lane: TLA+ scenario, test, or human review.

### F-01 — Reboot admission and signal cleanup are not epoch-owned

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenario 1, after introducing an explicit epoch/owner abstraction

`fast-reboot:883-894` tests existing warm/fast flags separately from the writes at `973,976-977,980,991`. There is no filesystem lock, Redis `SETNX`, transaction, attempt identifier, or owner field between check and publication. Two CLI/DBus callers can both observe admission open and begin globally mutating the same flags, CPA/LAG state, services, and dump paths.

The cancellation path has the same ownership problem. Traps at `975,990,996` invoke `clear_boot`; the handler at `341-370` removes shared state but does not terminate the invoking script. A caught signal can therefore clean flags/dumps/CPA state and then resume the main flow. If another attempt has begun meanwhile, old cleanup is not scoped away from the newer attempt.

The helper `check_warm_restart_in_progress` uses a pipeline without `pipefail`, weakening error propagation. `SIGKILL` in a trap list is not actionable because it cannot be caught.

**Failure trace**:

1. callers A and B both read warm/fast disabled;
2. A publishes flags; B publishes indistinguishable flags;
3. A receives a caught signal and removes global artifacts;
4. B continues through freeze/checkpoint with its admission state erased;
5. A may also resume after `clear_boot`, yielding two active coordinators.

**Required abstraction**: `epoch`, `owner`, monotonic `phase`, `cancelled`, and `cleanupOwner`. The current race itself is directly confirmable; the forward model question is whether a proposed epoch/CAS scheme also prevents stale cleanup/retry interference.

### F-02 — Orchagent `READY` precedes the actual quiescence boundary

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenario 2

The coordinator sends a RESTARTCHECK request and accepts any returned `READY` data at `orchagent_restart_check.cpp:108-140`. The reply has no operation ID, request ID, attempt epoch, or structured status correlation. `SwitchOrch` parses the request and sets warm-restart flags at `switchorch.cpp:1562-1608`.

`OrchDaemon::warmRestartCheck` scans pending tasks for a limited number of attempts and sends `READY` at `orchdaemon.cpp:1347-1413`. Only after that reply does the main warm path:

- drain the route ring (`1190-1200`);
- disable FDB aging/learning (`1204-1215`);
- flush SAI (`1217-1218`);
- freeze the heartbeat/progress path (`1220-1221`).

The helper returns as soon as it sees `READY`. The warm container-upgrade path in `sonic_installer/main.py:853-903` can kill immediately, so the additional latency often present in full fast reboot is not a fence. The post-READY `setAgingFDB` and learning-mode results are ignored.

The route ring is not represented in the pending-task predicate. Its head, tail, and idle fields in `orch.h:232-260` / `orch.cpp:29-79` are ordinary shared variables, so the check is neither a language-level data-race-safe snapshot nor a global producer barrier. Once `READY` succeeds, normal control does not return to the main select loop—an important compensation—but ring/channel work and the explicit post-reply operations remain.

**Failure trace**:

1. pending scans happen to be empty;
2. orchagent publishes `READY`;
3. the coordinator kills/restarts or moves toward checkpoint;
4. prior ring work or a post-reply mutation has not completed;
5. the checkpoint/restored view is treated as quiescent despite an unfinished producer action.

Historical commits `721f47d9`/#1556 and `bab7b933`/#1103 show that this boundary has repeatedly required layering fixes. They are evidence, not model targets. The open question is global: after locally reordering the reply, can any remaining producer/channel cross the new fence?

### F-03 — The real point of no return is crossed before validation and reliable failure control

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenarios 2-3

Multi-ASIC code sets `FORCE=yes` at `fast-reboot:1149-1152`. `pause_orchagent` at `1137-1146` can suppress a nonzero helper result in forced mode and log success. The surrounding wrapper therefore cannot execute its intended failed-ASIC removal/flag cleanup at `129-146`. The wrapper's fast-flag clear at line 144 also omits the explicit `STATE_DB` argument used by the neighboring path.

In single-ASIC flow, freeze occurs at `1155`; a subsequent retry-count lookup at `1158` can still fail under `set -e`, invoking cleanup with no unfreeze operation. Only at `1163` does the script use `set +e`. Thus freeze—not `set +e`, Docker stop, or checkpoint—is the irreversible boundary.

The dynamically generated stop-order file is checked only after freeze and after some traps have been disabled (`1199-1204`). A missing file exits and strands the frozen system. An existing-but-empty file is accepted. `service_creator/creator.py:490-516` writes the file directly through a truncating open rather than the temp-file/rename technique the same class uses at `368-375`, so a generator crash can make the empty-file case real.

Later platform hooks retain explicit exits and potentially unbounded calls. `stop_systemd_service` ignores the stop command's result and returns a successful debug command, so checkpoint can proceed without verified producer stop.

**Compensation**: historical utilities commit `6eedf8a7` documents the intended “remove faulty ASIC before continuing” behavior, but the current forced helper swallows the status before that caller can act.

### F-04 — Multi-ASIC swss warm shutdown addresses the wrong container

**Status**: confirmed-current, direct implementation defect  
**Severity**: high  
**Model fit**: integration test; the broader missing-writer outcome belongs to Scenario 3

Fast reboot maps a per-ASIC swss component to `systemctl stop swss@N`. The generated unit passes `N`, and `swss.sh` receives `DEV=N`. Yet the warm stop branch at `swss.sh:522-543` issues `docker kill swss`, not `docker kill swss$DEV`. Generated multi-ASIC containers are suffixed. No subsequent unit/cgroup action in this branch reliably compensates by killing the intended `swssN` container.

**Failure trace**:

1. namespace N is selected for shutdown;
2. the systemd instance calls `swss.sh stop N`;
3. the script targets base container `swss`;
4. `swssN` remains a Redis/ASIC producer;
5. checkpoint starts under the assumption that the participant stopped.

Buildimage commit `ca462d66` introduced the relevant integration; no correction was found at the pin. This should first be locked down by a multi-ASIC service test. The model should abstract the resulting possibility as `writerStopped[N] = FALSE`, not reproduce the string error.

### F-05 — The generated shutdown graph can omit legal writers

**Status**: confirmed-current design gap  
**Severity**: medium/high  
**Model fit**: human contract decision plus Scenario 3 abstraction

Package manifests default `before` and `after` arrays to empty. During graph construction, `creator.py:466-478` skips nodes without dependency edges. A legal extension daemon can therefore be installed and active yet absent from the warm-stop order. This is different from a topological-sort error: the participant never joins the graph.

The graph file is direct-truncated as described in F-03. Together, “valid but edge-less,” “generation crashed,” and “empty order accepted” all permit a checkpoint with an unmodeled writer.

The design question is which services must participate in a warm-reboot writer fence. Once that participant set is specified, the formal model only needs a finite set of required writers and missing/failed stop acknowledgements.

### F-06 — Syncd PRE/final shutdown status does not form a reliable participant contract

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenario 3

After swss stop, the coordinator invokes syncd PRE and nominally polls for 60 seconds, but it only logs a missing result and proceeds. The wrapper detects timeout status 124 specially while ordinary immediate `docker exec` failure can be masked; the Redis `HGET` used in the wait is itself not bounded. Final syncd shutdown at `syncd.sh:145-173` has a nominal 20-second wait but does not read back the actual warm/cold decision. Several `docker exec` and sync calls are unbounded or have ignored status.

Inside syncd, local warm mode can be downgraded to cold when the warm file is absent or `setRestartWarm` fails (`Syncd.cpp:6982-7010`). The coordinator never aggregates that result. `preserve-data-plane` failure is ignored (`7013-7016`); warm success is based mainly on `removeAllSwitches` (`7022-7029`), and a later API-uninitialize failure is only logged. Direct WARM does not require a durable successful PRE phase, while a partially applied PRE attribute sequence has no full rollback.

`WarmRestartTable.cpp:20-43` records only three unversioned HSET strings (`set-flag-failed`, `pre-shutdown`, `warm-shutdown`). It has no attempt ID, participant/ASIC scope, compare-and-set, or final policy acknowledgment.

This permits a global warm flag with local cold participants, or checkpoint/restart after an unknown PRE state. Model per-ASIC `localMode`, phase, and status independently from the global/shared decision.

### F-07 — Checkpoint creation and consumption lack a generation/validity commit

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenario 3

After `set +e`, checkpoint code at `fast-reboot:452-506` prunes STATE_DB, centralizes databases, copies dumps, and removes/transforms artifacts without governing progress by every result. A shell micro-test of the same function shape confirmed that an early failed command can be followed by a successful final command and yield status 0.

`centralize_database:10-42` performs synchronous Redis `SAVE`, a useful compensation that provides a fresh source dump when it succeeds. The STATE_DB pruning Lua script is atomic within its Redis instance. Neither fact makes the larger sequence atomic: producer stop, per-instance pruning, centralization, SAVE, copy, and publication span processes and filesystems.

There is no temp output plus atomic rename, generation manifest, checksum, expected namespace set, or attempt epoch on `/host/warmboot$DEV`. Database startup consumes a dump based on boot type and existence at `docker_image_ctl.j2:105-109`, then moves a loaded dump to `.old` at `296-299`.

The `.old` move refutes a broad “normal reboot always reuses an old dump” claim: a successful normal load does retire it. Missing/partial dumps remain possible, and stale residual consumption is relevant after abnormal prior paths. Multi-ASIC paths are distinct rather than colliding, but that turns the issue into partial, mixed-generation completion across namespaces.

**Failure trace**:

1. one writer is not stopped or one SAVE/copy fails;
2. another namespace successfully publishes its dump;
3. later successful commands mask the earlier failure;
4. global reboot proceeds;
5. boot accepts existence as validity, producing missing or mixed snapshots.

### F-08 — APPLY is a split, non-atomic hardware/database transaction

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenario 4

`Syncd.cpp:5716-5832` constructs and checks the comparison plan. At `5844-5849`, `ComparisonLogic` begins irreversible SAI operations. Only afterward do `5921-5980` delete ASIC/TEMP state, repopulate current objects, and replace identity maps. `RedisClient.cpp:582-600,664-680,886-908` executes field/key-at-a-time commands without MULTI/EXEC, a wrapping Lua script, key rename, or commit marker.

`ComparisonLogic.cpp:3681-3893` executes operations sequentially, reports/rethrows failure, and comments at `3864-3869` that retrying a subsequent APPLY may be unsafe. There is no journal, rollback, resume cursor, durable dirty flag, or boot-attempt ID. REMOVE erases `m_removedVidToRid` before the vendor remove (`3557-3565`); CREATE updates in-memory maps after vendor success (`3484-3545`); a SET workaround can reinterpret vendor failure as success (`3594-3611`).

On APPLY failure, syncd publishes failure and enters fail-stop shutdown-wait (`Syncd.cpp:5565-5580,6959-6977`). A later restart query may overwrite the default cold policy (`6752,6838-6865,7044-7059`). Warm startup then trusts surviving switch/map state after limited checks (`6257,6307-6321,6330-6348`).

**Crash cuts with different authorities**:

- after hardware operation k but before k+1;
- after all hardware operations but before deleting TEMP/current Redis state;
- during current-view object reconstruction;
- between VIDTORID and RIDTOVID replacement;
- after failure publication but before a later restart query selects mode.

Planner safeguards include a two-pass SET dry-run (`ComparisonLogic.cpp:1895-1917`), refcount checks (`AsicView.cpp:226-353,770-799`), dependency-oriented sorting (`ComparisonLogic.cpp:3075-3283`), and consistency checks (`2506-2656`). These protect planning, not already executed mutations; the caller enforces the consistency check only when unit tests are enabled (`Syncd.cpp:5851-5860`).

First-run and port persistence also use independent Redis writes with atomicity TODOs (`SaiSwitch.cpp:805-903,995-1039,1116-1185`). Async RedisRemote operations can report success before hardware completion (`RedisRemoteSaiInterface.cpp:1030-1137,1878-1920`), while synchronous paths have hardware/reply-before-Redis windows.

### F-09 — Equal-size identity maps can bypass reciprocity validation

**Status**: confirmed-current, direct code defect  
**Severity**: high  
**Model fit**: code review/test; the general ambiguity belongs to Scenario 5

`ComparisonLogic.cpp:2658-2685` contains a detailed VID/RID map validator. Its top-level wrapper at `3895-3917` calls that validator only when the two map sizes differ. Equal-sized but wrong, permuted, duplicate-derived, or nonreciprocal mappings therefore pass this specific gate.

The immediate fix is local: invoke the detailed check unconditionally and test equal-size corruption. The model should not recreate the conditional; it should require `IdentityMapBijective` and explore whether the matching protocol can establish it.

### F-10 — Object matching remains nondeterministic and incomplete

**Status**: confirmed-current/design gap  
**Severity**: high  
**Model fit**: Scenario 5

Every `ComparisonLogic` construction seeds process-global `rand` with `time(0)` (`ComparisonLogic.cpp:67-71`). Candidate traversal also depends on unordered containers (`AsicView.cpp:405-499`). Pre-match rules at `ComparisonLogic.cpp:2874-2999` reduce ambiguity for known ACL/special objects but do not provide a stable total tie-break for the whole graph.

Open PR #2007 demonstrates an externally meaningful consequence: random virtual-router matching can create duplicate RIFs and crash APPLY. Open PR #1672 and #2012, issue #1429, and the explicit unsupported/TODO sites show that the problem is broader than one object type:

- `AsicView.cpp:87-125` supports only a subset of non-OID object types;
- `ComparisonLogic.cpp:2051-2148` lacks several reverse-dependency/link-breaking cases;
- repeated-port and discovered-object conflicts remain TODOs at `2433-2468`;
- `transferNotProcessed` at `3001-3073` carries some current objects into TEMP, deferring removal to a later warm boot.

`SaiSwitch` supplies important compensations: lane-map equality (`321-361`) and hidden/internal OID matching (`488-578`). But warm discovery at `1188-1251` creates VID/RID mappings and dummy ASIC_STATE entries for newly discovered RIDs absent from RIDTOVID rather than rejecting them, and it does not validate the complete user-programmed hardware state.

The formal question is not whether PR #2007 can be replayed. It is whether, after all known stable labels are encoded, remaining graph automorphisms can still lead to externally distinct/non-bijective bindings.

### F-11 — Restart-query readiness can bypass shutdown-wait command handling

**Status**: confirmed-current interleaving hazard  
**Severity**: medium/high  
**Model fit**: Scenario 4 auxiliary action; targeted integration test

If restart-query handling wins selection, syncd drains queued ASIC commands through normal `processEvent` even while in shutdown-wait (`Syncd.cpp:6838-6855`). When the ASIC command selectable itself wins, shutdown-wait uses the failure/ignore handler (`6937-6946`, handler `428-457`). If both selectables are ready, behavior depends on selection order: the same queued command can be normally executed or rejected/handled as shutdown work.

This is distinct from the refuted notification-cache race below. Model a pre-APPLY/failed-APPLY auxiliary event and simultaneous readiness; test the concrete selectable order.

### F-12 — Timeout is used as evidence of input completeness

**Status**: confirmed-current design risk  
**Severity**: high  
**Model fit**: Scenario 6

Fpmsyncd selects a default or configured warm timer (`fpmsyncd.cpp:154-181`). Timer expiry and EOIU both cause reconciliation (`203-218`). `WarmStartHelper` treats entries present in restored state but absent from the refresh map as deletions (`warmRestartHelper.cpp:159-176`). Open swss issue #4579 reports real convergence at 240–280 seconds, beyond the common 120-second timer.

The timer is therefore not merely a liveness watchdog: it changes safety-relevant meaning from “not yet observed” to “deleted.” The desired model must separate `timerExpired` from `inputComplete`, and permit late input after a timeout decision.

### F-13 — Normal fpmsyncd can publish `RECONCILED` before buffered output is durable

**Status**: confirmed-current for normal non-ZMQ Redis path  
**Severity**: high  
**Model fit**: Scenario 6 plus crash-injection test

Fpmsyncd configures a pipeline of 50,000 operations (`fpmsyncd.cpp:87`, header configuration) and RouteSync uses buffered route-table writes (`routesync.cpp:172`). Reconciliation enqueues derived route changes and updates warm state to `RECONCILED` through `WarmStartHelper` (`warmRestartHelper.cpp:256`) before the caller flushes the pipeline at `fpmsyncd.cpp:218`. STATE_DB publication uses a separate connection.

**Failure trace**:

1. timeout/EOIU triggers reconciliation;
2. route output is placed in a client pipeline;
3. component state becomes `RECONCILED`;
4. finalizer observes terminal state;
5. process crashes before `flush`, losing derived output.

This exact claim does not apply to the ZMQ path, which must be excluded from the test. It also does not generalize to AppRestartAssist registered tables: those are unbuffered and their individual writes flush before terminal state.

### F-14 — Finalization can clear flags despite unresolved or late participants

**Status**: confirmed-current  
**Severity**: high  
**Model fit**: Scenario 6

`finalize-warmboot.sh` waits up to 60 iterations of five seconds for participating components. At `256-258` it logs timeout but continues. Per-ASIC flags are cleared at `284-289` and the global flag at `302`. Some database/HGET calls inside the bounded outer loop are themselves unbounded. Parallel child status is obscured by bare `wait` usage.

Per-ASIC clearing happens independently before a global barrier. FAST and WARM fields are separate writes, so observers can see mixed flag state. A failed namespace clear can be orphaned after the global flag changes. Buildimage issue #17943 provides a concrete late-observer example: pmon/xcvrd may inspect warm state after another path has finalized it.

Configuration/CPA reset failures are weakly handled before `config save`; in cleanup paths one CPA failure can also stop remaining cleanup. The formal barrier needs explicit participant terminal success/failure, output publication, and observer acknowledgment or a documented late-start policy.

### F-15 — Route refresh comparison destroys positional tuple semantics

**Status**: confirmed-current, direct implementation defect  
**Severity**: high  
**Model fit**: unit test, not TLA+

`WarmStartHelper::compareAllFV` compares fields independently (`warmRestartHelper.cpp:274-303`). `compareOneFV` tokenizes and sorts each comma-delimited value separately (`320-346`). APP route fields such as nexthop, interface, weight, and MPLS label are parallel positional vectors. Independent sorting can declare two entries equal even when the `(nexthop, interface, weight, label)` tuples have been re-paired.

Example: swapping interface assignments between two nexthops preserves every field's multiset but changes forwarding. Warm reconciliation can mark the entry unchanged and suppress the required update. A fake/helper-focused existing test can miss this because it does not assert tuple-level semantics.

### F-16 — Fpmsyncd warm caching loses destination-table identity

**Status**: confirmed-current, direct implementation defect  
**Severity**: high  
**Model fit**: integration test, not TLA+

RouteSync creates one warm helper bound to `ROUTE_TABLE` at `routesync.cpp:181`. Generic wrappers at `191-224` use that helper for route, label-route, and EVPN paths without retaining the destination table in the cached key/value representation. During reconciliation, label/EVPN updates are written into `ROUTE_TABLE`; deletes for the original table are discarded, and equal keys from different tables can collide.

A test should populate colliding keys in all three tables, exercise add/update/delete across warm restore, and assert the precise destination table. The formal model can abstract all of this as one producer emitting incorrect output; reproducing the table-name bug provides little state-machine value.

### F-17 — AppRestartAssist comparison can preserve removed optional fields

**Status**: confirmed-current, caller-dependent  
**Severity**: medium  
**Model fit**: unit/integration test

AppRestartAssist's comparison at `warmRestartAssist.cpp:339-351` effectively accepts a subset. Removing an optional field can classify an entry as SAME. Because Redis HSET of remaining fields does not delete an omitted old field, stale attributes can survive. VXLAN FDB's optional protocol behavior and its pre-delete sequence make this capable of losing or preserving the wrong entry depending on caller order.

The mechanism should be tested for each registered table contract. A broad claim that all AppRestartAssist output is buffered was refuted: registered tables are unbuffered and writes complete before state publication.

### F-18 — WarmStart shared state access has stale-cache and error-semantic gaps

**Status**: confirmed-current  
**Severity**: medium  
**Model fit**: code review and tests

`sonic-swss-common/common/warm_restart.cpp:94-107` does not reset cached booleans before re-reading enable state. A true→false transition can leave a long-lived caller considering warm restart enabled. Missing `restore_count` correctly falls cold, but malformed numeric data reaches uncaught `stoul`. Related HGET/HSET increment/update operations are composed from separate commands rather than one atomic epoch-aware update.

This layer does not need a full concurrent-memory model; it needs explicit refresh/error contracts and tests for true→false, missing, malformed, and competing writers. The distributed spec should treat these fields as lossy/unversioned shared state.

### F-19 — Bulk FlexCounter translation lacks the single-operation RID guard

**Status**: confirmed-current  
**Severity**: medium/high  
**Model fit**: race test; auxiliary Scenario 4 event

The bulk FlexCounter path at `Syncd.cpp:4140-4156` does not apply the RID-zero guard used by the single path at `4176-4210`. Open PRs #1767, #1783, and #1784 independently converge on the same pre-APPLY/reconstruction race. A bulk request can therefore translate before VID/RID reconstruction is ready.

The model should include only a nondeterministic auxiliary action before APPLY. The missing branch guard is better verified directly with bulk requests and a controlled mapping-reconstruction delay.

### F-20 — Additional deterministic orchestration defects

**Status**: confirmed-current unless noted  
**Severity**: low to medium individually  
**Model fit**: tests/review

## 6. Cross-finding failure sequences

The individual defects compose. These sequences motivated mechanism-level scenarios instead of one finding per file.

### 6.1 Concurrent attempt plus premature freeze acknowledgement

1. Attempts A and B both pass the non-atomic flag check (F-01).
2. A asks each orchagent to freeze; one publishes READY before its ring/flush boundary (F-02).
3. B observes the same unversioned READY/flags and also advances.
4. A is signaled; its unowned cleanup erases shared state and resumes.
5. Either coordinator may checkpoint while a producer is not globally fenced.

This sequence violates attempt uniqueness, phase monotonicity, and checkpoint-after-quiescence. It justifies modeling reply correlation and cleanup ownership in the same state space.

### 6.2 Partial multi-ASIC shutdown plus checkpoint acceptance

1. ASIC 0 stops normally; ASIC 1 freeze failure is swallowed by `FORCE` (F-03).
2. `swss@1` targets the wrong container, leaving its writer active (F-04).
3. An edge-less extension daemon is absent from the generated stop graph (F-05).
4. Syncd 1 downgrades locally to cold, but no final result reaches the coordinator (F-06).
5. SAVE/copy for one namespace fails and a later command returns success (F-07).
6. Boot selects warm globally and accepts whichever dump paths exist.

This motivates per-participant mode/status and same-epoch snapshot validity rather than one Boolean `warmRestart` variable.

### 6.3 APPLY failure followed by ambiguous warm recovery

1. Nondeterministic matching chooses an identity permutation (F-10).
2. Hardware operations execute; a REMOVE mutates in-memory bookkeeping and the vendor action fails (F-08).
3. ASIC_DB/maps still describe a different cut of state, and an equal-size wrong map evades the wrapper check (F-09).
4. Syncd enters shutdown-wait, but a simultaneously ready restart query drains commands normally (F-11).
5. A later restart request overwrites the default cold choice; warm startup repairs/synthesizes some missing discovered mappings.

The desired result is not a replay of a known closed defect: it is proof that an explicit journal/dirty marker always chooses safe resume or cold fallback at every cut.

### 6.4 Timer reconciliation plus premature global finalization

1. Route input remains incomplete beyond the configured timer (F-12).
2. Missing refresh entries are classified as deletions; cross-table/tuple defects may further alter output (F-15/F-16).
3. Fpmsyncd publishes `RECONCILED` while output remains buffered (F-13).
4. The finalizer sees terminal state or reaches timeout and clears flags (F-14).
5. The process crashes before flush, or a late participant/input arrives after flags are gone.

This sequence violates both `NoPrematureStaleDeletion` and `ReconciledImpliesOutputsPublished`.

## 11. Limitations and confidence

- GitHub archaeology used official REST/web/patch endpoints. Later sonic-swss-common REST requests were rate-limited, so its seven items received transparent patch/metadata review rather than full-discussion status; they are excluded from the 75-read total.
- Vendor SAI internals and platform services can add failure modes not visible in these repositories. Vendor-only claims were not generalized without code evidence.
- Line numbers and commit classifications are pin-specific. Upstream open PR/issue status can change after 2026-08-01.
- Shell orchestration has many platform hooks. The report focuses on paths that affect the reference warm protocol; it does not claim full coverage of every platform override.
- Absence of a standalone formal reference spec means “standard” invariants are derived from the repository-wide intended order, not imported from a published machine-checked model.

Confidence is **high** for the source-local ordering, status-masking, APPLY publication, map-validation, route comparison, cross-table, and pipeline findings. Confidence is **medium** for externally observable impact where it depends on scheduler timing, filesystem crash semantics, extension manifests, or vendor SAI behavior; those are explicitly routed to model checking or integration tests.
