## Oracle and reachability limits to preserve in the final validation result

- Standard `MC.cfg` has `CrashLimit=1`, `RequestLimit=2`, and no integration framing. Passing it does not establish the three-recovery combinations reserved for S2/S3/S4.
- The active histories are stronger than current-log comparisons: `CommittedPrefixAgreement` keeps historical execution agreement, checks original invocation arguments, and compares each replica's installed committed prefix with its actual prior executions (`base.tla:552-557`). It catches integration mutation when that mutation executes even if every survivor agrees on the same wrong value.
- `CommittedHistorySurvives` checks installation events (`301-312`), including a later DVC dropping an already executed earlier-view suffix. It is not an independent recoverability oracle over every combination of current replicas and in-flight buffers. If a committed entry disappears without a later conflicting installation, execution, or read, a continuation may be needed to expose harm. `brief-coverage.md` already records this limit; preserve it after a green run.
- The stable liveness workload is three total calls, with at most one before stabilization. Successful temporal checking would concern this bounded stream under the explicit synchronous scheduling premise, not an infinite sustained-work theorem. `BoundedNewWorkIsAdmitted` prevents success from simply omitting the reserved new calls.
- `LivenessBoundsNotReached` is an assurance alarm, not a source correctness invariant. If it fires, report that coverage limit rather than a core defect; if a BFS/simulation times out, report its explored coverage rather than a completed proof.
- The N=2 trace uses zero failure budget, correctly reflecting quorum two and no one-failure availability guarantee. A fresh recovery needs two external responders but can contact only one (`1171-1173,1404-1409`); that is a supported-configuration/availability-contract question, outside the within-budget crash hunt.
- Authentic content/identities, fixed membership, fresh recovery nonce, deterministic fresh application state on recovery, persisted views, and ordered per-client requests are the model assumptions. The kvstore EOF transport failure is a separate integration finding and should not be attributed to the core protocol under content-preserving transport.
