# CR-4 Investigation

## Finding

- ID: CR-4
- Source: Code Review
- Title: View file rename is released without durable directory publication
- Primary location: `examples/kvstore/main.rs:569`

## Step 1: Code Audit

### Cited code

- `examples/kvstore/main.rs:569-579`: `persist_view(path, persisted, view)` writes `"{view}\n"` to `"{path}.tmp"`, opens and `sync_all()`s the temporary file, then renames the temporary file over `path`. On `Ok(())`, it updates the in-memory `persisted` cache. There is no open or `sync_all()`/`fsync` on the parent directory after the rename.
- `examples/kvstore/main.rs:683-701`: startup reads `kvstore-node-N.view`; if it parses, startup calls `Replica::recover(..., view, nonce)`, otherwise it calls `Replica::new(...)`. It immediately calls `persist_view(...)` for the initial/recovered view.
- `examples/kvstore/main.rs:739-750`: after each event, the loop calls `replica.on_idle()` or handles a command/message, then calls `persist_view(&view_path, &mut persisted_view, replica.view_number())`, then `flush(...)`.
- `examples/kvstore/main.rs:545-566`: `flush(...)` drains replica messages, replies, and client messages to the sender thread/local client connection.
- `lib.rs:14-21`: the library documents the owner obligation: persist `Replica::view_number()` after every step and before delivering what the step produced; otherwise a replica can forget a view change and let two views run at once.

### Call chain and reachability

Normal example operation reaches the cited path:

1. `main()` starts the kvstore node, reads `kvstore-node-N.view`, creates or recovers a `Replica`, and calls `persist_view(...)`.
2. The main event loop receives `Event::Peer`, `Event::Command`, `Event::Disconnect`, or `Event::Tick`.
3. For events that may advance the replica/client state, the loop calls `persist_view(...)` before `flush(...)`.
4. `flush(...)` releases protocol messages and client replies generated by the step.

No caller-side guard was found that syncs the directory after `persist_view(...)` returns. The simulator models the same ordering in memory (`durable_view[id] = replica.view_number()` before drain/send in `simulator/lib.rs:944-947`) but does not model directory-entry loss after rename.

### Trigger scenario

A reachable trigger under the supported crash model is:

1. A kvstore node processes an event that advances `replica.view_number()`.
2. `persist_view(...)` writes and syncs `kvstore-node-N.view.tmp`.
3. `persist_view(...)` renames the temp file to `kvstore-node-N.view` and returns success, without syncing the parent directory.
4. The event loop calls `flush(...)`, releasing messages/replies that depend on the new view having been durably published.
5. A host/filesystem crash occurs before the parent directory entry is durably committed.
6. On restart, `main()` may read the old view file or no view file; that value is passed into `Replica::recover(...)` or `Replica::new(...)`.

## Step 2: Developer-Knowledge Search

### Comments and docs

- `README.md:69-72` says the owner must store `view_number()` after each step, before delivering outputs, and pass it to `Replica::recover` on restart.
- `README.md:85` marks recovery as done with a persisted view number.
- `examples/kvstore/README.md:38-39` says only the view number is stored on disk and a restarted node recovers the rest from others.
- `examples/kvstore/main.rs:683-685` repeats that the view number is the one thing that must survive a crash.

These docs show intent to rely on durable view persistence before releasing outputs. I found no nearby comment documenting that `persist_view` intentionally omits parent-directory syncing or excludes filesystem crash durability.
