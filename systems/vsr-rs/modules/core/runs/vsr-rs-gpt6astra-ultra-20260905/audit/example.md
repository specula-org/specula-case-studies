## Structure and atomicity

- `Store::apply` implements deterministic single-word Put/Get over an initially empty map (`main.rs:40-65`); main initializes `Store::default()` for both new and recovering replicas (`main.rs:690-700`). HashMap enumeration does not affect behavior: operations only insert and retrieve a named key. Keys/values being single words is documented (`examples/kvstore/README.md:37`) and enforced by client parsing (`main.rs:424-440`).
- The owner event loop serializes all replica and client mutations (`main.rs:711-750`). Peer readers and client connections have separate threads, plus one timer thread and one sender thread (`main.rs:397-414`, `478-499`, `653-681`). An individual Replica call is atomic with respect to other events; event handling, persistent publication, and actual output delivery remain separate boundaries.
- After each event, `persist_view` returns before `flush` releases newly produced replica messages and replies (`main.rs:749-750`). The initial view is persisted before event processing (`main.rs:701`). A storage-write error exits before that flush (`main.rs:575-583`). These are real compensations: the example does not simply omit persist-before-send ordering.
- Client socket handlers wait for a reply before reading the next command (`main.rs:454-472`), matching one outstanding request per logical client (`lib.rs:274-277`). Responses are routed by client ID and accepted only by the client's pending request number (`main.rs:528-539`, `lib.rs:334-347`). Retransmission is driven every five consumed ticks (`main.rs:739-745`, `lib.rs:350-369`).
- Library `commit_up_to` applies an ordered prefix (`lib.rs:1349-1376`). Recovery starts with an empty application and reconstructs state through ordered application without emitting recovery replies (`main.rs:697`, `lib.rs:1203-1205`). Local reapplication after lost volatile state reconstructs a replica; it is not by itself duplicate logical service execution. Store Put idempotence alone is insufficient to prove absence of duplicate logical execution for the general StateMachine contract.

Primary documentation supporting the platform-level limits: [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html) explains separate directory-entry persistence; [Rust SystemTime](https://doc.rust-lang.org/std/time/struct.SystemTime.html) documents non-monotonic wall clocks; [Rust TcpStream::set_write_timeout](https://doc.rust-lang.org/std/net/struct.TcpStream.html#method.set_write_timeout) documents blocking writes without a timeout. These were consulted live; the code inference and its limits are stated above.

The [official Linux man-pages project](https://www.kernel.org/doc/man-pages/) links its online pages to man7.org, confirming the filesystem reference's primary-source provenance. The event and frame queues are created with `std::sync::mpsc::channel` (`main.rs:650-651`): [Rust channel documentation](https://doc.rust-lang.org/std/sync/mpsc/fn.channel.html) specifies an unbounded asynchronous FIFO. There is no application-level priority, coalescing, or dropping of Tick events in `main.rs:716-747`. Tick generation can therefore continue while event consumption is paused, and queued logical ticks can subsequently be consumed more quickly than their original production interval. This describes the scheduling abstraction, not a demonstrated protocol failure.

## Known mechanism details, exclusions, and limits

- Known backoff: `main.rs:364-390` records failures for both failed connects and failed writes and drops frames during 500ms; `TICK=100ms`, primary timeout five periods (`main.rs:30-35`). The owner's alternative is relevant evidence of active example-availability investigation, not an accepted fix already in target.
- Known disconnect cleanup: read error (`main.rs:455`) and writes (`460`, `472`) return before Disconnect (`474`), leaving an existing Connection in the main loop map (`725-728`, `736-738`). A failed initial `try_clone` (`452`) occurs before any command creates that map entry and is therefore excluded as a map-entry leak by itself. The PR likewise still uses `try_clone()?` before the loop. While blocked on a pending reply (`469`) the thread does not read socket EOF; this is a related lifecycle limit rather than an independently claimed new defect.
- Known identity reuse: `main.rs:485-491` combines an eight-bit routing prefix, 24-bit wall-clock seconds, and an unbounded connection counter, then casts to `usize` at `726`. It has no persistent restart epoch. It is already #9 (3). The bit layout also presumes a 64-bit ClientID, fewer than 256 replicas, and a fitting connection counter without validation (`main.rs:501-503`, `628-629`); these are related representation/portability review obligations, not additional confirmed failures.
- No in-scope non-deterministic Store result was found. Keys/values are parsed using the same whitespace restriction used in protocol encoding (`main.rs:79-96`, `215-233`, `424-440`); authentic frames generated by the example do not lose embedded whitespace because the client interface does not admit it.
- Raw peer sockets are not authenticated (`main.rs:397-414`). The task assumes authentic messages, so malformed/forged peer-frame effects are excluded from core correctness findings. This audit did not construct or send abnormal wire data. Parser hardening and secure deployment would be separate scopes.
- No example regression suite or failing execution was run. No simulator-reproduced bug exists from this subtask; the user AGENTS.md regression-test requirement was therefore not triggered.
- Integration API obligations should remain assumptions in the primary conforming-library model. The concrete example filesystem, clock, and socket behavior belongs to code review and integration verification, or a separately labeled wrapper model. Do not introduce a contract-violating client/nonce/persistence input as evidence of a library bug.

## Independent follow-up: singleton API configuration

The parent requested an independent read-only cross-check of the one-member edge. `Config::new`/`add_replica` imposes no minimum beyond the caller adding members (`lib.rs:75-107`), and simulator option validation explicitly allows `replica_count >= 1` (`simulator/lib.rs:259`), while randomized defaults use 3 through 7 (`simulator/lib.rs:226`). A full `.rs`/`.md` text search found no documented singleton restriction. The example argument validator also accepts one address with node ID zero (`main.rs:628-629`).

**EX-Q1 — no-fault singleton request progress, code-review/test-verifiable candidate.** `on_request` registers the primary's own acknowledgement (`lib.rs:684`) but tests no quorum at that point. It then sends only to other members (`686`, `1404-1408`). The normal primary commits only when `on_prepare_ok` accepts an additional distinct acknowledgement (`737-767`). Primary idle handling sends heartbeats and retransmits Prepare without a local quorum check (`1235-1253`); client retransmission of the already-appended request returns while its reply is absent (`662-672`). No compensating normal path was found. This is a supported-configuration/progress edge, distinct from attempting to recover a one-member cluster when its only replica's volatile state is gone (which lacks a sufficient available recovery quorum). No execution or reproduction was performed. Keep it in code-review/test verification, outside the central multi-replica model-checking scenarios.
