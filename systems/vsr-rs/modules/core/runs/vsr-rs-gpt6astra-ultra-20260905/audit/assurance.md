## What the existing simulator actually checks

The default set contains seven properties (`simulator/properties.rs:38-48`). It is substantially stronger than comparing current accumulator totals:

| Property | Established by its code | Boundary of the claim |
|---|---|---|
| CommitNumberMonotonic | Each sampled replica has `commit <= log.len`; log-derived op number equals length; commit never decreases within an incarnation (`107-150`). | Its saved commit resets on reboot (`119-122`), correctly permitting reconstruction from zero. |
| StateMatchesCommittedLog | Applied history length equals commit; each newly observed applied operation matches its committed log position; expected application value folds the operations in order (`153-204`). | Already verified positions are skipped (`185-195`); after reboot, expected value/history starts at the default state (`166-169`). |
| CommittedPrefixAgreement | A global `canonical` prefix records every newly observed committed entry; future newly observed commits must match it (`207-246`). | This is historical, not just pairwise current agreement. Per-replica cursors reset on reboot, but `canonical` does not. Existing verified slots are not reread and final convergence does not require the final core to reach canonical length. |
| NoDuplicateOps | Newly observed committed `op.id` values must be unique within each replica incarnation (`250-288`). | The set/cursor resets at reboot (`264-267`). Its identity is the workload's globally assigned operation id, not directly the protocol's `(client_id, request_number)` key. |
| RepliesMatchCommits | Each retained client reply has a matching committed logical request and the expected sequential result; duplicate replies are permitted; finalization requires a reply for every expected committed request (`291-363`). | The expected map and cumulative value survive reboots, but learn newly committed history from the currently furthest replica (`315-331`). They assume that earlier committed history is unchanged. |
| Durability | For each newly observed committed position, sufficient non-recovering replicas hold that entry to intersect every quorum among the current non-recovering participants (`51-104`). | It does not recheck already verified committed entries when support changes later. The support threshold accounts for recovering replicas; this is not a naive unconditional majority check. |
| Convergence | The final selected core has identical full logs, commits all entries, and equal final application values (`365-408`). | It does not explicitly require Normal status, same view, or completed recovery; it compares the current core rather than requiring coverage of all historical committed positions. |

The accumulator records every applied operation (`simulator/state_machine.rs:36-52`), so additions/subtractions commuting in their final value do not make operation reordering invisible. The history comparison and sequential reply oracle matter. The restricted workload remains a choice: all applications start from `Accumulator::default()`; inputs are only wrapping Add/Sub; each operation embeds a simulator-wide unique id (`simulator/workload.rs:12-18`; `simulator/lib.rs:471-475,698-703,840-844`). This does not establish the public generic application's semantics for every deterministic state machine.

Clients obey single-outstanding-request discipline: `client_inflight` blocks another submission until a matching reply (`simulator/lib.rs:834-848,955-960`); identities are fixed and never restarted (`474-476`). Within this workload each protocol request key has one stable unique `op.id`, so `NoDuplicateOps` does detect repeated committed slots for that logical request. A service specification should express uniqueness by the actual client/request key without importing a synthetic application field as a service obligation.

## Verified assurance gaps and model implications

### A1. Commit-time checks are not continuous historical preservation

`Durability.verified` skips all committed slots already checked (`simulator/properties.rs:89-101`). `CommittedPrefixAgreement` retains a canonical historical prefix, but only compares newly observed slots (`233-244`); `StateMatchesCommittedLog` makes the same append-only assumption (`185-195`). Final convergence compares only final live-core log/value state (`378-407`), and `pending()` does not compare that state with the historical canonical length (`simulator/lib.rs:793-807`). Thus the observer implementation assumes some of the intended preservation: once checked, old committed positions/content/support are not continuously checked. This is a verified checker boundary, not evidence that a permitted library execution violates preservation.

Recommended service-level history: a monotonic ghost committed sequence and a monotonic set of completed client results that survive all replica reboots, accompanied by historical emitted acknowledgements and installed-view log provenance. Check each handler boundary against the ghost sequence and continuously check that a sufficient admissible non-recovering support set preserves its required prefix. Allow replacement of genuinely uncommitted suffixes. Do not require a recovering replica's empty log to hold that prefix until it rejoins protocol participation.

### A2. Tick-level observation and output batching narrow the schedule

One tick runs client submission, crash/restart decisions, all due idle calls, all due message deliveries, then properties (`simulator/lib.rs:712-718`). All due messages are processed sequentially before checking properties (`907-926`); the second flush drains their accumulated outputs. Hence a property is not checked after each `on_message`, each application callback, or each output emission.

The transport does support authentic message loss, duplication, independent exponential delay and reordering (`simulator/network.rs:147-175,186-225`), including same-link reorder; it is not FIFO. Duplicate injection creates at most one extra copy of each send, with protocol retransmissions adding further sends. All replica/client idle calls share one global cadence (`simulator/lib.rs:891-900`) and the same configured timeout. The public owner can schedule distinct replicas independently while honoring regular local timers (`README.md:50-71`). Model individual handler and timer steps with suitable stable-period fairness and timing assumptions, not just the exact tick batch order.

The simulator synchronously persists `view_number` before draining any replica output (`simulator/lib.rs:944-950`). This honors the required output-ordering obligation, although multiple handlers can be processed before that flush. It models no persistence delay/error or crash between a handler and its caller's durable write. A library model should keep unsent outputs separate from delivered network messages and enforce persist-before-release. A permitted crash before persistence must lose volatile outputs; do not invent an output-before-persistence path and blame the library.

### A3. Request and reply transport have different coverage

`Network` transports `Message<Op>` to replica ids; `Reply` is separate (`simulator/network.rs:24-30`; pinned `lib.rs:133-135`). Even when `fault_client_messages` is true, that option affects client requests (`simulator/network.rs:157-160`), while replies go straight from `drain_replies` to client `on_reply` and retained oracle history (`simulator/lib.rs:950-962`). Reply loss, delay, duplicates introduced by transport, and reordering are therefore not injected. Duplicate replies produced by protocol retransmission are checked.

Model reply creation and delivery separately, retain accepted invocation identity and prior client completions, and check returned values against a deterministic sequential reference independent of implementation client-table updates. Reboot replay may invoke `apply` again to reconstruct a fresh replica's state; that is not a second logical request commit. Track application history per replica incarnation and logical service history globally. Initial application states must be compatible (`Replica::new`/`recover` receive an application object; `lib.rs:478-487,505-524`) instead of assuming the implementation can repair arbitrary divergent application initialization.

### A4. Stable convergence differs from service and recovery liveness

The automatic crash action preserves all replica state; Restart resumes it unchanged (`simulator/lib.rs:42-47,610-625`). Reboot explicitly replaces it with `Replica::recover` using durable view and fresh application state, resetting appropriate property cursors (`694-708`). The random reboot gate bounds the number currently recovering to `f=(N-1)/2` (`869-880`). Random retained-state crashes are not bounded by that gate; fault scripts bypass it entirely (`606-637`). Do not treat more than `f` simultaneous unavailable replicas during fault injection as a service-progress counterexample. Distinguish a pause, loss of volatile state, and the recovery interval in the model's failure budget.

The liveness transition disables new network faults, heals partitions, selects at least a quorum of non-recovering replicas first, brings the selected core up, and keeps the others down (`simulator/lib.rs:729-780`). This is an explicit compensation for recovery counting toward the failure budget. Existing in-flight delays remain; eventual stable communication is stronger than the noisy safety phase. New client submissions stop in this mode (`823-825`), but existing clients keep retrying on idle (`898-900`). `pending()` requires no sent-but-unreplied requests, no queued messages, and a fully committed equal-length core before finalization (`786-807`). It is thus more than a log-equality-only test, yet it is a bounded quiescent-run check rather than a quantified service guarantee under continued workload.

`pending()` and `Convergence.finalize` do not explicitly check core status or recovery completion (`simulator/lib.rs:793-807`; `simulator/properties.rs:378-407`). They can only establish recovery completion indirectly when the data and remaining-message conditions entail it; the assertion itself is absent. Specify `PendingRequest ~> MatchingReply` and `Recovering(r) ~> Normal(r)` as separate leads-to properties with a stable reachable non-recovering quorum, compatible timers, and fair delivery/retry assumptions. Progress does not require an empty network or all replicas, including permanently unavailable ones, to converge.

Harness outcome caveat: `requests_done` records whether all `requests_max` replies arrived before the safety-to-liveness transition (`simulator/lib.rs:566-576`). It is not refreshed when replies arrive during liveness. Therefore a run that transitions after the no-reply budget and later drains successfully still fails the final `!requests_done` branch (`586-592`). This is a verified outcome-definition choice; distinguish “did not finish the configured workload in the fault phase” from “an outstanding legal request fails to finish after stability.” No new simulator trace was run to evaluate how often this condition occurs.

## Retained Lean: proof status, semantic scope, conformance

Immutable source links use the archived revision, not current main: [README](https://github.com/penberg/vsr-rs/blob/de1a84376afe1102c197c2e0f4ade41eb4494458/lean/README.md), [System](https://github.com/penberg/vsr-rs/blob/de1a84376afe1102c197c2e0f4ade41eb4494458/lean/Vsr/System.lean), [Invariant](https://github.com/penberg/vsr-rs/blob/de1a84376afe1102c197c2e0f4ade41eb4494458/lean/Vsr/Invariant.lean), [Check](https://github.com/penberg/vsr-rs/blob/de1a84376afe1102c197c2e0f4ade41eb4494458/lean/Vsr/Check.lean), [Liveness](https://github.com/penberg/vsr-rs/blob/de1a84376afe1102c197c2e0f4ade41eb4494458/lean/Vsr/Liveness.lean), [conformance](https://github.com/penberg/vsr-rs/blob/de1a84376afe1102c197c2e0f4ade41eb4494458/verify/lib.rs).

The retained README distinguishes proved local bounds/message well-formedness from unfinished global safety and general liveness (`lean/README.md:27-35,158-182`). Those status claims were checked against theorem bodies: `Safety.lean:184-205` proves message well-formedness/commit bounds and leaves `safety` as `sorry`; `Liveness.lean:89-93` leaves general `settles` as `sorry`. This audit does not rerun Lean or independently recheck compiled proof objects.

The proposed invariant is significantly historical. `System.sent` and `System.started` only grow (`System.lean:12-19,47-55`), and `Invariant.Committed` means a historical fragment plus distinct-sender quorum acknowledgements (`Invariant.lean:31-62`). `Survives` requires that history to cross future views (`90-99`). An acknowledgement is keyed by sender id/view/op-number, without replica incarnation (`53-58`); this does not count one sender twice. Same-view historical acknowledgements remain meaningful only if recovery reestablishes their promises. The stated helper clauses `AcksHold`, `StartedVotesCover`, and `RecoveryCoversAcks` express that obligation (`121-123,181-183,201-204`). Their global inductiveness remains open, so the absence of an incarnation field alone is not evidence of an error.

One concrete property-coverage difference deserves preserving in the handoff: the formal `Survives` antecedent is any historically quorum-acknowledged entry (`Invariant.lean:60-62,90-99`), whereas executable `committedSurvives` loops over entries currently committed on a replica (`Check.lean:283-301`). The latter does not literally check the same domain when no current replica commit cursor reaches a historically acknowledged slot. Treat passing candidate checks as evidence on their actual definitions, not as execution of every quantified theorem clause.

The safety theorem's target is `NoPanic`, pairwise current `PrefixAgreement`, and `Durability` (`Safety.lean:25-46,202-205`); it states no independent logical exactly-once, sequential application, or reply-correctness theorem. The executable all-check list likewise contains protocol/log obligations but no client-result reference oracle (`Check.lean:319-345`). This is a scope limitation, not a defect claim.

The operational model permits independent Idle and arbitrary historical message delivery; it is not FIFO (`System.lean:21-32,64-73`). Its bare Step allows arbitrary request parameters and recovery nonces and imposes no cumulative failure-budget precondition. The conformance generator separately chooses globally increasing nonces, two fixed clients, one outstanding request each, and 3/5 replicas; it does not guard its recovery actions by the failure budget (`verify/lib.rs:340-395`). A new specification should explicitly encode contract assumptions instead of assuming the operational model and test generator have identical reachable domains.

Conformance executes one replica step and drains it, then compares all current replica statuses/views/commit numbers/logs/applied-operation sequences and all new sends/replies (`verify/lib.rs:112-189,289-307`; `lean/Main.lean:104-117`). Both sides use a recorder application returning its history length (`verify/lib.rs:16-30`; `lean/Main.lean:24-27`), and the replica definitions deliberately track Rust control flow (`lean/Vsr/Replica.lean:3-9`). This validates observational correspondence on generated traces, not the service contract independently. Private client/ack tables and timers are only exposed by later observable effects. The standard conformance test has 40 seeds × 200 steps and skips if `lake` is unavailable (`verify/verify_tests.rs:10-11,88-102`); the retained README's larger historical campaign is a report, not a campaign rerun here.

Lean liveness uses synchronous rounds that idle every replica, deliver all due messages, and retain new output for the next round (`Liveness.lean:50-57`). `settled` requires all replicas Normal in one view with an empty queue, and starts after discarding prior in-flight messages (`63-78`); it does not submit clients or state a matching-reply obligation. The general theorem is open, while the bounded executable oracle searches 1,000 rounds (`Check.lean:303-315`). Do not promote quiescent settlement or the existing repaired storm example into a general service-liveness proof.

## Exclusions / false-positive controls

1. Exclude “the simulator checks only current replica pairs”: its canonical committed history survives reboots.
2. Exclude “the commutative accumulator cannot catch reordering”: it also stores and checks ordered applications and sequential reply results.
3. Exclude “all re-execution after reboot violates exactly-once”: reconstruction of a fresh replica's deterministic state is permitted; use logical requests and incarnation-scoped application histories.
4. Exclude “recovery needs only any up majority”: the liveness core explicitly prioritizes non-recovering replicas, and the protocol failure budget includes recovery.
5. Exclude “simulator transport is FIFO”: independent delays reorder even same-origin messages.
6. Exclude “the simulator forgot view persistence”: its flush persists before output release. Persistence failures/crash windows are simply absent from this abstraction.
7. Exclude “Lean has proved general preservation/liveness”: the retained global theorem bodies are unfinished, as documented.
8. Exclude “unfinished proofs demonstrate an implementation defect”: they establish no such conclusion.
9. Exclude “passing conformance independently proves service semantics”: observable agreement between aligned operational models has a different objective.
10. Exclude out-of-contract client pipelining as a core service defect: several hand-driven integration fixtures submit requests without waiting (`tests/cluster.rs:197-199,233-234,475-477`), but the public client discipline remains single outstanding (`lib.rs:274-277`). These fixtures are useful protocol regressions, not a relaxation of the public contract.

## Handoff priorities

- S1: Preserve historical committed prefixes and acknowledged obligations across view changes, state transfer, and valid recovery; distinguish client acceptance, quorum acknowledgement, local commit/application, and reply delivery.
- S2: State sequential application/reply semantics independently of the implementation client table; use `(client, request)` identity and explicit compatible initial state and replica incarnation.
- S3: State pending-client and individual-recovery progress under a stable non-recovering quorum and suitable local timer/message fairness; do not use quiescent convergence as their substitute.
- S4: Separate contract constraints from simulator/Lean workload, scheduler, persistence, observation, and property choices. Validate after each handler boundary and maintain historical ghost observations across reboots.
- Existing repaired regression mechanisms remain historical evidence. No reproduction of an already fixed regression is proposed as a new model-checkable finding.
