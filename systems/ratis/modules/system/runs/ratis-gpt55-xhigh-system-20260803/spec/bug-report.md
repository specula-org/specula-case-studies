## Bugs

### MC-1: Stale AppendEntries SUCCESS after higher-term vote can let an old leader commit an entry absent from the new leader

- Severity: High
- Status: MODEL_CHECKED_SOURCE_CONFIRMED
- Invariant: `LeaderCompleteness`
- Configs: `MC.cfg`, `MC_hunt_scenario1.cfg`
- Evidence:
  - `output/mc/MC_convergence_round3.log`
  - `output/mc/MC_convergence_round3_trace.json`
  - `output/hunt/MC_hunt_scenario1_sim.log`
  - `output/hunt/MC_hunt_scenario1_sim2.log`
- Counterexample summary: a follower accepts an AppendEntries request from an old leader, then grants a higher-term vote before the asynchronous physical append finishes. The follower later returns `SUCCESS` using the old captured term, and the old leader counts that reply to commit an entry that the newly elected leader does not contain.
- Affected code:
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/RaftServerImpl.java:1523`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/RaftServerImpl.java:1669`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/RaftServerImpl.java:1730`
  - `ratis-grpc/src/main/java/org/apache/ratis/grpc/server/GrpcLogAppender.java:519`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/LeaderStateImpl.java:953`
- Root cause: `appendEntriesAsync` captures the current term before asynchronous append completion and builds a later `SUCCESS` reply without rechecking whether the follower has since advanced term or granted a vote. The leader-side `SUCCESS` handler updates follower progress without rejecting a stale-term success reply.
- Recommendation: after the append future completes, re-read the follower's current term/leader state and return `NOT_LEADER` or an inconsistency result if term or leadership changed. The leader-side success handler should also validate reply term before updating match/next index.

### MC-2: Append compose can return SUCCESS for a mismatched future at the same start index

- Severity: High
- Status: MODEL_CHECKED_SOURCE_CONFIRMED
- Invariant: `AppendSuccessReflectsLog`
- Config: `MC_hunt_scenario1.cfg`
- Evidence:
  - `output/hunt/MC_hunt_scenario1_sim3.log`
  - `output/hunt/MC_hunt_scenario1_sim3_trace.json`
- Counterexample summary: a new leader sends AppendEntries at the same start index as an older in-flight append. The compose map reuses the old append future and the follower can reply `SUCCESS` for the later leader/term/value even though the follower stored the older term/value.
- Affected code:
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/ServerImplUtils.java:150`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/ServerImplUtils.java:163`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/RaftServerImpl.java:1713`
  - `ratis-server-api/src/main/java/org/apache/ratis/server/RaftServerConfigKeys.java:475`
- Root cause: `NavigableIndices.alreadyExists` deduplicates append work by `startIndex` only. With append compose enabled by default, a later request at the same index can observe an old future rather than forcing term/value validation and truncation.
- Recommendation: deduplicate append work by the full term/index range or reject/retry same-index requests whose term/value differs from the in-flight work. A follower should not send `SUCCESS` unless its durable log or snapshot contains the exact term/value being acknowledged.

### MC-3: Metadata persist failure can leave an accepted leader term non-durable

- Severity: Medium
- Status: MODEL_CHECKED_SOURCE_CONFIRMED
- Invariant: `PersistedTermBeforeAccept`
- Config: `MC_hunt_scenario2.cfg`
- Evidence:
  - `output/hunt/MC_hunt_scenario2.log`
  - `output/hunt/MC_hunt_scenario2_trace.json`
  - `output/hunt/MC_hunt_scenario2_rerun.log`
  - `output/hunt/MC_hunt_scenario2_rerun_trace.json`
- Counterexample summary: `changeToFollowerAndPersistMetadata` advances the in-memory term, but metadata persistence throws. A later same-term heartbeat or AppendEntries can be accepted without retrying persistence because `ServerState.updateCurrentTerm(newTerm)` returns false when the volatile term already equals the new term.
- Affected code:
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/RaftServerImpl.java:642`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/RaftServerImpl.java:1669`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/ServerState.java:213`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/ServerState.java:337`
- Root cause: the implementation can leave a dirty in-memory term after a failed metadata persist, then skip the persistence retry for same-term leader recognition.
- Recommendation: track dirty term/vote metadata after a failed persist and require a successful retry before accepting same-term leader requests or returning successful follower responses. Restart should not observe an accepted leader term that was never durably persisted.

### MC-4: Higher-term step-down event can be dropped by type-only queue deduplication

- Severity: Medium
- Status: MODEL_CHECKED_SOURCE_CONFIRMED
- Invariant: `StepDownTermNotLost`
- Config: `MC_hunt_scenario2.cfg`
- Evidence:
  - `output/hunt/MC_hunt_scenario2_rerun2.log`
  - `output/hunt/MC_hunt_scenario2_rerun2_trace.json`
- Counterexample summary: a leader already has a queued `STEP_DOWN` event. A later follower response observes a higher term and submits another `STEP_DOWN`, but the event queue drops it because equality compares only the event type. The lower-term queued event may run while the higher observed term is never persisted.
- Affected code:
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/LeaderStateImpl.java:128`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/LeaderStateImpl.java:155`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/LeaderStateImpl.java:507`
  - `ratis-server/src/main/java/org/apache/ratis/server/impl/LeaderStateImpl.java:740`
- Root cause: `StateUpdateEvent.equals` and queue de-duplication use only the event type, so term-carrying `STEP_DOWN` events with different terms collapse into one pending event.
- Recommendation: include term in step-down event identity, replace queued step-down with the maximum observed term, or update/persist the higher term synchronously before de-duplication can discard it.
