# Validation Changelog

## Round 1 - Trace Validation
- [init] Phase 0 complete: verified base/Trace/MC specs, four NDJSON traces, six hunting configs, instrumentation spec, and harness instrumentation notes.
- [fix] TraceSpec: added weak fairness for TraceNext so TraceMatched reports real trace blockage instead of arbitrary stuttering counterexamples (Trace: all traces).
- [fix] RaftServerImpl_requestVote_Grant: allowed a higher-term candidate to replace an old-term votedFor value, matching VoteContext.checkTerm and ServerState.updateCurrentTerm clearing votedFor before grantVote (Trace: leader-loss-restart.ndjson).
- [fix] LeaderStateImpl_stepDown: modeled direct current-term stepdown without a queued StateUpdateEvent for lost-majority heartbeat/read-index paths, while preserving queued higher-term stepdown semantics (Trace: grpc-reconnect-timeout.ndjson).
- [fix] appendEntries leader recognition: higher-term append/register/compose/inconsistency paths now clear vote metadata and persist the recognized term before accepting or replying, matching RaftServerImpl.appendEntriesAsync and ServerState.updateCurrentTerm.
- [fix] Trace heartbeat/register bridge: added trace-only leader-recognition heartbeat and observed inconsistency-reply bridges for events where the harness records post-recognition state but compresses the original request/retry cleanup.
- [fix] LeaderStateImpl_updateCommit trace bridge: allowed a compressed bootstrap/current-term entry to justify commit advancement without relaxing base CanCommit for model checking; skipped appliedIndex post-state validation on commit events where apply is emitted separately.
- [fix] ConfigurationManager purge trace bridge: accepted observed leader/term state and unchanged logical log frontiers caused by per-server index compression.
- [fix] RaftServerImpl_changeToLeader: initialized follower nextIndex to leader logEnd + 1, matching LeaderStateImpl follower initialization.
- [fix] HasLogAt: treated nonzero-term NoEntry placeholders as log entries so compressed startup/config/no-op entries can carry Raft term/index facts.
- [fix] Trace SUCCESS bootstrap bridge: modeled old-stream/bootstrap SUCCESS replies that advance follower progress without a matching current pending request, including stale pending cleanup.
- [fix] Trace RegisterInFlight compressed prefix bridge: synthesized a one-entry NoEntry prefix only when per-server logical indexing hid the previous raw entry but leader progress already observed the prefix.
- [fix] TraceLogMatching: Trace.cfg now uses a trace-only log matching predicate that treats NoEntry placeholders as non-user-entry wildcards; MC.cfg still uses strict base LogMatching.
- [result] Trace validation converged: normal-consensus-read.ndjson, leader-loss-restart.ndjson, grpc-reconnect-timeout.ndjson, and snapshot-catchup.ndjson all pass.

## Round 2 - Model Checking
- [case-a] MC.cfg first run found a LeaderCompleteness counterexample caused by over-approximated old-stream SUCCESS progress: the model allowed a delayed SUCCESS reply to advance follower matchIndex for an entry the follower did not contain.
- [fix] GrpcLogAppender_AppendLogResponseHandler_onNext_SUCCESS_OldStream: require the leader to have the matched entry and the follower/snapshot to contain the same term/value before applying stale-stream SUCCESS progress.
- [case-a] MC.cfg second run found an IndexBounds counterexample where a stale in-flight physical append completed after snapshot reload and lowered logEnd/flushIndex below commitIndex.
- [fix] SegmentedRaftLog_appendImpl_CompletePhysicalAppend: require the append start to remain AppendConsistent at completion time, so a future invalidated by snapshot/commit frontier advancement cannot lower log frontiers.
- [bug] LeaderCompleteness: MC.cfg third run found a reachable stale append-success / higher-term vote race. A follower can accept an AppendEntries request, grant a higher-term vote before the asynchronous physical append completes, then return a SUCCESS reply using the old captured term; the old leader can count that reply and commit an entry absent from the newly elected leader. Evidence: `output/mc/MC_convergence_round3.log` and `output/mc/MC_convergence_round3_trace.json`.
- [fix-inv] LeaderCompleteness: added a narrow `KnownBug_StaleAppendSuccessAfterVote` exception so the recorded Case C does not mask later model-checking violations; this does not treat the implementation behavior as safe.
- [case-b] MC.cfg fourth run found a LeaderCompleteness counterexample caused by global follower progress: s1's successful replication to s3 updated the model's one-dimensional `matchIndex[s3]`, and s2 then reused that progress to commit a different term-1 entry. In Ratis, `FollowerInfo.matchIndex` is owned by a specific `LeaderStateImpl`, not shared across leaders.
- [fix-spec] CanCommit: require counted followers to contain or snapshot-cover the leader's term/value at the committed index, preserving the per-leader progress ownership that the implementation has.
- [fix] TraceLeaderStateImpl_updateCommit_CompressedBootstrap: kept the trace-only bridge for hidden leader-startup placeholder commits after the stricter MC `CanCommit` majority rule; this preserves Ratis trace compression without relaxing MC.
- [fix] TraceLeaderStateImpl_updateCommit_KnownCommittedPrefix: accepted trace-only commit advancement for an already committed logical prefix after re-election, where Ratis' raw startup/metadata entries are compressed out of the trace.
- [fix-inv] KnownBug_StaleAppendSuccessAfterVote: widened the recorded Case C exception to match persisted-vote election evidence even when a later metadata persist failure clears the follower's volatile `votedFor`; evidence: `output/mc/MC_convergence_round5.log` and `output/mc/MC_convergence_round5_trace.json`.
- [fix-inv] KnownBug_StaleAppendSuccessAfterVote: added `voteGranted` history so the same Case C remains recognized after the voter later starts another election and overwrites current vote metadata; evidence: `output/mc/MC_convergence_round6.log` and `output/mc/MC_convergence_round6_trace.json`.
- [fix-inv] KnownBug_StaleAppendSuccessAfterVote: anchored the exception on the still-present in-flight append leader/term instead of requiring the old leader to remain `LEADER` in the final state, covering the same bug after the old leader steps down; evidence: `output/mc/MC_convergence_round7.log` and `output/mc/MC_convergence_round7_trace.json`.
