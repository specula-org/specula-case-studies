## Round 2 - Model Checking
- [case-b] Invariant fidelity: weakened `NextBeyondMatch`, `StaleReplyNoProgressRegression`, and `PendingResetDoesNotLoseSafety` to the implementation guarantee that `nextIndex` remains at or above `LeastValidLogIndex`.  The previous `nextIndex >= matchIndex + 1` claim conflicts with `LogAppenderBase.getNextIndexForInconsistency`, which intentionally may return `requestFirstIndex - 1` after an INCONSISTENCY reply; match/commit proof indexes carry safety.
- [case-a] Follower inconsistency reply generation: constrained newly generated INCONSISTENCY replies after a proven follower snapshot boundary to `replyNext >= snapshotIndex + 1`, matching `RaftServerImpl.checkInconsistentAppendEntries` plus `ServerState.getNextIndex/containsTermIndex`.  Pre-existing old replies remain modeled through `replyQueue` and `OldAppendReplyAfterSnapshot`.
- [case-a] Staging restart lifetime: made `usefulProgressBeforeRestart` staging-specific by recording it only when the peer is already `StagingNewPeer`, and reset it on `AddStagingPeer`, so an ordinary existing-peer restart cannot retroactively violate `RestartPreservesUsefulProgress` after the peer is later added as staging.
- [case-b] Snapshot retry invariant: narrowed `SnapshotRetryPreservesCatchup` so snapshot unavailable/expired requires `retryRequired` only while the staging peer is still not caught up.  `LeaderStateImpl.checkProgress` may legitimately mark the peer caught up after independent AppendEntries progress satisfies the catch-up predicate.
- [case-b] Restart useful-progress definition: stopped treating `attemptedSnapshot` alone as restart-preserved useful progress.  A failed or unavailable snapshot attempt is a retry signal, not a proven catch-up boundary; `RestartPreservesUsefulProgress` now tracks only match/snapshot indexes that reached `ConfLogIndex`.
