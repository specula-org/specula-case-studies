## Issues Found

- **[Blocking] Both temporal hunt configurations fail during fairness evaluation.** `MC.tla:240-262` uses base actions in `SF_mcvars`/`WF_mcvars`, where `mcvars = <<s, faults>>`, but those actions assign only `s'`. `MCNext` adds `UNCHANGED faults` around ordinary actions; the service operators used by fairness do not. Fresh runs of the unchanged `MC_hunt_s2_progress.cfg` and `MC_hunt_s3_cleanup.cfg` both exit **255**, reporting that the fairness action does not specify the primed value of `faults`. They stop after 14 and 17 distinct states respectively. Give each fairness service a complete MC transition relation, including its counter updates or `UNCHANGED faults`, and rerun the actual `MCFairSpec` configs. The initialization checks in `checks/run-validation.py:28-33` replace `MCFairSpec` with `InitOnlySpec`, removing precisely the fairness that fails; those checks cannot validate temporal execution. Evidence: [dispatch log](output/review-specgen-evidence/MC_hunt_s2_progress.log), [cleanup log](output/review-specgen-evidence/MC_hunt_s3_cleanup.log).

- **[High] Predicate widening is semantically unreachable in the advertised S2 coverage bound.** `base.tla:41-45` widens only when `Cardinality(p) > PredicateLimit`. Every supplied MC config has two groups and a limit of either 0 or 1. Zero disables widening; with limit 1, the only triggering predicate is already `Groups`. Thus `Widen(p) = p` for every subset of `Groups`, including in `MC_hunt_s2_coverage.cfg:6,13`. This contradicts the widening/overlap coverage claimed in `brief-coverage.md:40` and leaves part of brief MC-2 untested. The real size test is predicate representation size (`service/history/queues/slice.go:473-479`), not semantic group cardinality. Represent that distinction, or choose bounds under which a proper subset actually expands, and add a reachable witness showing newly included work and overlapping scopes. A fresh TLC constant assertion over all four subsets confirms the current identity behavior: [probe](output/review-specgen-evidence/ReviewWiden.tla), [log](output/review-specgen-evidence/ReviewWiden.log).

- **[High] A delayed acquisition completion resurrects a stopped owner.** `AcquireShardComplete` checks only `renewPC = "reply"` and unconditionally sets `mode = "active"` (`base.tla:249-260`). `StopReaderGroup` sets `mode = "stopped"` without invalidating that pending completion (`base.tla:263-265`). TLC reaches `active → lost → acquiring → stopped → active`: allocate/append, timeout, begin same-owner renewal, commit the renewal, stop the owner, then complete acquisition. The probe has eight distinct states and violates the expected stopped-state preservation. Temporal explicitly prohibits this: `service/history/shard/context_impl.go:1692-1700,1805-1825` rejects acquisition transitions after stopping; `:2097-2104` handles the rejected completion. Preserve the committed durable range while rejecting the stale lifecycle completion; retain a distinct new owner for reconstruction. Evidence: [probe](output/review-specgen-evidence/ReviewStoppedOwner.tla), [log](output/review-specgen-evidence/ReviewStoppedOwner.log). This is a **model defect**, not a Temporal defect.

- **[Medium] Multi-task batches bind executable identities in logical-task order instead of persisted-key order.** Selection compares `TaskKey`, but `ts == Sort(selected)` sorts logical identities (`base.tla:285-302`). Allocate task 2 first and task 1 second: their keys are 5 and 6. With `BatchSize = 2` and `es = <<1,2>>`, the model assigns executable 1 to key 6 and executable 2 to key 5. SQLite returns ascending task keys (`common/persistence/sql/sqlplugin/sqlite/execution.go:106-107`), and `service/history/queues/slice.go:376-402` preserves that iteration order. This conflicts with the explicitly ordered `es` contract in `instrumentation-spec.md:106` and `TraceSelectTasks` at `Trace.tla:155-159`. Sort selected tasks by `TaskKey` before assigning `es`. Default batch1 fixtures hide this problem; the two-task review probe reaches it in 11 distinct states: [probe](output/review-specgen-evidence/ReviewTaskOrder.tla), [log](output/review-specgen-evidence/ReviewTaskOrder.log).

- **[Medium] Reader admission and partial-read failures are collapsed into unconditional successful loading.** `SelectTasks` permits `lost` and `acquiring` owners and reads directly from current `s.db.rows` (`base.tla:281-302`), without an admitted read request or buffered page. Actual immediate-queue reads call `shard.GetHistoryTasks` (`service/history/queues/queue_immediate.go:44-60`), which checks `errorByState` and rejects an acquiring context (`service/history/shard/context_impl.go:526-535,1130-1140`). Already-admitted calls or buffered rows may still finish; they require separate state to distinguish them from new reads. Also, `service/history/queues/slice.go:378-387` retains a remaining iterator and can return a partial successful batch after a later read error. The model has only full-success or exhausted-partial-success behavior: a non-full selection clears every iterator. Model admission/buffering and the distinct read-error branches, or explicitly narrow S2/S4 coverage to the controlled successful-read projection. `brief-coverage.md:50` and `instrumentation-spec.md:113` already acknowledge part of this limitation; it remains a completeness gap for the requested compositions.

- **[Medium] The MC wrapper bounds ordinary shard-snapshot initiation.** `MCUpdateShardInfoSnapshot` consumes `faults.snapshot` (`MC.tla:57-61`) for the normal neighboring writer modeled by `base.tla:414-418`. Most configs permit only 0–2 such initiations. This can be an explicit finite environmental-workload assumption, but it does not satisfy the checklist's fault-only bounding rule or establish coverage of arbitrary same-epoch snapshot traffic. Use the existing reusable snapshot slots to limit concurrency while leaving ordinary initiation repeatable, or state the finite-writer restriction in every resulting conclusion. Request counting is similarly a workload bound, although currently redundant with the one-use task population.

- **Validation evidence is narrower than full spec convergence.** Fresh SANY analysis of base/MC/Trace passes. An independent static check found all 65 base actions in both the trace wrappers and instrumentation table, with a post-state check in every wrapper. `vars`, `mcvars`, and `tracevars` include all declared variables. The six reviewed TLA/config hashes match the prior generation-validation manifest; its one-task exhaustive result and synthetic adapter tests therefore remain relevant at their stated bounds. They do not cover the newly exposed paths. No full multi-task safety exploration, successful temporal hunt, or implementation-produced trace validation was completed by this review. CR-1 remains the brief's existing source/native finding; none of the review probes establishes a new upstream bug. Commands, frozen inputs, and results are in [review evidence](output/review-specgen-evidence/README.md).
