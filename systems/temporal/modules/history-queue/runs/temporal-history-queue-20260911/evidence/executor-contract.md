## Atomicity and concurrency boundaries

1. A concrete executable is a volatile wrapper around a durable History task. It begins Pending (`executable.go:232-264`). `Execute` checks Pending under its mutex and releases that mutex before calling the actual executor (`273-298`, `402`). Cancel/Abort can therefore interleave with an already-started effect; they cannot retract the RPC. Ack changes only Pending to Acked under the mutex (`742-765`), so cancellation before late Ack prevents that wrapper from changing to Acked. New ownership has distinct readers/executables; old local Ack is not a durable checkpoint publication.
2. FIFO calls Execute, invokes HandleErr on failure, then chooses Nack/Abort or Ack (`common/tasks/fifo_scheduler.go:192-216`). History executables disable retries while occupying the worker; Nack either immediately TrySubmits or enters the rescheduler (`executable.go:709-722`, `768-802`, `860-917`). Rejection from TrySubmit is not acknowledgment.
3. The rescheduler serializes its queue maps and timer gate under one lock. Add publishes both entry and wakeup before unlock (`rescheduler.go:120-135`). A due task remains in its priority queue when TrySubmit returns false; timer backoff re-arms it (`208-240`). Cancelled wrappers are removed. Stop drains volatile references; it does not delete durable History rows (`254-266`). Recovery depends on unfinished task scopes still being durable, which is the parent queue/checkpoint audit's responsibility.
4. The host scheduler is weighted-round-robin over namespace/priority, with a FIFO pool and optional per-execution serialization (`scheduler.go:95-185`, `221`). Invalid/nonpositive configured weights fall back to positive default weights (`131-142`). Fair submission, positive worker count and eventual release of rate limiting are progress assumptions. A finite transient-error bound alone does not imply scheduling fairness under permanent capacity saturation.

## Ordinary Workflow/Activity dispatch: both sides

### History eligibility and release

- `processActivityTask` (`transfer_queue_active_task_executor.go:250-307`) loads workflow state, checks activity exists, stamp matches, not paused, task version matches, workflow running, then copies timeout/directive/priority and releases the workflow lock before AddActivityTask. Already missing/completed/stale activity is an obsolete obligation, not proof required work vanished.
- `processWorkflowTask` (`309-396`) checks running workflow/current scheduled-event task/stamp/version, uses the **queue captured in the Transfer task**, and releases the workflow lock before Matching RPC. Using a later sticky mutable-state queue would lack the corresponding timeout; the source explicitly avoids that. StickyWorkerUnavailable retries the original normal queue with the already-created sticky timeout/TTL; timeout or later worker start repairs stickiness (`367-393`).
- `loadMutableStateForTask` (`ndc_task_util.go:129-205`) validates task vector clock, task-generation clock, and reloads cache when event ID appears ahead of durable state. Transient WFTs have a deliberate exception (`260-279`). An old task clock is allowed; a future task clock unloads the stale shard (`207-231`). This check is not a distributed lock held across the Matching RPC.
- AddActivityTask/AddWorkflowTask carry run identity, scheduled event ID, stamp, priority, and vector clock derived from the History task ID (`transfer_queue_task_executor_base.go:95-198`). Unexpected Matching NotFound is logged, but returned to generic HandleErr, which acknowledges it. Do not synthesize a backend NotFound and call the resulting drop a newly discovered bug without showing an actual eligible-work path that generates it.

### Matching acceptance and later validation

- Matching handlers return the engine's Add result (`service/matching/handler.go:176-227`). The engine validates partition, detects sticky unavailability, copies identity/stamp/vector-clock into TaskInfo, and calls partition AddTask (`matching_engine.go:586-695`). Partition AddTask attempts sync match, otherwise `SpoolTask` and returns its error (`task_queue_partition_manager.go:555-688`).
- Backlog acceptance waits for the task writer: `physical_task_queue_manager.go:470-472` → `backlog_manager.go:164-171` → `task_writer.go:85-119`. The response channel is completed after `db.CreateTasks` returns (`140-177`). This is a persistence acknowledgment boundary, not just an in-memory enqueue. The writer uses task-queue lifetime context, so an originating History request timing out does not prove the write failed.
- Sync match waits for the consuming poller's start result (`pri_matcher.go:390-412`, legacy `matcher.go:108-180`). Matching calls History Record*TaskStarted before handing an ordinary task to the worker (`matching_engine.go:809`, `1036`). History checks current task/running state, stamp and request identity; same request ID can return the previous start response, while a different request for an already started task yields TaskAlreadyStarted (`recordworkflowtaskstarted/api.go:61-121`; `recordactivitytaskstarted/api.go:52-189`). Durable mutations execute through `api/update_workflow_util.go:69-124`, then shard/persistence fencing applies.
- History clock consistency rejects requests ahead of the currently loaded shard clock and unloads it (`api/consistency_checker.go:177-238`). It intentionally accepts comparable **older** clocks. Late old-owner dispatch is thus handled by current workflow state, task identity/stamp and mutation fencing, not blanket RPC rejection by old epoch.
- A successful Matching Add is **not** completed workflow execution. Even a successfully started Activity may require timeout/retry after its poll response is lost; application external effects may be duplicated. The primary queue model should represent Matching responsibility or observed workflow/Activity start separately from final workflow completion.

### Terminal-discard exception to acceptance

Matching deliberately drops History Record*Started `Internal` and `DataLoss` as nonretryable, as well as stale/missing/already-started tasks (`matching_engine.go:810-864`, `1037-1108`). `task.finish` stores a drop reason but nil `startErr` (`task.go:373-403`), and sync Offer returns success/nil when startErr is nil. Thus Add*Task nil is not an unconditional guarantee of durable spool or successful start: it can reflect configured terminal/error discard. Existing `TestPoll{Activity,Workflow}TaskQueues_{InternalError,DataLossError}` explicitly expect one failed start call and no retry. This is known design behavior, not a newly discovered bug. A valid liveness theorem needs an explicit exclusion/recovery assumption for unrecoverable corruption/terminal start errors; any proposed failure under a merely transient Internal must establish the concrete producer and compensation first. Matching backlog internals remain outside the primary model.

### Optional build-ID postprocessing

After Matching success, assigned build ID updates are attempted only for assignment-rule dispatch (`transfer_queue_task_executor_base.go:130-144`, `184-198`). Both helpers deliberately log and mask persistence failures, because acceptance already happened and task-start handling records the build ID (`worker_versioning_util.go:22-116`, `119-199`). WFT initialization additionally skips an already started/completed task to avoid overwriting newer routing state (`176-179`). This is not a missing required task retry; #10775's reported path inconsistency lacks demonstrated progress impact. Keep versioning outside the ordinary baseline and retain this masking contract in the audit.

## Complete executable error disposition

| Error/outcome | Decision | Durable/business interpretation |
|---|---|---|
| nil from executor or successful DLQ write | FIFO Ack, Pending→Acked | Local completion; persistence checkpoint/deletion occurs later. Meaning depends on executor outcome. |
| wrapped NotFound, ErrStaleReference; exact NamespaceNotFound, ErrTaskVersionMismatch | HandleErr nil (`451-475`, `602-607`) | Must establish obsolete/satisfied/deleted obligation upstream. `invalidTask` only controls metrics on attempt 1. |
| ErrTaskDiscarded | HandleErr nil (`478-484`, `609-611`) | Explicit safe-discard interface; not generic transient error. |
| ResourceExhausted incl busy/APS | Expected retry (`519-533`) | Keeps Pending; per-cause scheduling policy, no unexpected-error DLQ budget increment. |
| NamespaceNotActive, dependency incomplete, standby retry, namespace handover | Expected retry (`536-556`) | Depends on ownership/namespace/dependency progress; one-cluster baseline can omit failover states. |
| true MaybeTerminalTaskError, DataLoss; Internal only if configured | Terminal intent then DLQ attempt, or drop if DLQ disabled (`561-579`, `645-668`) | Terminal does not mean original workflow obligation was satisfied. |
| other errors, including persistence timeout/Unavailable and ordinary Internal by default | Unexpected retry; at configured budget become DLQ intent (`630-688`) | Must preserve Pending until DLQ accepts; finite default budget bounds automatic retries. |
| configured regex match | DLQ intent before stale/expected classification (`596-599`, `684-707`) | Operator override; do not assume safe-drop classes bypass it. |
| executor panic | Recovered into error (`343-355`) | Goes through the same classification; not successful execution. |
| DLQ Create/Enqueue failure | Execute returns wrapped ErrCreateDLQ/ErrSendTaskToDLQ (`dlq_writer.go:77-103`) | Original task stays Pending, even if reply was lost after commit. `%v` wrapping prevents inner NotFound from being mistaken for obsolete History task. |
| Cancel/Abort races with result | Pending becomes Cancelled/Aborted; late Ack/Nack no-op (`724-750`, `768-772`) | No durable task deletion; recovery relies on queue scope retention. |

Default configuration from `common/dynamicconfig/constants.go:2949-2971`: DLQ enabled=true; unexpected-error budget=70; Internal immediate DLQ=false; regex empty. Transfer factory passes these settings into executable creation (`transfer_queue_factory.go:166-178`). The constructor's fallback DLQ=false is not the production Transfer default. The setting description claiming non-Cassandra support is absent is stale: current SQL QueueV2 exists and the file-SQLite test below successfully persists and reads DLQ rows through both the manager and an independently opened database/sql connection.

Terminal intent is **volatile** in Executable. Reload may retry original work because intent/attempt counters were not persisted. This permits duplicate successful downstream delivery or duplicate DLQ rows, but does not justify skipping required work. Once a task is in durable DLQ, automatic History queue progress is complete; business progress requires an explicit operator replay assumption. Default finite budget does not establish eventual worker execution from eventual transient recovery alone. #11402/#11842 already report variants of this limitation; do not turn reproducing that operator contract into a novel MC target.

## DLQ durability and ownership

`DLQWriter.WriteTaskToDLQ` creates the queue or accepts AlreadyExists, serializes same-process enqueue attempts by QueueKey, then calls EnqueueTask (`dlq_writer.go:63-103`). Namespace lookup/metrics/logging happen after accepted enqueue and do not replace persistence evidence (`105-142`). The mutex does not fence other processes or History shard ownership.

`HistoryTaskQueueManager.EnqueueTask` serializes the original task plus source-shard ID before `QueueV2.EnqueueMessage` (`common/persistence/history_task_queue_manager.go:59-114`). SQL checks queue metadata then starts a transaction, gets the locked last message ID, inserts one row and commits before success (`common/persistence/sql/queue_v2.go:45-113`). DLQ storage is not a History shard RangeID write. An old owner can therefore deposit a duplicate after ownership changes; that is acceptable recovery duplication, provided required work remains represented or was already satisfied. Queue-state fencing belongs to the shard/checkpoint audit, not DLQ locking.

## Verified exclusions and handoff questions

- Source does not prove a task was lost merely because its original executor was cancelled, a Matching reply timed out, a post-acceptance build-ID write failed, or a durable checkpoint lags. Follow the row/scope/retry or already-started/stale-task compensation.
- #10320's asserted Matching deadlock is explicitly disputed by a maintainer. #10321's sql.Tx sharing hypothesis is not supported by a log saying the transaction was already committed/rolled back. #9563 is worker event-loop blocking, not queue scheduling loss.
- Already-fixed rescheduler wakeup #3396, backoff #3413, priority-read race #7180, terminal classification #5371, parent-close retry #2814 and sticky fallback #2811 are reference context. Do not revert them as modeling adversaries.
- The primary forward question for Spec Generation is the **composition** of accepted-but-unacknowledged effect, cancellation/ownership reload, and reader/slice checkpoint movement: can required work lose both durable responsibility and eligible reconstruction? Represent effect acceptance, History Ack, durable queue state and row deletion separately. A new owner may execute a duplicate and must consult durable workflow task identity/stamp before deciding it is obsolete.
- Preserve the parent audit's reader-cursor finding as source-review discovery and real-store queue reproduction. The functional workflow+Activity test here is a separate healthy control. It does not convert controlled scheduler non-submission into an end-to-end stalled workflow reproduction.
- Matching terminal-discard behavior and DLQ operator intervention are explicit contract limits. Do not silently assume every nil Add response means successful start, or every durable DLQ entry implies eventual user workflow completion.
- No TLC/trace validation ran in this executor audit; model checking discovery/reconfirmation counts are both zero. No claim that source review proves the coupled checkpoint system correct.
