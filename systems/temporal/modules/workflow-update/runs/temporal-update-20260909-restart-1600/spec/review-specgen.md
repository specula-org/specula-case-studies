## Issues Found

Source references below are relative to `/home/ubuntu/temporal-investigation-20260909/restart-20260909-1600/source-update`, whose HEAD was verified as `0c010ce5fe8c0180aa7573c72fe8fc87c6df7025`. Review findings concern the generated verification artifacts; they are not new Temporal bug confirmations.

- **R1 — HIGH: Speculative completion errors omit the deferred sticky cleanup/write.** In `base.tla:762-768`, a late error goes directly through `errorClear -> clearing -> cancel -> idle`; `BufferCancelDone` at `:829-834` ends the handler. Only the NotFound branch at `:401-409` selects `stickyClear`. The implementation's deferred function runs for any applicable error, using the task captured at handler entry: `service/history/api/respondworkflowtaskcompleted/api.go:158,167-200`. Its `clearStickyTaskQueue` performs Clear, Load, ClearStickyTaskQueue, and an execution write at `:1169-1183`. This remains relevant after a successful commit/effect publication and an error creating the inline successor response. A directed 37-action base-spec execution completes one Update, leaves a second for an inline speculative successor, injects the late error, and returns to a loaded idle context with both durable and cached stickiness still TRUE. The model has skipped the required cleanup transaction and its possible failures. Preserve the original handler task/cleanup eligibility and route each error through the actual defer sequence. Evidence: [schedule](checks/review-specgen-d8wthrs8/late-cleanup-schedule.txt), [TLC log](checks/review-specgen-d8wthrs8/late-cleanup.log).

- **R2 — HIGH: The progress model can permanently disable the timeout needed after a finite worker-completion loss.** `MC.tla:289-292` charges every start-to-close timer eligibility transition to `FaultLimits.timeout`; `:388-391` independently permits losing a worker completion. `ServiceFairness` at `:495-498` covers STS eligibility and already-eligible timer processing, but not the required STC eligibility after such a loss. Under the exact Scenario 2 progress limits, a directed execution consumes two STC expirations, loses the third completion once, and then repeats same-ID client retries forever. The current normal task's timer is valid but cannot become eligible: the base action is enabled and its MC wrapper is disabled. TLC finds the temporal violation in 63 distinct states, with the loop returning to state 57. A separate check of `PROPERTY MCProgressSpec` passes for this witness, including the original fairness assumptions; this is not an unfair or frontier-pruned schedule. No committed completion exists in this witness, so the failing obligation is `RetriedEligibleUpdateMakesProgress`. The real timeout executor at `service/history/timer_queue_active_task_executor.go:408-477` has no exhausted-budget guard. Separate injected worker delay/loss from the fair timer recovery it necessitates; increasing a timeout bound alone also leaves the fairness omission. Evidence: [witness](checks/review-specgen-d8wthrs8/BudgetWitness.tla), [schedule](checks/review-specgen-d8wthrs8/budget-schedule.txt), [violation](checks/review-specgen-d8wthrs8/budget.log), [MCProgressSpec projection check](checks/review-specgen-d8wthrs8/budget-projection.log).

- **R3 — MEDIUM: Trace wrappers accept transitions outside base.Next's parameter domains.** `Trace.tla:55-60` checks the parameter record's keys, then directly calls `UpdateWorkflowExecution`. It never checks `u \in Updates` or the allowed wait-stage values. Those restrictions occur in `base.tla:1244`, outside the action; `TypeOK` at `:1213-1228` does not check call UID/wait stage or the domain of `everRequested`. Consequently, a one-event trace with `u = "outside-Updates"`, or one with `stage = "BOGUS"`, passes the supplied `Trace.cfg` when the post-state consistently reflects those invalid values. Both controls exited 0 and consumed the event. Strict post-state equality therefore does not establish that the event is a transition of the base specification. Audit every wrapper for the parameter domains supplied by `Next`, including worker result kind/value, and strengthen the relevant type checks. Evidence: [invalid Update ID](checks/review-specgen-d8wthrs8/bad-update.ndjson), [invalid stage](checks/review-specgen-d8wthrs8/bad-stage.ndjson), [results](checks/review-specgen-d8wthrs8/probe-results.json).

- **R4 — MEDIUM: An append timeout can be injected after execution transaction submission.** `AppendHistoryTimeout` at `base.tla:639-645` accepts `write.state = "executing"` and changes it to a definite noncommit without shard reacquisition. The five-action sequence `ScheduleNormalWorkflowTask -> UpdateWorkflowExecutionWithNew -> AppendHistoryNodes -> ExecutionTransactionBegin -> AppendHistoryTimeout` is executable. In SQL, an append error returns at `common/persistence/sql/execution.go:338-348`, before transaction submission at `:351-357`; Cassandra has the same ordering at `common/persistence/cassandra/execution_store.go:114-125`. An execution timeout belongs to the distinct uncertainty/reacquisition path in `service/history/shard/context_impl.go:1518-1548`. The instrumentation row at `instrumentation-spec.md:90` itself says the execution mutation was not submitted. Restrict append errors to the pre-execution append phase, preserving the distinction between physical append success/uncertainty and execution submission. Evidence: [directed probe](checks/review-specgen-d8wthrs8/AppendTimeoutWitness.tla), [TLC log](checks/review-specgen-d8wthrs8/append-timeout.log).

- **R5 — MEDIUM: The completion-identity invariant is self-referential.** `CurrentTaskOwnsAcceptedCompletion` at `base.tla:1197-1198` applies `CompletionMatches` to `s.applied`. The only insertion into that set is at `:393-397`, immediately guarded by precisely the same predicate over precisely the stored tuple. A missing identity comparison in `CompletionMatches` would weaken both the transition and its purported oracle, leaving the invariant unable to detect that omission. This is a structural restatement of the guard rather than independent Scenario 2 protection; `MC_hunt_scenario_2.cfg` otherwise enables only storage/task structure checks. Retain implementation guards, but express the expected identity contract independently and tie evidence to actual command application; validate the oracle with a controlled missing-guard mutation.

- **R6 — MEDIUM: The delivered-with-lost-dispatch-response mapping combines delivery and later error handling.** `base.tla:252-257` creates the Matching entry only when `AddWorkflowTaskToMatchingFailed(i, TRUE)` fires. Its documented hook is *after the failure is swallowed* (`instrumentation-spec.md:59`). During synchronous matching, however, the poller invokes History's task-start handler before finishing the task (`service/matching/matching_engine.go:808,885`), while the AddTask side waits for that result (`service/matching/matcher.go:130-140`). If the subsequent AddWorkflowTask response is lost, a real `RecordWorkflowTaskStarted` event has already occurred before the specified failure hook. The trace cannot replay that event with an empty `s.matching`, and there is no later result-only action after an ordinary delivery action. Split Matching acceptance from the sender's RPC result/error handling, correlate both by dispatch identity, and give each its own hook. The 89-to-89 name match does not resolve this semantic mapping gap.

- **R7 — LOW: Block annotations need branch-specific and complete source ranges.** For example, `base.tla:415-430` and `instrumentation-spec.md:73` cite `service/history/workflow/workflow_task_state_machine.go:687-808` for the completion-event action, but the actual completion event is added at `:830-841`, followed by state updates at `:852`. `BufferApplyFirst` at `base.tla:664-687` repeats one combined collection of ranges across several different callbacks rather than attributing each CASE branch. Update the ranges and annotate the individual branch/state mutations. This would also make omissions such as R1 easier to audit.
