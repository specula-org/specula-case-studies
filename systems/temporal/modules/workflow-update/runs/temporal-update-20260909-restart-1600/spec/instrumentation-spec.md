# Instrumentation specification: temporal-update

Source revision: `0c010ce5fe8c0180aa7573c72fe8fc87c6df7025`. Category A, single linear NDJSON trace. This is a harness handoff, not a claim that implementation instrumentation or validation already exists.

## 1. Trace event schema

Store implementation traces under `../traces/` relative to this directory. `Trace.tla` defaults to `../traces/trace.ndjson`; set process environment `JSON=/absolute/path/to/trace.ndjson` for another run. Run TLC with `tla2tools.jar` and the CommunityModules jar (Json/IOUtils runtime overrides) on the Java classpath. Do not copy stub JSON operators into the spec.

Emit exactly one `temporal-update.meta` line with `schema: 1`, the exact `sourceRevision`, `constants`, and `initialState`. `constants` contains arrays `updates`, `values`, `clients`, `hosts`, scalar `initialHost`, `namespaceID`, `workflowID`, `runID`, `eventVersion`, and boolean `hostCacheEnabled`. All IDs are strings; `eventVersion` is numeric. `initialState` is the complete mapped `s` snapshot below. Trace bootstrap is a running Workflow immediately after its first WFT completed at event 4, with next event 5, record version 1 (normalize an observed initial record version by a constant offset), sticky enabled, no Updates, no pending WFT, and empty per-run caches. Capture/clear only the chosen run's cache entries when arranging this bootstrap. Record actual configuration separately; do not assert this baseline against an arbitrary preexisting execution.

Each transition has exactly these envelope fields:

```json
{"tag":"temporal-update","ordinal":1,"event":"UpdateWorkflowExecution","params":{"c":"client-1","u":"update-A","stage":"COMPLETED"},"post":{"...":"complete mapped state, see below"}}
```

`ordinal` is contiguous, 1-based, counting only transition lines. Event names are exactly base action names. `params` contains exactly the parameters in the mapping table, with their actual observed values. `post` contains ALL top-level `s` fields; it is never a partial snapshot. The illustrative `...` above is not a valid trace. A complete **synthetic** example is `checks/synthetic-healthy.ndjson`; do not relabel it as an implementation trace.

`Trace.tla` decodes only set-vs-sequence representation and compares the entire post-state. Missing fields, inconsistent values, unknown actions, and unmatched transitions fail validation. No action is silent. Captured fields must not be dropped to make replay pass.

Mutable State has event pointers, not the result payload: join to committed History, never infer result from a future. Track transfer acknowledgment separately from the atomic write. |
| `ctx` | Actual `ContextImpl` / MutableState / registry snapshot under workflow lease: `loaded`, `host`, `generation`, `range`, `rv`, `next`, `closed`, `sticky`, `task`, `transfer`, Update `info` and `reg` mapping UID to observer object index (0 absent). | `objects` | Append-only observer table of real `*Update` identity: `uid`, `generation`, `state`, `accepted`, `outcome`, `acceptedID`, `callbacks`. Keep detached objects referenced by old waiters. | `batch`, `commands`, `closeCommand`, `rejectTodo`, `successor`, `skip` | Handler-local event builder and command/message cursor, final-close flag, captured Sent objects selected for automatic rejection, actual successor decision, and actual speculative-discard branch. Accepted/completed Update event batch IDs are the real WFTCompleted batch start. For generic non-Update events, model `batchID` is a normalized unused sentinel equal to that event's ID; it is not a backend physical-batch claim. |
| `write` | Backend call observer: state none/prepared/appended/executing/committed/noncommit, independently observed `returned` and error class, expected `range`/`rv`, frozen `next/info/closed/sticky/task/transfer/events`. `ExecutionTransactionTimeout` may leave state executing or committed. Observe the underlying backend, not merely the injected API return. For process loss before execution submission, no later execution commit is possible. |
| `effects`, `cancels`, `active`, `second` | Actual effect registration order and callback cursor: `{oid,kind,prev,result}` records; active callback and next publication/removal stage. | `pc`, `returnPC`, `clearTodo`, `clearReturn`, `handler`, `caller`, `selected`, `inlineWorker` | Observer control-location labels derived from the exact hook boundaries, held lease/continuation, registry clear iteration, handler kind and actual request/worker indices. Real server response construction, network loss and CLIENT receipt are separate hooks. |
| `observed`, `applied`, `timeoutApplications`, `everRequested` | Ghost evidence sets accumulated ONLY from real receipt, real compared token/current tuple, real timer/current/pointer tuple, and real request respectively. These records retain evidence needed by invariants; never manufacture them from expected behavior. |

A `result` is `{kind,value}`. Kinds success and handlerFailure retain distinct equality classes of the actual serialized worker outcome (for failures, include failure type/message/details as needed to distinguish the two tested outcomes). Other kinds are pending, rejection, closing, retry, closedError, lookupError, notFound, and taskError; their `value` is the string `none`. Rejection and synthetic closing failure are not worker-handler failures. NoInfo uses zero IDs and pending result. NoTask uses kind none and zero IDs/attempt/time, fixed eventVersion, stamp 0, transient false, route normal.

JSON arrays are ordered sequences except these exact set-valued fields: `clearTodo`, `rejectTodo`, `everRequested`, `observed`, `applied`, `timeoutApplications`, and each worker's `delivered`/`accepted`. The decoder converts only those to sets. Update/client/host-indexed maps use the exact header string IDs as keys. Include zero/false/empty fields; Go `omitempty` must not remove them.

## 3. Special considerations and handoff

**A linear trace needs an actual linearization at each hook.** Use a test observer mutex to assign ordinal and merge immutable captured deltas at the semantic boundary, then write outside production locks. Do not sort asynchronous log lines by wall-clock timestamp. Never hold the observer mutex while awaiting Workflow lease, Matching reentry, backend I/O or a future. For the tightly controlled fault schedules, barriers establish the required order. If a genuinely unobserved concurrent mutation cannot be assigned to a point consistent with captured snapshots, stop and report the capture gap; do not add unconstrained silent actions or infer a favorable order.

**Observe the backend truth independently.** With SQLite, use a commit hook plus a separate connection/reopen readback of execution metadata, UpdateInfo/event pointer and internal tasks. With Cassandra, preserve applied-CAS/conditional failure evidence and real readback; a mock is insufficient for durability claims. ExecuteAndTimeout proves a returned timeout, not by itself whether or when a particular transaction committed. Persist raw expected/actual range and record-version, History branch/node/transaction metadata, and fault occurrence in sidecars referenced by the trace manifest. The model abstracts the proven backend atomicity and committed-History selection contracts; validation of a fabricated cache insertion is not a production MC-4 reproduction.

**Generation/clock guards are scoped, not removed.** This model fixes one run and no Mutable State rebuild/task refresh: `TaskGenerationShardClockTimestamp` remains 0, and generated task IDs are below the acquired shard clock. Check these actual preconditions before admitting a timer trace (`ndc_task_util.go:141-155,209-255`). A memory timer bypasses event-ID stale reload regardless of the current task's type (`:280-305`); the later pointer check still depends on the current WFT type. Cross-run/task-generation rebuild or equal/future vector-clock cases require a model extension rather than silently accepting the trace.

**Bootstrap and identifier normalization.** This phase models the interval after the first WFT completed, with no intervening signal/history shipping and no pause/build-ID/version change. Preserve event-ID arithmetic and relative offsets, both Update payload equality classes, the five cache-key fields, and distinct start timestamps. NewRegistry creation has no externally held waiter to its newly created objects: canonicalize the new accepted-object indices by Update ID while preserving every old object index; other Go map loops have actual per-object events and remain order-sensitive. Do not normalize different Update IDs/results to the same value. Distinct raw backend batch IDs are retained in sidecars; completion's logical batch-start reference is checked in `ctx.info`/`db.info` and cache event records.

**Explicit current limits.** One active Workflow context/lease and one outstanding execution write are modeled. Controlled ownership movements happen between handler operations or after uncertain write return; simultaneous execution on two active old/new owners is not modeled. The successful speculative skip path therefore does not establish safety for all stale-owner overlap reports. Late handler errors preserve post-commit effects. Forced-limit termination preserves its exceptional precommit abort and requires the recorded configuration restoration for recovery. Client context cancellation/deadline has no separate action in this first slice: use server soft timeout/retry or response-loss schedules, and add a sourced action before validating traces that rely on client-deadline distinctions. This limitation is distinct from modeled backend timeout uncertainty.

**Reuse the existing evidence.** Begin with `tests/update_analysis_commit_test.go` and `tests/update_workflow_test.go` for normal/speculative commit controls; `tests/update_analysis_identity_test.go` for stale sticky cleanup/retry; `tests/update_analysis_state_test.go` and `service/history/workflow/update/update_analysis_state_test.go` for mixed outcomes and callback buffering; the forced-termination fixture is `TestAnalysisUpdateForceTerminationReadback` in `tests/update_analysis_commit_test.go:172-263`; `service/history/update_analysis_timer_test.go` for submitted/cancelled timer conversion; `common/persistence/tests/update_analysis_persistence_test.go` for physical-tail/commit readback. These files already exist and were not edited by this generation phase. Follow source `AGENTS.md`: include `-tags test_dep` when running Go tests. Extend hooks/fixtures in the harness phase, not by altering production semantics.

**First trace schedules.** Collect: healthy speculative acceptance+completion; normal WFT control; rejection-only legitimate persistence skip; accepted-but-unfinished plus same-WFT close; independent two-Update effects with waiter between Future.Set calls; known noncommit versus executing write timeout versus ExecuteAndTimeout; old sticky completion with cache clear and same-ID recovery; real direct Matching failure followed by due STS normal delivery; callback ignore then capable-worker/retry recovery; forced termination healthy/failed write with explicit limit restoration. For MC-4, `checks/cache-witness-schedule.txt` is a model-derived 74-transition candidate using the exact hunt bounds: two real hosts, ordinary precommit PutEvent for A, noncommit, H2 commit B at reused event ID/version, H1 reacquisition and public same-ID lookup. Do not bypass ownership or insert a fabricated cache entry.

**Validation status.** Synthetic fixtures check the replay engine itself only. Real implementation traces, exhaustive convergence/hunts and maintainer confirmation remain separate subsequent work. Preserve every mismatch with the raw trace, full command, source revision, actual configuration and backend evidence; investigate model/capture/implementation causes before changing a property.
