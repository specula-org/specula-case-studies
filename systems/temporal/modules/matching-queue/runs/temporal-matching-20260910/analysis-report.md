### Complete source execution paths and actual acknowledgement points

These are **source-derived execution paths**, not recorded runtime traces.

1. **Admission.** `matchingEngine.AddWorkflowTask`/`AddActivityTask` constructs TaskInfo, including namespace/workflow/run, scheduled event, stamp, clock, expiry and priority, then calls partition `AddTask` (`matching_engine.go:586-694`). The partition resolves the physical queue and initializes it before use (`matching_engine.go:465-548`; `task_queue_partition_manager.go:555-617`).
2. **Sync matching.** `TrySyncMatch -> priMatcher.Offer -> MatchTaskImmediately` pairs a task and poller under matcher lock; no durable queue write occurs at that pairing (`physical_task_queue_manager.go:730-744`; `pri_matcher.go:387-454`; `matcher_data.go:359-386`). `Offer` waits for `task.responseC`, which is filled by `task.finish` after start-result classification (`task.go:321-326,373-395`). A pair alone is not successful admission. `syncMatchSuccess` can carry a non-nil start error; preserve both fields.
3. **Sync fallback.** Unmatched tasks spool. A locally matched BUSY_WORKFLOW error also spools; other matched start errors return to the caller rather than automatically spooling (`task_queue_partition_manager.go:615-674,707-715`). A nil result may also reflect a legitimate drop reported by History, so classify the logical eligibility/result, not merely the sync flag.
4. **Durable enqueue.** `SpoolTask -> appendTask` queues a request; writer allocates a fresh storage ID, invokes the store and then signals readers before replying to callers (`pri_backlog_manager.go:248-263`; `pri_task_writer.go:68-137,152-179`). Database transaction outcome, writer-observed outcome, reader notification, buffered writer reply and external Add RPC receipt are separate events. Queue context cancellation after append submission is an uncertain receipt, despite the comment at `pri_task_writer.go:94-95`.
5. **Store commit.** Selected V1 SQL inserts task rows and checks the queue range in one transaction; a failed range check cannot expose the earlier SQL inserts as committed rows. Cassandra V1 uses a conditional same-partition logged batch. See the backend audit below. A generic unavailable/timeout can follow a commit; only the direct store error categories proven definite by `writeDefinitelyFailed` may be treated as noncommit.
6. **Notification/bypass.** DB returns each subqueue's before/after max read bound. Writer notifies only after nil store error. Reader can bypass persistence only if its current read equals the captured previous max and the batch fits; it registers outstanding entries under lock before adding to matcher. Otherwise it signals DB loading (`db.go:535-598`; `pri_task_writer.go:124-137`; `pri_task_reader.go:382-411`). Notifications coalesce; they are not task counts.
7. **DB read.** Reader snapshots read and max bounds, scans inclusive/exclusive ID windows, with at most ten empty windows per pump iteration, then processes the result later (`pri_task_reader.go:214-244`). Nonempty processing applies max(read,id), filters expiry, already-acked IDs and outstanding duplicates, then registers remaining entries under lock (`247-295`). The physical queue routes the registered task to `priMatcher.AddTask` (`physical_task_queue_manager.go:601-611`; `task_queue_partition_manager.go:951-1010`). Do not use the legacy `DispatchSpooledTask` as the priority dispatch path.
8. **Dispatch.** Matcher atomically removes a selected task/poller pair and wakes both; cancellation only removes an as-yet-unmatched poll/task (`matcher_data.go:295-350,519-551`). Physical PollTask rechecks expiry after the match (`physical_task_queue_manager.go:517-531`). History start request uses a fresh RequestId per outer attempt (`matching_engine.go:3511-3527,3590-3606`); retries within the History client reuse that request (`client/history/retryable_client_gen.go:674-687,704-717`).
9. **History result.** History accepts a repeated RequestId idempotently; a different RequestId for an already-started task gets `TaskAlreadyStarted`. Workflow scheduled/stamp mismatches and obsolete work have explicit rejection paths (`service/history/api/recordworkflowtaskstarted/api.go:63-111`; `recordactivitytaskstarted/api.go:119-183`). Matching calls finish on success **before** returning the poll response (`matching_engine.go:885-887,1128-1130`). Consequently queue completion is not evidence the Worker received or executed the task.
10. **Completion/retry.** Transient service/context errors re-add the same record without ack. Other errors request a replacement write, and ack the original only after replacement succeeds (`pri_task_reader.go:114-156`). Failure of replacement eventually sets skipFinalUpdate and unloads, leaving original unacked (`pri_backlog_manager.go:360-387`). Matcher-add failures use a bounded set of retry goroutines and queue context cancellation; some errors drop explicitly (`pri_task_reader.go:310-380`).
11. **Ack.** A completion marks an existing outstanding record true and decrements loaded count, then removes only the contiguous completed minimum prefix. Ack can jump to read when completely drained (`pri_task_reader.go:452-479`). The cached DB ack/stat update follows; it is still memory (`db.go:336-368`). Out-of-order completion can free read capacity without releasing earlier required work.
12. **Sync and cleanup.** GC captures reader ack and deletes IDs below `ack+1`; metadata synchronization is separate. GC can commit before a corresponding durable ack. SQL may delete a bounded number of rows; Cassandra reports unknown count after range delete. GC failure does not advance gcAck (`pri_task_reader.go:522-577`). Normal GC is triggered by completion, not a periodic independent sweep.
13. **Unload/reacquire.** Physical Stop best-effort synchronizes reader/cached metadata before canceling the queue context; fatal range errors skip the final write (`physical_task_queue_manager.go:319-344`; `pri_backlog_manager.go:108-144`). Unloading an unversioned physical queue unloads the whole partition. Engine map deletion checks object identity and a later request creates/initializes a new manager (`task_queue_partition_manager.go:1953-1991`; `matching_engine.go:465-548,3176-3201`). Fresh takeover loads persisted ack, conditionally increments RangeID, and scans all IDs below the next allocation block (`db.go:176-207`). Model this supported lifecycle, rather than assigning a new range to the same cached object arbitrarily.

### Logical work identity and History boundary

Keep **logical work** distinct from **storage record** and **start request**. The record key must include persistence queue identity, subqueue and TaskId. Logical work uses namespace, workflow/run, task type, scheduled event and stamp/eligibility generation; a retry or re-spool can produce another record for the same work. Start RequestId is separate from both. Correlating only TaskId or only scheduled event across queues/runs is invalid (`matching_engine.go:615-631,665-680,3511-3527,3590-3606`; `task.go:24-27,150-188`).

History acceptance is an interface result, not universal proof of a durable History start: speculative workflow starts can use `UpdateWorkflowAction.Noop` (`recordworkflowtaskstarted/api.go:177-184`). The model must state the external History recovery/replacement contract rather than invent internal outbox or speculative-state transitions. `TaskAlreadyStarted` establishes accepted start, not Worker receipt. Recovery from a lost Worker response needs the appropriate History timeout/replacement mechanism and its configured progress conditions; that mechanism is outside this queue model.

Admission bookkeeping must distinguish a successful Matching acknowledgement whose network reply is lost from a store call that returns an error even if a row committed. Track those committed-error rows and their eventual retry/readback, but do not infer a promised successful admission from their mere existence. An original already-accepted task retains its obligation throughout an uncertain replacement. This distinction is especially material to fairness.md:142-144, which does not promise success for timeout writes.

Legitimate disposal: real expiry; History NotFound for completed/missing current work; obsolete stamp/work; already-started work; permitted replacement on transition where that interface applies. Validator transport errors mean **maybe valid**, so they do not justify dropping (`task_validation.go:69-84,159-204`). Internal/DataLoss are deliberately dropped by Matching to avoid endless retry (`matching_engine.go:810-819,1037-1046`); the stronger claim that every such error proves ineligibility is **not established**. Keep that classification audit as CR-2, and state any baseline assumption excluding corrupt/fatal History failures explicitly.

## Phase 3: Verified contracts, findings, and exclusions

### Backend conditions and error classification

The initial priority path uses **V1**, despite the target's useful V2 source pointer. `common/persistence/sql/task_store.go:38-47` selects V1 unless fairness is enabled; V2's GetTasks rejects FIFO bounds. SQL and Cassandra must be modeled separately at their real atomic boundaries, with backend choice recorded in each run.

The complete transaction, lease/readback, metadata-piggyback and GC audit is in [writer-store.md](analysis-evidence/writer-store.md). Its key modeling consequence is that range fencing applies to writes/metadata at their conditional transaction, while range task reads/deletes carry no owner range guard. Stale-owner GC safety follows from its captured completed prefix and globally disjoint record allocation across successful lease generations, not from an invented CAS on deletion. A prior owner's late completion can still be valid for logical work. No invariant should require that exactly one in-memory owner object exists at every instant.

The error distinction is call-site-specific: do not reinterpret a later queue-shutdown `ConditionFailedError` as proof that an earlier store write did not commit. Readback and supported reacquisition must distinguish durable outcome from client-observed outcome. SQL metadata may lag task commits; Cassandra can piggyback metadata when requested. Cached ack, durable ack, allocation high-water, current read, outstanding completion and GC boundary are separate state.

Even **persisted ack can regress safely across takeover**: the new owner reads metadata/range; the old owner writes a newer ack under the same range; takeover CAS then succeeds on that range while writing its older snapshot (`db.go:176-207,241-258`). Range comparison alone does not compare the metadata version. This permits replay, so require per-owner cursor monotonicity and semantic safety of durable ack, not global durable-ack monotonicity.

### Forward-looking findings pending verification

- **MC-1 — Uncertain admission and read recovery.** Does each eligible logical work item that committed or returned successful Add retain an accepted History start or a recoverable record/replacement across read/bypass overlap, range renewal, lost append response, and caller retry? Current guards are retained. This is a cross-operation obligation, not a counter mismatch. Anchors: `pri_task_writer.go:68-137`; `pri_task_reader.go:214-282,382-411`; `db.go:176-207,520-598`.
- **MC-2 — Cross-owner cleanup and lagging metadata.** Can late old-owner completions/GC plus independently committed metadata/lease changes remove all recoverable records of still-eligible work? Track each request's captured owner/range/ack bound and durable transaction, including replacement lineage. Anchors: `pri_task_reader.go:142-156,452-479,522-577`; `db.go:298-368,741-765`; `matching_engine.go:3176-3201`.
- **MC-3 — Failure/replacement progress.** Under recovered store/History, stable owner, eligible polling, finite interference and eventual processing, does an accepted work item retain a delivery path through transient retry, nontransient re-spool, replacement commit with lost response, replacement failure/unload and reload? History already-started/obsolete/expired outcomes must discharge the right identity. Anchors: `pri_task_reader.go:114-156,310-380`; `pri_backlog_manager.go:360-387`; `matching_engine.go:809-887,1036-1130`.
- **MC-4 — Empty nonterminal persistence page (backend-conditional).** Priority `getTaskBatch` ignores `NextPageToken` and treats an empty `Tasks` slice as proof the whole requested ID interval is empty (`pri_task_reader.go:224-244`). `db.GetTasks` supplies no page token (`db.go:700-715`); Cassandra V1 enables explicit paging and returns continuation state (`common/persistence/cassandra/matching_task_store_v1.go:154,187-188`). The pinned gocql `PageState` disables automatic paging even for nil state. If the backend returns an empty nonterminal page before an eligible row, current gap handling can advance read and, when ack==read, ack across that row. The stale-gap and duplicate guards do not compensate. **Not reproduced, not a SQLite result**: validate whether a prospective Apache Cassandra release/configuration/query can actually emit it before treating that failure mode as its behavior. The [Cassandra native protocol paging contract](https://cassandra.apache.org/doc/latest/cassandra/reference/native-protocol.html#_7_result_paging) requires checking continuation rather than inferring completion from row count; [Scylla's documented tombstone page limit](https://docs.scylladb.com/manual/stable/reference/configuration-parameters.html#query-tombstone-page-limit) explicitly permits empty pages. Scylla documentation establishes a conditional compatible-backend possibility, not supported-backend equivalence or a Temporal reproduction.
- **MC-5 — Fairness replacement callback after eviction (separate extension).** `fairTaskReader.completeTask` checks outstanding membership, unlocks to re-spool, then on success relocks and completes without rechecking membership (`fair_task_reader.go:153-218`). Concurrent write merging can evict already-matched tasks and retract the read boundary (`514-551`). A late replacement callback can reinsert an ack above that boundary, decrement loaded count twice and advance past other evicted eligible work (`608-637`). A concrete permitted source schedule and compensations are below. This is a new source-derived pending candidate, **not a confirmed bug or an executed model counterexample**.
- **T-1 — Observation and backend conformance.** Real-store controlled schedules must establish transaction outcomes, exact record identities and cursor snapshots; current fake fault injection fails before any insert. The file SQLite tests establish selected store operations separately, not their composition with Matching. Preserve full scenarios and negative identity/boundary controls.
- **T-2 — Uncertain write wakeup.** The writer advances maxRead on uncertain store error without success notification. A parked reader has no periodic scan. Successful retry/write, queued read/backoff, or reload can recover; continuously active polls can prevent idle unload. This is not confirmed accepted-work loss: failed admission requires caller retry and original durable data remains. Measure the actual required wakeup/recovery path rather than assume autonomous polling (`pri_task_reader.go:98-105,163-207`; `pri_task_writer.go:124-137`; `pri_backlog_manager.go:229-246`).
- **T-3 — All-expired tail.** Expired read records advance read but are not outstanding completions; later empty reads advance ack only when ack==read. With no valid completion the cursor/GC can remain behind. The source explicitly skips this priority test as unsupported (`backlog_manager_test.go:761-765`). This is a known cleanup/replay limitation for ineligible tasks, not fresh eligible-task loss. Verify SQL file retention and recovery separately from Cassandra TTL.
- **CR-1 — Shutdown certainty comment.** `pri_task_writer.go:94-95` claims shutdown means the submitted request never reaches persistence. A commit can precede cancellation/receipt selection. Audit the comment and callers' certainty interpretation; no upstream edit is made here.

### Explicit false-positive and non-target decisions

1. Duplicate delivery/replay is permitted. A missing row is not loss when History accepted the work, expiry/obsolescence is justified, or a valid replacement carries it.
2. Durable ack lagging memory is expected; per-owner monotonicity does not forbid a new owner starting from older persisted ack.
3. `ApproximateBacklogCount` is not task conservation. Uncertain writes and batch/piggyback metadata can diverge; use actual identity sets and store readback.
4. GC ahead of persisted ack is not by itself unsafe. The relevant bound is a completed/replaced prefix, not a durable cursor inequality.
5. SQL task inserts before range-lock verification are not separately visible commits: they are inside one transaction. Reject a model counterexample that splits them.
6. An unavailable response in the existing fake is not a committed-error test; the fake returns the injected error before insertion.
7. An already-started History result does not prove Worker receipt, but is an allowed queue terminal result. Do not label the stronger end-to-end delivery question a new queue bug from a report title alone.
8. The all-expired skipped case concerns ineligible-task cleanup and remains visible as T-3; it is not an eligible-work safety finding.
9. Migration, dynamic partitioning/forwarding, worker-version routing, cross-priority guarantees and multi-cluster replication are outside the requested initial model. Historical fixes there are scoped references, not active hunts.
10. Root validator state is single-goroutine in the initial path. The shared-retrier/validation warnings for multiple child forwarders do not establish an in-scope root data race (`pri_matcher.go:126-158,265-295`).

### Separate fairness extension

Fairness uses pass/task-ID ordering, write/read merge, a pinned acknowledgement floor during writes, and bounded in-memory eviction rather than priority's monotonically appended FIFO bypass. The full source comparison, standing-backlog tests and any remaining reachability questions are in [history-fairness.md](analysis-evidence/history-fairness.md). This extension is **not trace-calibrated or model-checked**; do not combine its state or error classification with the initial V1 model. Complete the priority acceptance/read/GC/ownership traces and bounded baseline before enabling a V2 extension. Weighted/global fairness guarantees remain outside scope even then; target persistence, merging and acknowledgement safety.

For MC-5, use valid small configuration batch=3, reloadAt=0, fixed priority, dither=false, unit key weights and an exact counter for three keys (`fair_task_writer.go:118-140`; `counter/map.go:27-44`; `counter/hybrid.go:27-64`). Source-derived schedule:

1. Start from an empty initialized queue after its empty read completed (atEnd=true). Successfully spool same-key records A=(pass 1000,id 1), B=(2000,2), C=(3000,3), then create pollers. All three match pollers but remain reader-outstanding during History calls.
2. C receives a nontransient start error and passes the membership check. Suspend after the reader unlocks but before its replacement reaches the writer. Namespace-scoped RPS ResourceExhausted is a concrete possible interface result; it is passed to finish, and is not the system-scoped transient category (`matching_engine.go:1109-1115`; `common/util.go:204-207,338-353`; `common/rpc/interceptor/namespace_rate_limit.go:25-28`; `service/history/fx.go:341-364`).
3. The single writer persists two fresh-key records Y=(1000,4), Z=(1000,5). With `atEnd=true`, merge keeps the three lowest loaded records A,Y,Z and evicts B,C, setting read=(1000,5), atEnd=false, loaded=3. B/C may already be matched, so matcher removal is a no-op; durable records remain.
4. C's replacement R=(4000,6) now commits. As atEnd=false and R>read, its write merge leaves R durable but unloaded. The writer unpins ack normally. C's old completion then unconditionally reinserts ack C and decrements loaded to 2, although A,Y,Z remain loaded.
5. Complete A,Y,Z before a newly spawned read processes. Leading acks can reach C across absent B; B's later namespace-scoped RPS rejection sees no outstanding entry and returns without replacement; it never accepted a History start. A metadata update/reload can skip B. GC through C can delete it when the ordinary completion-triggered interval/count gate permits; do not force a synthetic delete. R covers C, not B.

This schedule retains single-writer ordering, the existing ack pin, eviction callback and read-trigger mechanisms; it needs only finite goroutine delays, not a reversed store order or disabled historical guard. It remains subject to controlled real V2 execution and model/trace validation. Keep it gated behind priority calibration rather than use a synthetic snippet to declare loss.

### Proposed bounded verification (not executed)

### Progress assumptions and final scope limits

Eligible-work progress requires an eventually stable successfully acquired owner, available store and History, compatible pollers with eventually available rate capacity, finite interfering work/failures, eventual processing of registered tasks and notifications, and caller retry or supported reload when admission response is uncertain. Poll traffic can keep a queue alive; do not assume idle reload is inevitable. Accepted History work whose Worker response is lost additionally needs the external History timeout/replacement contract. Cleanup of an expired-only tail cannot be promised from the current completion-triggered GC alone.

The audit establishes source contracts, historical evidence and narrowly scoped executed tests. Remaining work is explicitly assigned to Spec Generation, harness/trace validation and bounded model checking. It does not establish end-to-end durable delivery or a new counterexample.
