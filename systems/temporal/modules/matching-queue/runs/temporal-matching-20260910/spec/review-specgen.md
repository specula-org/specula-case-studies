## Issues Found

- **R1 — HIGH: invalid trace initialization reports success without checking any behavior.** `Trace.tla:174-196` expresses revision, evidence class, configuration, and initial-state compatibility as conjuncts of `TraceInit`. Except for the minimum-length check, these are not assertions. A mismatch eliminates every initial state, so `TraceMatched` has no behavior to check. Fresh probes against the unchanged specs produced **exit 0, zero initial/distinct states, and “No error has been found”** for (a) bootstrap durable ack changed from 0 to 1, (b) a wrong revision, and (c) the existing synthetic fixture under the implementation-only `Trace.cfg`. Thus the `EvidenceClass` check does not reliably reject synthetic evidence through the documented TLC command. Assert header/configuration validity and initial-state compatibility, and make the validation runner require a nonempty initial state and actual completion. Add negative controls for bootstrap state, revision, and evidence class, alongside the existing event-level controls.

- **R2 — HIGH: sync completion atomically publishes the response and completes the Add caller.** `FinishSyncTask` (`base.tla:675-689`) changes the Add call to `reply`/`spool`, records successful acceptance, and releases the poller toward Worker receipt in one step. In the implementation, `task.responseC` is buffered (`service/matching/task.go:159`); `finishInternal` sends into it (`task.go:385-395`), while `getResponse` receives in another goroutine (`task.go:322-326`, `pri_matcher.go:391-412`). The partition manager processes that result and returns Add later (`task_queue_partition_manager.go:617-638`). Consequently, Worker receipt or a crash can occur after publishing the sync result but before Add consumes it. The model cannot represent that ordering, and instrumentation row `instrumentation-spec.md:101` explicitly combines the two boundaries. Split response publication from Add receipt/return, retaining the pending sync response and independent poller progress. This affects the S1/S4 acceptance boundary even with successful History processing.

- **R3 — MEDIUM: terminal allocation-block renewal errors never reach the waiting append.** `RenewLeaseBegin` starts metadata I/O while the writer remains at `assign` (`base.tla:923-935`). `UpdateTaskQueueReturn` updates the owner and clears metadata but leaves the writer unchanged (`base.tla:1020-1046`). No action publishes an assignment/renewal failure from that state. The implementation returns a final renewal error through `allocTaskIDBlock`, `assignTaskIDs`, and the writer's response channel (`pri_task_writer.go:108-115,168-174,194-224`); its allocation retry policy expires after 30 seconds (`backlog_manager.go:27-29`). The model supports renewed attempts or eventual shutdown, but omits the terminal error response while the owner remains alive. A directed probe reached the post-error state with `writer.pc="assign"` and no enabled publication transition. Represent retryable intermediate failure separately from final failure, including the latter's append/replacement response, rather than retaining the request indefinitely at assignment.

- **R4 — MEDIUM: definite noncommit is incorrectly treated as nonretryable replacement failure.** `CreateTasksReject(...,"limit")` becomes `reply="definite"` (`base.tla:236-258`). `RespoolTaskRetry` only permits `appendReply="unknown"` (`base.tla:752-764`), while `RespoolTaskReturn` sends every non-`ok` result to failure/unload (`base.tla:737-749`). Persistence limiter `ResourceExhausted` errors are both definitely uncommitted and retryable: see `db.go:685-697`, `common/util.go:291-298`, and `pri_backlog_manager.go:367-369`. A directed probe reached a pending replacement with `appendReply="definite"`; the retry transition was disabled. This excludes a real limiter-rejection → recovery → successful replacement execution. Preserve error retryability independently of commit certainty, and distinguish retry from final exhaustion for both definite and uncertain outcomes.

- **R5 — MEDIUM: a pending backoff timer prevents ordinary reader wakeups.** `GetTasksError` puts the reader at `backoff`; only `BackoffSignal` restores `idle` (`base.tla:456-475`). `GetTasksPump` requires `idle` (`base.tla:408-419`). The actual pump schedules a timer and immediately continues its receive loop (`pri_task_reader.go:168-186`), so a successful write or completion can wake it before that timer fires. The timer is separate state (`pri_task_reader.go:415-427`). A directed probe reached `notify=TRUE`, zero loaded tasks, and `reader.pc="backoff"` after a subsequent successful write; the pump was disabled. Model the pending timer independently of the reader phase. Its callback also needs the real reader-lock condition, which the current `BackoffSignal` omits.

- **R6 — MEDIUM: MC budgets prune normal processing and recovery retries.** `MCTrySyncMatch` consumes `SyncLimit` (`MC.tla:17-21`), although admitted Add attempts already have a finite budget and each can match only once. Standard/S1/S4 configs allow multiple Adds but only one sync match; S2/S3 set this limit to zero. A second ordinary sync match is therefore suppressed. Also, failed takeover returns the same lifetime to `cold` (`base.tla:1040`), but every attempt consumes `TakeoverLimit` (`MC.tla:89-93`); with limit 1, a single failed attempt prevents retry after recovery. The implementation's startup renewal retries transient failures (`pri_task_writer.go:140-144,194-204`, `backlog_manager.go:31-34`). Bound external arrivals/new lifetime creation and injected failures, while allowing normal sync processing and retries within an already-started acquisition. `StableOwner` makes executions that never reacquire fall outside the progress claim; it does not repair this missing recovery path.

- **R7 — MEDIUM: the normal root validator is mapped only as TTL expiry.** `FinishExpiredTask` requires `history[work].expired` (`base.tla:893-905`), and its mapping requires expiry evidence (`instrumentation-spec.md:116`). However, the selected root matcher starts `validateTasksOnRoot` (`pri_matcher.go:123-133`). That loop can finish an **unexpired** record after History reports it invalid/not found, or requeue a still-valid record using `errReprocessTask` (`pri_matcher.go:249-279`; `task_validation.go:66-81,157-205`). Neither outcome requires `RecordTaskStarted`. The model lacks the corresponding validator handoff/results: reproducing them would require inventing expiry or a worker/start-error path, the latter also spending `HistoryFailLimit`. Add separate guarded validation-disposal and valid/error requeue actions with their observation hooks. Do not classify every negative validator result as TTL expiry.
