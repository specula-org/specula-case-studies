## Scenario: acceptance, uncertain outcomes, and record replacement

**Atomicity and identity.** The writer has one append goroutine and a buffered error response per request (`pri_task_writer.go:68-105,152-179`). It assigns monotonically increasing storage IDs; allocation can consume IDs before a later error, and they are never reclaimed (`:108-121`). A logical History task may consequently have multiple storage records across retries or re-spooling; record identity is `(physical queue, subqueue, task ID)` whereas logical identity must retain namespace/workflow/run/scheduled event and task kind.

`db.CreateTasks` holds `db.Mutex` through task construction, store call, and post-result max-read update (`db.go:528-597`). This serializes same-owner writes, metadata persistence, and lease renewal, but not `GetTasks` or `CompleteTasksLessThan` (`:699-715,738-765`). Database commit, wrapper result, reader notification/bypass, append waiter receipt, and outer RPC receipt must remain separate observations.

**Success path.** CreateTasks success updates maxReadLevel before returning to the writer; successful writer then signals readers before returning nil to append waiters (`db.go:575-597`; `pri_task_writer.go:124-137,168-174`). A crash after commit but before notification loses only volatile delivery state; reacquisition reconstructs a max-read bound through the prior ranges (`db.go:202-206`) and uses durable ack to replay. An RPC response lost after a successful append does not undo the record or notification.

**Uncertain result path.** MaxReadLevel advances even on a failed persistence result (`db.go:575-580`), and the writer does not bypass tasks on error (`pri_task_writer.go:125-136`). `writeDefinitelyFailed` only classifies actual `ConditionFailedError` and persistence/concurrency limiter causes as definite noncommit (`db.go:677-696`). SQL commit failure becomes `Unavailable` (`sql/common.go:77-79`); Cassandra write timeout/connection-close becomes `persistence.TimeoutError`, overloaded becomes SYSTEM_OVERLOADED, and other errors generally become Unavailable (`gocql/errors.go:15-67`). These are not definite noncommit classes. A pre-store rate-limit rejection is visible in `persistence_rate_limited_clients.go:511-520`.

Counter rollback here is statistical bookkeeping, not an exactly-once mechanism. Unknown errors retain count increments and can overestimate; SQL appends do not persist count with tasks at all. An outer caller error is not a received acceptance. Initial enqueue progress after an uncertain response needs the upstream retry/interface contract: an error does not signal the reader, so an otherwise idle owner can wait for a subsequent enqueue/read trigger or reload. Do not invent periodic read polling: the pump waits on notifyC (`pri_task_reader.go:160-200`), while periodicSync checks/saves metadata (`pri_backlog_manager.go:229-245`). A subsequent successful write cannot bypass an unresolved gap because its `maxReadLevelBefore` includes the earlier failed IDs and the reader's cursor must equal that value (`pri_task_reader.go:382-412`).

**Shutdown return is also uncertain.** The comment at `pri_task_writer.go:94-95` says a request will never reach persistence, but the waiting select can observe cancellation after the writer has already committed. This does not itself prove task loss: it requires retry/deduplication semantics and reload. Do not feed this higher-level `errShutdown` into the backend definite-failure rule simply because its type is ConditionFailedError.

**Replacement ordering.** `pri_task_reader.completeTask:123-139` retries transient start errors in memory; other errors call `respoolTaskAfterError` before ack. That helper retries writes and requires a successful replacement write before returning nil; on exhaustion it sets skipFinalUpdate and unloads (`pri_backlog_manager.go:360-387`). Original ack is performed only after successful replacement (`pri_task_reader.go:142-156`). An uncertain replacement may create extra records, but failure of all acknowledged replacement attempts preserves the original and reload path. The invariant must accept a durable eligible replacement of the same logical work, rather than insist the original storage row survive.

**Useful actions/observations.** `EnqueueAttempt`, `AllocateIDs`, atomic `StoreCreate` commit/reject, `StoreCreateResult`, `ReaderNotify`, `AppendResult`, interface acceptance receipt, `DispatchResult`, `ReplacementWrite`, `AckOriginal`, and `Unload`. For uncertainty include both noncommitted and committed/error outcomes, with the actual durable rows observed independently. Do not split a transactional insert from its RangeID fence.

## Scenario: owner epoch, metadata, read, and GC composition

**Lease acquisition.** A new DB object (`rangeID=0`) reads queue metadata then conditionally increments RangeID; missing queues use conditional creation at range 1 (`db.go:152-173,176-238`). Acquisition failure resets the new object's rangeID to zero; an uncertain acquisition that actually committed is rediscovered on another attempt. Existing owner renewal increments the current RangeID and updates memory only on successful response (`db.go:241-255`). Allocation requires the previous block end to match the DB's current range and renews before issuing a next block (`pri_task_writer.go:212-225`); block r covers `((r-1)*RangeSize, r*RangeSize]` (`backlog_manager.go:273-278`).

**SQL fence is one transaction.** V1 inserts tasks, locks queue metadata, compares RangeID, then commits as one transaction (`sql/task_v1.go:80-98,187-213`; `sql/common.go:52-80`). A mismatch rolls the insertion back; no visible task insertion may be modeled before a failed fence. V2 uses the same pattern (`sql/task_v2.go:77-95`). UpdateTaskQueue locks/checks PrevRangeID and writes the new range plus full metadata within one transaction (`sql/task_queues.go:97-127`). `UpdatedMetadata=false` on SQL CreateTasks is explicit: append and ack metadata are separate writes even if requested by matching.

**Cassandra fence is one conditional batch.** V1 builds a logged batch of task inserts, optionally with task TTL, plus same-partition `IF range_id = ?` metadata update or check (`matching_task_store_v1.go:59-133`; `matching_task_store_queue.go:67-90`). MapExecuteBatchCAS reports applied/rejected; rejected means the batch did not create these tasks. V2 analogous writes do not apply task TTL (`matching_task_store_v2.go:66-127`). Do not replace this with independent row writes and arbitrary partial commits. Cassandra appends may atomically update cached ack metadata with the tasks when UpdateMetadata is true; otherwise they preserve the fence without that metadata update.

**Epoch enforcement is operation-specific.** Writes and metadata updates are fenced. Reads and GC do not carry RangeID (`db.go:699-715,747-754`), and dispatching already loaded work does not acquire a new durable lease. Therefore “old owner has no effects after replacement” is too strong. Valid stale reads/deliveries/GC may finish. Safety depends on valid completion identity and old task-ID bounds: new-owner records occupy newer allocated ranges; accepted old work is either delivered, legitimately stale/expired, or represented by a valid replacement.

**Memory ack versus durable ack.** Reader ack, cached metadata ack, persisted metadata ack, and captured GC bound are separate. `completeTask` launches GC from an ack snapshot before copying ack into DB cache (`pri_task_reader.go:147-156`); `doGCAt` deletes IDs `< ack+1` without requiring persisted metadata ack (`:522-576`). Thus “GC bound <= persisted ack” is not the contract. GC can remove completed records while persisted ack lags, making replay scan gaps after reload.

**Durable ack can regress at takeover without task loss.** The new owner's GetTaskQueue at `db.go:179-195` can race a same-RangeID SyncState by the current owner. The new owner's later takeover CAS (`:196,241-255`) checks only RangeID and can overwrite the recently advanced ack with the earlier snapshot. SQL and Cassandra conditions do not compare a metadata version beyond RangeID. This causes safe replay, not a reason to require global persisted-ack monotonicity. Per-owner reader/cached ack monotonicity remains appropriate (`db.go:339-366`), as does requiring every persisted/captured ack to be semantically safe.

**Owner-loss detection.** If no metadata changed, SyncState still reads the queue range and returns ConditionFailedError on mismatch (`db.go:305-336`); otherwise it uses a conditional metadata write. `signalIfFatal` sets skipFinalUpdate and unloads on ConditionFailedError (`pri_backlog_manager.go:104-120`). Generic transient store errors do not prove loss of ownership and are retried on subsequent opportunities. Normal Stop attempts a final reader-to-cache ack copy and SyncState; physical Stop does this before context cancellation (`pri_backlog_manager.go:127-147`; `physical_task_queue_manager.go:319-340`). Failure or conflict may skip it, requiring durable recovery rather than final-sync assumptions.

**Deletion and expiry differ across backends.** SQL deletes a limited oldest-ID subset and reports actual rows affected (`sql/task_v1.go:158-184`; SQLite `task_v1.go:28-31,77-96`; PostgreSQL `task_v1.go:25-28,73-90`). Cassandra deletes the full ID range, ignores Limit, and returns UnknownNumRowsAffected (`matching_task_store_v1.go:197-220`). Reader retries full-size SQL deletes until a short result establishes completion (`pri_task_reader.go:571-576`). SQL stores expiry only in task blobs; reader expiry filtering determines legitimate drops (`pri_task_reader.go:250-256`). Cassandra V1 additionally uses ceil-to-seconds TTL, minimum 1 second and no TTL beyond maxCassandraTTL (`matching_task_store.go:41-51`; V1:69-89). These are permitted task-expiry effects, not arbitrary corruption.

## Forward-looking candidate: nonterminal database page mistaken for exhausted ID range

**Status: source-supported, backend-conditional, not reproduced.** `priTaskReader.getTaskBatch` ignores NextPageToken and treats `len(response.Tasks)==0` as proof that the entire requested ID interval is empty (`pri_task_reader.go:224-244`). Cassandra V1 deliberately disables driver automatic paging by calling `.PageState(request.NextPageToken)` (`matching_task_store_v1.go:154`) and separately exposes the next-page token (`:187-188`). The pinned gocql v1.7.0 implementation sets `disableAutoPage=true` even for nil state (`github.com/gocql/gocql@v1.7.0/session.go:1275-1278`; local module cache inspected); its connection response only schedules another page if that flag is false (`conn.go:1450`). The generic TaskManager preserves tokens without fetching them (`common/persistence/task_manager.go:214-226`).

An actual empty page with a nonempty token can therefore hide eligible rows later in the same requested interval. The reader jumps to `upper`, `setReadLevelAfterGap` may advance ack when old read==ack (`pri_task_reader.go:498-511`), and a later GC can delete those hidden rows. The stale-gap guard only prevents cursor regression and does not consult pagination. The reader reviewer independently confirmed no compensating token handling.

This is an actual backend contract to verify, not a made-up message fault: [Apache Cassandra native protocol paging](https://cassandra.apache.org/doc/latest/cassandra/reference/native-protocol.html) says to use the more-pages indicator rather than row count. [ScyllaDB configuration](https://docs.scylladb.com/manual/stable/reference/configuration-parameters.html#query-tombstone-page-limit) explicitly permits page cuts with zero rows after a tombstone threshold; [ScyllaDB 5.2 release discussion](https://www.scylladb.com/2023/05/04/scylladb-open-source-5-2-with-raft-based-schema-management/) describes empty pages for long tombstone sequences. Temporal's current Cassandra V2 queries contain an earlier Scylla compatibility change (`1784b467510b`), but this does not establish which exact Cassandra/Scylla deployments are supported or tested here.

**Required reproduction before confirmation:** select and record an actual supported Cassandra/Scylla release and consistency settings; create a real queue at the pinned code and eligible high-ID work; build a tombstone/expiry prefix with a persisted ack behind it; use the real store to capture an empty result plus nonempty token, prove a continued query returns eligible records, then allow real reader processing, ack, GC, and unload/reload. A mock empty page only demonstrates the branch consequence. SQLite cannot confirm this bug because its SQL result row count reflects its own complete bounded SELECT.

**Model extension if backend is calibrated:** represent `ReadPage(tasks, continuation, queriedBounds)` and keep backend `HasMore` independent of length. Check accepted eligible logical work remains available/delivered/replaced after page processing, cleanup, and reload. Never use this Scylla behavior as an unconstrained SQLite empty-read adversary.

**Fairness counterpart, separate extension:** reviewer found V2 UseLimit still uses driver PageState and emits token; fair reader interprets `len(res.Tasks)<batchSize` as read-to-end (`fair_task_reader.go:303-315`) and can suppress later reads (`:234-237`). Validate the real LIMIT-plus-paging behavior before claiming loss. No fairness trace or TLC result is claimed here.

## Explicit exclusions and false-positive checks

1. SQL task inserts appearing before RangeID validation are **not** partial visible commits: the enclosing transaction rolls back on mismatch (`sql/common.go:57-79`).
2. Cassandra metadata-on-append elision does **not** omit the lease fence (`matching_task_store_v1.go:93-133`).
3. A count that over/underestimates durable rows is **not** accepted-work loss. Counts deliberately omit exact conservation semantics; source and historical `d8c64b0da35b` agree.
4. Persisted ack lag, GC ahead of persisted ack, or takeover regression is **not** automatically corruption. Replayed/gapped reads and terminal/replacement obligations must be checked instead.
5. Stale-owner read, GC, or accepted dispatch is **not** automatically a fencing violation. The code fences mutations that create records or replace metadata, and History adjudicates already-started/obsolete work.
6. Generic unavailable, timeout, system-overloaded, or waiter cancellation is **not** proof of noncommit. Classify the actual operation and backend result.
7. A failed replacement write does **not** ack the original; skipFinalUpdate plus unload preserves recovery (`pri_task_reader.go:135-139`; `pri_backlog_manager.go:374-387`).
8. The SQL plugin's SQLite `SelectFromTasks` unbounded branch dereferences nil ExclusiveMaxTaskID (`sqlite/task_v1.go:62-68`), unlike PostgreSQL's InclusiveMinTaskID (`postgresql/task_v1.go:60-68`). This is a code-review/test candidate if that plugin API is exercised directly, but current Matching V1 always supplies a nonnil exclusive max (`sql/task_v1.go:124-131`), so it does not establish an in-scope queue-delivery defect. Keep the helper issue out of MC targets; no test executed.
9. Closed historical overlap/ack repairs and known writer goroutine/data-race fixes are reference context, not adversaries that revert those commits.
10. Issue #10730's early stopAt removal suggestion is explicitly rejected by the maintainer; #9987's stale-48h-bootstrap explanation is disproven; #10320's matching-specific root cause is disputed. None confirms queue-record loss.

## Precise downstream handoff

Build complete traces with independent observations of storage commit/readback (physical key and decoded logical identity), returned error class, before/after max-read bounds, bypass notification, query bounds and tokens, loaded/outstanding records, History acceptance result, replacement rows, memory/cached/persisted ack, captured GC bound and actual deletion, and owner RangeID. TaskManager reads return decoded blobs and discard the independent SQL/CQL row key (`sql/task_v1.go:136-140`; Cassandra V1:158-183), so tracing only deserialized task ID cannot independently check storage-key consistency.

Controls should alter identity, continuation, or queue bounds in a copied trace and fail validation; implementation state must be emitted from code/store, not reconstructed from a successful model path. `faultinjection.ExecuteAndTimeout` executes the real operation before returning Timeout and preserves a real underlying failure (`faultinjection/fault.go:42-47,61-71`), making it an appropriate committed/error control; use separate independent readback to establish what committed. Do not equate all injected Timeout errors with that control.

Priority required schedules: successful durable enqueue and delivery; commit with response loss followed by retry/reload; definite stale-range reject with no row; commit-before-steal versus steal-before-commit; uncertain lease renewal and supported unload/reacquire; captured old read delivered after bypass and completion; gapped read; GC before metadata save and metadata save before GC; takeover overwriting a stale metadata snapshot; transient dispatch retry; successful respool before original ack; replacement failures followed by unload/recovery. Backend pagination scenario is an additional conditional check after core traces are complete.

Progress assumptions must state stable ownership eventually, available and correctly configured store, actual repeated processing/notifications or caller retry after uncertain enqueue, eligible pollers and History eventually accepting or terminally rejecting work, finite interference, fair scheduling of each enabled background action, and finite faults. A permanently dead SQL connection pool (reported in #11691) does not satisfy the available-store assumption simply because the database server is up. Existing fake-backed tests cannot establish any of these backend-specific claims.
