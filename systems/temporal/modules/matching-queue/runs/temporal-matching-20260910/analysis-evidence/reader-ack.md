## Source-grounded state and atomicity

1. `priTaskReader` has one mutex protecting `outstandingTasks: TaskID -> acked`, `loadedTasks`, `readLevel`, `ackLevel`, GC snapshot bookkeeping and retry timer (`pri_task_reader.go:35-60`). The backlog manager uses `subqueueLock` for its reader/priority maps; one writer goroutine assigns increasing IDs and sequentially invokes CreateTasks (`pri_task_writer.go:108-137,152-179`). `db.Mutex` covers CreateTasks, ownership/metadata I/O and cached ack/stat mutation (`db.go:152-174,298-368,520-598`), but GetTasks and CompleteTasksLessThan intentionally do not take it (`db.go:700-715,741-765`). Therefore DB read and GC may overlap a serialized write/metadata call.
2. Restart starts reader read/ack at persisted `SubqueueInfo.AckLevel` (`pri_backlog_manager.go:180-191`, `pri_task_reader.go:67-93`). Lease takeover first reads old metadata then conditionally increments range; maxRead becomes the start of the new allocation block minus one (`db.go:176-207`). This captures all previously allocated IDs, including possibly committed writes whose result was lost. It is not a record count.
3. A read snapshots local readLevel, releases reader lock, then snapshots db.maxRead and performs range-bounded reads. It scans at most ten empty allocation windows per call (`pri_task_reader.go:214-244`). Represent the captured bounds/result separately from the current reader state. Do not turn GetTasks and processTaskBatch into one action.
4. Nonempty read processing is one reader-lock action: max readLevel with every returned ID; filter expired records; filter IDs at/below ack; filter IDs already outstanding; insert remaining unacked entries and increment loaded count (`pri_task_reader.go:247-280,288-295`). Adding these tasks to the matcher follows after lock release (`282,301-325`). A crash between registration and matcher add loses volatile work but leaves durable unacked records recoverable.
5. Bypass eligibility is equality to the write's **previous** max read bound plus memory space, with an outstanding-duplicate check (`pri_task_reader.go:382-408`). Only then does it set readLevel to that write's max and record tasks. Otherwise it signals the read pump. The write response includes before/after bounds computed under DB lock and advances maxRead even on error (`db.go:535-580`). `priTaskWriter` invokes `signalReaders` only on nil store error (`pri_task_writer.go:124-137`).
6. Completion first classifies result. Transient service/context errors re-add the same storage record without ack (`pri_task_reader.go:114-133`). Other errors synchronously try to re-spool the same TaskInfo at a new task ID; original completion stops if replacement writing fails (`135-139`). `respoolTaskAfterError` retries transient persistence failures, then sets skipFinalUpdate and unloads on failure, explicitly retaining original below ack (`pri_backlog_manager.go:360-387`). Success of replacement writing precedes original acknowledgement.
7. Ack marks only an existing, not-already-acked record; loaded count decreases immediately, while the ordered map removes only its minimum acked prefix (`pri_task_reader.go:452-474`). Thus completing high IDs out of order frees memory without acknowledging a lower uncompleted task. If outstanding is empty and read>=db.maxRead, ack may jump to read (`448-449,476-479`). This is ordered **record completion**, not strict History start or Worker processing order.
8. Empty read processing rejects stale bounds below current read and signals again (`pri_task_reader.go:484-497`). It advances ack through an empty range only when previous ack==read (`498-511`). Cached db ack is separately clamped monotonically within this owner (`db.go:336-355`). The per-owner monotonicity claim must not be applied to a fresh owner initialized from older persisted ack.
9. Completion chooses GC while still under reader lock, captures ack in a goroutine argument and then updates DB's cached ack/stat (`pri_task_reader.go:142-156,522-529`). GC calls deletion with exclusive max `capturedAck+1`, independently of metadata synchronization (`559-577`). It can durably delete completed records before their ack is durably stored; requiring durableAck>=gcAck would invent an implementation invariant. The correct safety obligation is that every deleted still-eligible logical work item already has accepted delivery or valid durable replacement, even when older metadata causes replay/empty reads after reload.
10. GC permits one ordinary pass in flight per reader. Error leaves gcAck unchanged; SQL exact-full batch requires another pass; Cassandra unknown row count means complete (`pri_task_reader.go:532-576`). Ordinary GC is triggered by completion, not an independent periodic sweep. Stop refreshes cached DB ack from each reader then best-effort SyncState (`pri_backlog_manager.go:125-144`); physical Stop invokes it **before** canceling tqCtx (`physical_task_queue_manager.go:319-334`). Lost ownership sets skipFinalUpdate and unloads (`pri_backlog_manager.go:108-118`). There is no shutdown wait for all outstanding I/O here; late GC/completion must remain possible until cancellation actually takes effect.

## Forward-looking mechanism questions and compensations

### Accepted work conservation across read/ack/GC and owner changes

Model pending read snapshots/results, current outstanding map, owner generation, cached/persisted ack, independent GC snapshots, record-to-logical-work identity, History accepted state and replacement links. Compose current bypass/dedup rules with late old-owner reads/completions/deletes and replacement-write outcomes. These cross-products are open verification questions; reverting #11570 or merely rechecking its exact schedules is not a new finding. Every GC-deleted eligible record needs its logical obligation discharged or transferred independently of persisted metadata. Acceptance and History terminal/stale-result guards must be supplied by the dispatch analysis.

### Uncertain write result and notification

Observed source behavior: an uncertain CreateTasks error can advance maxRead without signaling a parked reader (`db.go:575-597`, `pri_task_writer.go:125-136`). Current periodicSync only synchronizes/verifies metadata, and has no reader signal (`pri_backlog_manager.go:229-246`). Startup primes the reader (`pri_task_reader.go:163`). Successful retry/another write, completion at reload threshold, backoff or explicit reload can wake/read it. Idle unload exists (`physical_task_queue_manager.go:178-182`), but ongoing PollTask resets the idle timer (`492`), so do not assume a continuously polled queue inevitably unloads.

This is **not a confirmed accepted-task loss**: an error response is not observed success; request retry may sync-match the logical work, or persist a replacement and signal the gap, while original data remains durable and reload sees old IDs. Replacement failure unloads while preserving original ack as above. The handoff must state caller retry/reload progress conditions and validate actual backend uncertain outcomes; no artificial autonomous reader polling action should be added. New testing can ask whether every required retry path supplies a wakeup or valid replacement, rather than assert every failed enqueue must autonomously dispatch.

### Empty nonterminal persistence page (backend-qualified candidate)

Cross-review with writer/store analysis found that Cassandra GetTasks returns a `NextPageToken`, while priority `getTaskBatch` ignores it and interprets `len(response.Tasks)==0` as an empty whole ID window (`pri_task_reader.go:224-238`). If the selected Cassandra-compatible backend can return an empty page with a nonempty continuation token (the store audit identifies tombstone paging as a condition), live accepted records later in that page sequence can be skipped. `setReadLevelAfterGap` may ack the window and later GC can delete those records. There is no reader-side compensation: stale-gap detection only handles a lower captured read bound, and missing later-page records never enter outstandingTasks. This is a forward-looking, backend-qualified safety question for store-backed test and model checking, not a reproduced bug and not a SQLite claim. Require the actual supported backend/driver behavior from the persistence audit before adopting the page behavior in the model.

### All-expired suffix with no live completions

`TestSkipExpiredTasks_AllExpired` is explicitly skipped for priority (`backlog_manager_test.go:761-765`: case does not work yet). Source explains why: expired tasks move read but are not registered/completed (`pri_task_reader.go:250-256`), and subsequent empty range advances ack only if ack==read (`498-505`). With no valid completion, ack may remain old and ordinary GC has no trigger. This can preserve already-expired rows/lagging stats and re-read them on reload; it does not violate conservation of still-eligible work. Record as test-verifiable cleanup/progress limitation, not a fresh task-loss MC hunt. Backend TTL may independently remove expired rows; SQL and Cassandra must be distinguished.

### Retry queue behavior and classification boundaries

Transient dispatch errors return to matcher without advancing ack; no per-task start backoff exists yet (TODO at `pri_task_reader.go:126-130`). Historical #4612's per-failure persistence rewrite loop is partly superseded for transient errors; a CPU/RPC retry loop and task-local progress interaction remain performance/test questions. Liveness needs available History/store, an eligible poller, finite failures/interference and processing of every registered task. Nontransient errors may rewrite; don't classify all task disappearances as successful Worker execution. `addErrorBehavior` drops certain Internal/InvalidArgument/StickyWorkerUnavailable outcomes (`328-351`); in initial unversioned/nonsticky boundary, prove which can be emitted rather than inject arbitrary drop errors.
