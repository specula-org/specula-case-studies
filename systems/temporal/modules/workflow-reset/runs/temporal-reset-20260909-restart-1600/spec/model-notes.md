## Concrete state and atomicity

- `db.runs` contains durable execution metadata, record versions, current/reset/CAN identities and next-history frontier. `db.hist`, `db.cells`, `db.nodes` and `db.branches` distinguish persisted history, node references, physically retained nodes and registered fork metadata. A history append can precede or outlive its execution metadata transaction. `db.runs[r].n` limits public history to committed mutable-state history, even if a failed transaction left an appended tail.
- `op` is a per-public-operation attempt. Its program counter, base/current versions, source tokens, selected identity, volatile termination and rebuilt history survive only until cache/error release or process loss. `pending` keeps the datastore request independently of the caller: uncertainty may return before or after commit. Only already-issued datastore requests survive modeled process loss. Later client-side stages require the original live attempt. SQL IssueMetadata denotes COMMIT issuance after transaction construction; Cassandra denotes CAS issuance.
- Missing-current Reset performs a base bypass mutation, receives its result, then submits BrandNew. Ordinary base=current and base!=current paths use atomic two-/three-run metadata commits. No condition requires the missing-current base write to see an absent current: SQL checks base != current in the transaction; Cassandra checks it before the conditional batch. New-current creation requires actual absence. RangeID and record-version checks remain at commit.
- The per-call Reset I/O semaphore is held from submission through returned success/error, including the separately modeled current-termination and new-run history appends. An uncertain returned result frees the tracked I/O slot while a remote write may still resolve. Range renewal drains task requests whose completion callbacks have run; it does not wait for the I/O semaphore itself or indefinitely for remotely unresolved writes. BeginAcquireShard, RenewShardRange, and AcquireShard separate recovery initiation, durable fencing, and service-ready publication. Cassandra is capped at one slot; SQL configs exercise one and two.
- Base/current leases last through handler release. Successor lookup reads and releases its short lease before history reading. New reset state is a transient context, not a held cache lease on the newly created run. Start holds the current-lookup lock through its handler return, while Reset's lookup releases it immediately. Same-base attempts therefore serialize within one process; different-base attempts can overlap.

## History abstraction

One abstract node represents one relevant event. Start persists the abstract Start event first; a separate `AddWorkflowTaskStartedEvent` creates the valid prefix through a WorkflowTaskStarted boundary; `cut` is its last included index (the API finish ID is cut+1). Physical event/batch IDs must be mapped in the trace metadata. A later completed Update followed by a separate WFT-start transaction allows nonempty rebuilt Update maps. `ResetWFT` summarizes reset-internal WFT failure/scheduling and excluded activity bookkeeping, with one source-annotated boundary before reapplication. Those internal event details and worker task payloads are outside this model.

Signals, UpdateAccepted/Admitted, completion markers, Update IDs, payload classes, source run/event/version, and terminal CAN successor are retained. Reapplied accepted events become admissions with their original provenance. A repeated ID in the rebuilt map yields the actual Internal error; it is not silently deduplicated. Completed updates retain their ID in that map. An accepted event without a request is skipped. The initial environment currently generates accepted-with-request updates; admitted/accepted-without-request traces require extending the supported environment producers, not bypassing ReapplyEvents. Reset traversal itself implements both branches.

The original base token is retained for suffix traversal; the new fork token is used for prefix references. SQL/Cassandra in scope do not rewrite the base token; alternative storage token rewriting is excluded. CAN uses the last event's successor, not ResetRunId or visibility enumeration. A NotFound successor stops traversal; transient lookup/read failure returns an error. An unrelated current's suffix is never appended to the source list. Buffered Signal/Update events flushed by current termination are not currently generated: add explicit producers and flush steps before using traces that contain them. This is an explicit remaining reapplication coverage boundary, not a claim that such events are irrelevant.

Successful worker Update/Signal/CAN transactions are environment abstractions at their metadata commit point, preserving leases and available I/O. Their own history-write faults, activity behavior, worker availability schedules, child workflow state, replication and queue fairness are excluded. `CompleteWorkflowExecution` abstracts successful worker completion without serializing the completion-event payload. These abstractions are for Reset outcome interference, not verification of those subsystems.

## Deletion and observations

Delete is a supported public operation. Its acknowledgement schedules cleanup and can terminate an open run. The cleanup task holds a run lease, then acquires one I/O slot across visibility/current/mutable-state stages (`shard/context_impl.go:972-985`). It conditionally removes matching current, deletes mutable state, releases that slot, then snapshots branch references and deletes history. Deletion has per-stage shard-state validation, not an invented per-delete RangeID CAS. SQL deletes branch row and ranges in one transaction. Cassandra's logged batch permits either row/range visibility order, with eventual completion of both. Explicit deletion failure/crash after mutable-state removal leaves an orphan eligible for scanner verification. Scanner age is an abstract elapsed-time input, not immediate orphan eligibility: the pinned default threshold is 60 days. The default configuration enforces `ScannerAfterRequestDeadline=TRUE`: a newly allocated candidate cannot become scanner-old while its original attempt remains active. Public History Reset calls use the 30-second client timeout (`client/history/client.go:33-34,290-291`; `client_gen.go:1049-1055`), and a new persistence call rejects an already expired context (`shard/context_impl.go:2414-2427`). `ExpireResetRequest` models pre-write deadline expiration; an in-flight uncertain write retains its own fault/result path and can still resolve after caller loss. This is a relative-time abstraction, not a full clock model. The separate short-age sensitivity cfg sets the relation false and must be interpreted with its actual non-default scanner/RPC time configuration.

`audit` consists only of observations and property monitors; it never supplies a success precondition. Server success and delivered response are separate. Acknowledgement properties refer to the run's reset prefix and reapply slice at acknowledgement; later legal history extensions are allowed. Explicit deletion of the returned run is a stated exception, including deletion racing response delivery. Deletion of a different base is not an exception. ImmediateRetryIdentity is armed only when the same request's run is current, and disarmed by a distinct current-changing administrative operation/CAN/deletion. It is not permanent dedup after retention or replacement. Callback source identity stays equal to the selected original Start request identity, including the RequestIds-map fallback.

## Finite bounds and evidence limits

Base behavior does not consume MC counters. MC bounds only new client/environment work and injected failure opportunities. Reactive completion, backend result, retry, reload, reapplication, deletion and fencing steps are unbounded. Runs are never reused, including failed candidates, so finite ID exhaustion is visible. `FreshRunCapacity` is a liveness tripwire, not a claimed Temporal defect. `HistoryBound` and `PendingBuffer` are explicit exploration constraints; any boundary-hit run needs bounds enlarged before a complete verification claim.

`MCView` excludes diagnostic counters but is deliberately not installed as a TLC VIEW: counters affect enabled behavior and must remain in fingerprints. Safety configs use run/operation symmetry with model values. Trace and liveness configs disable symmetry. The base config is a reference configuration; use bounded MC configs for convergence.

The liveness property is conditional on the hunt's retained valid source, no fresh interference beyond finite input bounds, eventual healthy persistence, fair required reactive steps, available worker, and enough fresh IDs. Internal Update collision is not a documented terminal rejection; its deterministic T-2 evidence remains a test/regression concern. The liveness configuration contains no Update inputs. Full crash/restart/backend acceptance and real trace validation belong to subsequent responsible phases. Existing analysis logs are not converted into invented trace evidence.

All shipped configurations use `StartMapPresent=TRUE`, matching new runs at the pinned revision. The false value is only a legacy-record diagnostic abstraction; it is not reachable by supported current-version Start and is not an implementation-trace acceptance configuration. `FindStart` includes the fallback assignment, but historical initial-state migration is outside this empty-bootstrap suite.


## Validation refinements

Start/CAN creation persists DBRecordVersion 2; Reset persists 3 after rebuild and final transaction closes. Fork registration exposes inherited logical history immediately. The first CAN WFT schedule is an explicit one-time metadata action. Closed-run public deletion enqueues work without changing the execution row; open deletion includes termination.

The selected-history abstraction preserves a later committed extension against an older appended termination batch. Appends insert only their own physical cells, never recreating inherited cells. Transaction-ID ordering justifies this projection for the represented environment writes; multiple conflicting physical batch versions remain outside the SQLite trace projection.

The independent OracleChain walks durable CAN history using captured source frontiers, separately from batch/expected/reapplied output. An omitted source range or successor can make ReapplyGood false. CallbackSourceIdentity additionally compares against the original Start history event. AcknowledgedResetExists subsumes ReapplyProvenance's boolean monitor; they are not two independent oracles.

Trace evidence uses file SQLite, a private read-only observer connection, normal server write settings, 1 shard and I/O capacity 1. Quiescent CloseShard/reacquisition is actual execution evidence; an OS process kill or delayed remote datastore operation is not claimed as trace-tested. Multipage reapplication, admitted/accepted-without-request producers, termination-buffer flushing, child completion and Cassandra physical visibility remain explicit gaps.
