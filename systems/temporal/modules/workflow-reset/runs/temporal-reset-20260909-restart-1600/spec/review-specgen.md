## Issues Found

- **R1 — High: a delayed history append truncates newer committed history.** In `base.tla:443–477`, `AppendHistoryNodes_Current` replaces the complete stored history and cell sequence with the old request's prefix plus termination. A directed execution using unchanged base actions reaches: Start A → WFT → submit Reset B with `curN=2` → crash/reacquire → accept and complete an Update on A → finish the old current-history append. A's committed frontier remains 4, but its history and cell sequence shrink to length 3. TLC violates **TypeOK at state 28** ([schedule](output/specgen-review-20260909/work/OldAppend.tla), [log](output/specgen-review-20260909/old-append.log)). This is a **spec modeling defect**, not a Temporal data-loss discovery. The implementation inserts history nodes carrying transaction identities (`common/persistence/sql/history_store.go:40–52`; `sql/sqlplugin/sqlite/events.go:12–18,50–60`) and filters competing batches by transaction order (`common/persistence/history_manager.go:1039–1070`); an append does not truncate later rows. Both append actions also union inherited cells into `db.nodes`, potentially recreating ancestor data that the write did not contain. Model writes to their actual node ranges and preserve enough ordering information to distinguish stale and current history. Merely documenting batch transaction IDs as excluded does not justify destructive replacement semantics in a delayed-write model.

- **R2 — High: ReapplyProvenance cannot detect incomplete source traversal.** `ReadHistoryBranch` derives both `batch` and `expected` from the same `suffix` (`base.tla:285–300`), while `ReapplyEvents` uses the same `Eligible` predicate (`304–320`). `ReapplyGood` then compares the result with that traversal-derived expectation (`131–133`). An omitted range, successor, or eligibility class can therefore disappear from both sides. In an isolated one-line mutant, replacing the suffix read with `<<>>` drops a committed, non-excluded Signal; Reset still reaches server success with **AcknowledgedResetExists and ReapplyProvenance both passing**. The unchanged control includes the Signal ([mutation](output/specgen-review-20260909/oracle-mutation.txt), [mutant log](output/specgen-review-20260909/oracle-omission.log), [control log](output/specgen-review-20260909/oracle-control.log)). This is an oracle-sensitivity test, not an implementation counterexample. Derive the required source ranges and event identities independently, retaining the intended NotFound/exclusion semantics. Also, `AcknowledgedResetExists` already includes `~audit.reapplyBad`, so `ReapplyProvenance` is not an additional independent check (`950–952`). Similarly, `CallbackSourceIdentity` only compares two fields initialized from the same argument (`36–38,956`); it should compare against independently retained original Start provenance.

- **R3 — High: process crash leaves unissued persistence calls executable.** `CrashHistoryService` clears runtime ownership and marks replies lost but preserves every pending operation's stage (`base.tla:659–674`). The append/precheck/metadata actions remain enabled without distinguishing an already-issued database call from a later call that would require the dead History process to run (`443–510`). A second unchanged-base schedule crashes immediately after Reset submission, then performs current-history append, candidate-history append, and metadata commit while `rt.state="stopped"`; it installs B as current in **27 states** ([schedule](output/specgen-review-20260909/work/CrashContinuation.tla), [log](output/specgen-review-20260909/crash-continuation.log)). The diagnostic invariant marks this particular schedule's unissued continuation; it does not prohibit completion of an already-issued transaction after a crash. In the SQL implementation, those append calls and the subsequent metadata transaction are sequential client-side calls (`common/persistence/sql/execution.go:338–357`), not one autonomous server-side database request. Split issuance from completion and retain only already-issued remote work after process death. Keep process death distinct from a returned timeout or cache/shard recovery.

- **R4 — Medium: the Trace mapping cannot faithfully represent multipage branch reads.** The implementation alternates `iter.Next()` and reapplication for each batch (`service/history/ndc/workflow_resetter.go:865–883`). The model reads the entire range in one `ReadHistoryBranch` action, then applies its events (`base.tla:285–335`). Nevertheless, `instrumentation-spec.md:36,56–58` requires real event ordering, a complete range snapshot before application, and individual application events. With multiple pages, a later page can be deleted or fail after earlier events were already applied locally. There is no corresponding model page-read/error step during `reapply`, and strict full-state comparison cannot repair that mismatch. Split page fetches, page errors, and event application at the real boundaries, retaining the final-page CAN check; alternatively restrict trace acceptance explicitly to a justified single-page subset and mark deletion-during-pagination unverified.

- **R5 — Medium: scenario presence overstates executable branch and recovery coverage.** Accepted-without-request and direct admitted-then-accepted source histories have no environment producers; termination-time buffered reapplication is also omitted (`base.tla:723–760`; `model-notes.md:19–23`; implementation `workflow_resetter.go:166–208,950–1021`). These gaps are candidly documented, which is good, but the corresponding S4 branches are not established by action-name/configuration counts. In addition, only `MC_hunt_scenario2_liveness.cfg` enables HealthyRetryRecovers; it has no Update or scanner inputs, and `base.tla:979–981` observes acknowledgement or NotFound rather than an explicit execution-progress outcome. Thus the brief's S2–S5 recovery objective is only partly represented. Add supported producers and targeted recovery controls, separating known T-2 collisions from distinct-ID/exclusion controls, or narrow the coverage claims accordingly. The conditional omission of child-completion state is consistent with the brief and is not itself a defect.

- **R6 — Low: annotation density is not complete source traceability.** Important helpers such as `Eligible/FilterEligible`, `NewRun`, and `WriteFor` contain semantic choices without their own precise source anchors (`base.tla:21–28,36–38,88–95`). Many action comments repeat a broad range for every assignment instead of distinguishing implementation effects, abstractions, and ghost bookkeeping. `CreateWorkflowExecution_Start` cites Reset's BrandNew path (`base.tla:427–440`; `instrumentation-spec.md:65`), although the relevant Start path is `service/history/api/startworkflow/api.go:210,310–322`; the instrumentation prose partially corrects this. Add helper-level anchors, correct the primary Start mapping, and label abstraction/observer updates explicitly. Also split materially different take/skip/collision paths where the checklist requires distinct actions instead of relying entirely on nested conditionals.

## Verdict: NEEDS_IMPROVEMENT

Fix R1–R3 before treating fault-hunt outcomes as reliable evidence, and resolve or explicitly bound the Trace and scenario gaps. The suite has substantial scenario structure and working Trace checks, but currently admits impossible persistence behavior and misses a key class of reapplication omissions. **New Temporal implementation bugs established by this review: 0.**
