## Defect candidate E1: live timeout bypasses terminal node deletion

**Source-review discovery, high-confidence reachable defect; runtime durability/impact pending root probe.** Severity Medium: workflow can exhaust its allowed pending Nexus operation count after completed timeouts, despite API reporting zero pending operations.

- All three timeout executors call `executeOperationTimeout` -> `recordOperationTimeout` (`executors.go:614-645`). Minimum-request guard also calls it via `saveResult` -> `handleStartOperationError:554-556`.
- `recordOperationTimeout:645-676` adds the TimedOut history event and directly calls `TransitionTimedOut.Apply`; this transition (`statemachine.go:409-420`) returns `op.output()` and does **not** delete the node.
- In contrast, `TimedOutEventDefinition.Apply` (`events.go:262-272`) transitions then `node.Parent.DeleteChild`. This is the event replay/rebuild route, not invoked by the live timeout executor.
- `MutableStateImpl.AddHistoryEvent:1381-1387` adds an event/cache entry and records the event type; no event-definition application. `closeTransactionHandleWorkflowTaskScheduling:7928-7954` consults only `IsWorkflowTaskTrigger`. The framework timer loop removes timer groups and commits (`timer_queue_task_executor_base.go:338-345`, active executor:902-912); it does not delete operation nodes.
- `HandleScheduleCommand:184-191` limits `MachineCollection.Size()` including retained terminal nodes. Describe deliberately omits terminal nodes (`api/describeworkflow/api.go:706-721`), so description alone masks the capacity loss.
- Ordinary durable readback reconstructs from `dbRecord.ExecutionInfo` and `mustInitHSM` (`mutable_state_impl.go:530-533,573`, `:662-670`), preserving the persisted node. A history rebuild applies `TimedOutEventDefinition` and removes it. Do not equate cache eviction/reload with a full history rebuild.

**Historical compensation audit:** supplemental commit `e82422a2…` / #7171 explicitly repaired active/passive cleanup divergence for completed/failed/canceled results using EventDefinition.Apply, but its complete relevant diff did not change the timeout executor. #8598 later routes below-min request timeout through this remaining timeout path. E1 examines a surviving unaudited site; it does not propose reverting/reconfirming the historical fix.

Complete one operation by a normal timer (prefer this ordinary path); keep workflow run open, reload mutable state, then schedule another operation. Expect timeout event plus retained persisted TIMED_OUT node, Describe zero pending, second command WFT failure `PENDING_NEXUS_OPERATIONS_LIMIT_EXCEEDED`. Deterministic alternative sets `RequestTimeout=1ms`, `MinRequestTimeout=1s`, ScheduleToCloseTimeout=1h, causing no send at executor:287-289; valid endpoint/template still required because resolved before the guard. ## Defect candidate E2: pending cancellation skips start-to-close timer emission

**Source-review discovery independently shared by other analysis agents; root probing.** `TransitionStarted` (`statemachine.go:378-389`) immediately returns the child cancellation transition when a cancellation child exists, bypassing creation of `StartToCloseTimeoutTask` at397-400. The operation has already recorded token/start time and changed to STARTED. Initial schedule emits schedule-to-start/close only; therefore cancellation-before-start plus async acceptance leaves no start-to-close task. A later full task refresh calls `Operation.RegenerateTasks` and may repair it, whereas ordinary cache reload does not refresh tasks automatically.

External endpoint can acknowledge cancellation but ignore it, as contract allows. A missing start-to-close timer then matters independently of remote cancellation cooperation. Keep a longer schedule-to-close timer as eventual compensation; that does not enforce the shorter configured deadline. `tests/nexus_workflow_test.go:1958-2025` deliberately orders cancel intent before start and verifies cancel delivery but sets no start-to-close timeout and terminates workflow afterward. This misses the composition. Root is combining ordinary healthy start-to-close timeout control with this interleaving and DB timer observation.

## Code-review-only observation E3: cancel below-min error can name the wrong timeout

`executeCancelationTask:715-725` computes minimum request duration, first considering start-to-close and then schedule-to-close. It unconditionally overwrites `timeoutType` with ScheduleToClose whenever configured, even when the shorter start-to-close budget selected the minimum. The error at747-749 and persisted cancellation LastAttemptFailure at869-892 can therefore report ScheduleToClose exhaustion while substantial schedule-to-close time remains. The operation's timeout event, if a timer fires, uses the correct timer type; the issue is cancellation failure diagnostics. Existing cancellation cases test the timeout types individually (`executors_test.go:1115-1138`), not together. This is a direct arithmetic/path question suitable for a focused test, not a TLA+ target. No current runtime reproduction claimed here.

## Identity, concurrency and persistence contract

1. **Stable operation identity:** scheduling generates a UUID (`commands.go:53`) and puts it into history (`:233`), HSM state and every start request (`executors.go:381,264`). A callback token carries namespace/workflow/run, machine ref and request ID (`:206-218`). Retries reuse persisted request ID; the HTTP client generates a UUID only if input request ID is empty (`client.go:273-276`). The durable request ID is per scheduled operation, not per invocation attempt.
2. **Attempt number:** operation/cancellation Attempt increments on saved attempt outcomes (`statemachine.go:91-94,537-540`), serialized task Attempt is for tracing; `InvocationTask.Validate` and `CancelationTask.Validate` check state and workflow running, not task.Attempt (`tasks.go:98-103,179-184`). Repeated uncertain sends can happen without an increment if the result never commits. Do not derive attempt count solely from History or HSM Attempt.
3. **Outbound split:** first `env.Access(Read)` loads all arguments under workflow lock (`executors.go:364-408` or823-859). It returns and releases the lock. Endpoint/client setup, remote Start/Cancel call and response parsing run without that lock; final `env.Access(Write)` revalidates and commits (`:411-449`,863-923). Remote acceptance, response receipt, local memory transition, local commit and caller notification are separate observations/actions.
4. **Ref checks are at access:** `StateMachineTask:346-350` sets `ref.Validate=smt.Validate`. `stateMachineEnvironment.Access:363-410` gets the workflow lock, validates task generation/incarnation and task-specific state, invokes accessor, and commits writes via workflow context. The versioned path validates initial machine identity but does not compare last-update equality (`:234-288`); fallback validates initial failover version plus custom validation (`:291-324`). This is why a missing explicit Validate call inside executors is not a bug. `Node.CheckRunning` is enforced by task Validate even though argument-loading closures do not repeat it.
5. **Stale deliveries:** once callback or another successful start has changed operation to STARTED or deleted it, a late start result cannot pass invocation SCHEDULED validation. A stale task for the same surviving incarnation may pass after state cycles back to SCHEDULED/BACKING_OFF; this is permitted duplicate delivery with stable request identity, not automatically a protocol violation. Model overlapping delivery and current-state eligibility, not an invented exactly-once task guarantee.
6. **Result persistence failure:** an error returned after remote Start/Cancel may mean the local write committed or did not commit; executor returns save error. `Access` releases on write error, causing reload via workflow cache policy (root auditing exact persistence). If committed STARTED, retry access rejects old invocation; if not committed, reissue same start request ID to recover token or receive callback. Endpoint idempotency and retention of its request-ID->operation/outcome mapping are required for one external operation. Local code cannot guarantee exactly-once external effects without that contract.
7. **Token knowledge:** asynchronous operation token is persisted with NexusOperationStarted and HSM transition (`executors.go:454-480`). Losing response or failing noncommitted local save leaves token unknown; reconnect is Start retry under same request ID or early callback fabricating start. Synchronous starts need no asynchronous token. Cancel loads persisted token, sends it, and records acknowledgment; nil Cancel error means only request accepted (`handle.go:21-48`, executor:902-904), never operation CANCELED.
8. **Callback convergence:** completion path can fabricate STARTED before terminal event (`completion.go:207-223`), rechecks request ID, commits through environment. Late/duplicate callback after deletion returns NotFound; fixed single-run scope excludes Reset fallback at238-247. Successful duplicate acknowledgment is not required; one durable terminal result with protocol-acceptable late rejection is the relevant property.
9. **Task/control separation:** endpoint setup/read-history/client-provider errors return before a remote call and do not increment operation Attempt. Transient remote failures commit BACKING_OFF with NextAttemptScheduleTime; timer changes state to SCHEDULED and emits next invocation. DestinationDown wraps the result of save so circuit-breaker feedback must not be mistaken for an additional state transition.

## Exact timeout abstractions

Let r be RequestTimeout, s/c/t be schedule-to-start / schedule-to-close / start-to-close durations, S scheduled time, B local persisted started time, now local wall time.

- Start request: `callTimeout=min(r,s-(now-S))` if s>0, else `min(r,c-(now-S))` if c>0, else r. Schedule command caps positive s and t against positive c; s precedes c because both anchored at S. Start-to-close does not cap synchronous request execution.
- Operation-Timeout header: `min(t if positive else infinity,c-(now-S) if positive else infinity)`, set only when user header absent. Derived independently from request duration. This tells endpoint a bound but does not replace Temporal timer enforcement.
- Cancel request: minimum of r, t-(now-B) when positive, c-(now-S) when positive. Minimum-duration suppression marks cancellation request FAILED; operation's own timeout remains separately governed by timer.
- Too little start request budget resolves operation TimedOut immediately, potentially before exact deadline by MinRequestTimeout tolerance. Configure these thresholds explicitly; do not demand a request be sent in a knowingly insufficient remaining interval.
- Executors use `time.Since` for request-budget arithmetic and environment Now for local transition timestamps. Timers use workflow time conversion in queue framework. Primary analysis should exclude time-skipping/pause semantics unless validated deliberately.

## Boundary observations and exclusions

**User header override is documented behavior, not an SDK defect.** User NexusHeader values are accepted subject to finite blacklist and length (`commands.go:163-180`, config:78-103). `client.go:276,284` sets generated request ID then arbitrary user headers; `handle.go:30,33` sets stored token then headers. `api.go:122-126` uses Set. Pinned Nexus SDK `nexus/options.go:9,36` explicitly says Header values overwrite SDK values; only content-prefix reserved constraint is stated. Live Nexus HTTP SPEC permits arbitrary request headers. Thus an identity-preserving primary model must explicitly assume user headers do not override protocol fields, and traces should independently check wire request ID/token against HSM. A Temporal-level policy question remains code-review-only; no novel bug/MC claim from this documented behavior.

**Endpoint registry fallback:** lookup prefers stored endpoint ID then name (`executors.go:934-946`), historically compensating nonreplicated endpoint registries. Endpoint deletion/recreation could retarget same name, but endpoint administration is excluded; model stable endpoint binding. An endpoint NotFound currently fails operation/cancel request rather than indefinitely retrying.

**Metrics are not commit receipts:** timeout timer emits metric before transaction commit (`executors.go:626-639`); result/completion paths defer metric after successful returned commit (`:411-449`). An uncertain commit can omit metrics even if durable effect happened; timer retries can count twice. This is documented and must not become a durability oracle.

**Ownership corrections:** header maps cloned when loaded (`executors.go:393,854`), payload retained but HTTP payload serializer reads it. Separate system endpoint paths may reserialize payload via processor; read fully but excluded from primary worker/external endpoint model. Shared failure conversion now uses clone at shared entry point. No new ownership defect established here.

**Progress assumptions:** eventually schedulable outbound/timer tasks and available local persistence; live workflow run; endpoint eventually responds or configured terminal timeout governs; callback delivery retries appropriately; stable request identity with cooperative endpoint dedup/reconnect. Cancellation may be ignored remotely. Legitimate endpoint refusal and legitimate timeout are allowed terminal outcomes.
