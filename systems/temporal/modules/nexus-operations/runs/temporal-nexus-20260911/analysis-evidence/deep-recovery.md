## Exact execution and atomicity boundaries

`Environment.Access` acquires a workflow context/lock, loads and validates state, invokes the accessor, and on writes calls UpdateWorkflowExecutionAsActive (or the closed-workflow compatibility snapshot path). Reads release with nil; write/accessor/persistence errors release with the actual error (`statemachine_environment.go:363-410`). Cache release clears the context on any error and on panic (`workflow/cache/cache.go:364-405`). Consequently individual `MachineTransition` rollback must not be mistaken for a whole-transaction rollback: it restores this node's transition counters and invalidates this node's decoded data on error (`hsm/tree.go:585-634`); nested child changes/history effects are discarded by the enclosing write failure and cache clearing. A harness that directly calls the transition in an in-memory tree does not validate this durable boundary.

Network start/cancel is outside the workflow lock, between a read Access and a write Access. Validations therefore run again on save. Queue task identity and operation identity differ: outbound `StateMachineTask` copies task.Validate into the ref and includes physical task ID (:346-351), while the callback path supplies a broader ref and operation RequestId (completion agent covers entry path). No operation task checks its serialized Attempt field against the current attempt. `MachineTransitionCount` equality is available only through `hsm.ValidateNotTransitioned` (hsm/tasks.go:57-61), and Nexus task validators do not call it.

Task generation is a distinct step during close. `GenerateDirtySubStateMachineTasks` consumes only tasks present in the transition operation log (task_generator.go:297-335); it does not regenerate required tasks by inspecting every state. `generateSubStateMachineTask` fills refs, calls task.Validate, drops tasks that are no longer eligible, then either tracks a logical timer or appends a physical outbound task (:942-1009). Any validation error there is treated as ineligible, not propagated (:976-979); valid serialized Nexus state is assumed so deserialization errors are not a modeled adversary absent concrete corruption evidence.

Logical timer groups live in `ExecutionInfo.StateMachineTimers`. They are ordered by deadline; one physical StateMachineTimerTask wakes the first unscheduled group (`state_machine_timers.go:18-40`). The timer executor reads the **current persisted logical groups**, processes expired groups under the workflow lock, validates each ref/task, skips NotFound/stale/completed errors, and aborts on other errors (`timer_queue_task_executor_base.go:291-348`). Group removal and the next timer publication are persisted via the enclosing workflow transaction. A delayed physical wakeup is therefore not itself an old serialized operation attempt.

## Eligibility and regeneration table

All actual task execution requires the workflow still running via `node.CheckRunning` (tasks.go) and a valid HSM identity via Environment validation. Below, S2C = schedule-to-close, S2S = schedule-to-start, STC = start-to-close. Positive configured duration enables each timer; STC additionally needs a stored started time. Generation validation filters the raw `RegenerateTasks` result.

| Operation state | Raw Operation.RegenerateTasks | Eligible operation tasks after generation validation |
|---|---|---|
| SCHEDULED | invocation + S2C + S2S + STC if started-time field present | invocation; S2C; S2S. STC fails state check. |
| BACKING_OFF | backoff + S2C + S2S + STC if started-time field present | backoff; S2C; S2S. STC fails state check. |
| STARTED | S2C + S2S + STC | S2C; STC. S2S fails state check. |
| SUCCEEDED/FAILED/CANCELED/TIMED_OUT | configured timers, possibly STC | none: every timeout validator rejects terminal state. |
| UNSPECIFIED | configured creation timers | unreachable as committed normal operation: AddChild transitions immediately. |

Sources: statemachine.go:128-181; tasks.go:50-66,98-103,143-148,261-283,315-333. The operation RequestId is stored from the scheduling event and never replaced by retry transitions (:46-80,259-288); Attempt records completed attempts (:91-95), not number of network sends. Retry backoff preserves request identity, clears next schedule only on reschedule, and increments attempt on a processed retryable failure. TransitionStarted increments attempt and stores operation token/time (:364-400). A send whose local result does not commit may be replayed with unchanged durable Attempt.

| Cancellation child state | Raw cancellation regeneration | Effective behavior |
|---|---|---|
| absent | none | no cancellation requested |
| UNSPECIFIED | none | durable pending intent waiting for parent STARTED; no token exists yet |
| SCHEDULED | outbound cancellation task | child state + running workflow validate; outbound argument load additionally rejects terminal parent |
| BACKING_OFF | cancellation backoff timer | child state + running workflow validate; reschedule emits outbound cancellation |
| SUCCEEDED / FAILED | none | request delivery resolved; neither state changes operation to CANCELED |

Sources: statemachine.go:423-449,543-563,594-674; tasks.go:179-184,224-229; executors.go:823-858,863-924. Acknowledged cancellation is explicitly allowed to be ignored by the endpoint; completion callback determines operation outcome (executors.go:902-904). Retryable cancellation failure persists backoff, nonretryable failure only fails the cancellation child. RecordCancelRequestCompletionEvents controls optional request-ACK/failure history, not whether the child transition occurs (:874-921).

## References, stale tasks, and reload

With transition history, validation checks the ref's mutable-state versioned transition is in current history, resolves the path, compares initial versioned transition, then calls task-specific Validate. It does **not** compare current vs referenced last-update transition counts by default (`statemachine_environment.go:223-288`). Without usable transition history, it compares initial failover version and invokes the same validator; an API ref may trigger one stale-state reload, while a task ref is assumed to reference already-visible state (:291-324). The one-run scope removes branch/reused-scheduled-ID complications but must retain generation and operation identity.

`validateTaskGeneration` discards physical task IDs older than the workflow's task-generation watermark, with a repair refresh only for an anomalous watermark newer than the shard clock (`ndc_task_util.go:235-255`). Outbound tasks also validate their clock against current shard ownership (:209-232). Full Refresh updates the watermark before generating replacements (task_refresher.go:64-72). A late invocation for the same node may execute in a later SCHEDULED attempt because validation is state-based; this is permitted duplicate external delivery, not automatically an identity bug. Any proposed exactly-once effect invariant would exceed the implementation/remote endpoint contract.

Three recovery operations must remain distinct in the model:

1. **Ordinary cache loss, process crash, shard reacquisition and load:** `ContextImpl.LoadMutableState` loads the DB record, constructs NewMutableStateFromDB, and StartTransaction (:408-498). The constructor assigns `executionInfo = dbRecord.ExecutionInfo` (:530-573), retaining persisted logical timers, and `mustInitHSM` only creates a root over persisted children (:662-672). `NewRoot`/`Child` decode existing nodes and emit no tasks (hsm/tree.go:200-232,309-341). This does not synthesize a missing STC timer.
2. **Explicit full task refresh:** `ContextImpl.RefreshTasks` (:1382-1405) invokes TaskRefresher.Refresh, resets the watermark, clears/reconstructs logical timers, regenerates each eligible node's tasks, and persists the passive update. It can repair missing tasks implied by stored operation state.
3. **Partial state-application refresh/rebuild:** only nodes updated at/after the given transition are refreshed; relevant timers are trimmed and rebuilt (task_refresher.go:678-730; state_machine_timers.go:74-123). XDC state application is outside the primary model. History replay also is not identical to ordinary DB load.

## Finding R1: pre-start cancellation omits the operation STC timer

**Status:** source-review discovery, exact live path verified; root is independently executing functional/durable probes. Not an MC discovery. Medium severity as a timeout/liveness contract violation, with potentially indefinite wait if no larger timeout applies.

**Trigger:** schedule an async operation with positive StartToCloseTimeout; request cancellation while SCHEDULED or BACKING_OFF (including while a network start is in flight); let an async start result be locally committed; have the endpoint acknowledge cancellation without completing the operation.

**Mechanism:** Operation.Cancel creates an UNSPECIFIED child and emits no cancellation until started (statemachine.go:428-442). TransitionStarted sets parent STARTED/token/StartedTime, then when child exists returns immediately from the child scheduling transition (:376-389). This bypasses parent STC task creation at :397-398. With no preexisting child the same transition emits STC. The live saveStartedResult invokes precisely this transition (executors.go:452-480). The StartedEventDefinition replay path also uses it (events.go:139-145).

**Compensation checked:** creation-time S2S timer is now ineligible after STARTED; S2C may eventually time out but is independently configured and may be absent or much later. Cancellation ACK/failure does not transition the operation to terminal. Cancellation request budgeting considers remaining STC but a below-minimum request budget merely fails the child, not the operation (executors.go:715-749,863-901). Ordinary reload preserves the absence, as established above. Explicit RefreshTasks reconstructs STC from StartedTime and configured duration; that is a repair path, not evidence normal scheduling is correct. A simultaneous terminal callback can subsume the missing timer and mask the defect.

**Existing tests and historical provenance:** `TestTransitionStartedEmitsStartToCloseTimeout` (statemachine_test.go:171-214) has no cancellation child. `TestCancelationBeforeStarted` (:739-789) has no STC and explicitly expects the parent output empty. Functional `TestNexusOperationCancelBeforeStarted_CancelationEventuallyDelivered` (tests/nexus_workflow_test.go:1958-2025) verifies delivery then terminates the workflow, so never tests STC. `TestNexusOperationStartToCloseTimeout` (:3178 onward) has no cancellation. `git log -S startToCloseTimeoutTask` identifies current timeout feature introduction `f911e1e7a` (#9153), following reverts of #9010/#9033; do not treat a reverted intermediate fix as pinned behavior. Targeted fresh upstream searches are retained in archaeology-recovery/stc-omission-upstream-search.json; no exact omission report was found by these searches, which is not an exhaustive novelty guarantee.

**Executable handoff:** controlled endpoint records start accepted/token, waits until server durable cancellation intent observed, returns pending, ACKs cancellation, never sends completion. Assert raw durable operation STARTED+positive STC+StartedTime and absence of STC logical task; close shard/cache and reread; contrast with no-prestart-cancel control showing STC and timely timeout. Then explicitly RefreshWorkflowTasks and observe reconstructed STC/timeout, preserving that result separately from ordinary recovery. Add a second control where cancellation is requested after STARTED. Formal model must distinguish transition-emitted task set from state-derived regeneration and check required-timer availability after commit; this creates new interaction evidence, not a reverted historical bug target.

## Finding R2: live timeout transition retains a terminal node that admission counts

**Status:** code-review candidate with complete immediate call chain and no observed cleanup compensation; root coordinating runtime readback. Do not claim durable reproduction until root's evidence exists.

`recordOperationTimeout` (executors.go:645-676) adds history and directly calls TransitionTimedOut. It never invokes TimedOutEventDefinition.Apply, whose corresponding replay/event path deletes the child (events.go:262-272). Unlike terminal success/failure/cancel helpers, this live path can leave a TIMED_OUT node in the root. CloseTransaction uses added HSM event types for WFT scheduling only (mutable_state_impl.go:7928-7954); task publication consumes op log and does not reapply the event. Timed-out transition emits no tasks, and reload restores the retained node. `HandleScheduleCommand` counts `coll.Size()` at commands.go:185-190, which counts all persisted child nodes, not only nonterminal operations (hsm/tree.go:674-680). Thus max-pending=1 can reject scheduling after a genuine timeout despite no live operation. This is relevant even if the immediate terminal-result safety property remains correct.

Compensations/exclusions: existing terminal-state guard prevents ordinary cancellation of the retained node (commands.go:276-291); timeout validators prevent revival (tasks.go:50-66). Those guards do not reclaim the capacity. Explicit task refresh filters operation timeout tasks but does not delete the node. Replication/history event apply may delete it, but is outside ordinary one-cluster reload and cannot be assumed. Root should inspect default STC control raw HSM retention then issue a second schedule under MaxConcurrentOperations=1, with successful synchronous or callback-terminal control. Targeted fresh upstream searches retained in archaeology-recovery/terminal-retention-upstream-search.json; #7128/#6984 historic deletion discussions are reference only until compared with the current live alternate path.

## Other observations and rejected suspicions

- **Known field loss, not novel:** open #11312 explicitly addresses HSM canceled failure coercion dropping Source/EncodedAttributes. See archaeology-recovery/report.md for full discussion counts and exact live PR head. Keep as known code-review-only finding, not an MC target.
- **State-based task validation is intentional abstraction:** do not model task.Attempt or MachineTransitionCount as an equality fence just because serialized fields exist. Actual Nexus validators check eligible state; framework checks initial identity and generation watermark.
- **Terminal timer regeneration is filtered:** Operation.RegenerateTasks unconditionally asks for configured creation timers even in a terminal state, but generateSubStateMachineTask validates and drops them. Raw RegenerateTasks output alone is not a revived timer bug.
- **Timer head error can block other HSM timers:** timer_queue_task_executor_base.go:326-329 explicitly accepts this limitation. An arbitrary corrupt/unregistered timer injected directly into mutable state is not a justified new modeling adversary here.
- **Cancellation RequestTime tracks scheduling:** child RequestedTime is set when UNSPECIFIED becomes SCHEDULED, potentially later than actual cancel command (statemachine.go:598), while RequestedEventId records the command. Treat as field semantics/observability, not proof cancellation was never durably requested.
- **Timer deadline lower bound:** hsm/tasks.go:26-28 permits delayed execution. Assertions should distinguish no published timer from mere scheduler delay and require fair timer processing only when stating progress.
