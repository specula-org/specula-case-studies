## Issues Found

- **[High] Request expiry is disconnected from the recorded request budget.** `base.tla:192–204,373–385` records a budget, but `RequestDeadlineExceeded` at `240–243` requires only `phase = "Waiting"`. No send timestamp/deadline is stored, and neither elapsed time nor a separate parent-context cancellation is required. The implementation creates timed contexts at `service/history/hsm/nexusoperations/executors.go:223–257,715–727`. A fresh driver calling nine unmodified base actions reaches expiry with `now = 1` and `budget = 3`, without any clock advance: [ReviewExpiry.tla](output/review-specgen-20260911/ReviewExpiry.tla), [checker log](output/review-specgen-20260911/expiry.log), 10 distinct states, diagnostic invariant violation. This is a **modeling issue**, not a Temporal bug. It matters to S1/S4/S5 ordering: S1/S5 currently cap time at 3, while a request sent at 1 with budget 3 cannot expire until 4, before even allowing retry backoff. Store the request deadline, guard deadline expiry, represent earlier transport/parent-context failures separately, and adjust the hunt horizons accordingly.

- **[High] Strict trace snapshots do not match the documented timer and refresh hooks.** Timer actions remove individual entries from `s.v.timers` immediately (`base.tla:453–482`), while `instrumentation-spec.md:46,54,128–134` requires the actual mutable-state timer groups at each inner executor boundary. In the implementation, `service/history/timer_queue_task_executor_base.go:316–345` processes entries, advances a local group slice, and assigns `ms.GetExecutionInfo().StateMachineTimers` only after the loop. Thus an inner timeout hook still observes the old mutable-state timer list. A synthetic diagnostic retaining that source-backed field value at the documented hook is rejected at event 43 by the unmodified Trace: [fixture](output/review-specgen-20260911/source-shaped-timer-hook.ndjson), [log](output/review-specgen-20260911/timer-hook.log). This is a source-shape probe, **not an implementation trace**. Similarly, the refresh hook is specified after full refresh (`instrumentation-spec.md:146`), but `base.tla:592–598` leaves timers empty until a later generation action; the real refresher already generates tasks and the wake before returning (`service/history/workflow/task_refresher.go:699–730`). Align hooks and modeled phases, or explicitly distinguish the executor's processing cursor from raw mutable-state fields. Do not manufacture snapshots from model transitions to satisfy `Trace.tla:85–87`.

- **[Medium] The brief's progress obligation is not implemented as a checkable property suite.** `EligibleProgress` (`base.tla:715–720`) only covers Started operations with STC and live operations with S2C. A Scheduled operation with S2C disabled, or stranded cancellation/WFT work, can remain stuck without violating those clauses. `Spec` and `MCSpec` have no execution/commit/time fairness; no config enables this property (`MC.tla:275–277` explicitly defers it). Also, `s.notified` is only recorded, while `StartWorkflowTask` can start from Idle or Pending without consuming notification or published WFT work (`base.tla:536–542,619–624`); the current oracles therefore cannot detect loss of that notification path. The audit candidly acknowledges the missing liveness run, but this remains incomplete coverage of brief §5. Add an appropriately scoped progress model and runnable fairness configuration, including required-work and workflow-observation obligations. Merely enabling the current property under the finite time horizon would be unsound as a validation method.

- **[Low] Tighten the distinction between fault bounds, workload bounds, and source annotations.** `MCSendCompletionCallback` bounds every callback send, including the first normal delivery (`MC.tla:100–103`); `MCStartWorkflowTask` bounds a normal WFT start (`245–248`), including starts needed after events. These limits are useful workload restrictions, but are broader than “only fault-injection actions bounded.” Separate injected workload from reactive delivery if progress is to be checked. Source annotations are generally good, but examples such as `Wake` (`base.tla:100–105`), `TerminalCallUpdate` (`276–284`), and `DuplicateOutboundTask` (`612–617`) need more precise per-branch source or planned environment-hook references to satisfy the checklist literally.
