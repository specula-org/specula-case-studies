## 1. Acceptance guards and the actual identity contract

`common/tasktoken/token.go:33-60` creates an ordinary Activity token with namespace ID, Workflow ID, Run ID, scheduled event ID, activity ID/type, attempt, shard vector clock, version and start version. **It does not set StartedEventId or StartedTime.** Those belong to the separate Workflow Task token constructor (`:9-30`). Matching supplies `ActivityAttemptStamp=0` for Workflow Activities and fills it only for CHASM component refs (`service/matching/matching_engine.go:3429-3448`). Ordinary Activity Stamp is a server dispatch/timer identity, not a worker-result token field.

Frontend deserializes a worker's opaque task token and derives namespace identity from it (`service/frontend/workflow_handler.go:1453-1463`, `:1650-1659`, `:1856-1865`, `:2083-2092`). History routes using the namespace and token Workflow ID, then calls the corresponding engine/API; the generic handler token check only requires a Workflow ID when no CHASM component ref is present (`service/history/handler.go:392-440`, `:2304-2309`). Honest caller/use-of-issued-token is an environmental assumption; this model should not invent authenticated per-attempt secrets or include arbitrary token forgery.

All four History result/heartbeat APIs deserialize token, resolve optional Run ID via the current-run lookup for legacy ByID calls, check active namespace and Workflow running state, resolve scheduled event ID, and apply **the same shared guard**. `service/history/api/activity_util.go:58-79` enforces:

1. Pending ActivityInfo must be started, except force-completion ByID.
2. If the token contains a scheduled event ID, token Attempt must equal ActivityInfo.Attempt.
3. If both token.StartVersion and ActivityInfo.StartVersion are nonzero, those must match; when this branch is used, it returns immediately rather than also comparing last-write Version.
4. Otherwise a nonzero token.Version must equal ActivityInfo.Version; zero version is backward-compatible unspecified.

`common.EmptyVersion` is **0**, not -1 (`common/constants.go:15-16`). Missing response versions become zero and skip these guards. A model that rejects a zero-version token against nonzero ActivityInfo has stronger semantics than this server. The guard does not compare token Activity ID once a scheduled ID is present; scheduled identity within the Run is authoritative. Clock comparison checks whether the request proves this shard is stale, not equality to the current attempt: incomparable clocks and clocks <= current are allowed; a future comparable clock unloads the shard and yields ownership loss (`consistency_checker.go:201-225`).

History API anchors: completion `respondactivitytaskcompleted/api.go:58-87`; failure `respondactivitytaskfailed/api.go:59-86`; cancellation acknowledgement `respondactivitytaskcanceled/api.go:57-89`; heartbeat `recordactivitytaskheartbeat/api.go:49-75`. If a missing scheduled ID lies beyond cached NextEventID, each API reports ErrStaleState rather than deciding permanent absence. Handler retry policy explicitly includes ErrStaleState and persistence conflicts (`api/retry_util.go:12-18`, `service/history/fx.go:266-270`), and cache release clears on error (`workflow/cache/cache.go:373-409`).

For ordinary retries with monotonic Attempt and fixed Workflow Run/scheduled ID, a late prior-attempt completion, failure, heartbeat, or cancellation acknowledgement is rejected **before mutation** by the same attempt guard. During retry backoff, no attempt is started, so all ordinary token result calls are rejected even if a token happens to carry the upcoming attempt. A duplicate terminal message after deletion receives NotFound; successful-effect deduplication does not promise replayed RPC success. StartTime-based rejection must not be invented to explain this contract.

## 2. Starting an Activity and reconstructing an acknowledged start

`recordactivitytaskstarted/api.go:50-82` runs under the shared update helper. Pending ActivityInfo is loaded; absent state can produce stale-cache retry (`:124-136`). History fetches the scheduled History event because its input/type/timeout attributes are needed for dispatch (`:139-148`). If already started and RequestId matches, the server reconstructs a success response; if RequestId differs, it returns TaskAlreadyStarted (`:150-170`). For a fresh start, workflow rules/paused stamp logic and stamp equality execute before starting (`:173-184`), followed by deployment routing checks. The shared start transition stores worker control queue, StartedClock, StartedTime, RequestId and current versions (`mutable_state_impl.go:4457-4541`). Retry-policy Activities deliberately keep `StartedEventId=TransientEventID` in Mutable State without immediately materializing a History Started event (`:4527-4541`).

**Verified known code-review finding (open PR context): duplicate-start response is incomplete.** The same-RequestId branch fills StartedTime/Attempt/Clock, and common initialization fills ScheduledEvent/current scheduled time/priority. It skips HeartbeatDetails, Version, StartVersion, WorkflowType, WorkflowNamespace, and RetryPolicy assigned only at `recordactivitytaskstarted/api.go:294-310`. Matching forwards those fields and creates a token from the response (`matching_engine.go:3435-3478`). Thus an attempt recovered through this branch can lose its prior heartbeat checkpoint and policy/type/namespace metadata. The newly constructed token has zero Version/StartVersion; these zeros **do not themselves reject result APIs**, including for a global namespace, because zero is the empty-version sentinel. A claim that this omission causes universal completion rejection is false.

Parent fetched/read open [PR #11734](https://github.com/temporalio/temporal/pull/11734); its full body and comments were read from `prs/11734/view.json` and `comments.txt` here. The proposed PR explicitly fills the complete embedded-Activity response while retaining the parent-poll identity across ambiguous child deadlines. Existing pinned duplicate-request tests only assert Clock behavior with/without StartedClock (`api/recordactivitytaskstarted/api_test.go:280-378`); they leave other fields zero. Keep the finding as **known, pending code-review/test validation**, not a novel MC target or a reproduced current production bug. Control should compare independent ActivityInfo heartbeat/policy to the actual recovered poll payload and decoded token, rather than deriving both expectations from the same response.

## 3. Transfer/retry handoff, Matching acceptance and response loss

Ordinary initial transfer processing (`transfer_queue_active_task_executor.go:234-286`) obtains a Workflow lease, loads state, checks ActivityInfo existence, stamp equality/unpaused state, task version, and running Workflow. It snapshots scheduling timeout, directive and priority, releases the lease at `:284`, then calls Matching. This release is necessary because Matching calls History back to durably start. A delivery being in flight therefore cannot be represented as a single atomic lease-held transition.

`transfer_queue_task_executor_base.go:95-144` sends namespace/Workflow/Run/scheduled ID, queue, ScheduleToStart timeout, task-derived shard clock, stamp and priority. It sends **no Attempt**. Without assignment-rule routing, successful Matching return completes transfer processing immediately. Independent-build-ID writeback is an excluded routing extension, and happens after Matching accepts work. NotFound from AddActivityTask is logged because task error handling may drop it; code comments explicitly say it is unexpected (`:120-128`). Do not inject arbitrary NotFound as a healthy storage error and then label intentional invalid-task dropping as durability loss.

At the interface boundary, Matching `AddActivityTask` creates a task with current enqueue time/TTL, scheduled ID, clock and stamp (`matching_engine.go:646-693`), then the partition manager either completes a sync match or calls `SpoolTask` before returning (`task_queue_partition_manager.go:607-673`). Spooling waits for a task-writer completion channel, and writer success follows `db.CreateTasks` (`task_writer.go:85-174`; priority counterpart `pri_task_writer.go:68-173`; fair writer similarly waits for writer response). Thus “AddActivityTask succeeded but necessary asynchronous append was never awaited” is not supported. A successful sync match instead means History accepted a start; it is still distinct from the worker receiving the poll response. Matching queue implementation beyond this contract is excluded.

Matching constructs one UUID for each `recordActivityTaskStarted` call under a shorter child context (`matching_engine.go:3587-3624`). Its retryable History client retries the same request object within that context (`client/history/retryable_client_gen.go:674-686`). When that call ends in error, Matching finishes the task and continues its parent poll (`matching_engine.go:1117-1126`). Another concrete dispatch constructs a different UUID. A start committed with an undelivered response can therefore be rejected as already started on later delivery (`:1058-1060`). Successful dispatch calls `task.finish(consumedToken=true)` before constructing/returning the worker response (`:1128-1130`). Healthy timeout/retry remains the compensating mechanism for an orphaned accepted start; this establishes a latency boundary, not permanent loss. [Issue #11733](https://github.com/temporalio/temporal/issues/11733) is code-supported but has no maintainer comments or executable reproduction in the fetched thread. Its in-flight recovery fix is already proposed in #11734.

**Legacy retry-stamp configuration question, contained to historical context / code review.** The retry executor checks task Attempt while holding the lease, but the emitted AddActivityTask request carries only stamp, not attempt. History's fresh-start path has no ScheduledTime lower-bound guard. A delayed duplicate AddActivityTask from an old attempt can meet a later pending unstarted attempt if retry stamps were not incremented. A concrete schedule is: initial task accepted by Matching but transfer response lost; worker starts then fails; RetryActivity creates backoff successor; redelivered initial transfer still has stamp zero, which still matches under the default-disabled retry-stamp gate, and can deliver before successor ScheduledTime. Earlier stamp validation by Matching does not repair a same-stamp match. The exact public delivery order still needs runtime confirmation.

Merge commits `392f51b17184806921a25e610cf23b30c43d38e6` and `079e85c47976b183d2b409d30819fe9ffd96fe8d` are verified ancestors of the pinned tree; their relevant stamp-validation/gating diffs were read and complete patches saved in the PR directories. Full body, comments, reviews and inline comments of [#8536](https://github.com/temporalio/temporal/pull/8536) and [#8607](https://github.com/temporalio/temporal/pull/8607) were read and preserved. #8536 introduced validation and per-retry stamp changes explicitly to prevent invalid-task backlog; maintainers discussed missing mutation sites and first-task stamp zero. #8607 deliberately gates retry stamp increments until cross-cluster rollout completes to avoid compatibility and dropped tasks. Current `system.enableActivityRetryStampIncrement` defaults false (`common/dynamicconfig/constants.go:239-242`). Consequently, defaultfalse schedules directly exercise a known deliberately gated historical mechanism. Do not promote this into a new MC hunt merely as “verify stamp guard is load bearing.” If investigated further, ask the code-review/test contract question about early retry under the actual configuration and document the policy consequence; a new MC target requires a distinct mechanism/value beyond rederiving this gate.

## 4. Cancellation is a durable request with multiple permitted resolutions

Cancellation command handling adds ActivityTaskCancelRequested and updates ActivityInfo.CancelRequested (`mutable_state_impl.go:4741-4783`, `:4865-4892`). While scheduled or in backoff (StartedEventId empty), it immediately adds ActivityTaskCanceled and marks a follow-up Workflow Task obligation (`workflow_task_completed_handler.go:692-717`; `respondworkflowtaskcompleted/api.go:551-566`). While running, the request remains pending; completion has no CancelRequested veto (`respondactivitytaskcompleted/api.go:85-126`), so completed is a permitted winner. Failure and timeout obey RetryActivity's cancel-requested branch rather than forcing a canceled event. Cancellation acknowledgement requires both current token and CancelRequested (`respondactivitytaskcanceled/api.go:82-108`). It is incorrect to demand that every successful cancel request later yields canceled.

Heartbeat reads CancelRequested/Paused/ActivityReset and persists progress before returning the flags (`recordactivitytaskheartbeat/api.go:77-101`). Therefore a running worker need not have heartbeat timeout configured in order to heartbeat and discover cancellation. If it never heartbeats or otherwise supports cancellation delivery, no immediate worker-stop guarantee exists. Timer expiry remains a possible server resolution.

Optional worker-command cancellation is a separate observation path, disabled by default (`system.enableCancelActivityWorkerCommand`, `common/dynamicconfig/constants.go:208-227`). A running Activity with a worker control queue and StartedClock receives a reconstructed opaque token in a batched WorkerCommandsTask (`workflow_task_completed_handler.go:718-778`, `task_generator.go:585-599`). These tasks are created in the Workflow transaction, dispatched later by the outbound executor, and are explicitly best effort: missing worker / upstream timeout is dropped, transport faults retry with a cap (default 30), worker-returned permanent errors are dropped (`outbound_queue_active_task_executor.go:109-120`; `common/workercommands/dispatcher.go`, fully read). Command delivery success is not the ActivityCanceled event; the worker's valid acknowledgement still must reach the normal History API.

A superficially missing Paused guard at fresh start is normally compensated: pausing a scheduled/backoff Activity increments Stamp, whereas pausing a running Activity deliberately leaves its stamp so it may finish (`workflow/activity.go:267-275`). Transfer and History stamp checks reject the old delivery. Do not call this a new bug from reading only `processActivityWorkflowRules`.

## 5. Persistence, cache and external acknowledgement boundary

`GetAndUpdateWorkflowWithNew` acquires the lease and defers release with the returned error (`update_workflow_util.go:14-34`). The action mutates state; if CreateWorkflowTask is requested and none exists and Workflow is not paused, it adds a normal WFT before one `UpdateWorkflowExecutionAsActive` persistence call (`:70-117`). Completion, terminal failure and cancellation acknowledgement request this; retrying failure and heartbeat do not. An already pending/started WFT discharges the immediate new-WFT creation condition; buffered Activity events may still require a later WFT, so the model should express a Workflow obligation rather than one-new-transfer-per-terminal-RPC.

The successful History response occurs only after this helper returns. Cache release clears failed contexts and retains successful clean state (`workflow/cache/cache.go:373-409`); the next lease loads persisted state (`consistency_checker.go:275-315`). Explicit consistency mismatch clears and reloads once. The helper does not prove returned storage error means rollback: parent persistence analysis must retain definitely-uncommitted vs committed-with-lost-response outcomes and ownership conditions. ByID duplicate NotFound alone cannot distinguish earlier completion from timeout/cancellation; durable history/readback is required.

For read observations, GetMutableState response is built under a lease with copied fields (`get_workflow_util.go:266-419`), and long polling registers its watcher then rereads to close the notification race (`:129-181`). The response is a Workflow readback, not the full ActivityInfo/task-transaction oracle. A trace needs independent ActivityInfo/persistence observations, ordered under the lease or tagged by durable DB record/transaction version, plus separate client receipt records. History alone misses retry-policy starts and intermediate attempts.

## 6. Frontend transformations constrain acknowledgement invariants

Public RPC success is not always the requested terminal result. Oversized completion result is intentionally converted to nonretryable ServerFailure, then returns an empty successful CompletedResponse (`workflow_handler.go:1672-1706`). Oversized cancellation details similarly become failure before a successful CanceledResponse (`:2105-2139`). Oversized heartbeat details fail the Activity and return successful CancelRequested=true (`:1472-1496`). Ordinary model assertions about requested successful completion therefore require valid payload/identity/field sizes, or explicit transformed-operation actions.

Ordinary token failure API requires ApplicationFailureInfo (`workflow_handler.go:1871-1875`); ByID failure does not use that same top-level restriction and has its own retry-delay validation (`:2011-2014`). Final-heartbeat detail overflow in a failure request strips those details and adds a response failure; it does not silently count them as committed (`:1887-1905`, `:2016-2034`). Include actual frontend request normalization in trace provenance if testing these boundaries. These are established contracts, not new bugs.
