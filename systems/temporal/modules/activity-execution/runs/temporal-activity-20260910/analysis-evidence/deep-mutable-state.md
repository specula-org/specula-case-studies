## Ordinary lifecycle findings

**Scheduling and start.** Schedule captures FirstScheduledTime, per-attempt ScheduledTime, four timeout settings, retry policy, attempt 1, nil start/heartbeat state, and expiration anchored to original schedule-to-close at `4348-4397`; task generation is requested at `4327-4334`. Start updates only after History's external handler accepts its queue/start identity (the API agent owns that complete chain). This MutableState helper itself does not replace token/start guards. Match delivery and History accepted start must remain separate actions.

**Result applicability.** Shared token guard `service/history/api/activity_util.go:58-79` requires current started state, compares token attempt for ordinary scheduled-event tokens, prefers StartVersion when both present, and falls back to last-write Version for older tokens. It does not compare ActivityInfo.Stamp. Thus task stamp and worker result token have distinct roles. The terminal builders also require matching StartedEventId (`mutable_state_impl.go:4603,4652,4701-4712,4907-4914`). All four terminal apply functions delete the pending Activity (`4630-4636,4680-4686,4732-4738,4944-4950`), preventing another ordinary result from modifying the same pending Activity afterwards. Queue tasks can remain in storage until independently acknowledged and become stale against that deletion.

**Retry and deadlines.** `RetryActivity:6880-6975` checks mutability, policy presence, CancelRequested, server schedule timeouts, nonretryable failure, and pause/rules, before ordinary backoff calculation. Start-to-close/heartbeat timeout may retry; schedule-to-start and schedule-to-close return timeout retry disposition. No new attempt is installed if max attempts/expiry/backoff calculation says terminal. NextRetryDelay, if supplied by application failure, replaces the maximum interval as well as the backoff algorithm (`6942-6958`). Ordinary success installs attempt+1, current version, next ScheduledTime, cleared started state, last failure and per-attempt timer recreation bits, then generates retry work (`6964-6975`, `activity.go:59-89`). ScheduleToClose's creation bit is deliberately retained across retries. The parent timer analysis supplies exact deadline selection and timer duplication applicability.

Terminal timer processing can change the final timeout type to ScheduleToClose when policy leaves insufficient time for another retry (`timer_queue_active_task_executor.go:315-323`), whereas worker failure remains ActivityTaskFailed (`respondactivitytaskfailed/api.go:112-119`). `AddActivityTaskTimedOutEvent:4714` chains the last retry failure as Cause. A model must allow those distinct terminal reasons; they need not agree at the text/enum level to represent compatible outcomes.

**Cancellation is a request with multiple valid terminal resolutions.** `AddActivityTaskCancelRequestedEvent:4751-4779` accepts a cancel reference to a still pending Activity or an already buffered finish; duplicate pending request is rejected. Apply sets CancelRequested and CancelRequestId (`4881-4891`). Request-cancel handler immediately adds Canceled if StartedEventId is empty, which includes retry backoff (`respondworkflowtaskcompleted/workflow_task_completed_handler.go:701-717`). For running work, completion has no CancelRequested rejection; completion may win. Cancellation acknowledgement needs CancelRequested (`mutable_state_impl.go:4916-4925`). Failure/timeout after a request do not retry because RetryActivity returns CANCEL_REQUESTED, but can resolve as Failed/TimedOut; cancellation request does not require every race to end in ActivityTaskCanceled.

Worker visibility is heartbeat response after its state update succeeds (`recordactivitytaskheartbeat/api.go:77-100`), plus an optional Nexus worker-control push. Push construction is at `workflow_task_completed_handler.go:718-778`, close-time generation at `mutable_state_impl.go:4790-4862`, and actual task creation is gated by `task_generator.go:585-599`; default `system.enableCancelActivityWorkerCommand=false` (`common/dynamicconfig/constants.go:208-211`). For a calibrated ordinary baseline set this feature explicitly and record whether the worker supplies WorkerControlTaskQueue. The pushed token is an observation/request message, not an atomic proof worker side effects stopped.

## Current mechanism to model: terminal buffering and workflow progress across recovery

**Forward question:** Can a successfully persisted and acknowledged ordinary Activity result, committed while a Workflow Task is already started, lose its eventual workflow-observation obligation after response loss/cache reload/conditional-write retry, or can a duplicate result/late cancel cause the workflow to observe incompatible terminal results?

This is a current implementation composition, not a pre-fix replay. Use these code-backed boundaries:

1. Result handler validates current ActivityInfo, constructs a terminal event, deletes pending ActivityInfo, and requests CreateWorkflowTask. The shared update path only creates a new WFT if none is pending (`api/update_workflow_util.go:80-89`). Existing started WFT therefore carries the obligation indirectly through durable buffering.
2. EventStore buffers non-command Activity starts/finishes (`historybuilder/event_store.go:319-358`), and Finish keeps them buffered while a WFT remains started (`mutable_state_impl.go:8573`). Activity deletion, buffered terminal and task metadata must commit according to the backend's execution mutation contract.
3. On WFT completion, a snapshot of `HasBufferedEvents` is taken (`respondworkflowtaskcompleted/api.go:376-384`); pending buffered results or immediate not-started cancellation cause another normal WFT if the Workflow remains running (`557-566`). Close commands check the buffered-event barrier (`workflow_task_completed_handler.go:804-805,859-860,955-956`). Existing WFT timeout/failure also flushes/renews work; the helper `workflow/util.go:49,53-69` flushes after failure and schedules only when no WFT is pending.
4. At persistence close, WFT handling precedes event preparation (`mutable_state_impl.go:7786-7810`), event IDs are assigned and Started/terminal references wired, and task generation finishes before returning the mutation. Cache reload reconstructs pending ActivityInfo and buffers, but the heartbeat dedup watermark changes conservatively.
5. EventStore intentionally discards newly buffered cancellation results if the same command-processing transaction closes the Workflow (`event_store.go:168-175`). Do not conflate this command-generated case with a prior worker terminal acknowledged in an earlier transaction. A universal “every deleted Activity must eventually have a visible terminal History event even after workflow close” invariant would overstate the contract.

**Useful safety predicate:** For each pending ordinary Activity identity, an accepted worker terminal has at most one committed resolution; no later ordinary result changes a new attempt or new ScheduledEventId. If the Workflow stays open, a committed terminal outcome is either in durable History already or in the durable event buffer with an outstanding WFT that can flush/deliver it. State the actual storage condition and recoverability assumptions.

**Useful progress predicate:** Given time advancement, healthy history ownership/storage, eligible nonpaused work, and eventual worker/queue service, retry work eventually reaches accepted start or a policy deadline; committed Activity terminal information eventually reaches a Workflow Task (which may complete, fail, or timeout before the next WFT sees it). Do not require prompt processing by physical deadline or one fresh WFT for every terminal.

**Complete trace scenario for handoff:** Start an Activity while a WFT is held in flight; commit Activity completion or final failure; capture ActivityInfo deletion, durable buffered terminal, execution condition/version and actual generated task record(s); drop only the RPC response; release/lose cache and independently reload; resend the old result and issue a legal competing cancel command; then resolve/timeout the held WFT and execute the follow-up WFT to observe exactly the permitted terminal. Include a definitely aborted write control and a deliberately inconsistent attempt/durable-readback control. A prefix ending at server callback return is incomplete; no successor state may be synthesized from the model.
