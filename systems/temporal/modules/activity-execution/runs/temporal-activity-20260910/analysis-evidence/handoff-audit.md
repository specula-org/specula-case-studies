## Corrections/clarifications required in the synthesized handoff

1. **The field named DatabaseMutableState can still be a cache observation.** `service/history/api/describemutablestate/api.go:49-65` copies cache first, clears it only when `!req.GetSkipForceReload()`, then calls `LoadMutableState`; `service/history/workflow/context.go:416-446` reads persistence only when the cache is nil. A durable readback must explicitly use `SkipForceReload=false`, preserve the cache-clear/reload as an observed action, and record the returned durable version. Merely selecting `DatabaseMutableState` is insufficient. The request holds the workflow lease (`describemutablestate/api.go:33-47`), which prevents ordinary local handler interleavings, but uncertain old-owner writes still require completed ownership fencing. `LoadMutableState` can perform a write when StartTransaction requests flushing (`context.go:474-495`), so this endpoint is not universally a passive database snapshot.

2. **Terminal result does not imply one newly generated WFT transfer task.** `service/history/api/update_workflow_util.go:80-89` schedules only when no WFT is pending. Pending includes started (`workflow/workflow_task_state_machine.go:1194-1209`). Activity terminal events are buffered (`historybuilder/event_store.go:97-99,297-358`); `mutable_state_impl.go:8573-8582` keeps the buffer durable while a WFT is started. On its completion, `respondworkflowtaskcompleted/api.go:384,557-567` requests the follow-up. With ReturnNewWorkflowTask, transfer generation may be bypassed and the WFT is started inline (`:577-645`), leaving its durable started state/timer as responsibility. A valid obligation predicate must distinguish scheduled, started with buffered terminal, inline follow-up, and workflow observation. It must not require terminal => fresh transfer row or visible History event immediately.

3. **The fault recorder omission is concrete in normal test wiring.** `tests/testcore/onebox.go:172-187` wraps the production factory with HistoryTaskRecorder; the recorder is outside the production ExecutionManager (`history_task_recorder.go:57-64`). Fault injection wraps the lower DataStoreFactory (`common/persistence/client/fx.go:210-212`), before the ExecutionManager and retry wrapper (`client/factory.go:197-218`). Thus an injected ExecuteAndTimeout at ExecutionStore.UpdateWorkflowExecution can commit inside SQL and return Timeout past the recorder, which records only nil errors (`history_task_recorder.go:83-113`; `faultinjection/execution_store_gen.go:250-256`; `faultinjection/fault.go:42-47,61-71`). Timeout is not retried by the persistence retry classifier (`client/factory.go:270-277`). A missing recorder row is not a missing durable transaction. Capture an immutable lower-layer outcome or independently fence/read back execution and task-store state.

4. **Worker-control cancellation uses Nexus transport.** An initial audit terminology objection was incorrect and was retracted after the parent supplied the dispatcher anchor and this reviewer read `common/workercommands/dispatcher.go` completely. WorkerCommands tasks are sent through `DispatchNexusTask` with a Nexus StartOperation request and `TASK_QUEUE_KIND_WORKER_COMMANDS` (`dispatcher.go:27-35,102-139`). SDK Core handles these commands directly rather than language-SDK Nexus handlers (`:105-109`). Therefore the original deep report's “Nexus worker-control push” is source-supported; concise “worker-control cancellation push” in the brief is also accurate. No change to the deep report was warranted.

## Material claims independently confirmed

- SQL History append precedes the execution transaction (`common/persistence/sql/execution.go:334-357`). Execution row, generated tasks, ActivityInfo updates/deletions, and buffered events share the same transaction (`sql/execution_util.go:23-190`); callback failure rolls back and Commit errors become Unavailable (`sql/common.go:52-80`). Treat the durable transaction atomically, while separating its returned observation and prior raw History append.
- Execution reads query the execution row then ActivityInfo/maps/buffer via the DB independently (`sql/execution.go:210-331`). Take readbacks quiescent under a valid owner/lease or bracket with unchanged record versions; do not join racing reads into a fictional atomic snapshot.
- Generated-task notification occurs when the surfaced persistence result is possibly successful, before returning a nonnil error; History notification is after nil success (`workflow/transaction_impl.go:184-214`). These are wakeups, not evidence of committed task rows. Internal persistence retry exists (`client/factory.go:217`), so both the observer and fault plan should identify the layer/error on which classification is based.
- Shard write-error handling fences uncertain writes by reacquiring ownership; known condition failures are separately classified (`shard/context_impl.go:1501-1549`). Detached contexts can outlive caller cancellation (`:2408-2432`). A client timeout does not establish rollback.
- Shared result-token guard checks ordinary Attempt and started state and StartVersion/legacy Version; it does not compare Stamp (`api/activity_util.go:58-79`). Stamp is a queue/start contract. Start same-RequestId idempotency precedes stamp validation (`recordactivitytaskstarted/api.go:150-184`); it has no ScheduledTime acceptance gate. Do not invent one in the model.
- Retry clears only per-attempt timer bits (`workflow/activity.go:71-73`), and the enableActivityRetryStampIncrement gate controls stamp changes (`:87-89`). Timer executor’s current-deadline recalculation must remain distinct from worker token guard semantics; `deep-timers.md` correctly contains already-known stale-delivery/default-gate concerns as reference/configuration contracts, not a new MC hunt.
