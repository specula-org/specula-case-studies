## Fundamental representation and atomicity

An `ActivityTimeoutTask` is a durable wake-up cue, **not an instruction to timeout its recorded attempt unconditionally**. `executeActivityTimeoutTask` obtains Workflow context/lease, reloads if needed, rejects closed/missing Workflow, reconstructs and sorts all current Activities' applicable deadlines, then processes every expired entry (`timer_queue_active_task_executor.go:204-280`). The task's original EventID matters to heartbeat dedup reset; all current pending Activities may otherwise be affected. Timeouts in a batch share one Workflow mutation/persistence update, not one DB transaction per timer.

`CreateNextActivityTimer` sorts all deadlines and creates only the globally earliest candidate when its created bit is unset (`timer_sequence.go:118-164`). It does **not** create one physical task per timer/Activity. If the earliest deadline is already covered by a pending cue, later deadlines wait: processing that cue and closing the transaction regenerates the next required cue. If the earliest deadline is after Workflow run expiration, timer creation is intentionally skipped because Workflow expiration is the covering obligation (`:127-132`).

Generated task and ActivityInfo created-mask update occur together in the mutable-state change (`timer_sequence.go:143-163`); retry task generation is an in-memory AddTasks call (`task_generator.go:572-583`). Closing an active running Workflow transaction regenerates its next Activity/user timers (`mutable_state_impl.go:9055-9071`). `updateWorkflowExecution` schedules needed Workflow Task first and invokes `UpdateWorkflowExecutionAsActive` (`timer_queue_active_task_executor.go:1015-1029`). Persistence commit atomicity must be taken from parent backend audit; `AddTasks` alone is not evidence of durable work.

## Exact timeout semantics

| Timeout | Applicability and deadline | Retry/terminal contract |
|---|---|---|
| ScheduleToStart | ScheduledEventId exists, StartedEventId empty, duration nonzero; `ScheduledTime + ScheduleToStartTimeout` (`timer_sequence.go:295-322`). During backoff ScheduledTime is **future next eligible schedule time**, so this does not consume the backoff interval itself. | Server-enforced terminal deadline. With retry policy, RetryState TIMEOUT; cancellation/no-policy checks occur first (`mutable_state_impl.go:6888-6914`). |
| StartToClose | Scheduled and started; nonzero duration; `StartedTime + StartToCloseTimeout` (`timer_sequence.go:369-396`). Transient StartedEventId sentinel counts as started. | Retry if policy, attempts and expiration allow; type can be converted to ScheduleToClose if next retry cannot fit. |
| ScheduleToClose | Scheduled regardless of started state; nonzero duration; `FirstScheduledTime + duration`, with old-record fallback to ScheduledTime (`timer_sequence.go:331-360`). | Global Activity deadline spans all attempts/backoff. RetryActivity classifies it TIMEOUT, subject to prior no-policy/cancel branches. |
| Heartbeat | Scheduled and started; nonzero duration; `max(StartedTime, LastHeartbeatUpdateTime) + HeartbeatTimeout` (`timer_sequence.go:405-443`). | Retry policy applies to Heartbeat, including reserved `TemporalTimeout:Heartbeat` exclusion; latest details travel in terminal timeout (`timer_queue_active_task_executor.go:359`). |

All paused Activities are omitted from LoadAndSortActivityTimers (`timer_sequence.go:187-191`), including their global deadline. This is a separate administrative contract; a paused Activity cannot be assigned ordinary timeout progress obligations. Workflow-wide pause is another distinct feature and remains outside the calibrated core.

`IsTimeExpired` compares at **millisecond precision**, with reference `max(executorNow, task.FireTime)` to handle clock skew (`queues/queue_scheduled.go:280-301`). A model cannot require nanosecond-precise timeout firing, nor assume timers execute immediately at deadlines. The initial core should use monotonic logical time in millisecond units, no time-skipping feature, and arbitrary finite queue delay. Production clock skew/time skipping are separate coverage extensions with explicit transformations; they must not silently enter a simple logical-time model.

Sorting is by deadline, EventID, numeric TimeoutType (`timer_sequence.go:477-510`). Preserve deterministic tie order; enumerate actual enum values from pinned API if exact equal-deadline outcomes are modeled. The final equality branch returns true (non-strict comparator); ordinary construction yields at most one entry per Activity/type and unique map keys, so no demonstrated lifecycle consequence. Keep this local comparator defect candidate for code-review-only audit; do not create artificial duplicate logical timers just to trigger it.

## Retry policy and state transition

`RetryActivity` first checks running mutability, HasRetryPolicy, CancelRequested, schedule-deadline type, then generic retryability (`mutable_state_impl.go:6880-6915`). Effective policy comes from normalized ActivityInfo, not raw SDK input. Nonretryable application/server failures, canceled/terminated failures and timeout-type exclusions are established in `common/retrypolicy/retry_policy.go:24-63`.

For ordinary nonpaused work, backoff is computed against server time, current attempt, maximum attempts, initial/max interval and absolute RetryExpirationTime (`mutable_state_impl.go:6942-6975`). Application `NextRetryDelay` overrides policy maximum interval here. `nextBackoffInterval` rejects currentAttempt >= positive maximum; caps interval; rejects next start **strictly after** expiration (`retry.go:69-111`). It does not require that the next attempt's whole StartToClose interval fit. A scheduled next start equal to expiration remains representable; eventual timers/start ordering determines observation.

Successful retry updates Attempt to prior+1, version, future ScheduledTime; clears StartedEventId/StartVersion/RequestId/StartedTime/StartedClock; retains heartbeat progress unless reset flags request clearing; retains last failure and last worker identity (`activity.go:48-90`, `mutable_state_impl.go:7002-7018`). It then generates ActivityRetryTimerTask with scheduled time, event ID, attempt, stamp and version (`task_generator.go:572-582`). No terminal History event or Workflow Task is owed merely for a retryable failed attempt.

On terminal timer outcome, `AddActivityTaskTimedOutEvent` removes Activity and records History/buffer state; the executor sets Workflow Task obligation (`timer_queue_active_task_executor.go:359-379`). On retry outcome it sets only mutable-state update (`:352-356`). Outcome vocabulary must distinguish event kind, RetryState, timeout type, heartbeat details, original failure cause. For historical compatibility, timer-driven inability to fit the next retry becomes ScheduleToClose timeout, but a failed RPC still resolves as failed (`:315-324`). This is an intentional selected-path contract, not automatically an incompatible terminal result.

## Attempt and stamp checks at handoff

Default `system.enableActivityRetryStampIncrement` is **false** (`common/dynamicconfig/constants.go:239-242`). With true, ordinary retry increments stamp only when Attempt actually increases (`activity.go:87-89`); all settings must be recorded, and the parent must distinguish default configuration from specific test overrides.

`executeActivityRetryTimerTask` checks: Activity exists; task.Stamp==ActivityInfo.Stamp; not paused; task.Attempt is not older than current; not started; version check (effective only for global namespaces); Workflow running (`timer_queue_active_task_executor.go:553-597`). It processes rules and rechecks paused/stamp after rule update (`:599-608`). Under lease it captures queue, timeout, version directive, build-ID mode and priority, then releases before Matching RPC (`:611-636`). Matching request carries event ID, stamp and shard clock, **not Attempt**. Independent build-ID update afterwards reacquires state; excluded routing policy must not be conflated with start acceptance.

History's start path rechecks Activity existence, currently started RequestId idempotency, rules and stamp (`recordactivitytaskstarted/api.go:118-184`), and durably accepts the start via mutable-state update before responding (`:50-101`). It does not check `now >= ScheduledTime`. Thus sender validation and receiver validation are distinct actions. A duplicate/lease-raced old task can be a question about backoff eligibility when the gate is false; the same-stamp old-delivery behavior may be exactly the known fix behind the gate. **Historical containment resolved by sibling issues_identity:** full #8607/#8536 discussion/diff evidence confirms the default-false gate is deliberate during all-cluster rollout, and preventing invalid backlog with stamp checks is the documented mechanism. Thus old-delivery/early-backoff with this gate disabled is reference/configuration contract and code-review/test-only, **not a new MC hunt** unless a distinct mechanism is independently established. Parent has the full PR evidence under `prs/`. Faithful baseline must still expose configured behavior and cannot add a fictional receiver Attempt/ScheduledTime guard.

## Duplicate timers, heartbeat, and reload

The timeout executor intentionally has **no Activity stamp check** (`timer_queue_active_task_executor.go:304-305`). This applies to all timeout types; ScheduleToClose is not singled out by a stamp exception here. It re-derives current deadlines first. Snapshot sequence entries contain current Attempt; if processing one timeout advances that Activity's attempt, subsequent entries from the same precomputed snapshot are skipped (`:299-302`). If a terminal timeout removes Activity, later entries are skipped by map lookup (`:258-262`). These are the compensating mechanisms for duplicate/delayed timeout task execution.

The specific ScheduleToClose exception is in **timer mask preservation**: `TimerTaskStatusCreatedPerAttempt` excludes its bit (`timer_sequence.go:34-41`); retry clears only per-attempt bits (`activity.go:72-73`). Its original physical cue remains valid across attempts and stamp increments because the whole-Activity deadline is unchanged. A model that drops old-stamp ScheduleToClose tasks will manufacture a lost-timer bug.

Heartbeat updates retain the existing physical heartbeat task; new heartbeat time moves the logical deadline (`mutable_state_impl.go:2110-2127`). When an old heartbeat cue executes, the executor clears the heartbeat created bit only if its visibility time reaches the pending watermark, then checks actual current deadline and commits/recreates the next needed task (`timer_queue_active_task_executor.go:235-248`, `timer_sequence.go:147-150`). Duplicate cues with earlier visibility cannot keep clearing a newer watermark.

The pending heartbeat visibility map is **volatile**, not separately durable. On NewMutableStateFromDB, a persisted heartbeat created bit causes its map watermark to be reconstructed as **2000-01-01** (`mutable_state_impl.go:471-477`); the first pending heartbeat cue will therefore repair/regenerate its deadline as needed. The bit and ActivityInfo LastHeartbeatUpdateTime are persisted; exact old in-memory watermark is not. Cache reload may legitimately produce extra timer task creation. Do not compare this volatile watermark for equality before/after recovery or infer a missing durable task from that reset.

## Verified suspicious code and compensations

**CR-T1: discarded RetryActivity error** (`timer_queue_active_task_executor.go:310-312`) is a real error-propagation gap: returns `(result,nil)` instead of error. Caller can turn no update into `errNoTimerFired` (NotFound) (`:276-279`, `timer_queue_task_executor_base.go:35`), and task framework classifies NotFound invalid/droppable (`queues/executable.go:451-473`).

**Reachability audit:** On ordinary consistent state, the same lease already established Workflow running and Activity map presence; RetryActivity's checkMutability cannot newly fail, UpdateActivity finds that same Activity, its ordinary retry callback returns nil, and the concrete GenerateActivityRetryTasks unconditionally returns nil (`mutable_state_impl.go:6885-6887,7008-7018,7031-7070`, `task_generator.go:572-583`). Persistence errors occur later and are propagated from updateWorkflowExecution. Therefore this source reading did **not establish a permitted storage fault or normal lifecycle input that makes RetryActivity return error**. Keep CR-T1 in code-review-only findings with this limit, not an MC fault action that invents failure inside AddTasks.

**Dirty-cache caveat:** release(nil) tests `MutableState.IsDirty`, clears and panics on dirty transactions (`cache/cache.go:391-405`); queue Execute captures panic into error (`queues/executable.go:343-351`). However IsDirty checks HistoryBuilder, InsertTasks, HSM, CHASM, **not every updateActivityInfos map mutation** (`mutable_state_impl.go:7531-7538`). It is not a blanket theorem that arbitrary partial ActivityInfo mutations will be detected. A later audit that finds an actual reachable error after an ActivityInfo-only mutation must re-evaluate this compensation specifically. No such trigger was confirmed here.

**CR-T2: non-strict comparator equality** at `timer_sequence.go:508-509`. No demonstrated product consequence for ordinary unique generated deadline entries. Appropriate local review/test rather than protocol modeling.

## Modeling and trace handoff

Calibrate complete healthy lifecycle first; then compose timer processing, heartbeat/failure/completion arrival, retry dispatch, cancellation, and **real persistence outcome**. Candidate forward questions are timer-obligation conservation after successful commit and recovery, terminal-observation compatibility with concurrent completion/cancel, and whether ready work eventually resumes the Workflow under explicit healthy-environment assumptions. These are current implementation boundaries, not pre-fix replay targets.

Recommended trace observations under one unambiguous sequence/transaction ID:

1. Before each mutation under Workflow lease: Workflow key, Activity map fields, timer mask, volatile heartbeat watermark tagged as volatile, buffered/history event IDs, pending WFT and execution DB version/condition.
2. Timer cue identity (TaskID, FireTime, EventID, Attempt, Stamp, TimeoutType); executor reference time; sorted logical deadline entries; selected branch/rejection reason. A cue may resolve multiple Activities atomically.
3. The exact transaction submitted: Activity update/delete map, generated retry/timeout/WFT tasks, History/buffer batch, ownership/CAS condition; storage outcome independently read back. A wrapper that records only nil-returning persistence calls misses executed-write/timeout commits and is insufficient.
4. Lease release and Matching add request/return, then independently observed History accepted start commit and worker token/response. Queue delivery is not accepted start. Only external acknowledgments count as acknowledged outcome.
5. Reload readback and independent task-store readback. Distinguish cache clear/reload, shard acquisition, process restart, database restart; do not rename one as another.
6. End condition: final Activity event/absence plus committed pending WFT or later Workflow completion, and no unaccounted eligible retry/timeout debt. Passing prefixes are INCOMPLETE. Negative controls must reject wrong current-attempt identity and inconsistent durable state, without filling observations from model successors.
