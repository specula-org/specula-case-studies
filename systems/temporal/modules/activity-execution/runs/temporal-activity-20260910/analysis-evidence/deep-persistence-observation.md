## Atomicity and recovery

- Workflow mutual exclusion is a priority semaphore of capacity one (`context.go:143,156-164`). Cache clearing discards Mutable State, query/update registries and speculative WFT timer state (`174-186`); it does not undo a database commit.
- Reload uses `GetWorkflowExecution`, its `DBRecordVersion`, and `NewMutableStateFromDB`; it is not History replay (`context.go:408-497`). A baseline should model cached and durable ActivityInfo separately, but each handler's in-lock mutations remain private until its persistence decision.
- Update builds a mutation and History batches (`context.go:973-1001`) and executes the transaction (`1044-1057`). An error clears cached Mutable State (`888-909`). Resource-limit enforcement can deliberately replace an update with workflow termination and return an error after committing that termination (`695-751,1566-1605`); keep payload/aggregate limits below thresholds in the calibrated Activity model.
- Shard update acquires the I/O semaphore, snapshots ownership, allocates/tracks generated task keys, sets `RangeID`, invokes persistence, resolves task-key tracking, then classifies write error (`shard/context_impl.go:597-656`). Its detached context can outlive caller cancellation and uses a minimum timeout (`2414-2435`). Caller timeout therefore does not prove no commit.
- SQL first appends History nodes (`sql/execution.go:334-348`), then starts the shard-locked Mutable State transaction (`350-357`). The transaction checks current-run identity (`392-434`), locks/checks the concrete execution record (`execution_util.go:44-60,629-695`), updates execution row, inserts generated tasks, updates/deletes ActivityInfo and other maps, and persists buffered events (`23-190`). Do not split those SQL statements into independently committed model actions.
- `DBRecordVersion > 0` compares stored version with proposed version minus one; legacy zero uses `NextEventID` (`execution_util.go:645-661`). `readLockShard` compares the transaction's RangeID (`sql/shard.go:152-176`). These are independent ownership and workflow-revision fences.
- `SqlStore.txExecute` rolls back on callback error and commits otherwise; a commit error becomes `Unavailable` (`sql/common.go:52-83`). Such an error is an uncertain outcome, not an assertion that all writes rolled back. Fault wrappers must preserve that distinction.
- Shard write classification: condition/size/resource/not-found errors classify the concrete backend attempt as uncommitted; a surfaced error after internal retry does not establish that earlier attempts of the logical request were uncommitted; ownership loss stops the shard; otherwise uncertain outcomes trigger shard reacquisition to fence late writes before readback (`shard/context_impl.go:1501-1549`). `AppendHistoryTimeoutError` concerns only the prior History stage. `OperationPossiblySucceeded` uses the same distinction (`common/persistence/error_type.go:5-22`).
- Generated task notification occurs for possibly successful updates, even when the returned error is non-nil; History notification occurs only on nil error (`transaction_impl.go:184-214`). Notifications are wakeups, not durable task insertion. Recovery must continue from database task rows even if the notifier or response is lost.
- Best-effort deletion of obsolete History tasks occurs after successful execution persistence and can fail independently (`execution_manager.go:247-309`). Thus duplicate timer tasks must remain legal inputs to the model, not be erased atomically with Activity completion.
- Raw History append is not logical commit evidence. Public History initializes its upper boundary from Mutable State (`api/getworkflowexecutionhistory/api.go:274-289`); persistence selects node/transaction versions and filters nodes (`history_manager.go:728-811`). Condition failure invokes History trimming (`execution_manager.go:263-274`). Do not treat garbage History batches as acknowledged Activity outcomes.

## Observation pitfalls and required harness changes

1. `HistoryTaskRecorder.UpdateWorkflowExecution` records only when its delegate returns nil (`tests/testcore/history_task_recorder.go:83-113`). An inner `ExecuteAndTimeout` wrapper can commit and make this recorder omit a real durable write. Inspect wrapper ordering; record the storage outcome below fault injection, or independently read back the task and execution state after fencing.
2. The recorder timestamps after its delegate returns and flattens by category (`137-168`). Its getters copy slices but retain task pointers. It supplies neither a global commit order nor an immutable cross-category transaction snapshot. Clone transaction payloads under the workflow lock and use transaction/request IDs plus a monotonically ordered observation sequence; correlate post-commit receipt with that immutable payload.
3. A multi-query SQL `GetWorkflowExecution` reads execution row then ActivityInfo and other tables (`sql/execution.go:210-330`). Independent administrative reads should be taken with the workflow quiesced/fenced, or bracketed by matching record versions. Do not manufacture an atomic snapshot from racing observations.
4. `DescribeMutableState` returns cache and database projections separately (`api/describemutablestate/api.go:52-65`); its database field is reconstructed Mutable State, not a direct immutable SQL transaction receipt. Explicitly set `SkipForceReload=false`; with true and a populated cache this field can also be a cache projection. Record the cache clear/reload and any StartTransaction flush/write as observed actions. Preserve the actual persistence payload and committed task evidence too.
5. Worker execution count and SDK heartbeat calls are not History commit observations. The ordinary timeout test explicitly documents SDK heartbeat batching (`tests/activity_test.go:188-211`). Capture worker-facing RPC receipt/response and History persistence separately.
6. `TestTryActivityCancellationFromWorkflow` stops at Activity acknowledgement (`909-1052`), and `TestActivityTaskCompleteRejectCompletion` stops after rejecting an old token during backoff (`1454-1482`). Their passing executions are not complete end-to-end formal-validation traces. Extend a later harness through a terminal durable readback and the Workflow Task that consumes the result.
