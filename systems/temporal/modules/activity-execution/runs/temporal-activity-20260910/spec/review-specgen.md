## Issues Found

- **[P1] Physical timer visibility is not the logical deadline; task allocation and the timer invariant omit this distinction.** `base.tla:147-155` creates a cue with `due = Deadline(...)`, and `SetAndTrackTaskKeys` at `base.tla:412-416` changes only IDs/range. The implementation's `service/history/shard/task_key_generator.go:55-96` also sets immediate-task visibility to allocation time, rounds scheduled visibility using `Add(1 ms).Truncate(1 ms)`, and clamps older scheduled times against the shard's minimum scheduled time. The precision is explicitly one millisecond (`common/constants.go:52`). For the existing healthy synthetic control, an STS deadline of 3 therefore becomes physical visibility 4 even without clamping; the model insists it remains 3. A focused probe fails at event 4, `SetAndTrackTaskKeys`. This also invalidates the intended interpretation of `DeadlineCovered` (`base.tla:634-636`): its `t.due <= d.due` rejects an ordinarily generated covering task once the real visibility is represented. Distinguish logical obligation time from physical visibility, model allocation/rounding/clamping, revise coverage accordingly, and revisit MC time horizons. The instrumentation must capture both meanings instead of treating a persisted timestamp as the unadjusted deadline.

- **[P1] Buffered events are flushed in the wrong order, including a cancellation ordering error.** `CompleteWFT` appends `w.buffer` unchanged (`base.tla:330-332`); rejected-close recovery also concatenates it unchanged (`base.tla:385-388`). Actual `FlushBufferToCurrentBatch` calls `reorderBuffer` (`service/history/historybuilder/event_store.go:178-197`), which stably moves Activity terminal events after nonterminal buffered events (`:461-490`). A buffer `<<Started(2), Completed(2), Started(1), Completed(1)>>` becomes `<<Started(2), Started(1), Completed(2), Completed(1)>>`. The supplied SharedTimers control retains the first order; substituting the source-required order fails replay at event 122. Additionally, `HandleCommandCancelBufferedActivity` flushes before appending `CancelRequested` (`base.tla:349-354`). Source cancellation appends that command event while the terminal is still buffered (`service/history/workflow/mutable_state_impl.go:4751-4779`); command events are unbuffered (`service/history/historybuilder/event_store.go:319-336`), and subsequent WFT scheduling flushes the buffer (`service/history/workflow/workflow_task_state_machine.go:326-333`). Thus the cancellation event precedes that terminal in committed History. Correct the flush helper and command/flush order consistently. Preserving event sequences in `Trace.tla` is appropriate; weakening comparison to sets would hide this defect.

- **[P1] Notification is enabled only after the source call has already occurred.** `FinishUpdateWorkflowExecution` both releases the modeled lease and inserts the transaction into `notifyPending` (`base.tla:472-485`); only then can `NotifyOnExecutionMutation` execute (`:517-519`). The mapped implementation invokes `NotifyOnExecutionMutation` synchronously immediately after the persistence call and before returning success/error (`service/history/workflow/transaction_impl.go:184-206`); that helper invokes `engine.NotifyNewTasks` at `:608-616`. Consequently, the hook specified in `instrumentation-spec.md:152,158` observes notification before the update helper finishes and releases its Workflow lease. A probe placing it in that source order fails at event 8 because the transaction is absent from `notifyPending`. Model notification eligibility at persistence-result classification and its actual call before lease release. If downstream asynchronous processing is also modeled, give it a separate capture point. The MC view projects these ledgers away, so safety convergence cannot validate this ordering.

- **[P2] The full durable-task observation contract exceeds the modeled task vocabulary.** `instrumentation-spec.md:48,96,145` requires actual durable queue rows and every committed generated task category, but `base.tla:619-620` admits only Activity timeout kinds, Transfer, Retry and WFT transfer tasks. `RecordWorkflowTaskStarted` creates no timeout descriptor (`base.tla:324-328`). A real normal WFT start calls `GenerateStartWorkflowTaskTasks` (`service/history/workflow/workflow_task_state_machine.go:630-634`), which adds a durable `WorkflowTaskTimeoutTask` (`service/history/workflow/task_generator.go:519-547`). This also matters to the bootstrap, which already has a started normal WFT. A recorder cannot both preserve all such task observations and satisfy exact state equality. Define an explicit projection of included task types, bootstrap rows and category/range deletions, with excluded raw rows retained in evidence; alternatively, extend the task model. Document the WFT-timeout boundary separately from the existing WFT-transport abstraction. Counting matching action names alone does not establish an implementable observation mapping.
