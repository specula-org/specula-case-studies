## R4 correction and source evidence

The mapping now saves the actual `has_unparked` Acquire load result and gives
the two branches different post-state and interval endpoints:

- The false branch captures `pc = "dequeue"`, `rqHeld = TRUE`, and
  `observedToken = FALSE` immediately after the load at
  `ostd/src/task/scheduler/mod.rs:455`, before `update_current` and
  `dequeue_current` at lines 469-470. The guard remains held across the
  check/dequeue window, where a concurrent wake swap can set the token.
- The true branch saves that same load result, follows the callback's
  `DoNothing` return at `ostd/src/task/scheduler/mod.rs:455-456`, and waits
  for `ClassScheduler::mut_local_rq_with` to release its guard at
  `kernel/core/src/sched/sched_class/mod.rs:255-259`. `reschedule` receives
  the callback result at `ostd/src/task/scheduler/mod.rs:577-579` and returns
  at lines 581-584. Capture `pc = "token"`, `rqHeld = FALSE`,
  `observedToken = TRUE`, and the interval end after that return to
  `park_current` at line 485, before the next swap at
  `ostd/src/sync/wait.rs:273`. Do not reread the atomic for this event.

The true branch's represented operation includes lock release. This follows
the existing projection without introducing a separate release action: the
source skips dequeue, leaves the current task runnable, and returns directly
to the token loop. Until that return, this waiter does not change the token,
and other wake swaps leave an observed true token set. The false branch
retains its separate check/dequeue boundary. `ParkCurrentResume` is explicitly
limited to the dequeued path, including when the scheduler later selects the
same task. A true check emits neither dequeue nor resume.

Only the instrumentation documentation changes the suite's contract wording.
No TLA+ logic changes. The actual load result and exact post-state comparisons
are preserved, with the same 41 action/event/dispatch/post-state/mapping
correspondence. No invariant, guard, expected outcome, bound, or fairness
condition is altered.

## Executed checks and limits

The true fixture contains a failed token-consumption swap, a child wake, a
true check, and direct return to token consumption. Its complete witness has
55 states for 54 events and final cursors `T1=35, T2=7, child=15`.

The false fixture observes false while holding the runqueue lock, permits the
wake swap before dequeue, then dequeues, completes the blocked unpark, and
resumes. Its complete witness has 57 states for 56 events and final cursors
`T1=37, T2=7, child=15`. Both fixtures complete both calls with returns 41
and -10, complete both notifier paths, clear signal registration, and release
the children and park runqueue locks. The witness audit checks this ordering
and final state. These are synthetic traces, not kernel executions.

The unchanged overlap and sequential inputs are again accepted with complete
28-state witnesses. The unchanged corrupted input is again rejected by
exhaustion after 19 distinct states with no states queued. The universal
overlap diagnostic again fails with
`Error: Temporal property TraceMatched was violated.` Its log and
counterexample remain available. As the r1 review already established, an
overlapping acquisition order can become stuck while another order completes.
The source's children mutex permits the accepted ordering
(`ostd/src/sync/mutex.rs:35-36,62-69` and
`kernel/core/src/process/wait.rs:293-319,344-374`). This is the retained R2
checker-quantifier limitation, not a candidate kernel behavior or a new R4
model error. The four existential witnesses intentionally violate only
`TraceNoCompleteMatch` after passing every other enabled invariant and the
complete final-state check. No other property or evaluation failure occurred.

All runs use the supplied Java and jars. Each TLC process uses `-Xmx3g`,
`-XX:MaxDirectMemorySize=1g`, two workers, and metadata under `states/`.
Processes run one at a time. Parse and trace runs each have a 60-second
limit. No MC run is affected or rerun because all modules and configurations
are byte-identical to r1. The driver now uses an explicit 1200-second MC
limit for future invocations. Historical r1 MC logs retain their original
600-second limits. Both historical liveness runs remain TIME-LIMITED.

Implementation trace collection, harness execution, Linux controls,
Asterinas runtime cases, WR-SQ, WR-CF, and independent acceptance of r2 remain
NOT RUN. The complete commands, logs, counts, and input hashes are recorded
in [generation-checks/results.md](generation-checks/results.md) and
[generation-checks/results.json](generation-checks/results.json).
