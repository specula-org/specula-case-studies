`RwMutex::upread` is not an ordinary shared reader: only one upgradeable reader exists, and writers require an empty lock. Ordinary readers, including exFAT backend callbacks, may coexist with an upreader. Upgrade is atomic. Evidence: `ostd/src/sync/rwmutex.rs:148-203,320-337`. The model must not translate the exFAT comment about parallel writes into parallel copy actions.

### Size and content vocabulary

- `L`: logical file length. This determines EOF at the filesystem layer.
- `C`: VMO/page-cache accessible bound, rounded to page size. It is neither logical EOF nor initialized/durable data.
- `A`: exFAT `size_allocated`, separate from `L` and actual cluster-count capacity (`exfat/inode.rs:104-110,286-312`).
- `N`, `O`, `S`, `K`: requested length, original offset, sampled logical size, and backend-computed return length.
- `D`: actual bytes copied, measured by cursor advance or an explicit copy trace. A zero byte overwriting a nonzero sentinel counts as delivery; comparing nonzero payload alone misses it.
- Page state distinguishes absent, uninitialized, initialized, and modified data. `Vmo::write_pages_with_backend` intentionally preserves an uninitialized page on a failed partial overwrite (`kernel/core/src/vm/page_cache/vmo/mod.rs:724-750`).

`PageCache::resize` clears a partial tail before publishing rounded capacity and removes wholly truncated pages (`kernel/core/src/vm/page_cache/mod.rs:246-282`). `Vmo::read` and `Vmo::write` clamp against `C` and can return success after zero transfer (`kernel/core/src/vm/page_cache/vmo/mod.rs:533-575`). A filesystem must either limit the copy and maintain matching bounds or derive its result from actual progress; the wrapper does neither automatically.

## Reference contract and oracle limits

The supplied reference is an implementation revision, not a separate published algorithm or TLA+ specification. Reference comparison uses the pinned implementation, Linux syscall documentation, Linux v6.12 source, and Asterinas's own regression expectations.

- A successful read returns the bytes read and advances the shared offset by that count; short reads are permitted. Linux documentation leaves position on error unspecified. This does not authorize a successful count different from delivery. [read(2)](https://man7.org/linux/man-pages/man2/read.2.html).
- `pread`/`pwrite` use their explicit offset and leave the open-description offset unchanged. [pread(2)](https://man7.org/linux/man-pages/man2/pread.2.html).
- Successful supported truncation sets the requested length, discards the removed range, and exposes zeros on extension; it leaves the file offset unchanged. Some filesystem extensions may be rejected, so test successful supported operations, not presumed universal feature support. [truncate(2)](https://man7.org/linux/man-pages/man2/truncate.2.html).
- A successful write may be short; later reads observe data actually written. Its result does not establish crash durability. [write(2)](https://man7.org/linux/man-pages/man2/write.2.html).
- Linux buffered reads recheck EOF after obtaining pages, add actual copy progress to their result/position, and return accumulated progress in preference to a later copy error. They do not promise an immutable whole-call snapshot. [Linux v6.12 `filemap_read`](https://github.com/torvalds/linux/blob/v6.12/mm/filemap.c#L2610-L2716).
- Linux shmem reads recheck size during traversal and accumulate actual copied bytes. Its write completion updates length from accepted bytes. [Linux v6.12 shmem](https://github.com/torvalds/linux/blob/v6.12/mm/shmem.c).
- Linux buffered write completion may reject a partially copied chunk; generic code reconciles iterator progress with the backend's accepted count. Thus `copied == committed` is not a universal failed-write invariant. [Linux v6.12 `generic_perform_write`](https://github.com/torvalds/linux/blob/v6.12/mm/filemap.c#L4015-L4102).

The target test `test/initramfs/src/regression/fs/ext2/short_rw.c:16-53` deliberately expects `EFAULT`, unchanged position, and original contents after a partial overwrite of an uninitialized cache page (assertions at lines 40-46). Its setup uses direct I/O to create a cold page, which is excluded from this task's operational scenarios. Read its expectation as evidence about uncommitted page state, not permission to require every failed write to roll back every earlier initialized-page modification. The already-fixed uninitialized-page defect is reference only.

Do not use EOF at return as the oracle for overlapping reads. Do not require a short read to fill the entire available file range. Use successful `result == D <= N`, untouched output suffix, controlled positions, and settled histories with no remaining competing mutation. An initial sentinel must differ from both payload and zeros. For reads that overlap mutations, match content to permitted progress/ordering rather than one chosen whole-call snapshot.

## Phase 3: verified code paths and pending outcomes

### S1: logical EOF is sampled separately from the transfer

**Current concurrency question, ramfs.** Start with one page of data, `L=C=P`, request `N=P` at offset zero. A read samples `S=P`, computes `K=P`, and pauses before the cache lock (`ramfs/fs.rs:703-709`). `ftruncate(0)` completes with `L=C=0` (`:796-814`). The read acquires the cache lock; `Vmo::read` sees `C=0` and returns `Ok(())` without touching the destination (`vmo/mod.rs:533-537`). Ramfs returns `K=P` (`ramfs/fs.rs:710-718`). No error, alignment ambiguity, partial page, or allocation failure is needed. `read` also advances the shared offset by `P`; `pread64` leaves it unchanged but returns the same mismatched count (`inode_handle.rs:286-289,323-331`). This makes the concern already raised in PR3778's review precise; it is a source-derived schedule pending execution/model confirmation.

**Extension direction.** A ramfs read can sample old EOF and then copy after an extending write. The lower layer sees a larger capacity and the unlimited writer; the saved count does not track the new delivery. If the original offset was beyond the sampled EOF, ramfs additionally substitutes that old EOF as the copy offset (`ramfs/fs.rs:704-709`). Model original and clamped offsets separately. A stale old EOF alone is permitted; extra delivery or a wrong successful data/offset relationship is the potential defect.

**Known sequential behavior.** Ramfs and exFAT compute a logical length but pass an unlimited writer to the cache (`ramfs/fs.rs:703-710`; `exfat/inode.rs:648-657`). With `L=2`, `C=P`, `O=1`, `N=64`, the result can be one while 64 bytes are stored. This is already documented by open [PR #3778](https://github.com/asterinas/asterinas/pull/3778), whose complete body, issue comments, reviews, inline discussions, and diff were read. Its reviewer separately flags the ramfs size/cache locking gap. Keep the known sequential case as test-verifiable reference; model the still-unresolved overlapping histories without pretending they are a new discovery of the known case.

Ext2 limits the writer while holding its inode guard (`ext2/inode/file.rs:31,234-242`). ExFAT holds its upreader across the read. Neither admits the ramfs snapshot/lock-gap schedule in a consistent starting state. They still require independent evaluation of their own size and error paths.

### S2: preparation and final publication use different critical sections

**ExFAT two extenders.** Let `P` be a page and start `L=A=C=P`. Writer B requests one page at `2P`, prepares `A=C=3P`, saves candidate length `3P`, then releases its exclusive guard. Writer A requests one page at `P`, still samples `L=P`, and calls `PageCache::resize(2P,P)`, reducing the actual cache bound to `2P` despite taking its extension branch. A copies one page and publishes `L=2P`. B resumes under its upreader: `Vmo::write` at `2P` sees no capacity, copies zero, and returns success. B then publishes `L=3P` and returns one page. Settled state has `L=3P`, `C=2P`, `A=3P`. Sources: `exfat/inode.rs:711-755`; `page_cache/mod.rs:250-278`; `vmo/mod.rs:568-575`.

All copy sections remain serialized. The transition between prepare and reacquire is essential; a model that atomically downgrades the first guard would silently fix the implementation. Include the opposite publication order to investigate a smaller saved length overwriting a newer longer length. The oracle is not `L` monotonic under arbitrary truncate: apply monotonicity only to completed extending writes with no truncation.

**ExFAT writer/shrink.** A writer can prepare an extension, release its guard, and allow `ftruncate(0)` to finish. When it resumes, the cache may be empty while the saved candidate length survives. Follow both the returned write count and a subsequent read below published `L`. Use page-aligned bounds to avoid depending on the independent partial-tail resize defects. Sources: `exfat/inode.rs:715-744,1436-1462`; `vmo/mod.rs:568-575`.

The post-copy assignment `inner.size = new_size` does not recheck current `L` or `C` (`exfat/inode.rs:743`). `is_sync()` returns false (`:243-245`), and neither the syscall wrapper nor atime updates repairs these fields. Do not model a background repair without a source path.

### S3: resize confuses logical length with allocation or capacity

ExFAT's public `Inode::resize` calls the page-cache resize only for shrink and then delegates to `ExfatInodeInner::resize` (`exfat/inode.rs:1436-1462`). The latter updates `L` only when cluster count decreases, while always assigning `size_allocated` (`:286-312`). Consequently, successful extension does not publish the requested logical size or grow `C`; a shrink within the same cluster count can leave old `L` while reducing `C` or zeroing data. These are test-verifiable sequential candidates; the same faithful transitions must remain in the base model when exercising S2. A successful public truncation cannot be interpreted as mere preallocation because VFS forwards its result unchanged (`syscall/truncate.rs:25-30`; `vfs/path/mod.rs:756-760`).

Choose cluster-aware cases: a nonempty file smaller than one cluster shrunk within that cluster, a shrink crossing a page but staying within a multi-page cluster, a shrink that reduces cluster count, and extension from zero. Record cluster size separately from page size. Do not make `cluster_size == P` a universal backend assumption.

For hole/data initialization, exFAT's backend returns zeros for a page starting at or beyond current `L`, but reads disk after `L` passes it (`exfat/inode.rs:150-166`). A gapped extending write can leave untouched pages cold while publishing them as logical data. The backend audit checks allocation zeroing and a legal same-inode history before treating a stale-data outcome as confirmed. A freshly zeroed disk image alone cannot establish correctness.

### S4: copy failure, accepted state, and result must be distinguished

The user buffer may fail at a pre-established inaccessible boundary while mappings remain stable (`context.rs:87-117`; `ostd/src/mm/vm_space.rs:160-201`). OSTD records bytes actually copied even on failure; conversions into kernel errors discard the count (`ostd/src/mm/io/mod.rs:340-370`; `kernel/core/src/error.rs:209-219`). Broad partial-copy limitations are acknowledged by fully read [issue #711](https://github.com/asterinas/asterinas/issues/711); that known limitation alone is not a new model-checking target.

| Backend | State before copying | Effect of a copy failure to investigate |
|---|---|---|
| ramfs | Publishes full requested length before cache growth and copy (`ramfs/fs.rs:733-750`). | A failed extending write can leave the full requested size even after zero or partial copy; investigate subsequent readable zeros/data without assuming transactional rollback. |
| ext2 | Prepares cache/blocks, keeps old logical size until successful copy (`ext2/inode/file.rs:193-215,246-271`). | Attempts extension cache/block rollback on error; cleanup is best effort and writes within old initialized content may remain. Uninitialized partial pages have separate acceptance rules (`vmo/mod.rs:732-744`). |
| exFAT | Enlarges allocation/cache, saves candidate size, releases guard (`exfat/inode.rs:715-736`). | An error skips saved-size publication, but preparation and previously initialized-page modifications can survive; compose only with S2's real lock gap. |

Use a zero-progress failure and a page-aligned successfully completed prefix followed by a fault as separate tests. Track bytes copied, pages accepted as initialized/modified, final logical size, and returned status. A Linux/Asterinas difference already acknowledged by #711 stays a compatibility/test finding unless it demonstrates an additional size/content protocol failure.

**Separate zero-progress size question.** For ramfs, begin with `L=C=P` and attempt pwrite of `P` bytes at `P` from a pre-established wholly inaccessible canonical user range. Range construction succeeds, metadata and cache become `2P`, and the copy returns EFAULT after zero bytes; neither field is restored (`ramfs/fs.rs:731-750`; `ostd/src/mm/vm_space.rs:160-170`; `vmo/mod.rs:671-690`). A later valid one-byte pread at `P` returns a logical zero byte. This is an extent change after zero accepted input, independent of the general partial-count question. Linux ramfs's generic write path rejects this first source span before its modifying helper; its write completion bases size on accepted progress. [Linux ramfs operations](https://github.com/torvalds/linux/blob/v6.12/fs/ramfs/file-mmu.c#L41), [generic write](https://github.com/torvalds/linux/blob/v6.12/mm/filemap.c#L4038), [simple completion](https://github.com/torvalds/linux/blob/v6.12/fs/libfs.c#L960). Test verification remains pending.

**Empty operation.** Ramfs and exFAT lack ext2's empty-write early return. With valid arguments, `pwrite64(O>L,N=0)` can return zero while increasing logical size (`ramfs/fs.rs:734-750`; `exfat/inode.rs:711-744`; compare `ext2/inode/file.rs:44-47`). This is a size semantic edge, not arithmetic or resource exhaustion. Add an isolated size/content no-effect test; no independent model hunt is required.

### S5: offset consequences are attached to the same transfer

Use one open file description with a known starting offset and no concurrent seeks, then a competing `pwrite64` or `ftruncate`. For successful `read`, compare final offset with start plus returned count and start plus actual delivery. Both can be checked: the wrapper may satisfy the former while a backend count error breaks the latter (`inode_handle.rs:284-290`). For `pread64`, compare the original shared offset before/after, independently of its explicit read offset (`:323-331`). Do not infer a position defect from a negative return alone; report the target's unchanged-on-error behavior separately from Linux's unspecified general error position.

### Additional verified boundaries

- **Request limit:** for non-overflowing bounded requests, all three read-count formulas yield `0 <= K <= N`, and OSTD bounds each copy by the writer's remaining space (`ramfs/fs.rs:704-707`; `exfat/inode.rs:649-652`; `ext2/inode/file.rs:234-242`; `ostd/src/mm/io/mod.rs:339-355`). No greater-than-request result was established. The identified successful mismatches are count versus delivery, in both directions.
- **Measurement:** use writer cursor delta or explicit per-copy progress. Ext2's `writer.limit` changes the end without copying; subtracting final available capacity from the original request produces a false measurement (`ext2/inode/file.rs:239-241`; `ostd/src/mm/io/mod.rs:902-924`). VMO collects batches of at most 32 pages before copying; a later batch population failure differs from a fault during the copy itself (`vmo/mod.rs:531,548-559,773-805`).
- **exFAT cold tail:** a valid pre-existing regular file starts with absent data pages (`exfat/inode.rs:967-1026`; `vmo/options.rs:107-144`). A partial-tail ftruncate holds the inode write guard while PageCache zeroing may initialize a page through a callback that takes the same inode read lock (`exfat/inode.rs:1450-1453,151`; `page_cache/mod.rs:250-255`; `vmo/mod.rs:1028-1051`; `ostd/src/sync/rwmutex.rs:162-169`). This source-derived lock dependency needs a bounded completion test, not an assumption that every tail is warm. It requires no file mapping. Detailed derivation: [deep-exfat.md](evidence/deep-exfat.md).
- **ext2 qualified control:** healthy backing I/O plus its retained inode guard rules out the two primary lock-gap schedules; this does not prove every error path correct. Truncation of block pointers is expressly best effort. A cold indirect-block read error can return from cleanup before pointer removal, while the caller publishes smaller size (`ext2/inode/block_manager/block_ptr_tree.rs:138-170`; `ext2/inode/file.rs:412-415`). A later extension could revisit those mappings. The actual device-error setup and post-error content contract remain unresolved, so this is a conditional source/test caveat outside the default model. No arbitrary EIO is injected. Detailed derivation: [deep-ext2.md](evidence/deep-ext2.md).

## Exclusions and false-positive controls

- No whole-call snapshot or EOF-at-return requirement for overlapping reads. A valid short result is not a finding.
- No `C == L` invariant: capacity is rounded. Extra capacity or allocation after an error is not by itself observable corruption.
- No assumption that disk allocation, an absent cache page, or an uninitialized cache frame contains logical zeros. Check each backend population path.
- No shared-offset race imported into positional I/O; `pread64` and `pwrite64` preserve the open-description offset.
- No arbitrary storage/OOM/error adversary. Start with successful backing I/O and stable user mappings; copy faults must be reached through actual fallible copy sites.
- No artificial weakening of locks, atomic memory order, tail zeroing, or already-fixed page initialization. Historical defects stay evidence, not model mutations.
- Excluded by user scope: vectored I/O atomicity, signal/restart, append atomicity, O_DIRECT, mmap/page faults as file operations, crash durability, pipes, FD publication, SCM_RIGHTS, parser-only arithmetic, and resource exhaustion. Anonymous user mappings established before an attempted copy are test fixtures, not a file-mapping workload.
- The page-cache resize documentation says extension cannot fail, but the implementation calls fallible partial-tail clearing before capacity publication (`page_cache/mod.rs:202-204,250-255`). Record the documentation/code mismatch for review; admit an actual failure only after proving its backend path.
