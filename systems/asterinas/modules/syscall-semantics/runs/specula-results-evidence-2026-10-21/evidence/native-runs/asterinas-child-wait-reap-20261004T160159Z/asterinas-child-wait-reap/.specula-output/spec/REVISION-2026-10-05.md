modeling brief, analysis report, and pinned Asterinas source were read-only

## R1: comparable pending return

The changed definitions are `PendingRet` (`base.tla:19`), `NewCall`
(`base.tla:47`, return field at line 54), and `CallType` (`base.tla:398`,
return domain at line 410). `PendingRet = -9999` is an integer distinct from
all possible fixture results: positive `ChildPid`, zero, and -10. `TypeOK`
continues to apply `CallType` to every admitted call.

`SysWaitReturn` and `ApiOutcomeCorrect` retain their original numeric checks.
The string outcome tag `"pending"` still belongs to a string-only domain.
`MC.tla` has no separate return marker or pending-return comparison. Its
initialization and admission wrappers inherit `NewCall`, and `Completed`
uses `pc = "done"`. `Trace.tla` likewise inherits the marker. Its existing
`SysWaitReturn` post-state arm validates only completed numeric ABI results,
libc return/errno, and output. The instrumentation document now states this
mapping explicitly, without adding a fabricated pending return to events.

## R2: existential trace acceptance

`TraceSearch.cfg` uses the unchanged initialization and event relation. It
retains every existing safety, cursor, and final-state invariant. Its final
invariant, `TraceNoCompleteMatch`, is false exactly when `TraceComplete`
holds: all events were consumed and `TraceEndOK` holds. Every consumed event
still calls the full base action and validates exact arguments and post-state.
There are no new guards, state constraints, silent actions, or fairness
assumptions in the search. `Trace.cfg` remains unchanged as a stricter
universal check.

A complete invariant counterexample is acceptance. An exhausted nonempty
search with no witness is rejection. Any incomplete run or checker error is
inconclusive. An unrelated invariant violation is reported, not interpreted
as acceptance or exhausted rejection. The instrumentation specification
documents these decisions and how to retain the witness.

The generator writes three synthetic grouped JSON inputs. `overlap.json`
uses the review's exact T1 `[10,20]` and T2 `[11,100]` acquisition intervals.
`sequential.json` contains a successful wait4 consume followed by ECHILD.
`corrupted.json` changes only the copyout status field from 9472 to 9473.
Both positive fixtures produced 28-state complete witnesses. Their final
cursors are T1=15, T2=7, child=8, consuming all 27 events. The final calls
return 41 and -10, both at `pc = "done"`, with notifier and lock cleanup
complete. The corrupted fixture exhausts 19 states without a witness.

The unchanged universal check reports a temporal counterexample on the
valid overlap fixture. At state 11, T2 holds the children mutex while T1's
`TryWaitChildrenLock` remains pending. T2's next event starts at 101, after
T1's still-pending lock event ended at 20. T1 cannot acquire and T2 cannot
advance under `ViablePIDs`, so that branch stutters. This is the R2 replay
quantifier problem, not a candidate kernel behavior. At the source pin,
`ostd/src/sync/mutex.rs:35-36,62-69` permits T1 to acquire and release before
T2's blocking acquisition completes. `process/wait.rs:293-319,344-374`
preserves the children lock through consuming cleanup. The accepted
T1-first witness follows those source boundaries. No model action or
Linux-derived outcome was changed in response to this diagnostic.

These fixtures test the checker and are not collected implementation traces.

## R3: general blocking completion coverage

`MC_hunt_3_blocking.cfg` checks `MCBlockingWaitCompletes` under the existing
`MCFairSpec`. `Hunt = "all"` admits all six supported API/option combinations,
including blocking WNOWAIT. Four total call admissions preserve the brief's
two observations, consume, and post-reap call. They also admit repeated
generations on either thread. One optional spurious scheduler return is
retained, including schedules without it. No existing bound is narrowed.

The existing weak fairness for exit/notification and runnable thread steps,
strong fairness for children-lock acquisition, and first-admission fairness
are unchanged. Reactive steps have no new bound. Both temporal configurations
omit symmetry. All existing safety configurations retain thread symmetry.
`MC_hunt_3_wakeup.cfg` remains unchanged and still checks
`MCCompetingConsumersComplete` in its two-initial-consumer fixture. The new
configuration does not impose that pair property on observers or later calls.

## Execution and evidence limits

See [generation-checks/results.md](generation-checks/results.md) for C1-C6,
every MC outcome, state counts, depth, exact commands, logs, and counterexample
interpretation. MC searches have a 600-second time limit each. Trace searches
and SANY checks have a 60-second limit each. Every TLC process uses the
supplied Java/jars, at most 3 GiB heap, 1 GiB direct memory, and two workers.
TLC processes run serially and metadata stays under the ignored `states/`
directory. The reviewer's off-heap fingerprint implementation and `-deadlock`
flag are retained. That flag disables deadlock checking, agreeing with the
existing `CHECK_DEADLOCK FALSE` configurations.

Time-limited searches are incomplete and provide no exhaustive safety or
liveness pass. Runtime harness collection, Linux controls, guest cases,
WR-SQ, WR-CF, and independent acceptance of the revised suite are not run.
The static audit checks the unchanged 41-action correspondence and preserved
logic against the Git baseline. It also parses all ten configurations using
TLC's `ModelConfig` parser without starting a second model checker.
